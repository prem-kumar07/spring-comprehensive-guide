Maven Deep Dive

Maven 3.x

Apache Maven is a build automation and project management tool based on the Project Object Model (POM). It manages dependencies, compiles source code, runs tests, packages artifacts, and publishes to repositories — all driven by convention over configuration.

Maven Coordinates & POM Structure

Every Maven project is uniquely identified by its GAV coordinates — groupId, artifactId, version. These three values form the address of your artifact in any repository. The pom.xml is the single source of truth for the project's build metadata, dependencies, plugins, and inherited configuration.

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
           https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.example</groupId>
  <artifactId>my-app</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>jar</packaging>            <!-- jar (default), war, pom -->
  <name>My Application</name>

  <properties>
    <java.version>21</java.version>
    <maven.compiler.source>${java.version}</maven.compiler.source>
    <maven.compiler.target>${java.version}</maven.compiler.target>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>
</project>

Build Lifecycle & Phases

Maven defines three built-in lifecycles: default (build and deploy), clean (remove target/), and site (generate documentation). The default lifecycle runs phases in strict order — you run a phase and every phase before it executes automatically.

# Run all phases up to and including package
mvn package

# Skip tests during packaging
mvn package -DskipTests

# Common phase sequence (default lifecycle):
# validate → initialize → compile → test-compile →
# test → package → verify → install → deploy
PhaseWhat it does
validateCheck POM is correct and all information is available
compileCompile src/main/java into target/classes
testRun unit tests with Surefire; does NOT require the project to be packaged
packagePack compiled code into JAR/WAR in target/
verifyRun integration tests and checks (Failsafe plugin)
installInstall artifact into local ~/.m2/repository
deployUpload artifact to remote repository (Nexus, Artifactory)

Dependency Scopes

Scopes control when a dependency is available on the classpath and whether it is included in the packaged artifact. Choosing the wrong scope is a common source of "works in test, fails in prod" bugs.

<dependencies>
  <!-- compile (default): on classpath everywhere, included in jar -->
  <dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.0</version>
  </dependency>

  <!-- test: only during test compile + test execution -->
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.2</version>
    <scope>test</scope>
  </dependency>

  <!-- provided: compile+test only; container (Tomcat/servlet) provides at runtime -->
  <dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <version>6.0.0</version>
    <scope>provided</scope>
  </dependency>

  <!-- runtime: not needed to compile, but needed to run (JDBC drivers) -->
  <dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <version>42.7.3</version>
    <scope>runtime</scope>
  </dependency>
</dependencies>

Key Build Plugins

Maven does all real work through plugins. The three most important plugins in any Java project are bound to lifecycle phases automatically — but you often need to configure them explicitly to control Java version, test behaviour, or output format.

<build>
  <plugins>
    <!-- Compiler: set Java version -->
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.13.0</version>
      <configuration>
        <release>21</release>       <!-- preferred over source+target -->
        <compilerArgs>
          <arg>-parameters</arg>    <!-- preserve param names (needed by Spring) -->
        </compilerArgs>
      </configuration>
    </plugin>

    <!-- Surefire: unit tests (bound to test phase) -->
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
      <version>3.2.5</version>
    </plugin>

    <!-- Failsafe: integration tests (bound to verify phase) -->
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-failsafe-plugin</artifactId>
      <version>3.2.5</version>
      <executions>
        <execution>
          <goals>
            <goal>integration-test</goal>
            <goal>verify</goal>
          </goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Multi-Module Projects

A multi-module project has a root POM with packaging=pom that lists child modules. Each child module has its own pom.xml and can depend on sibling modules. The parent POM centralises dependency versions via <dependencyManagement> so child POMs declare dependencies without specifying versions.

<!-- root pom.xml -->
<groupId>com.example</groupId>
<artifactId>my-project</artifactId>
<version>1.0.0</version>
<packaging>pom</packaging>

<modules>
  <module>common</module>
  <module>service</module>
  <module>api</module>
</modules>

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.example</groupId>
      <artifactId>common</artifactId>
      <version>${project.version}</version>
    </dependency>
  </dependencies>
</dependencyManagement>
<!-- service/pom.xml -->
<parent>
  <groupId>com.example</groupId>
  <artifactId>my-project</artifactId>
  <version>1.0.0</version>
</parent>
<artifactId>service</artifactId>

<dependencies>
  <dependency>
    <groupId>com.example</groupId>
    <artifactId>common</artifactId>
    <!-- version inherited from parent dependencyManagement -->
  </dependency>
</dependencies>
# Build all modules in reactor order
mvn install

# Build only one module and its dependencies
mvn install -pl service -am

Maven Wrapper

The Maven Wrapper (mvnw) pins a specific Maven version to the project and downloads it automatically. No local Maven installation required. Every developer and CI server uses exactly the same version — eliminates "works on my machine" build differences.

# Generate wrapper (requires Maven installed once)
mvn wrapper:wrapper -Dmaven=3.9.6

# Files created:
# mvnw                           (Unix shell script)
# mvnw.cmd                       (Windows batch)
# .mvn/wrapper/maven-wrapper.properties

# Use exactly like mvn:
./mvnw package
./mvnw spring-boot:run
# .mvn/wrapper/maven-wrapper.properties
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.6/apache-maven-3.9.6-bin.zip
wrapperUrl=https://repo.maven.apache.org/maven2/org/apache/maven/wrapper/maven-wrapper/3.2.0/maven-wrapper-3.2.0.jar

spring-boot-starter-parent

The easiest way to manage Spring Boot dependencies. Declaring spring-boot-starter-parent as your parent POM inherits pre-configured plugin versions, encoding settings, resource filtering, and the entire spring-boot-dependencies BOM — so all Spring starters are versioned automatically. You only specify the Boot version once.

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.3.4</version>
  <relativePath/>  <!-- always look up from repository -->
</parent>

<dependencies>
  <!-- No version needed — parent manages it -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
  </dependency>
</dependencies>

BOM Import (without parent)

When you already have a corporate parent POM and can't use spring-boot-starter-parent, import the spring-boot-dependencies BOM via <dependencyManagement> with scope=import, type=pom. You lose the plugin pre-configuration from the parent but gain the same dependency version management.

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.3.4</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- Override a single managed version -->
<properties>
  <jackson.version>2.17.1</jackson.version>
</properties>

spring-boot-maven-plugin

Provides the goals that make Spring Boot work: repackage creates an executable fat JAR (bound to the package phase automatically when you use spring-boot-starter-parent), run starts the application with hot-reload via DevTools, and build-image creates an OCI container image using Cloud Native Buildpacks.

<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <!-- Exclude DevTools from production fat JAR -->
    <excludeDevtools>true</excludeDevtools>
    <!-- Add build info to /actuator/info -->
    <additionalProperties>
      <encoding.source>UTF-8</encoding.source>
    </additionalProperties>
  </configuration>
  <executions>
    <execution>
      <goals><goal>build-info</goal></goals>
    </execution>
  </executions>
</plugin>
./mvnw spring-boot:run          # run with DevTools live reload
./mvnw package                  # produces target/my-app-1.0.jar (executable)
./mvnw spring-boot:build-image  # OCI image via Cloud Native Buildpacks
java -jar target/my-app-1.0.jar # run the fat JAR

Layered JARs for Docker

By default, the fat JAR packs everything together — meaning a one-line code change rebuilds and re-pushes the full JAR layer in Docker. Layered JARs split the artifact into four layers (dependencies, Spring Boot loader, snapshot-dependencies, application) ordered by change frequency. Docker caches the dependency layers and only the thin application layer changes on most rebuilds.

<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <layers>
      <enabled>true</enabled>
    </layers>
  </configuration>
</plugin>
# Dockerfile using layered extraction
FROM eclipse-temurin:21-jre AS builder
WORKDIR /app
COPY target/*.jar app.jar
RUN java -Djarmode=layertools -jar app.jar extract

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

Native Image (GraalVM)

Spring Boot 3.x supports GraalVM native image compilation via the native-maven-plugin. Native images start in milliseconds and use a fraction of the heap — ideal for serverless and CLI tools. AOT processing runs at build time to generate reflection hints, proxy configurations, and serialization metadata.

<profiles>
  <profile>
    <id>native</id>
    <build>
      <plugins>
        <plugin>
          <groupId>org.graalvm.buildtools</groupId>
          <artifactId>native-maven-plugin</artifactId>
        </plugin>
      </plugins>
    </build>
  </profile>
</profiles>
# Compile to native binary (requires GraalVM JDK)
./mvnw native:compile -Pnative

# Or build OCI image with native binary inside (no local GraalVM needed)
./mvnw spring-boot:build-image -Pnative

# Run the native binary
./target/my-app

Testcontainers + @ServiceConnection

Spring Boot 3.1+ integrates Testcontainers with @ServiceConnection — the annotation reads the container's exposed port and sets the matching spring.datasource.* / spring.redis.* etc. properties automatically. No manual @DynamicPropertySource needed.

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-testcontainers</artifactId>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.testcontainers</groupId>
  <artifactId>postgresql</artifactId>
  <scope>test</scope>
</dependency>
@SpringBootTest
@Testcontainers
class UserRepositoryTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired UserRepository repo;

    @Test
    void savesUser() {
        repo.save(new User("alice"));
        assertThat(repo.count()).isEqualTo(1);
    }
}
