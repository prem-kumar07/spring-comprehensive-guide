Maven Deep Dive

Maven 3.9.x

Apache Maven is a build automation and project management tool based on the Project Object Model (POM). It manages dependencies, compiles source code, runs tests, packages artifacts, and publishes to repositories — all driven by convention over configuration. Maven 3.9.x is the current stable line; Maven 4.x (RC) introduces a new API surface and improved multi-module handling.

Full POM Structure

The Project Object Model (pom.xml) is the central descriptor for every Maven project. The sections shown here cover the full set of top-level elements; most projects only need a subset. Elements marked (required) must be present in every POM.

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">

  <modelVersion>4.0.0</modelVersion>  <!-- required; always 4.0.0 -->

  <!-- ── Identity (required) ── -->
  <groupId>com.example</groupId>
  <artifactId>my-app</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>jar</packaging>   <!-- jar (default), war, pom, ear -->

  <!-- ── Human-readable metadata ── -->
  <name>My Application</name>
  <description>A sample Spring Boot application</description>
  <url>https://github.com/example/my-app</url>

  <!-- ── Global properties — referenced as ${key} anywhere in the POM ── -->
  <properties>
    <java.version>17</java.version>
    <spring.version>6.2.0</spring.version>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <!-- ── Dependency version management (no transitive pull-in) ── -->
  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework</groupId>
        <artifactId>spring-framework-bom</artifactId>
        <version>${spring.version}</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  <!-- ── Runtime dependencies ── -->
  <dependencies>
    <dependency>
      <groupId>org.springframework</groupId>
      <artifactId>spring-context</artifactId>
      <!-- version omitted — managed by BOM above -->
    </dependency>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.11.0</version>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <!-- ── Build configuration ── -->
  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.13.0</version>
        <configuration>
          <release>${java.version}</release>
        </configuration>
      </plugin>
    </plugins>
  </build>

</project>

Maven Wrapper

The Maven Wrapper (mvnw) pins a specific Maven version to the project so every developer and CI server uses the same version without installing Maven globally. It is equivalent to the Gradle Wrapper.

# Generate the wrapper (requires Maven installed locally, one time)
mvn wrapper:wrapper -Dmaven=3.9.9

# Files created:
# .mvn/wrapper/maven-wrapper.properties   ← version + download URL
# mvnw                                    ← Unix shell script
# mvnw.cmd                                ← Windows batch script

# Use the wrapper instead of system mvn:
./mvnw clean package
./mvnw.cmd clean package   # Windows
# .mvn/wrapper/maven-wrapper.properties
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.9/apache-maven-3.9.9-bin.zip
wrapperUrl=https://repo.maven.apache.org/maven2/org/apache/maven/wrapper/maven-wrapper/3.3.2/maven-wrapper-3.3.2.jar
Commit the wrapper Commit mvnw, mvnw.cmd, and .mvn/wrapper/ to version control. Do not commit the downloaded Maven distribution itself.

Maven Coordinates (GAV)

Every artifact is uniquely identified by its GroupId, ArtifactId, and Version — the GAV triple. Two additional optional qualifiers are classifier and type.

<!-- Standard dependency with GAV -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <version>3.5.3</version>
</dependency>

<!-- Classifier: selects a secondary artifact published alongside the main jar.
     Common classifiers: sources, javadoc, tests, linux-x86_64 -->
<dependency>
  <groupId>com.example</groupId>
  <artifactId>my-library</artifactId>
  <version>1.0.0</version>
  <classifier>tests</classifier>   <!-- pulls in the test-jar -->
  <scope>test</scope>
</dependency>

<!-- Type: artifact file extension. Default is jar.
     Other types: pom, war, ear, zip, tar.gz -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-dependencies</artifactId>
  <version>3.5.3</version>
  <type>pom</type>
  <scope>import</scope>
</dependency>
SNAPSHOT vs RELEASE A version ending in -SNAPSHOT is mutable — Maven re-downloads it from the snapshot repository on each build (controlled by -U flag). A RELEASE version (no suffix) is immutable; once deployed it must not change.

Standard Directory Layout

Maven's convention-over-configuration philosophy means the standard directory structure is understood by all plugins without explicit configuration.

my-app/
├── pom.xml
├── mvnw / mvnw.cmd
├── .mvn/
│   └── wrapper/
│       └── maven-wrapper.properties
├── src/
│   ├── main/
│   │   ├── java/          ← production Java source
│   │   │   └── com/example/App.java
│   │   ├── resources/     ← production classpath resources
│   │   │   ├── application.properties
│   │   │   └── logback.xml
│   │   └── webapp/        ← web application root (WAR packaging only)
│   └── test/
│       ├── java/          ← test Java source
│       │   └── com/example/AppTest.java
│       └── resources/     ← test classpath resources
│           └── test.properties
└── target/                ← all build output (git-ignored)
    ├── classes/           ← compiled production classes
    ├── test-classes/      ← compiled test classes
    ├── surefire-reports/  ← unit test reports
    └── my-app-1.0.0.jar   ← packaged artifact

Command-Line Basics

Common Maven commands you use every day, with the flags that matter most.

# Core build commands
./mvnw compile                  # compile src/main/java only
./mvnw test                     # compile and run unit tests
./mvnw package                  # compile, test, package (creates JAR/WAR)
./mvnw verify                   # package + run integration tests
./mvnw install                  # verify + install to local ~/.m2 repo
./mvnw deploy                   # install + upload to remote repo

# Skipping tests
./mvnw package -DskipTests          # skip test execution (still compiles tests)
./mvnw package -Dmaven.test.skip=true  # skip compile AND execution of tests

# Multi-module: select specific modules
./mvnw -pl api,service package      # build only 'api' and 'service' modules
./mvnw -pl web -am package          # build 'web' AND all modules it depends on
./mvnw -pl service --also-make-dependents install

# Parallel builds (speeds up multi-module projects)
./mvnw -T 4 install             # 4 threads
./mvnw -T 1C install            # 1 thread per CPU core

# Clean before build
./mvnw clean package            # delete target/, then build

# Verbose / quiet
./mvnw package --no-transfer-progress   # hide download progress (CI-friendly)
./mvnw package -q               # quiet — only errors
./mvnw package -X               # debug — very verbose

# Activate a profile
./mvnw package -P prod

# Override a property
./mvnw package -Dspring.profiles.active=prod

# Run a specific plugin goal (without full lifecycle)
./mvnw dependency:tree
./mvnw help:effective-pom
./mvnw versions:display-dependency-updates

settings.xml — User and Global Configuration

~/.m2/settings.xml holds configuration that is not project-specific: credentials, mirrors, proxy settings, and environment-specific profiles. It is never committed to source control.

<!-- ~/.m2/settings.xml -->
<settings xmlns="http://maven.apache.org/SETTINGS/1.2.0">

  <!-- Local repository path (default: ~/.m2/repository) -->
  <localRepository>/opt/maven-repo</localRepository>

  <!-- Mirror: redirect all central repo requests to a corporate Nexus -->
  <mirrors>
    <mirror>
      <id>nexus-mirror</id>
      <name>Corporate Nexus</name>
      <url>https://nexus.corp.com/repository/maven-public/</url>
      <mirrorOf>*</mirrorOf>   <!-- mirror ALL repositories -->
    </mirror>
  </mirrors>

  <!-- Server credentials — matched by repository <id> in POM -->
  <servers>
    <server>
      <id>nexus-releases</id>
      <username>deploy-user</username>
      <password>${env.NEXUS_PASSWORD}</password>
    </server>
    <server>
      <id>github</id>
      <username>${env.GITHUB_ACTOR}</username>
      <password>${env.GITHUB_TOKEN}</password>
    </server>
  </servers>

  <!-- HTTP proxy -->
  <proxies>
    <proxy>
      <id>corp-proxy</id>
      <active>true</active>
      <protocol>https</protocol>
      <host>proxy.corp.com</host>
      <port>8080</port>
      <nonProxyHosts>localhost|*.corp.com</nonProxyHosts>
    </proxy>
  </proxies>

  <!-- Profile active for all projects on this machine -->
  <activeProfiles>
    <activeProfile>corp-settings</activeProfile>
  </activeProfiles>

</settings>
Never store plaintext passwords Use environment variable interpolation (${env.MY_VAR}) or Maven's encrypted passwords (mvn --encrypt-password) instead of plaintext credentials.

Three Built-In Lifecycles

Maven defines three lifecycles. Each lifecycle is a sequence of named phases. Running a phase runs all preceding phases in order. Plugins bind their goals to phases; Maven invokes them in phase order.

# default lifecycle — build, test, and deploy the project
./mvnw deploy        # runs: validate → ... → deploy

# clean lifecycle — remove build output
./mvnw clean         # runs: pre-clean → clean → post-clean

# site lifecycle — generate project documentation
./mvnw site          # runs: pre-site → site → post-site → site-deploy

# Combine lifecycles in one command:
./mvnw clean install                # clean first, then full default lifecycle to install
./mvnw clean verify -DskipTests     # clean, compile, package, verify (skip tests)

Default Lifecycle — All 23 Phases in Order

Every phase in the default lifecycle is listed below. Most plugins bind to the shaded phases; the others exist as extension hooks for custom plugin bindings.

# Phase order (top to bottom). Running any phase runs all above it first.
# ─────────────────────────────────────────────────────────────────
# 1.  validate              ← check POM is valid, required info present
# 2.  initialize            ← set build properties, create directories
# 3.  generate-sources      ← generate source code (e.g. JAXB, Thrift)
# 4.  process-sources       ← post-process generated sources
# 5.  generate-resources    ← generate resources (properties, XMLs)
# 6.  process-resources     ← copy and filter resources → target/classes
# 7.  compile               ← compile src/main/java → target/classes
# 8.  process-classes       ← post-process compiled classes (e.g. bytecode weaving)
# 9.  generate-test-sources ← generate test source code
# 10. process-test-sources  ← post-process test sources
# 11. generate-test-resources
# 12. process-test-resources ← copy and filter test resources
# 13. test-compile          ← compile src/test/java → target/test-classes
# 14. process-test-classes
# 15. test                  ← run unit tests (Surefire); fail build on failure
# 16. prepare-package       ← pre-package operations
# 17. package               ← assemble JAR/WAR → target/my-app-1.0.jar
# 18. pre-integration-test  ← start containers, servers
# 19. integration-test      ← run integration tests (Failsafe)
# 20. post-integration-test ← stop containers, servers
# 21. verify                ← check integration test results; fail if needed
# 22. install               ← copy artifact to ~/.m2/repository
# 23. deploy                ← upload artifact to remote repository
# ─────────────────────────────────────────────────────────────────

Plugin Goals and Phase Binding

A plugin goal is a single unit of work (like compiler:compile). Plugins declare a default phase for each goal. You can override the phase or add extra executions via <executions>.

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-antrun-plugin</artifactId>
      <version>3.1.0</version>
      <executions>

        <!-- First execution: bind to validate phase -->
        <execution>
          <id>print-start</id>
          <phase>validate</phase>
          <goals><goal>run</goal></goals>
          <configuration>
            <target>
              <echo message="Build started for ${project.artifactId}:${project.version}"/>
            </target>
          </configuration>
        </execution>

        <!-- Second execution: bind to package phase -->
        <execution>
          <id>print-packaged</id>
          <phase>package</phase>
          <goals><goal>run</goal></goals>
          <configuration>
            <target>
              <echo message="JAR created at target/${project.build.finalName}.jar"/>
            </target>
          </configuration>
        </execution>

      </executions>
    </plugin>
  </plugins>
</build>
# Invoke a goal directly without running a lifecycle phase:
./mvnw compiler:compile       # compile only (no test, no package)
./mvnw surefire:test          # run tests only
./mvnw dependency:tree        # print dependency tree
./mvnw help:effective-pom     # show the fully resolved POM (after inheritance)
./mvnw help:effective-settings
./mvnw versions:display-dependency-updates  # check for newer versions

Skipping Phases and Goals

Several system properties allow skipping phases or goals without modifying the POM. These are especially useful in CI pipelines where different stages handle different concerns.

# Skip test execution (tests still compile)
./mvnw package -DskipTests

# Skip test compilation AND execution
./mvnw package -Dmaven.test.skip=true

# Skip Javadoc generation
./mvnw install -Dmaven.javadoc.skip=true

# Skip source attachment
./mvnw install -Dmaven.source.skip=true

# Skip checkstyle
./mvnw verify -Dcheckstyle.skip=true

# Skip spotbugs
./mvnw verify -Dspotbugs.skip=true

# Run a specific test class or method
./mvnw test -Dtest=OrderServiceTest
./mvnw test -Dtest=OrderServiceTest#createOrder_returnsId
./mvnw test -Dtest="Order*Test,Payment*Test"   # glob pattern

Useful Utility Goals

These goals are not part of the standard lifecycle but are invaluable for day-to-day development and maintenance.

# Dependency analysis
./mvnw dependency:tree                       # full transitive tree
./mvnw dependency:tree -Dincludes=org.slf4j  # filter by groupId
./mvnw dependency:analyze                    # used-undeclared & declared-unused
./mvnw dependency:resolve                    # resolve all deps (pre-warm local repo)
./mvnw dependency:copy-dependencies          # copy all JARs to target/dependency/

# Version management (versions-maven-plugin)
./mvnw versions:display-dependency-updates   # show available newer versions
./mvnw versions:display-plugin-updates       # show newer plugin versions
./mvnw versions:use-latest-releases          # auto-update POM to latest releases
./mvnw versions:set -DnewVersion=2.0.0       # change project version across modules

# Project info
./mvnw help:effective-pom                    # full resolved POM with defaults
./mvnw help:describe -Dplugin=compiler       # describe all goals in a plugin
./mvnw help:describe -Dcmd=compile           # describe a lifecycle phase

# Source code
./mvnw source:jar                            # build sources jar
./mvnw javadoc:jar                           # build javadoc jar

Dependency Scopes

Scope controls when a dependency is on the classpath. The table below shows what is available at compile time, during test compilation and test execution, and when the final artifact runs.

compile (default)✔✔✔YesNormal library dependency
provided✔✔✘NoContainer provides it at runtime (Servlet API)
runtime✘✔✔YesJDBC drivers, SLF4J implementations
test✘✔✘NoJUnit, Mockito, AssertJ

<dependencies>
  <!-- compile (default): available everywhere -->
  <dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context</artifactId>
    <version>6.2.0</version>
  </dependency>

  <!-- provided: compile-time API; not bundled (server provides it) -->
  <dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <version>6.1.0</version>
    <scope>provided</scope>
  </dependency>

  <!-- runtime: needed at runtime but not at compile time -->
  <dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <version>42.7.3</version>
    <scope>runtime</scope>
  </dependency>

  <!-- test: only for test compilation and execution -->
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.11.0</version>
    <scope>test</scope>
  </dependency>
</dependencies>

Transitive Dependencies — Mediation and Exclusions

Maven resolves transitive dependencies automatically. When two paths in the dependency tree require different versions of the same artifact, Maven applies nearest-wins mediation — the version declared closest to your project wins. Use <exclusions> to remove transitive dependencies that cause conflicts, and <optional> to prevent a dependency from being pulled in transitively by consumers of your library.

<dependencies>

  <!-- Exclude a transitive dependency that conflicts with another version -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-logging</artifactId>
    <version>3.5.3</version>
    <exclusions>
      <!-- Exclude Logback so we can use Log4j2 instead -->
      <exclusion>
        <groupId>ch.qos.logback</groupId>
        <artifactId>logback-classic</artifactId>
      </exclusion>
    </exclusions>
  </dependency>

  <!-- optional: consumers of YOUR library will NOT get this transitively -->
  <dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.0</version>
    <optional>true</optional>
  </dependency>

</dependencies>
# Diagnose version conflicts:
./mvnw dependency:tree -Dverbose         # shows omitted-for-conflict versions
./mvnw dependency:tree -Dincludes=org.slf4j:slf4j-api
./mvnw dependency:analyze                # used-but-undeclared / declared-but-unused

Dependency Management — Centralising Versions

<dependencyManagement> declares versions (and scopes) centrally without adding those artifacts to the classpath. Child POMs or the same POM's <dependencies> section can then omit the version — it is inherited from management.

<!-- Parent POM or shared corporate parent -->
<dependencyManagement>
  <dependencies>

    <!-- Declare the version once; no artifact pulled in yet -->
    <dependency>
      <groupId>org.slf4j</groupId>
      <artifactId>slf4j-api</artifactId>
      <version>2.0.13</version>
    </dependency>

    <!-- Force a specific version to override transitive conflict -->
    <dependency>
      <groupId>com.fasterxml.jackson.core</groupId>
      <artifactId>jackson-databind</artifactId>
      <version>2.17.2</version>
    </dependency>

  </dependencies>
</dependencyManagement>

<!-- In <dependencies>, version is omitted — taken from management -->
<dependencies>
  <dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <!-- version not needed — inherited from dependencyManagement -->
  </dependency>
</dependencies>

BOM (Bill of Materials) Import

A BOM is a POM with <packaging>pom</packaging> that declares <dependencyManagement> for a set of related artifacts at compatible versions. Importing a BOM adds all its managed versions to your project. You can stack multiple BOMs — the first declaration wins in case of conflict.

<dependencyManagement>
  <dependencies>

    <!-- Import Spring Boot BOM — manages all Spring Boot dependency versions -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.5.3</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>

    <!-- Stack a second BOM — Spring Cloud; Boot BOM versions take precedence
         for any artifact declared in both, because it is listed first -->
    <dependency>
      <groupId>org.springframework.cloud</groupId>
      <artifactId>spring-cloud-dependencies</artifactId>
      <version>2024.0.1</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>

  </dependencies>
</dependencyManagement>

<!-- With BOMs imported, starters need no version -->
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-gateway</artifactId>
  </dependency>
</dependencies>

maven-compiler-plugin

Controls Java compilation. The <release> element (since JDK 9) sets source, target, and bootstrap classpath in one shot and is preferred over the older <source>/<target> pair.

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <version>3.13.0</version>
  <configuration>
    <release>17</release>
    <encoding>UTF-8</encoding>

    <!-- Extra compiler flags -->
    <compilerArgs>
      <arg>-parameters</arg>   <!-- preserve parameter names (needed by Spring) -->
      <arg>-Xlint:unchecked</arg>
    </compilerArgs>

    <!-- Annotation processors (e.g. Lombok, MapStruct) -->
    <annotationProcessorPaths>
      <path>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <version>1.18.34</version>
      </path>
      <path>
        <groupId>org.mapstruct</groupId>
        <artifactId>mapstruct-processor</artifactId>
        <version>1.6.0</version>
      </path>
    </annotationProcessorPaths>
  </configuration>
</plugin>

maven-surefire-plugin — Unit Tests

Surefire runs unit tests during the test phase. Version 3.x supports JUnit 5 natively (via the junit-platform-launcher on the classpath). Tests in src/test/java whose names match *Test, Test*, or *Tests are included by default.

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <version>3.3.1</version>
  <configuration>

    <!-- Include / exclude patterns -->
    <includes>
      <include>**/*Test.java</include>
      <include>**/*Tests.java</include>
    </includes>
    <excludes>
      <exclude>**/*IT.java</exclude>  <!-- exclude integration tests -->
    </excludes>

    <!-- Parallel test execution -->
    <parallel>methods</parallel>     <!-- classes | methods | both -->
    <threadCount>4</threadCount>
    <forkCount>1</forkCount>

    <!-- JVM args for tests -->
    <argLine>-Xmx512m -Dfile.encoding=UTF-8</argLine>

    <!-- System properties available inside tests -->
    <systemPropertyVariables>
      <spring.profiles.active>test</spring.profiles.active>
    </systemPropertyVariables>

  </configuration>
</plugin>
# Run a specific test class or method
./mvnw test -Dtest=OrderServiceTest
./mvnw test -Dtest=OrderServiceTest#createOrder_returnsId

# Run tests matching a glob
./mvnw test -Dtest="Order*,Payment*"

# Run failing tests only (after first failure)
./mvnw test -Dsurefire.failIfNoSpecifiedTests=false

maven-failsafe-plugin — Integration Tests

Failsafe runs integration tests (*IT.java) during the integration-test phase and reports results during verify. This separation is important: it allows pre/post-integration-test hooks (starting/stopping containers) to run even if tests fail, so you don't leave dangling processes.

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-failsafe-plugin</artifactId>
  <version>3.3.1</version>
  <executions>
    <execution>
      <goals>
        <goal>integration-test</goal>  <!-- run *IT tests -->
        <goal>verify</goal>             <!-- fail build if ITs failed -->
      </goals>
    </execution>
  </executions>
  <configuration>
    <includes>
      <include>**/*IT.java</include>
      <include>**/*IntegrationTest.java</include>
    </includes>
    <argLine>-Xmx1g</argLine>
  </configuration>
</plugin>
# Run full integration test cycle (unit + IT):
./mvnw verify

# Run only integration tests (skip unit tests):
./mvnw verify -DskipTests -DskipITs=false

# Tip: combine with Testcontainers — containers start inside the test itself,
# so no separate pre/post-integration-test hooks needed.

maven-assembly-plugin & maven-shade-plugin — Fat JARs

Assembly plugin creates a JAR containing all dependencies using a built-in jar-with-dependencies descriptor. Shade plugin produces an uber JAR with relocation and resource merging — the right choice for libraries to avoid classpath conflicts.

<!-- Assembly plugin: simple fat JAR for runnable apps -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-assembly-plugin</artifactId>
  <version>3.7.1</version>
  <configuration>
    <archive>
      <manifest>
        <mainClass>com.example.Main</mainClass>
      </manifest>
    </archive>
    <descriptorRefs>
      <descriptorRef>jar-with-dependencies</descriptorRef>
    </descriptorRefs>
    <appendAssemblyId>false</appendAssemblyId>
  </configuration>
  <executions>
    <execution>
      <id>make-assembly</id>
      <phase>package</phase>
      <goals><goal>single</goal></goals>
    </execution>
  </executions>
</plugin>

<!-- Shade plugin: uber JAR with relocation (for libraries) -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-shade-plugin</artifactId>
  <version>3.6.0</version>
  <executions>
    <execution>
      <phase>package</phase>
      <goals><goal>shade</goal></goals>
      <configuration>
        <createDependencyReducedPom>true</createDependencyReducedPom>
        <relocations>
          <relocation>
            <!-- Relocate Guava to avoid conflicts with app's Guava version -->
            <pattern>com.google.common</pattern>
            <shadedPattern>com.example.shaded.google.common</shadedPattern>
          </relocation>
        </relocations>
        <transformers>
          <!-- Merge META-INF/services for SPI -->
          <transformer implementation="org.apache.maven.plugins.shade.resource.ServicesResourceTransformer"/>
          <!-- Set main class in MANIFEST.MF -->
          <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
            <mainClass>com.example.Main</mainClass>
          </transformer>
        </transformers>
      </configuration>
    </execution>
  </executions>
</plugin>

Parent POM Structure

A multi-module Maven project has a parent POM with <packaging>pom</packaging> that lists all child modules. The parent centralises shared configuration: Java version, plugin versions, dependency management, and common dependencies.

<!-- pom.xml (project root — parent and aggregator) -->
<project>
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.example</groupId>
  <artifactId>my-platform</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>pom</packaging>  <!-- must be pom for a parent -->
  <name>My Platform</name>

  <!-- List all child modules (directory names relative to this POM) -->
  <modules>
    <module>platform-api</module>
    <module>platform-service</module>
    <module>platform-web</module>
    <module>platform-common</module>
  </modules>

  <properties>
    <java.version>17</java.version>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <dependencyManagement>
    <dependencies>
      <!-- BOM import -->
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-dependencies</artifactId>
        <version>3.5.3</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
      <!-- Cross-module dependency version management -->
      <dependency>
        <groupId>com.example</groupId>
        <artifactId>platform-common</artifactId>
        <version>${project.version}</version>
      </dependency>
    </dependencies>
  </dependencyManagement>

  <!-- Shared test dependencies for all modules -->
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <build>
    <pluginManagement>
      <plugins>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-compiler-plugin</artifactId>
          <version>3.13.0</version>
        </plugin>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>

          <version>3.3.1</version>

      </plugin>
    </plugins>
  </build>

</project>

Building Multi-Module Projects

Maven computes the reactor build order automatically based on inter-module dependencies. The -pl and -am flags let you build subsets of the reactor.

# Build everything from the root
./mvnw clean install

# Build only specific modules (comma-separated module artifact IDs or paths)
./mvnw -pl platform-api,platform-service clean package

# Build a module AND all modules it depends on (--also-make / -am)
./mvnw -pl platform-web -am clean package
# → also builds platform-common, platform-api, platform-service (web's deps)

# Build a module AND all modules that depend on it
./mvnw -pl platform-common --also-make-dependents install
# → rebuilds everything that uses platform-common

# Parallel build — 4 threads, massive speed-up for large multi-module projects
./mvnw -T 4 clean install

# Show reactor build order without building
./mvnw -N install              # -N = non-recursive; installs root POM only
./mvnw dependency:tree         # run from root to see full cross-module tree
Reactor build order Maven sorts modules topologically — a module is built after all modules it depends on. Maven detects cycles and fails fast if one is present.

Defining and Activating Profiles

Profiles allow conditional configuration — different plugins, dependencies, and properties for different environments. A profile can be activated explicitly (-P), by default, or automatically based on JDK version, OS, environment variable, property, or file existence.

<profiles>

  <!-- ── dev: active by default ── -->
  <profile>
    <id>dev</id>
    <activation>
      <activeByDefault>true</activeByDefault>
    </activation>
    <properties>
      <app.log.level>DEBUG</app.log.level>
      <db.url>jdbc:h2:mem:testdb</db.url>
    </properties>
  </profile>

  <!-- ── prod: activated with -P prod ── -->
  <profile>
    <id>prod</id>
    <properties>
      <app.log.level>WARN</app.log.level>
      <db.url>jdbc:postgresql://prod-db:5432/app</db.url>
    </properties>
  </profile>

  <!-- ── native: activated by property -Pnative or -Dnative ── -->
  <profile>
    <id>native</id>
    <activation>
      <property>
        <name>native</name>
      </property>
    </activation>
    <build>
      <plugins>
        <plugin>
          <groupId>org.graalvm.buildtools</groupId>
          <artifactId>native-maven-plugin</artifactId>
          <extensions>true</extensions>
        </plugin>
      </plugins>
    </build>
  </profile>

  <!-- ── java24: activated when JDK >= 24 ── -->
  <profile>
    <id>java24</id>
    <activation>
      <jdk>[24,)</jdk>
    </activation>
    <properties>
      <extra.compiler.args>--enable-preview</extra.compiler.args>
    </properties>
  </profile>

  <!-- ── windows: activated on Windows OS ── -->
  <profile>
    <id>windows</id>
    <activation>
      <os>
        <family>windows</family>
      </os>
    </activation>
  </profile>

  <!-- ── ci: activated by CI env variable ── -->
  <profile>
    <id>ci</id>
    <activation>
      <property>
        <name>env.CI</name>
      </property>
    </activation>
  </profile>

</profiles>
# Activate a profile explicitly
./mvnw package -P prod

# Activate multiple profiles
./mvnw package -P prod,signing

# Deactivate a profile that is active by default
./mvnw package -P !dev,prod

# List active profiles for a build
./mvnw help:active-profiles

Resource Filtering — Inject Build Properties into Files

With <filtering>true</filtering>, Maven replaces ${property} placeholders in resource files at build time. This is useful for injecting the active profile's properties into application.properties, SQL scripts, or configuration files.

<build>
  <resources>
    <resource>
      <directory>src/main/resources</directory>
      <filtering>true</filtering>
      <!-- Optionally restrict which files are filtered (binary files must NOT be filtered) -->
      <includes>
        <include>**/*.properties</include>
        <include>**/*.yml</include>
        <include>**/*.xml</include>
      </includes>
    </resource>
    <!-- Binary resources (images, fonts) without filtering -->
    <resource>
      <directory>src/main/resources</directory>
      <filtering>false</filtering>
      <includes>
        <include>**/*.png</include>
        <include>**/*.woff2</include>
      </includes>
    </resource>
  </resources>
</build>
# src/main/resources/application.properties
# ${db.url} replaced by the active profile's property at build time
spring.datasource.url=${db.url}
logging.level.root=${app.log.level}
app.version=${project.version}
app.build-time=${maven.build.timestamp}
Spring Boot and resource filtering Spring Boot's starter-parent already configures resource filtering for *.properties and *.yml but uses @property@ delimiters instead of ${} to avoid conflicts with Spring's own ${} placeholder syntax. When using starter-parent, use @db.url@ in your properties files.

The local repository at ~/.m2/repository acts as a cache and a way to share artifacts between local projects before they are published remotely.

Configure <distributionManagement> in the POM to point to your internal repository manager. Credentials go in ~/.m2/settings.xml — never in the POM.

<servers>

Release Process — maven-release-plugin

The release plugin automates the SNAPSHOT → RELEASE → next SNAPSHOT version cycle: it verifies no uncommitted changes, updates the version, commits, tags, deploys, then bumps to the next development version.

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-release-plugin</artifactId>
  <version>3.1.1</version>
  <configuration>
    <tagNameFormat>v@{project.version}</tagNameFormat>
    <autoVersionSubmodules>true</autoVersionSubmodules>
    <releaseProfiles>release</releaseProfiles>
  </configuration>
</plugin>
# Step 1: prepare — checks, updates version (1.0.0-SNAPSHOT → 1.0.0),
#          commits, tags, bumps to next dev (1.0.1-SNAPSHOT), commits
./mvnw release:prepare

# Step 2: perform — checks out the tag and deploys the release artifact
./mvnw release:perform

# Rollback if something went wrong during prepare (before perform)
./mvnw release:rollback

# Dry-run (no commits or tags written):
./mvnw release:prepare -DdryRun=true
Version numbering Start at 1.0.0-SNAPSHOT. After release:prepare the POM becomes 1.0.0 (tagged), then 1.0.1-SNAPSHOT (next development). Use -DreleaseVersion and -DdevelopmentVersion to override the defaults.

GPG Signing for Maven Central

Maven Central requires all published artifacts to be GPG-signed. The maven-gpg-plugin signs the artifact, sources JAR, and Javadoc JAR during the verify phase.

<!-- In a 'release' profile so signing only happens during releases -->
<profile>
  <id>release</id>
  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-gpg-plugin</artifactId>
        <version>3.2.5</version>
        <executions>
          <execution>
            <id>sign-artifacts</id>
            <phase>verify</phase>
            <goals><goal>sign</goal></goals>
            <configuration>
              <!-- Non-interactive signing for CI -->
              <gpgArguments>
                <arg>--pinentry-mode</arg>
                <arg>loopback</arg>
              </gpgArguments>
            </configuration>
          </execution>
        </executions>
      </plugin>
    </plugins>
  </build>
</profile>
# CI: import GPG key and set passphrase as env var
export GPG_PASSPHRASE="${{ secrets.GPG_PASSPHRASE }}"
./mvnw deploy -P release -Dgpg.passphrase="${GPG_PASSPHRASE}"

The Spring Boot Maven plugin provides bootRun (run the app) and repackage (create a fat JAR). It is bound to the package phase by default when using starter-parent.

Layered JAR for Docker

Spring Boot's layered JAR structure separates the application's classes from its dependencies into distinct Docker image layers. Because dependencies change far less often than application code, Docker only rebuilds the upper layers when you push an update — dramatically reducing push/pull times.

<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <layers>
      <enabled>true</enabled>
    </layers>
  </configuration>
</plugin>
# Inspect layers in a built JAR (Boot 3.3+):
java -Djarmode=tools -jar target/demo.jar list-layers
# Output:
# dependencies
# spring-boot-loader
# snapshot-dependencies
# application

# Extract layers (Boot 3.3+ jarmode):
java -Djarmode=tools -jar target/demo.jar extract --destination target/extracted
# Multi-stage Dockerfile using extracted layers:
# ── Stage 1: Extract ──────────────────────────────────────────
FROM eclipse-temurin:17-jre AS builder
WORKDIR /app
COPY target/demo.jar demo.jar
RUN java -Djarmode=tools -jar demo.jar extract --destination extracted

# ── Stage 2: Runtime ──────────────────────────────────────────
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=builder /app/extracted/dependencies/ ./
COPY --from=builder /app/extracted/spring-boot-loader/ ./
COPY --from=builder /app/extracted/snapshot-dependencies/ ./
COPY --from=builder /app/extracted/application/ ./
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

GraalVM Native Image

The native-maven-plugin (from GraalVM Buildtools) compiles the Spring Boot application to a platform-native binary. Native images start in under 100ms and use a fraction of the heap compared to a JVM run, at the cost of longer build times.

<!-- In a 'native' profile — activate with -Pnative -->
<profile>

          <buildArgs>
            <buildArg>--no-fallback</buildArg>
            <buildArg>--verbose</buildArg>
          </buildArgs>
        </configuration>
        <executions>
          <execution>
            <id>build-native</id>
            <goals><goal>compile-no-fork</goal></goals>
            <phase>package</phase>
          </execution>
          <execution>
            <id>test-native</id>
            <goals><goal>test</goal></goals>
            <phase>test</phase>
          </execution>
        </executions>

    </plugins>

./mvnw -Pnative native:compile

# Run native tests:

./mvnw spring-boot:build-image -Pnative

# Run the native binary:
./target/demo

AOT Processing and DevTools

Spring Boot 3+ runs an AOT (Ahead-of-Time) processing step that generates code for GraalVM native images and improves startup performance even on a regular JVM. Spring Boot DevTools enables hot restart during development — changes to classes trigger a fast context restart without a full JVM restart.

<!-- DevTools: optional so it is excluded from the production JAR -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-devtools</artifactId>
  <optional>true</optional>
</dependency>
# Run AOT processing explicitly (generates code in target/spring-aot/):
./mvnw spring-boot:process-aot

# What AOT generates:
# target/spring-aot/main/sources/     ← BeanFactoryRegistrations.java (no reflection)
# target/spring-aot/main/resources/   ← reflect-config.json, resource-config.json
# target/spring-aot/main/classes/     ← compiled AOT-generated classes

# DevTools hot-restart — just run normally; file changes trigger restart:
./mvnw spring-boot:run
# src/main/resources/application.properties — DevTools configuration
spring.devtools.restart.enabled=true
spring.devtools.livereload.enabled=true
# Exclude paths from triggering restart:
spring.devtools.restart.exclude=static/**,public/**
