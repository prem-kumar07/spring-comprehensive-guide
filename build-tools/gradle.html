Gradle Deep Dive

Gradle 8.x

Gradle is a flexible, high-performance build tool using a Groovy or Kotlin DSL. Unlike Maven's fixed lifecycle, Gradle models the build as a directed acyclic graph (DAG) of tasks — giving you fine-grained control and incremental, cacheable builds out of the box.

Build File Structure (Kotlin DSL)

The build.gradle.kts file is Kotlin script that configures the project. Gradle recommends the Kotlin DSL (`.kts`) over the Groovy DSL for new projects because it provides type safety, IDE completion, and refactoring support. The settings.gradle.kts file defines the project name and included subprojects.

// settings.gradle.kts
rootProject.name = "my-app"

// build.gradle.kts
plugins {
    java
    application
}

group = "com.example"
version = "1.0.0"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("com.fasterxml.jackson.core:jackson-databind:2.17.0")
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

application {
    mainClass = "com.example.Main"
}

tasks.test {
    useJUnitPlatform()
}

Task DAG & Lifecycle

Gradle builds are not phases — they are a graph of tasks. When you run ./gradlew build, Gradle computes which tasks need to run based on dependencies and up-to-date checks, then executes them in dependency order. Incremental builds skip tasks whose inputs and outputs haven't changed.

# Show all available tasks
./gradlew tasks

# Run the build task (compileJava → processResources → classes → jar → test → check → build)
./gradlew build

# Run only tests
./gradlew test

# Skip tests
./gradlew build -x test

# Show the task dependency graph
./gradlew build --dry-run

# Force re-run even if up-to-date
./gradlew test --rerun-tasks

# Show task timing
./gradlew build --profile
TaskWhat it does
compileJavaCompile src/main/java → build/classes/java/main
processResourcesCopy src/main/resources → build/resources/main
classesLifecycle task depending on compileJava + processResources
jarPackage compiled classes into build/libs/*.jar
testRun unit tests; report in build/reports/tests/
checkLifecycle task; depends on test + any other verification tasks
buildTop-level lifecycle: assemble + check
cleanDelete build/ directory

Dependency Configurations

Dependency configurations in Gradle correspond roughly to Maven scopes, but they're more granular. The Java plugin (and Spring Boot plugin) define the common ones; you can also create custom configurations for specific needs.

dependencies {
    // implementation: compile + runtime, NOT exposed to consumers' compile classpath
    implementation("com.google.guava:guava:33.0-jre")

    // api: compile + runtime, IS exposed to consumers (use sparingly — library modules only)
    api("org.slf4j:slf4j-api:2.0.12")

    // compileOnly: compile only, not in runtime (like Maven's provided)
    compileOnly("org.projectlombok:lombok:1.18.32")
    annotationProcessor("org.projectlombok:lombok:1.18.32")

    // runtimeOnly: runtime only, not needed to compile (JDBC drivers)
    runtimeOnly("org.postgresql:postgresql:42.7.3")

    // testImplementation: test compile + runtime
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")

    // testRuntimeOnly: test runtime only
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")

    // testCompileOnly: test compile only
    testCompileOnly("org.projectlombok:lombok:1.18.32")
}

Custom Tasks

Tasks are first-class objects in Gradle. You can define custom tasks, make them depend on others, and configure inputs/outputs for incremental builds. Declaring inputs and outputs lets Gradle skip the task when nothing has changed.

// Simple ad-hoc task
tasks.register("hello") {
    doLast {
        println("Hello, Gradle!")
    }
}

// Typed task with inputs/outputs for incrementality
tasks.register<Copy>("copyConfigs") {
    from("src/main/config")
    into(layout.buildDirectory.dir("config"))
}

// Custom task class
abstract class GenerateVersionTask : DefaultTask() {
    @get:OutputFile
    abstract val outputFile: RegularFileProperty

    @TaskAction
    fun generate() {
        outputFile.get().asFile.writeText("version=${project.version}")
    }
}

tasks.register<GenerateVersionTask>("generateVersion") {
    outputFile = layout.buildDirectory.file("version.txt")
}

// Make a task depend on another
tasks.named("processResources") {
    dependsOn("generateVersion")
}

Multi-Project Builds

Multi-project builds use settings.gradle.kts to declare included subprojects. A root build.gradle.kts can apply common configuration to all subprojects using allprojects {} or subprojects {}. Subprojects declare dependencies on siblings by project path.

// settings.gradle.kts
rootProject.name = "my-platform"
include("common", "service", "api")

// Root build.gradle.kts — shared config
subprojects {
    apply(plugin = "java")

    repositories {
        mavenCentral()
    }

    java {
        toolchain {
            languageVersion = JavaLanguageVersion.of(21)
        }
    }

    tasks.withType<Test> {
        useJUnitPlatform()
    }
}

// service/build.gradle.kts
plugins { java }

dependencies {
    implementation(project(":common"))  // sibling project dependency
}

// Build one subproject and its dependencies
// ./gradlew :service:build
// Build all subprojects
// ./gradlew build

Gradle Wrapper

The Gradle Wrapper (gradlew) pins the exact Gradle version for the project and auto-downloads it on first run. Commit the wrapper files — never the Gradle distribution itself. CI servers and other developers automatically use the same version without any installation.

# Generate wrapper (requires Gradle installed once)
gradle wrapper --gradle-version 8.8

# Files created:
# gradlew                               (Unix shell script)
# gradlew.bat                           (Windows batch)
# gradle/wrapper/gradle-wrapper.jar     (minimal bootstrapper)
# gradle/wrapper/gradle-wrapper.properties

# Use exactly like gradle:
./gradlew build
./gradlew bootRun
# gradle/wrapper/gradle-wrapper.properties
distributionBase=GRADLE_USER_HOME
distributionPath=wrapper/dists
distributionUrl=https\://services.gradle.org/distributions/gradle-8.8-bin.zip
networkTimeout=10000
validateDistributionUrl=true
zipStoreBase=GRADLE_USER_HOME
zipStorePath=wrapper/dists

org.springframework.boot Plugin

The org.springframework.boot plugin is the entry point for all Spring Boot Gradle builds. It adds bootJar (executable fat JAR), bootRun (run with DevTools), and bootBuildImage (OCI image) tasks. It also disables the plain jar task by default and configures the main class automatically if only one @SpringBootApplication class exists.

// build.gradle.kts
plugins {
    java
    id("org.springframework.boot") version "3.3.4"
    id("io.spring.dependency-management") version "1.1.6"
}

group = "com.example"
version = "0.0.1-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    testImplementation("org.springframework.boot:spring-boot-starter-test")
}

tasks.withType<Test> {
    useJUnitPlatform()
}
./gradlew bootRun          # Run with DevTools hot reload
./gradlew bootJar          # Build executable fat JAR → build/libs/*.jar
./gradlew build            # Compile + test + bootJar
java -jar build/libs/my-app-0.0.1-SNAPSHOT.jar

io.spring.dependency-management Plugin

Imports the Spring Boot BOM so all Spring dependency versions are managed centrally — just like spring-boot-starter-parent does in Maven. Without this plugin you'd need to specify versions on every Spring dependency. Alternatively you can use Gradle's native platform() / enforcedPlatform() BOM support instead of this plugin.

// Option A: io.spring.dependency-management plugin (classic)
plugins {
    id("io.spring.dependency-management") version "1.1.6"
}
// No versions needed on Spring starters — managed by BOM
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-data-jpa")
    runtimeOnly("org.postgresql:postgresql")
}

// Option B: Gradle native BOM platform (no plugin needed)
dependencies {
    implementation(platform("org.springframework.boot:spring-boot-dependencies:3.3.4"))
    implementation("org.springframework.boot:spring-boot-starter-data-jpa")
    runtimeOnly("org.postgresql:postgresql")
}

// Override a managed version in either option
extra["jackson.version"] = "2.17.1"

Layered JARs for Docker

Layered JARs split the fat JAR into Docker-cacheable layers ordered by change frequency: dependencies (rarely change), Spring Boot loader, snapshot dependencies, and application classes (change on every commit). The Docker build only re-uploads the thin application layer on most changes, cutting image push times dramatically.

// Layered JARs are enabled by default in Spring Boot 3.x Gradle plugin
// Explicitly configure custom layers if needed:
tasks.named<org.springframework.boot.gradle.tasks.bundling.BootJar>("bootJar") {
    layered {
        application {
            intoLayer("spring-boot-loader") {
                include("org/springframework/boot/loader/**")
            }
            intoLayer("application")
        }
        dependencies {
            intoLayer("snapshot-dependencies") {
                include("*:*:*SNAPSHOT")
            }
            intoLayer("dependencies")
        }
        layerOrder.addAll("dependencies", "spring-boot-loader",
                          "snapshot-dependencies", "application")
    }
}
# Dockerfile using layered extraction
FROM eclipse-temurin:21-jre AS builder
WORKDIR /app
COPY build/libs/*.jar app.jar
RUN java -Djarmode=layertools -jar app.jar extract

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

bootBuildImage (Cloud Native Buildpacks)

bootBuildImage creates an OCI-compliant container image using Cloud Native Buildpacks — no Dockerfile required. It detects your Java version, sets memory limits intelligently, and produces a production-ready image. The Spring Boot Gradle plugin configures Paketo Buildpacks by default.

// Configure image name and builder
tasks.named<org.springframework.boot.gradle.tasks.bundling.BootBuildImage>("bootBuildImage") {
    imageName = "myregistry/my-app:${project.version}"
    // Use a specific builder (default is paketobuildpacks/builder-jammy-base)
    builder = "paketobuildpacks/builder-jammy-base:latest"
    // Pass environment to the buildpack
    environment = mapOf(
        "BP_JVM_VERSION" to "21",
        "BPE_SPRING_PROFILES_ACTIVE" to "production"
    )
    // Push to registry after build
    publish = false
    docker {
        publishRegistry {
            username = System.getenv("DOCKER_USERNAME")
            password = System.getenv("DOCKER_PASSWORD")
        }
    }
}
./gradlew bootBuildImage                   # Build OCI image locally
./gradlew bootBuildImage --imageName=myapp # Override image name
docker run --rm -p 8080:8080 myregistry/my-app:0.0.1-SNAPSHOT

Native Image (GraalVM)

The org.graalvm.buildtools.native plugin enables AOT compilation to a GraalVM native binary. Native images start in <50ms and use a fraction of the JVM heap — ideal for AWS Lambda, Google Cloud Run, and CLI tools. Spring Boot 3.x includes all necessary AOT processing.

plugins {
    java
    id("org.springframework.boot") version "3.3.4"
    id("io.spring.dependency-management") version "1.1.6"
    id("org.graalvm.buildtools.native") version "0.10.2"
}

graalvmNative {
    binaries {
        named("main") {
            imageName = "my-app"
            buildArgs.add("--verbose")
        }
    }
    // Test support
    testSupport = true
}
# Compile to native binary (requires GraalVM JDK)
./gradlew nativeCompile

# Run the native binary
build/native/nativeCompile/my-app

# Or build OCI image with native binary (no local GraalVM needed)
./gradlew bootBuildImage -PnativeImage=true

# Run native tests
./gradlew nativeTest

Testcontainers + @ServiceConnection

Spring Boot 3.1+ works with Testcontainers using @ServiceConnection — the annotation wires the container's dynamic port to the matching Spring property automatically. Gradle includes Testcontainers BOM management when using the Spring dependency-management plugin.

dependencies {
    testImplementation("org.springframework.boot:spring-boot-testcontainers")
    testImplementation("org.testcontainers:junit-jupiter")
    testImplementation("org.testcontainers:postgresql")
}
@SpringBootTest
@Testcontainers
class ProductRepositoryTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired ProductRepository repo;

    @Test
    void persistsProduct() {
        repo.save(new Product("Widget", 9.99));
        assertThat(repo.count()).isEqualTo(1);
    }
}

Kotlin DSL Tips for Spring Projects

When writing Spring Boot builds in Kotlin DSL, a few patterns come up constantly: configuring compiler options for Kotlin projects, using extra[] to override managed versions, and using tasks.withType<> for type-safe task configuration.

import org.jetbrains.kotlin.gradle.tasks.KotlinCompile

plugins {
    kotlin("jvm") version "2.0.0"
    kotlin("plugin.spring") version "2.0.0"     // opens classes for proxies
    kotlin("plugin.jpa") version "2.0.0"        // no-arg for JPA entities
    id("org.springframework.boot") version "3.3.4"
    id("io.spring.dependency-management") version "1.1.6"
}

java {
    toolchain { languageVersion = JavaLanguageVersion.of(21) }
}

tasks.withType<KotlinCompile> {
    compilerOptions {
        freeCompilerArgs.addAll("-Xjsr305=strict")
        jvmTarget = org.jetbrains.kotlin.gradle.dsl.JvmTarget.JVM_21
    }
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    implementation("com.fasterxml.jackson.module:jackson-module-kotlin")
    implementation("org.jetbrains.kotlin:kotlin-reflect")
    testImplementation("org.springframework.boot:spring-boot-starter-test")
}

// Override a BOM-managed version
extra["jackson.version"] = "2.17.1"
