Gradle (Groovy DSL)

Gradle 9.x

Gradle is a flexible, high-performance build tool that models a build as a directed acyclic graph (DAG) of tasks. All examples here use the Groovy DSL (build.gradle). Unlike Maven's fixed lifecycle, Gradle gives you fine-grained control, incremental and cacheable builds, and a rich plugin ecosystem covering everything from simple JAR packaging to GraalVM native images.

Quick Start — Java + JUnit 5

Initialize a bare Java project, then add JUnit 5. Two options: use gradle init (interactive wizard) or create the files manually.

package com.example;

import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;
import static org.assertj.core.api.Assertions.*;

@TestMethodOrder(MethodOrderer.OrderAnnotation.class)
class AppTest {

    @Test @Order(1)
    @DefaultLocale("en-US")         // JUnit 6 built-in, no extra extension
    @SetSystemProperty(key = "env", value = "test") // JUnit 6 built-in
    void environment_is_test() {
        assertThat(System.getProperty("env")).isEqualTo("test");
    }

    @Test @Order(2)
    void app_returns_greeting() {
        assertThat(new App().greeting()).isEqualTo("Hello, World!");
    }

    @ParameterizedTest
    @ValueSource(strings = {"Alice", "Bob"})
    void greets_by_name(String name) {
        assertThat(new App().greet(name)).contains(name);
    }
}

build.gradle — Full Project Structure (Groovy DSL)

The top-level build.gradle defines plugins, project metadata, repositories, dependencies, and task configuration. The Groovy DSL uses plain method calls and closures — no type annotations, no .set() calls.

// build.gradle (Groovy DSL)

plugins {
    id 'java'                                            // Java compilation, test, jar
    id 'application'                                     // adds 'run' task + distribution zip
    id 'checkstyle'                                      // static analysis
}

// Project coordinates
group   = 'com.example'
version = '1.0.0'
description = 'Order management service'

// Java toolchain — reproducible across machines
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
    withSourcesJar()   // produce *-sources.jar
    withJavadocJar()   // produce *-javadoc.jar
}

// Repositories searched in declaration order
repositories {
    mavenCentral()
    maven { url 'https://repo.spring.io/milestone' }    // Spring milestones
    mavenLocal()                                         // ~/.m2 (last resort in dev)
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web:3.5.0'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa:3.5.0'
    runtimeOnly    'org.postgresql:postgresql:42.7.4'
    compileOnly    'org.projectlombok:lombok:1.18.36'
    annotationProcessor 'org.projectlombok:lombok:1.18.36'

    testImplementation 'org.springframework.boot:spring-boot-starter-test:3.5.0'
    testRuntimeOnly    'org.junit.platform:junit-platform-launcher'
}

// Configure the application entry point (required by 'application' plugin)
application {
    mainClass = 'com.example.order.OrderApplication'
}

// Fine-tune the test task
test {
    useJUnitPlatform()
    maxHeapSize = '1g'
}

// Compiler options
compileJava {
    options.encoding    = 'UTF-8'
    options.compilerArgs << '-parameters'    // preserve parameter names (needed by Spring)
}

// Jar manifest
jar {
    manifest {
        attributes(
            'Implementation-Title':   project.name,
            'Implementation-Version': project.version
        )
    }
}
Groovy vs Kotlin DSL Groovy DSL uses single or double quotes, optional parentheses, and closures ({ }). Kotlin DSL (.kts) requires double quotes everywhere and uses lambdas. This page uses Groovy DSL exclusively.

settings.gradle — Project Name and Submodules

settings.gradle is always the entry point for Gradle. It declares the root project name and includes any subprojects. For single-project builds it is minimal; for multi-module builds it lists every subproject path.

// settings.gradle

// Required: sets the root project name (also the default artifact ID)
rootProject.name = 'order-service'

// Plugin management — where to resolve plugins from
pluginManagement {
    repositories {
        gradlePluginPortal()
        mavenCentral()
        maven { url 'https://repo.spring.io/milestone' }
    }
}

// Dependency resolution management — centralize for all subprojects
dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)  // enforce central repos
    repositories {
        mavenCentral()
    }
    // Point to the version catalog
    versionCatalogs {
        libs {
            from(files('gradle/libs.versions.toml'))
        }
    }
}

// Include subprojects (for multi-module builds)
include ':api'
include ':service'
include ':web'
include ':common'

Gradle Wrapper

The Gradle Wrapper (gradlew / gradlew.bat) pins the Gradle version for a project so everyone on the team — and CI — uses the same version without installing Gradle manually. Always commit the wrapper files.

# Generate or upgrade the wrapper to a specific version
./gradlew wrapper --gradle-version=9.7.1 --distribution-type=bin

# Use the wrapper for all builds (never use a system-installed gradle)
./gradlew build
./gradlew clean build
./gradlew bootRun
# gradle/wrapper/gradle-wrapper.properties
distributionBase=GRADLE_USER_HOME
distributionPath=wrapper/dists
distributionUrl=https\://services.gradle.org/distributions/gradle-9.7.1-bin.zip
networkTimeout=10000
validateDistributionUrl=true
zipStoreBase=GRADLE_USER_HOME
zipStorePath=wrapper/dists
Files to commit Always commit gradlew, gradlew.bat, gradle/wrapper/gradle-wrapper.jar, and gradle/wrapper/gradle-wrapper.properties. Add .gradle/ to .gitignore.

gradle.properties — Build Configuration

gradle.properties in the project root sets Gradle behaviour flags and project properties. Values are available in build.gradle as project properties. Sensitive values (passwords, tokens) belong in ~/.gradle/gradle.properties (the user home properties), never in the project file.

# gradle.properties (project root — commit this)

# JVM settings for the Gradle build itself (not for the application)
org.gradle.jvmargs=-Xmx2g -XX:MaxMetaspaceSize=512m -Dfile.encoding=UTF-8  # Gradle 9 daemon requires JVM 17+

# Build performance
org.gradle.parallel=true            # build independent subprojects in parallel
org.gradle.caching=true             # enable local build cache
org.gradle.daemon=true              # keep the daemon alive between builds (default true)
org.gradle.configuration-cache=true  # stable in Gradle 9; prompts to enable if not set

# Custom project properties — read in build.gradle as `project.appPort`
appPort=8080
appEnv=development

# Spring Boot specific
spring.profiles.active=dev
// Reading gradle.properties values in build.gradle
bootRun {
    systemProperty 'server.port', project.findProperty('appPort') ?: '8080'
    systemProperty 'spring.profiles.active', project.findProperty('spring.profiles.active') ?: 'dev'
}

Command-Line Reference

Gradle's CLI accepts task names, flags, and project properties in any order. Multiple tasks can be chained; Gradle resolves the DAG and executes each task at most once per build.

# ── Discovery ──────────────────────────────────────────────────
./gradlew tasks                       # list all available tasks with descriptions
./gradlew tasks --all                  # include internal/lifecycle tasks
./gradlew help --task bootRun          # detailed help for a specific task
./gradlew properties                   # dump all project properties

# ── Core build lifecycle ────────────────────────────────────────
./gradlew assemble                     # compile + package (no tests)
./gradlew check                        # run all verification tasks (tests, lint)
./gradlew build                        # assemble + check (full build)
./gradlew clean build                  # delete outputs then full build
./gradlew clean build --parallel       # run independent subprojects in parallel

# ── Running and testing ─────────────────────────────────────────
./gradlew run                          # run the application (application plugin)
./gradlew test                         # run unit tests
./gradlew test --tests "com.example.order.*"          # filter by package
./gradlew test --tests "com.example.OrderServiceTest" # specific class
./gradlew test --tests "*.OrderServiceTest.save*"     # by method pattern

# ── Diagnostics ─────────────────────────────────────────────────
./gradlew build --info                 # extra lifecycle logging
./gradlew build --debug                # full debug output
./gradlew build --stacktrace           # print full stack traces on errors
./gradlew build --scan                 # publish a Build Scan to scans.gradle.com
./gradlew dependencies                 # full dependency tree for all configurations
./gradlew :service:dependencies        # dependency tree for a specific subproject
./gradlew dependencyInsight --dependency spring-core  # trace why a dep is included

# ── Daemon management ───────────────────────────────────────────
./gradlew --status                     # show running daemons
./gradlew --stop                       # stop all daemons

# ── Skipping tasks ──────────────────────────────────────────────
./gradlew build -x test               # skip the test task
./gradlew build --continue            # keep going after a failure

Extra Properties and the ext Block

The ext block (short for project.extensions.extraProperties) stores arbitrary key-value pairs on the project or any domain object. Use it to centralise version strings or share constants across subprojects.

// Root build.gradle — define shared constants in ext
ext {
    javaVersion        = 21
    springBootVersion  = '3.5.0'
    lombokVersion      = '1.18.36'
    postgresVersion    = '42.7.4'
    junitVersion       = '5.11.4'

    // Computed value
    isRelease = !version.endsWith('-SNAPSHOT')
}

// Use in the same build.gradle
java {
    toolchain { languageVersion = JavaLanguageVersion.of(javaVersion) }
}

dependencies {
    implementation "org.springframework.boot:spring-boot-starter-web:${springBootVersion}"
    compileOnly    "org.projectlombok:lombok:${lombokVersion}"
}

// In a subproject — read ext defined in root
dependencies {
    implementation "org.springframework.boot:spring-boot-starter-web:${rootProject.ext.springBootVersion}"
}

// Conditional logic using ext properties
if (ext.isRelease) {
    apply plugin: 'signing'
}

Dependency Configurations — When to Use Each

Each configuration controls the classpath scope in which a dependency is visible. Choosing the right one reduces classpath pollution and improves compile times.

dependencies {

    // ── Runtime + compile classpath; leaked to consumers ──
    // Use for: APIs you expose in your own public method signatures
    api 'com.example:common-types:1.0.0'

    // ── Runtime + compile classpath; NOT leaked to consumers ──
    // Use for: internal implementation details (99% of your deps)
    implementation 'org.springframework.boot:spring-boot-starter-web:3.5.0'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa:3.5.0'
    implementation 'com.fasterxml.jackson.core:jackson-databind:2.18.2'

    // ── Compile classpath only; NOT on runtime classpath ──
    // Use for: annotations, code generation tools, Servlet API (provided by container)
    compileOnly 'jakarta.servlet:jakarta.servlet-api:6.1.0'
    compileOnly 'org.projectlombok:lombok:1.18.36'

    // ── Annotation processors (separate from compileOnly) ──
    annotationProcessor 'org.projectlombok:lombok:1.18.36'
    annotationProcessor 'org.mapstruct:mapstruct-processor:1.6.3'

    // ── Runtime classpath only; NOT available at compile time ──
    // Use for: JDBC drivers, logging implementations, DB migration tools
    runtimeOnly 'org.postgresql:postgresql:42.7.4'
    runtimeOnly 'ch.qos.logback:logback-classic:1.5.15'
    runtimeOnly 'org.flywaydb:flyway-core:10.21.0'

    // ── Test compile + runtime classpath ──
    testImplementation 'org.springframework.boot:spring-boot-starter-test:3.5.0'
    testImplementation 'org.testcontainers:postgresql:1.20.4'
    testImplementation 'org.assertj:assertj-core:3.26.3'

    // ── Test runtime only (e.g. JUnit launcher) ──
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'

    // ── Compile-time test annotation processor ──
    testAnnotationProcessor 'org.mapstruct:mapstruct-processor:1.6.3'
}
api vs implementation Only use api for dependencies whose types appear in your public API signatures. Every api dependency is recompiled when it changes, affecting downstream consumers. Prefer implementation — it avoids leaking internal dependencies and speeds up incremental compilation.

Rich Versions and Dynamic Resolution

Gradle's rich version model lets you express constraints beyond a simple version string — strictly pinned, preferred, required ranges, and rejection patterns.

dependencies {

    // ── Dynamic version (resolves at build time — avoid in production) ──
    implementation 'com.example:some-lib:1.+'          // latest 1.x
    implementation 'com.example:some-lib:latest.release'

    // ── Version range ──
    implementation 'com.fasterxml.jackson.core:jackson-databind:[2.16,3.0)'

    // ── Rich versions (use inside a dependency { } closure) ──
    implementation('com.google.guava:guava') {
        version {
            require  '[32.0,)'   // minimum version required
            prefer   '33.4.0-jre'  // use this if nothing else forces a different version
            strictly '[33.0,34.0)' // reject anything outside this range
            reject   '33.1.0-jre'  // never use this specific version (known bug)
        }
    }

    // ── Exclude a transitive dependency ──
    implementation('org.springframework.boot:spring-boot-starter-web:3.5.0') {
        exclude group: 'org.springframework.boot', module: 'spring-boot-starter-tomcat'
    }
    // Add Undertow instead
    implementation 'org.springframework.boot:spring-boot-starter-undertow:3.5.0'

    // ── Disable transitive dependencies entirely ──
    implementation('com.example:legacy-lib:2.0.0') {
        transitive = false
    }
}

Dependency Resolution Strategy

Resolution strategies allow you to globally force versions, substitute modules, or fail on dynamic versions — useful for ensuring reproducible builds across teams.

configurations.all {
    resolutionStrategy {

        // Force a specific version regardless of what dependencies request
        force 'com.fasterxml.jackson.core:jackson-databind:2.18.2'
        force 'org.yaml:snakeyaml:2.3'

        // Fail the build if any dependency uses a dynamic version
        failOnDynamicVersions()

        // Fail if any version was changed by conflict resolution
        // failOnVersionConflict()

        // Cache dynamic versions for this long (default: 24h)
        cacheDynamicVersionsFor 10, 'minutes'

        // Module substitution — replace one module with another
        dependencySubstitution {
            substitute module('log4j:log4j') using module('org.apache.logging.log4j:log4j-core:2.24.2')
            substitute module('commons-logging:commons-logging') using module('org.slf4j:jcl-over-slf4j:2.0.16')
        }
    }
}

// Enforce consistent versions across a configuration
configurations.runtimeClasspath {
    resolutionStrategy.eachDependency { DependencyResolveDetails details ->
        if (details.requested.group == 'org.slf4j') {
            details.useVersion '2.0.16'
            details.because 'Align all SLF4J modules'
        }
    }
}

BOM and Platform Imports

A BOM (Bill of Materials) enforces consistent versions across a set of related dependencies. Use platform() to import a BOM — the BOM's version recommendations are applied as constraints, not forced versions. Use enforcedPlatform() to override any dependency's own version.

dependencies {

    // ── Import a BOM (recommended — respects local overrides) ──
    implementation platform('org.springframework.boot:spring-boot-dependencies:3.5.0')

    // After importing the BOM, omit versions for managed dependencies:
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'

    // ── Import multiple BOMs (order matters — first BOM wins on conflict) ──
    implementation platform('org.springframework.cloud:spring-cloud-dependencies:2024.0.1')

Custom Task Classes with Incremental Build

Define a custom task class with annotated inputs and outputs so Gradle can determine whether the task is up-to-date and skip it when nothing changed.

// buildSrc/src/main/groovy/com/example/GenerateVersionFileTask.groovy
import org.gradle.api.DefaultTask
import org.gradle.api.file.RegularFileProperty
import org.gradle.api.provider.Property
import org.gradle.api.tasks.*

@CacheableTask   // makes the task cacheable in the build cache
abstract class GenerateVersionFileTask extends DefaultTask {

    @Input
    abstract Property<String> getVersion()

    @Input
    abstract Property<String> getBuildTime()

    @OutputFile
    abstract RegularFileProperty getOutputFile()

    @TaskAction
    void generate() {
        outputFile.get().asFile.text = """\
            app.version=${version.get()}
            app.build-time=${buildTime.get()}
            """.stripIndent()
    }
}

// ── Use the custom task in build.gradle ──
tasks.register('generateVersionFile', GenerateVersionFileTask) {
    group       = 'build'
    description = 'Write version info to a properties file'
    version     = project.version.toString()
    buildTime   = new Date().format("yyyy-MM-dd'T'HH:mm:ssZ")
    outputFile  = layout.buildDirectory.file('resources/main/version.properties')
}

// Ensure the file is generated before resources are processed
processResources.dependsOn generateVersionFile

Task Dependencies and Ordering

Gradle resolves a task DAG from dependency declarations. Declare semantic dependencies with dependsOn; use ordering hints (mustRunAfter) when tasks are independent but must not run concurrently in a certain order.

// ── dependsOn: task A must complete before task B can start ──
tasks.register('generateCode') {
    doLast { println 'Code generation complete' }
}

tasks.register('compileGeneratedCode') {
    dependsOn 'generateCode'     // explicit dependency
    doLast { println 'Compilation complete' }
}

// ── finalizedBy: run cleanup task after main task, even on failure ──
tasks.register('integrationTest', Test) {
    description = 'Run integration tests'
    group       = 'verification'
    testClassesDirs = sourceSets.integrationTest.output.classesDirs
    classpath       = sourceSets.integrationTest.runtimeClasspath
    finalizedBy 'stopTestContainers'   // always stop containers after tests
}

tasks.register('stopTestContainers') {
    doLast { println 'Stopping test containers' }
}

// ── mustRunAfter: ordering without dependency (both may not always run) ──
test.mustRunAfter compileJava
integrationTest.mustRunAfter test

// ── doFirst / doLast: add actions to existing tasks ──
test {
    doFirst {
        println "Starting test run with ${maxParallelForks} parallel forks"
    }
    doLast {
        println "Test results: ${testResultsDir}"
    }
}

// ── taskGraph.whenReady: react to the full resolved task graph ──
gradle.taskGraph.whenReady { graph ->
    if (graph.hasTask(':release')) {
        println "RELEASE BUILD — signing will be applied"
    }
}

Task Lifecycle — Configuration vs Execution

Gradle builds in two phases: configuration (all build.gradle files evaluated, task DAG assembled) and execution (selected tasks run in DAG order). Code inside a task closure but outside doFirst {} / doLast {} runs at configuration time — a common mistake.

// ── WRONG — println runs at configuration time for every ./gradlew invocation ──
tasks.register('badTask') {
    println 'This runs even if badTask is not selected!'  // ← configuration-time side effect
    doLast {
        println 'This runs at execution time'
    }
}

// ── CORRECT — configuration code reads properties, execution code does work ──
tasks.register('generateReport') {
    group       = 'reporting'
    description = 'Generate HTML report'
    // Configuration: declare inputs/outputs
    def outputDir = layout.buildDirectory.dir('reports/custom')
    outputs.dir(outputDir)

    doLast {
        // Execution: do the actual work
        println "Writing report to ${outputDir.get()}"
        outputDir.get().asFile.mkdirs()
        new File(outputDir.get().asFile, 'report.html').text = '<html><body>Report</body></html>'
    }
}

// ── Lazy evaluation with providers — avoids configuration-time evaluation ──
tasks.register('printVersion') {
    doLast {
        // providers.provider {} is lazy — evaluated at execution time
        def ver = providers.provider { project.version }.get()
        println "Version: ${ver}"
    }
}
Configuration cache When org.gradle.configuration-cache=true is set, the configuration phase result is cached. Tasks must not capture non-serialisable objects at configuration time (e.g. direct references to project inside doLast {}). Use providers and layout APIs instead.

Parallel Execution and Test Filtering

Gradle can run test classes across multiple JVMs simultaneously via maxParallelForks. Use --tests on the CLI or include/exclude in the task to filter which tests run.

test {
    useJUnitPlatform()

    // Run tests in multiple JVM forks (class-level parallelism)
    maxParallelForks = Runtime.runtime.availableProcessors().intdiv(2) ?: 1

    // JUnit 5 method-level parallelism (within a single JVM fork)
    systemProperty 'junit.jupiter.execution.parallel.enabled', 'true'
    systemProperty 'junit.jupiter.execution.parallel.mode.default', 'concurrent'

    // Class filter — only run classes matching these patterns
    include '**/*Test.class'
    include '**/*Tests.class'
    include '**/*Spec.class'
    exclude '**/*IT.class'          // exclude integration tests from unit test task

    // Tag-based filtering (JUnit 5 tags)
    useJUnitPlatform {
        includeTags 'unit'           // @Tag("unit")
        excludeTags 'slow', 'manual'
    }
}

./gradlew test --tests "com.example.order.OrderServiceTest.save*" # method pattern

Writing a Custom Gradle Plugin

A custom plugin encapsulates reusable build logic. Define it in buildSrc (project-local) or a standalone plugin project (shareable via the Plugin Portal).

// buildSrc/src/main/groovy/com/example/build/BannerPlugin.groovy
package com.example.build

import org.gradle.api.Plugin
import org.gradle.api.Project

class BannerPlugin implements Plugin<Project> {

    @Override
    void apply(Project project) {
        // Register an extension so users can configure the plugin
        def extension = project.extensions.create('banner', BannerExtension)

        // Register a task that uses the extension
        project.tasks.register('printBanner') {
            group       = 'application'
            description = 'Print the application start banner'
            doLast {
                println "=" * 60
                println "  App:     ${extension.appName.getOrElse(project.name)}"
                println "  Version: ${project.version}"
                println "  Env:     ${extension.environment.getOrElse('development')}"
                println "=" * 60
            }
        }

        // Make bootRun print the banner first
        project.tasks.matching { it.name == 'bootRun' }.configureEach {
            dependsOn 'printBanner'
        }
    }
}

// buildSrc/src/main/groovy/com/example/build/BannerExtension.groovy
import org.gradle.api.provider.Property

    abstract Property<String> getAppName()
    abstract Property<String> getEnvironment()
}

}

}

Gradle Daemon and Performance

The Gradle Daemon is a long-lived JVM process that keeps the build warm between invocations, dramatically reducing startup time. It is enabled by default. The configuration cache takes this further by caching the configuration phase result.

# gradle.properties — performance tuning

org.gradle.parallel=true               # build independent subprojects concurrently

Configuration Cache

Stable in Gradle 9 — the configuration cache stores the resolved task graph so Gradle skips the entire configuration phase on cache hits. Gradle 9 prompts users to enable it automatically and reports problems gracefully instead of failing the build.

# Treat problems as warnings (not errors) during migration (Gradle 9 default):

# First build: configuration cache MISS (computed and stored)
./gradlew build
# > Calculating task graph as no cached configuration is available for tasks: build
# > Configuration cache entry stored.

# Second build: configuration cache HIT (skips configuration phase entirely)
./gradlew build
# > Reusing configuration cache.

# Invalidate the cache

bootJar and bootRun Tasks

bootJar creates the executable fat JAR (replaces the standard jar task). bootRun runs the application from the build, passing JVM args and system properties. DevTools enables live class reloading.

// Configure the executable fat JAR
bootJar {
    // Override the main class (auto-detected if there is only one @SpringBootApplication)
    mainClass = 'com.example.order.OrderApplication'

    // Custom archive name
    archiveFileName = "order-service-${project.version}.jar"

    // Exclude dev-only resources from the JAR
    exclude 'application-local.properties'

    // Manifest entries
    manifest {
        attributes 'Implementation-Title':   project.name,
                   'Implementation-Version': project.version
    }
}

// Disable the default plain jar task (only ship the fat JAR)
jar {
    enabled = false
}

// Configure the bootRun task for local development
bootRun {
    mainClass = 'com.example.order.OrderApplication'

    // Active Spring profiles
    systemProperty 'spring.profiles.active', findProperty('spring.profiles.active') ?: 'local'

    // Pass arbitrary system properties
    systemProperties System.properties.subMap(['server.port', 'logging.level.root'])

    // JVM arguments
    jvmArgs '-Xmx512m', '-XX:+UseG1GC', '-Dfile.encoding=UTF-8'

    // Application arguments
    args '--debug'

    // Source sets for live reload with DevTools
    sourceResources sourceSets.main
}

// Run with a specific profile: ./gradlew bootRun -Pspring.profiles.active=dev

Layered JAR for Docker

Layered JARs split the fat JAR into Docker layers (dependencies, Spring Boot loader, snapshot dependencies, application code) so that the largest layers — third-party dependencies — are cached by Docker and not re-pushed on every code change.

bootJar {
    layered {
        enabled = true
        // Optional: customise the layer order and which files go where
        application {
            intoLayer('spring-boot-loader') {
                include 'org/springframework/boot/loader/**'
            }
            intoLayer('snapshot-dependencies') {
                include '*:*:*SNAPSHOT'
            }
            intoLayer('dependencies')
            intoLayer('application')
        }
        layerOrder = ['dependencies', 'spring-boot-loader', 'snapshot-dependencies', 'application']
    }
}

FROM eclipse-temurin:21-jre AS builder
WORKDIR /app
COPY build/libs/order-service-*.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --launcher --destination extracted

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=builder /app/extracted/dependencies/          ./
COPY --from=builder /app/extracted/spring-boot-loader/   ./
COPY --from=builder /app/extracted/snapshot-dependencies/ ./
COPY --from=builder /app/extracted/application/          ./

ProjectLayout — File & Directory Paths

project.layout is the recommended way to reference files and directories — it returns lazy Provider-backed paths that work with configuration cache and incremental builds. Never use new File(...) inside tasks.

// build.gradle
tasks.register('generateSources', Copy) {
    // layout.projectDirectory — root of the project
    from layout.projectDirectory.dir('src/templates')

    // layout.buildDirectory — project's build/ folder
    into layout.buildDirectory.dir('generated/sources')
}

// Set the build directory to a custom location
layout.buildDirectory = layout.projectDirectory.dir('out')

// Inside a custom task class
abstract class MyTask extends DefaultTask {
    @InputDirectory
    abstract DirectoryProperty getSourceDir()

    @OutputDirectory
    abstract DirectoryProperty getOutputDir()

    @TaskAction
    void generate() {
        def src  = sourceDir.get().asFile
        def dest = outputDir.get().asFile
        // ...
    }
}

tasks.register('myTask', MyTask) {
    sourceDir = layout.projectDirectory.dir('src/data')
    outputDir = layout.buildDirectory.dir('data-out')
}
Key types — DirectoryProperty, RegularFileProperty, Directory, RegularFile. Prefer layout.buildDirectory.file('...') over "$buildDir/..." string interpolation — the latter breaks configuration cache.

ProviderFactory — Lazy Values & External Inputs

project.providers gives you lazy, cacheable reads of Gradle properties, environment variables, system properties, and file contents. Values are resolved only when a task actually runs.

// Gradle property (-PmyProp=value or gradle.properties)
Provider<String> appVersion = providers.gradleProperty('appVersion')
    .orElse('0.0.1-SNAPSHOT')

// Environment variable
Provider<String> ciToken = providers.environmentVariable('CI_TOKEN')

// System property (-DjavaOpts=...)
Provider<String> javaOpts = providers.systemProperty('javaOpts')

// File contents (lazy)
Provider<String> buildTag = providers.fileContents(
    layout.projectDirectory.file('BUILD_TAG')
).asText.orElse('local')

// Use inside a task — value resolved at execution time
tasks.register('printVersion') {
    doLast {
        println "Version: ${appVersion.get()}"
        println "Tag:     ${buildTag.get()}"
    }
}

// Pass a provider to a task property (wires the value lazily)
tasks.register('archive', Zip) {
    archiveVersion = appVersion
    from layout.buildDirectory.dir('dist')
}
Configuration cache rule — always read external state (env vars, files, system props) via providers, never via System.getenv() or file(...).text at configuration time. Direct reads break the configuration cache.

TaskContainer — Querying & Wiring Tasks

project.tasks is the container for all tasks. Use register (lazy, preferred) over create (eager). Wire tasks by referencing their providers — Gradle builds the dependency graph without realizing tasks prematurely.

// Register (lazy — task is not created until needed)
def compileTask = tasks.register('compileTemplates', JavaExec) {
    classpath = configurations.compileClasspath
    mainClass = 'com.example.TemplateCompiler'
    args layout.projectDirectory.dir('templates').asFile.absolutePath
    outputs.dir layout.buildDirectory.dir('compiled-templates')
}

// Named — get a lazy reference to an existing task
tasks.named('processResources') {
    dependsOn compileTask
}

// withType — configure all tasks of a type (e.g. all Test tasks)
tasks.withType(Test).configureEach {
    useJUnitPlatform()
    maxHeapSize = '512m'
    systemProperty 'spring.profiles.active', 'test'
}

// withType — disable all JavaDoc tasks in CI
tasks.withType(Javadoc).configureEach {
    enabled = !System.getenv('CI')
}

// Query by name at execution time
tasks.named('build').configure {
    dependsOn tasks.named('generateOpenApi')
}

// Task ordering without a direct dependency
tasks.named('startServer').configure {
    mustRunAfter tasks.named('cleanDatabase')
}
Avoid tasks.create — it eagerly creates the task and forces all its configuration to run even when the task is never used, slowing configuration time. Prefer tasks.register + tasks.named.

ExtensionContainer — Plugin Extensions

project.extensions is where plugins register their configuration DSL blocks. You can create your own DSL extension for a custom plugin and query extensions registered by other plugins.

// ----- Defining an extension in a custom plugin -----
// Extension class (can be abstract; Gradle injects ObjectFactory)
abstract class MyPluginExtension {
    abstract Property<String> getOutputDir()
    abstract Property<Boolean> getVerbose()

    MyPluginExtension() {
        outputDir.convention('build/my-plugin')
        verbose.convention(false)
    }
}

class MyPlugin implements Plugin<Project> {
    void apply(Project project) {
        def ext = project.extensions.create('myPlugin', MyPluginExtension)

        project.tasks.register('myPluginRun') {
            doLast {
                println "Output: ${ext.outputDir.get()}"
                println "Verbose: ${ext.verbose.get()}"
            }
        }
    }
}

// ----- Consuming the extension in build.gradle -----
apply plugin: MyPlugin

myPlugin {
    outputDir = 'dist/generated'
    verbose   = true
}

// ----- Querying an extension from another plugin -----
// Find by type (null-safe)
def javaExt = extensions.findByType(JavaPluginExtension)

extensions.getByName('publishing') // PublishingExtension

// ---- Sub-project references ----
project(':api').tasks.named('jar')          // task in sibling project
project(':service').configurations.runtimeClasspath

// ---- afterEvaluate (use sparingly) ----
afterEvaluate {
    // Runs after all build.gradle files in this project are evaluated
    if (plugins.hasPlugin('java')) {
        tasks.named('jar').configure { archiveClassifier = 'core' }
    }
}
Avoid afterEvaluate when possible — it forces eager evaluation and breaks lazy configuration. Prefer tasks.withType(...).configureEach and plugins.withId('...') for reacting to other plugins.
