Spring Proxy Internals

Spring 5/6/7

Spring's AOP, transaction management, security, and caching all work through proxies — wrapper objects that intercept method calls and inject cross-cutting behaviour before or after the real method executes. Understanding how proxies are created and their limitations is essential for debugging Spring applications.

How a Proxy Works

When a bean is eligible for proxying (it has an aspect, a @Transactional method, etc.), Spring replaces the bean in the application context with a proxy object. Callers receive the proxy, not the real object. Every method call goes through the proxy's interception chain before reaching the target.

The key insight: the caller never knows it's talking to a proxy. The proxy implements the same interface or extends the same class as the real bean, so it's type-compatible and can be injected anywhere the real type is expected.

How JDK Dynamic Proxy Works

JDK Dynamic Proxies are part of the Java standard library (java.lang.reflect.Proxy). They work by creating a new class at runtime that implements one or more interfaces. Every method call on the proxy is routed to an InvocationHandler which decides what to do — run advice, delegate to the real object, or both.

// What Spring does internally (simplified)
UserService proxy = (UserService) Proxy.newProxyInstance(
    UserService.class.getClassLoader(),
    new Class[]{UserService.class},       // interfaces to implement
    new InvocationHandler() {
        @Override
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            // ① run Before advice
            System.out.println("Before: " + method.getName());
            try {
                // ② delegate to real bean
                Object result = method.invoke(realUserService, args);
                // ③ run AfterReturning advice
                System.out.println("After: " + method.getName());
                return result;
            } catch (Throwable t) {
                // ④ run AfterThrowing advice
                throw t;
            }
        }
    }
);

Requirements

For a JDK proxy to work, the bean must implement at least one interface. The proxy only exposes methods defined in those interfaces — methods on the concrete class that are not in any interface are invisible through the proxy.

// ✅ Works with JDK proxy — has interface
public interface UserService {
    User findById(long id);
    void save(User user);
}

@Service
@Transactional
public class UserServiceImpl implements UserService {
    @Override public User findById(long id) { ... }
    @Override public void save(User user) { ... }

    // ❌ Not accessible through proxy — not in interface
    public void internalHelper() { ... }
}

// ✅ Caller injects interface — proxy is transparent
@Autowired
private UserService userService;  // receives JDK proxy, not UserServiceImpl

What the Generated Class Looks Like

At runtime, the JVM generates bytecode for a class like $Proxy42 that implements your interface. You can dump it to inspect it — Spring Boot Actuator and -Dsun.misc.ProxyGenerator.saveGeneratedFiles=true let you see it on disk.

// The generated proxy class (conceptually):
public final class $Proxy42 extends Proxy implements UserService {
    // One static Method field per interface method
    private static Method m1; // findById
    private static Method m2; // save

    static {
        m1 = UserService.class.getMethod("findById", long.class);
        m2 = UserService.class.getMethod("save", User.class);
    }

    public $Proxy42(InvocationHandler h) { super(h); }

    @Override
    public User findById(long id) {
        // Calls h.invoke(this, m1, new Object[]{id})
        return (User) h.invoke(this, m1, new Object[]{id});
    }

    @Override
    public void save(User user) {
        h.invoke(this, m2, new Object[]{user});
    }
}

How CGLIB Proxy Works

CGLIB (Code Generation Library) creates proxies by generating a subclass of the target class at runtime. The subclass overrides every non-final, non-private method and inserts interceptor chain calls. Because it subclasses rather than implementing an interface, CGLIB works even when the bean has no interfaces.

Spring has bundled CGLIB since Spring 3.2 (org.springframework.cglib package) — no extra dependency needed.

// What CGLIB does internally (simplified)
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(UserServiceImpl.class);  // subclass target
enhancer.setCallback(new MethodInterceptor() {
    @Override
    public Object intercept(Object proxy, Method method,
                            Object[] args, MethodProxy methodProxy) throws Throwable {
        // ① run Before advice
        System.out.println("Before: " + method.getName());
        // ② invoke super (real class method — NO reflection overhead)
        Object result = methodProxy.invokeSuper(proxy, args);
        // ③ run AfterReturning advice
        System.out.println("After: " + method.getName());
        return result;
    }
});
UserServiceImpl proxy = (UserServiceImpl) enhancer.create();

Requirements & What Gets Subclassed

CGLIB generates a class that extends your bean class. This means:

  • The target class must not be final (can't subclass a final class)
  • Intercepted methods must not be final or private (can't override them)
  • The class needs a no-arg constructor (Spring instantiates the subclass)
  • No interface required — works on plain classes
@Service
@Transactional
public class OrderService {          // no interface — CGLIB is used
    public Order createOrder(...) { ... }    // ✅ intercepted (overridden)
    public final void audit() { ... }        // ❌ NOT intercepted (final)
    private void helper() { ... }            // ❌ NOT intercepted (private)
}

// CGLIB generates (conceptually):
public class OrderService$$SpringCGLIB$$0 extends OrderService {
    @Override
    public Order createOrder(...) {
        // run interceptor chain, then call super.createOrder(...)
    }
    // audit() and helper() are NOT overridden
}

Performance: CGLIB vs JDK

CGLIB uses MethodProxy.invokeSuper() which calls the parent method via generated bytecode — no reflection. JDK proxies use Method.invoke() (reflection). In practice, both are extremely fast for typical Spring usage, but CGLIB is measurably faster under high throughput since JDK reflection has been optimised over the years. The creation cost (class generation) is one-time per class and cached.

Decision Rules

Spring Boot 3.x defaults to CGLIB (proxyTargetClass=true) for all proxies. You can force JDK proxies back by setting spring.aop.proxy-target-class=false in application.properties.

Bean has interface(s)?
│
├─ No  → CGLIB (only option)
│
└─ Yes → Default choice depends on config:
         proxyTargetClass=false (old default) → JDK proxy
         proxyTargetClass=true  (Boot 3.x default) → CGLIB
                                (subclasses even when interface exists)
// @EnableAspectJAutoProxy — controls AOP proxy type
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = false)  // JDK proxies when possible
public class AppConfig {}

@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true)   // Always CGLIB (Spring Boot default)
public class AppConfig {}

// @EnableTransactionManagement — same flag
@EnableTransactionManagement(proxyTargetClass = false)
# application.properties — Boot 3.x global override
spring.aop.proxy-target-class=false   # prefer JDK proxies when interface available
spring.aop.auto=true                  # enable auto-proxy (default: true)

ProxyFactory — Creating Proxies Programmatically

ProxyFactory is Spring's low-level API for creating proxies without the application context. Useful for understanding how Spring works internally, writing custom infrastructure, or testing advice in isolation.

@Service
public class UserService {
    public String greet(String name) {
        return "Hello, " + name;
    }
}

// Create proxy manually
UserService real = new UserService();

ProxyFactory factory = new ProxyFactory(real);
factory.setProxyTargetClass(true);   // true=CGLIB, false=JDK (needs interface)

// Add advice directly
factory.addAdvice((MethodInterceptor) invocation -> {
    System.out.println("Before: " + invocation.getMethod().getName());
    Object result = invocation.proceed();
    System.out.println("After: "  + invocation.getMethod().getName());
    return result;
});

UserService proxy = (UserService) factory.getProxy();
proxy.greet("World");
// Output:
// Before: greet
// After:  greet

Inspecting Proxies at Runtime

You can inspect the proxy type and unwrap it at runtime using Spring's AopUtils and AopProxyUtils utilities — useful for debugging "why isn't my advice firing?" situations.

@Autowired
private UserService userService;   // this is actually a proxy

// Check proxy type
boolean isJdkProxy  = AopUtils.isJdkDynamicProxy(userService);    // true/false
boolean isCglib     = AopUtils.isCglibProxy(userService);          // true/false
boolean isAnyProxy  = AopUtils.isAopProxy(userService);            // true/false

// Get the real target class (not the proxy class)
Class<?> targetClass = AopUtils.getTargetClass(userService);       // UserServiceImpl.class

// Unwrap to access target object
Object target = ((Advised) userService).getTargetSource().getTarget();

// Print proxy class name — CGLIB looks like:
// com.example.UserService$$SpringCGLIB$$0
// JDK looks like:
// com.sun.proxy.$Proxy42
System.out.println(userService.getClass().getName());

Self-Invocation (The #1 Gotcha)

When a method inside a bean calls another method on the same bean using this, the call bypasses the proxy entirely — it goes directly to the real object. This means advice does not fire on self-invoked methods, even if they're annotated with @Transactional, @Cacheable, etc.

@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {
        saveOrder(order);    // ❌ self-invocation — @Transactional on saveOrder is IGNORED
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveOrder(Order order) {
        // This REQUIRES_NEW does nothing when called from placeOrder() above
        repo.save(order);
    }
}

Fix options:

// Option 1: Inject self (ugly but works)
@Service
public class OrderService {
    @Autowired
    private OrderService self;   // Spring injects the proxy, not 'this'

    public void placeOrder(Order order) {
        self.saveOrder(order);   // ✅ goes through proxy → advice fires
    }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveOrder(Order order) { ... }
}

// Option 2: Extract to a separate bean (cleaner)
@Service
public class OrderService {
    @Autowired private OrderPersistenceService persistence;

    public void placeOrder(Order order) {
        persistence.saveOrder(order);   // ✅ different bean → goes through proxy
    }
}

// Option 3: Use AspectJ weaving instead of proxy-based AOP
// (compile-time or load-time weaving — advice fires even on self-invocation)

Final Classes and Methods

CGLIB cannot subclass a final class, and neither CGLIB nor JDK proxies can intercept final, static, or private methods. Spring will either throw an exception at startup or silently ignore advice on those methods depending on the version and configuration.

// ❌ Spring cannot create a CGLIB proxy for this
@Service
@Transactional
public final class PaymentService {         // final class — CGLIB fails
    public void charge() { ... }
}
// Startup error: Cannot subclass final class com.example.PaymentService

// ❌ Final method — advice silently not applied
@Service
public class InvoiceService {
    @Transactional
    public final void generateInvoice() {   // final method — @Transactional ignored
        ...
    }
}

// ✅ Fix: remove final (or use AspectJ weaving if you must keep final)
@Service
public class InvoiceService {
    @Transactional
    public void generateInvoice() { ... }
}

Constructor Injection vs Field Injection in Proxied Beans

CGLIB proxies require a no-arg constructor because the proxy subclass must be instantiated. When you use constructor injection (the recommended approach), Spring uses objenesis to bypass the constructor for the proxy and then calls the real constructor on the target object. This is handled automatically since Spring 4.0.

// ✅ Constructor injection works fine — objenesis handles proxy instantiation
@Service
@Transactional
public class UserService {
    private final UserRepository repo;

    public UserService(UserRepository repo) {  // no no-arg constructor needed
        this.repo = repo;
    }
}

// ✅ Field injection also works
@Service
@Transactional
public class UserService {
    @Autowired
    private UserRepository repo;
}

Casting and instanceof with Proxies

With JDK proxies, the proxy object is not an instance of the concrete implementation class — only of the interface. Casting to the impl class will throw ClassCastException. With CGLIB proxies the subclass relationship means instanceof works for both the class and any interfaces.

// JDK proxy example (proxyTargetClass=false)
@Autowired
private UserService userService;  // JDK proxy

userService instanceof UserService       // ✅ true  (implements interface)
userService instanceof UserServiceImpl   // ❌ false (not a subclass)
(UserServiceImpl) userService            // ❌ ClassCastException

// CGLIB proxy example (proxyTargetClass=true, the Boot default)
userService instanceof UserService       // ✅ true
userService instanceof UserServiceImpl   // ✅ true  (proxy IS-A UserServiceImpl subclass)
(UserServiceImpl) userService            // ✅ works (but avoid — use interface)
