Spring Tooling & Local Setup

This page covers everything you need to go from zero to a running Spring Boot application — project generation, IDE configuration, build tools, hot reload, testing strategies, Actuator endpoints, and common errors. Whether you are using Maven or Gradle, IntelliJ or VS Code, the examples below give you working commands and code you can use immediately.

1. Spring Initializr

start.spring.io is the official project-generation tool. Fill in a short form and download a zip containing a ready-to-run project with the correct directory layout, wrapper scripts, and dependency declarations. Each field controls a distinct aspect of the generated project:

  • Project — Choose Maven or Gradle. Maven uses pom.xml; Gradle uses build.gradle. Both ship with a wrapper script (mvnw / gradlew) so a local install is not required.
  • Language — Java, Kotlin, or Groovy. Java is the most common and has the widest documentation coverage.
  • Spring Boot version — Always pick the latest stable (non-SNAPSHOT, non-M) release. Avoid milestone (M) and release-candidate (RC) builds for learning projects.
  • Group / Artifact — Become your Maven coordinates (groupId + artifactId) and the root Java package. Convention: reverse-domain for Group (e.g. com.example), kebab-case for Artifact (e.g. my-api).
  • Packaging — Jar embeds Tomcat and is self-contained (recommended). War is for deploying into an external servlet container.
  • Java version — Match the JDK installed locally. Spring Boot 3.x requires Java 17+.

Recommended Dependencies for Learning

Dependency Group ID Purpose
Spring Web org.springframework.boot REST APIs, MVC controllers, embedded Tomcat
Spring Data JPA org.springframework.boot Database access via JPA/Hibernate with repository abstraction
H2 Database com.h2database In-memory database — zero config, great for testing

<dependencies>

        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-data-jpa</artifactId>
    </dependency>

    <!-- H2: in-memory DB, auto-configured with DataJpaTest -->

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-devtools</artifactId>
        <scope>runtime</scope>
        <optional>true</optional>
    </dependency>

    <!-- Actuator: /actuator/health, /actuator/beans, etc. -->
    <dependency>
        <groupId>org.springframework.boot</groupId>

    </dependency>

    <!-- Test slice: JUnit 5 + Mockito + MockMvc -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
    </dependency>

</dependencies>

3. Maven vs Gradle

Both build tools are first-class citizens in the Spring ecosystem. Spring Initializr generates wrapper scripts for both, so neither requires a local installation. Below is the same task expressed in each tool.

Adding a Dependency

Maven — pom.xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
Gradle — build.gradle
implementation 'org.springframework.boot:spring-boot-starter-web'

Common Commands Side-by-Side

Maven
# Run tests
./mvnw test

# Build executable JAR
./mvnw package

# Run the application
./mvnw spring-boot:run

# Inspect dependency tree
./mvnw dependency:tree
Gradle
# Run tests
./gradlew test

# Build executable JAR
./gradlew build

# Run the application
./gradlew bootRun

# Inspect dependency tree
./gradlew dependencies
Which to choose? Maven's XML is more verbose but its conventions are extremely stable and widely documented. Gradle's Groovy/Kotlin DSL is more concise. If you have no preference, pick Maven — most Spring tutorial examples show Maven syntax.

Changing the Default Port

By default Spring Boot listens on port 8080. To change it, add one line to src/main/resources/application.properties:

server.port=8081

Then restart the application. Alternatively, pass it on the command line without touching the file:

./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=8081

5. Spring Boot DevTools — Hot Reload

DevTools monitors the JVM classpath for changes and triggers a fast restart — not a full JVM restart. It keeps the JVM alive, swaps only the application's own classes (the app classloader), and restarts the Spring context. This typically takes 1–3 seconds vs 5–20 seconds for a cold start.

Add to pom.xml

<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-devtools</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>

application.properties

# Enable classpath watcher and restart on change
spring.devtools.restart.enabled=true

# Enable LiveReload server (port 35729) — browser extension triggers refresh
spring.devtools.livereload.enabled=true

How It Works

  1. DevTools starts a file watcher on the classpath (your compiled classes).
  2. When your IDE saves and compiles a changed class, the watcher detects the update.
  3. DevTools discards the application classloader and creates a new one, reloading only your code (third-party library classes are kept).
  4. The Spring context restarts using the new classloader — typically in under 3 seconds.
  5. If LiveReload is enabled, connected browsers automatically refresh.
IDE Setting: In IntelliJ, enable Build project automatically (Settings → Build, Execution, Deployment → Compiler). In VS Code, the Java extension auto-builds on save by default. Without auto-build, DevTools never sees the updated class files.

6. Testing Pyramid

Spring Boot provides test slice annotations that load only a subset of the application context — far faster than bootstrapping everything. The rule of thumb: use the narrowest slice that exercises your code path.

Annotation Loads Speed Use when
None (plain JUnit 5) Nothing — no Spring context Fastest (< 1s) Pure logic, no Spring dependencies
@WebMvcTest(Ctrl.class) MVC layer only (controllers, filters, security) Fast (< 3s) Controller endpoint tests
@DataJpaTest JPA + in-memory DB (H2 auto-configured) Medium (3–10s) Repository query tests
@SpringBootTest Full application context Slow (5–30s) Integration tests, end-to-end flows

Plain Unit Test — No Spring Context

// No Spring annotation needed — instantiate directly
class PriceCalculatorTest {

    private final PriceCalculator calculator = new PriceCalculator();

    @Test
    void shouldApplyDiscount() {
        assertThat(calculator.withDiscount(100.0, 0.1)).isEqualTo(90.0);
    }
}

@WebMvcTest — MVC Layer Only

// @WebMvcTest loads controllers, filters, Jackson — but NOT service or repository beans
@WebMvcTest(UserController.class)
class UserControllerTest {

    @Autowired
    private MockMvc mockMvc;

    // Replace real service with Mockito mock — it is NOT in the MVC slice
    @MockBean
    private UserService userService;

    @Test
    void shouldReturnUser() throws Exception {
        given(userService.findById(1L)).willReturn(new User(1L, "Alice"));

        mockMvc.perform(get("/users/1"))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.name").value("Alice"));
    }
}

@DataJpaTest — JPA Slice with H2

// @DataJpaTest starts JPA, configures in-memory H2, and rolls back each test
@DataJpaTest
class UserRepositoryTest {

    @Autowired
    private UserRepository userRepository;

    @Test
    void shouldSaveAndFindUser() {
        User saved = userRepository.save(new User("Bob"));
        assertThat(userRepository.findById(saved.getId())).isPresent();
    }
}

@SpringBootTest — Full Context Integration Test

// Boots the complete application context — use sparingly
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class ApplicationIntegrationTest {

    @Autowired
    private TestRestTemplate restTemplate;

    @Test
    void healthEndpointShouldBeUp() {
        ResponseEntity<String> response =
            restTemplate.getForEntity("/actuator/health", String.class);
        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.OK);
    }
}

7. Actuator Endpoints

Spring Boot Actuator exposes operational information about a running application. By default only /actuator/health is exposed over HTTP. Expose additional endpoints via application.yml:

management:
  endpoints:
    web:
      exposure:
        include: health,info,beans,conditions,env,mappings,metrics
  endpoint:
    health:
      show-details: always
Security note: Never expose all actuator endpoints on a public server without authentication. Use Spring Security or a firewall rule to restrict access in production.
Endpoint What it shows Useful for
/actuator/health App + component status (DB, disk, custom indicators) Kubernetes liveness/readiness probes
/actuator/info Custom app info (git commit, build version) Version introspection in CI/CD
/actuator/beans All registered Spring beans, their types and dependencies Debugging unexpected bean wiring
/actuator/conditions Why each auto-configuration class fired or was skipped Debugging starter issues ("why isn't DataSource configured?")
/actuator/env All property sources and their resolved values Debugging config values across profiles
/actuator/mappings All URL routes and their handler methods Documenting or auditing API surface
/actuator/metrics Micrometer metrics — JVM, HTTP, custom timers Performance monitoring, feeding Prometheus/Grafana

Trying it Out

# Health — shows component details
curl http://localhost:8080/actuator/health | python3 -m json.tool

# List all registered beans (large output — pipe through grep)
curl -s http://localhost:8080/actuator/beans | python3 -m json.tool | grep '"bean"'

# See all URL mappings
curl -s http://localhost:8080/actuator/mappings | python3 -m json.tool

# Why did DataSourceAutoConfiguration fire?
curl -s http://localhost:8080/actuator/conditions | python3 -m json.tool | grep -A5 "DataSource"

8. Common Errors and Fixes

The table below covers the most frequent errors encountered when starting with Spring Boot, their root cause, and the fastest fix.

Error Cause Fix
Web server failed to start. Port 8080 was already in use Another process (another Spring app, another server) is already listening on 8080 lsof -i:8080 to find the PID, then kill <pid>; or set server.port=8081 in application.properties
NoSuchBeanDefinitionException: No qualifying bean of type 'X' Class is missing a stereotype annotation (@Component, @Service, @Repository) or is outside the component scan path Add the appropriate stereotype annotation; verify the class package is under the @SpringBootApplication class's package (or add @ComponentScan)
UnsatisfiedDependencyException Circular dependency between beans, or a required bean cannot be created Add @Lazy on one injection point to break the cycle; or restructure beans to eliminate the circular reference
Failed to configure a DataSource Spring Data JPA is on the classpath but no database configuration is present Add H2 to dependencies + set spring.datasource.url=jdbc:h2:mem:testdb in application.properties; or add the H2 starter and Spring Boot will auto-configure it
Context load failed Any bean initialization error — Spring wraps the real cause in generic context-load messages Read the full stack trace to the bottom — the root Caused by: at the end is the actual error. The top-level message is just the symptom
ClassNotFoundException: javax.servlet.Servlet Spring Framework 6 / Spring Boot 3 requires jakarta.* namespaces; code or a library still imports javax.* Replace javax.servlet-api with jakarta.servlet-api; update all import javax.servlet to import jakarta.servlet — this is the javax→jakarta namespace migration
Debugging tip: Always start with ./mvnw spring-boot:run 2>&1 | tee app.log to capture the full output. Then search for Caused by: — the last one before the stack ends is the true root cause.
