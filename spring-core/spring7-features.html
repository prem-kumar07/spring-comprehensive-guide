Spring 7 Features

Spring 7.x — GA: Nov 13, 2025 Java 17+ baseline • Latest: 7.0.3 (Jan 2026) • Jakarta EE 11

Spring Framework 7.0, released on November 13, 2025, is the beginning of a new framework generation serving as the foundation for Spring Boot 4.0. It retains a Java 17 baseline while embracing Java 21/25 idioms, and raises the Jakarta EE level to Jakarta EE 11 (Servlet 6.1, JPA 3.2, Bean Validation 3.1, WebSocket 2.2). The headline themes of the release are standardised null safety via JSpecify, built-in resilience primitives (@Retryable, @ConcurrencyLimit), first-class REST API versioning on both server and client, native OpenTelemetry integration, and deeper GraalVM AOT support.

Java 17 required Spring 7.x requires Java 17 or higher. Spring 6.x also required Java 17, but Spring 7 adds first-class support for Java 21 virtual threads, Java 24 ClassFileMetadataReader, and is tested against Java 25 LTS.

JSpecify Null Safety Annotations [Basic]

Spring Framework 7 replaces its own @Nullable / @NonNull (JSR-305-based) annotations with JSpecify — a vendor-neutral, tooling-supported standard for expressing nullability contracts. The entire Spring Framework codebase has been annotated with JSpecify, which also covers array and vararg elements and generic type arguments. The legacy Spring nullness annotations are deprecated and will be removed in a future release. With JSpecify, IDEs and static analysis tools (SpotBugs, NullAway, Error Prone) can surface null-safety violations at compile time.

Dependency

<!-- Spring 7 pulls in JSpecify transitively; explicit declaration for clarity -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-core</artifactId>
  <version>7.0.3</version>
</dependency>

<!-- JSpecify annotations (transitive, shown for documentation) -->
<dependency>
  <groupId>org.jspecify</groupId>
  <artifactId>jspecify</artifactId>
  <version>1.0.0</version>
</dependency>

Example

import org.jspecify.annotations.NonNull;
import org.jspecify.annotations.Nullable;
import org.jspecify.annotations.NullMarked;

// Mark the whole package/class as null-safe by default (non-null unless stated)
@NullMarked
public class UserService {

    // Return type is @NonNull by virtue of @NullMarked on the class
    public User findById(long id) {
        return userRepository.findById(id)
               .orElseThrow(() -> new EntityNotFoundException("User not found: " + id));
    }

    // Explicitly declare that null is a valid return value
    public @Nullable User findByEmail(String email) {
        return userRepository.findByEmailIgnoreCase(email).orElse(null);
    }

    // Null-safe generic method — generic type argument is non-null by default
    public <T extends User> void save(@NonNull T entity) {
        userRepository.save(entity);
    }
}
Migration note Replace org.springframework.lang.@Nullable / @NonNull with org.jspecify.annotations.@Nullable / @NonNull and add @NullMarked at the package or class level to opt into strict null checking.

ClassFileMetadataReader for Java 24+ [Intermediate]

Spring 7 introduces a new ClassFileMetadataReader implementation in spring-core that uses the Java 24+ Class-File API (java.lang.classfile) to parse bytecode metadata. On Java 24 and above, Spring automatically uses this implementation instead of the legacy ASM-based reader, delivering lower memory overhead during classpath scanning and faster startup when processing large numbers of class files. On Java 17–23, ASM continues to be used transparently.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-core</artifactId>
  <version>7.0.3</version>
</dependency>

Example

// No code change required — Spring selects the reader automatically.
// To verify which reader is active, enable DEBUG logging:

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class App {
    public static void main(String[] args) {
        // On Java 24+, ClassFileMetadataReader is used during component scan.
        // Component scanning is faster with the new reader — no code change needed.
        try (var ctx = new AnnotationConfigApplicationContext("com.example")) {
            ctx.getBean(MyService.class).run();
        }
    }
}

// application.properties — enable debug to confirm active reader strategy
// logging.level.org.springframework.core.type=DEBUG
No action required for most projects The switch to ClassFileMetadataReader on Java 24+ is fully automatic. If you are running on Java 17–23, there is no impact — ASM is still present and used.

spring-jcl Module Removal [Intermediate]

Spring 7 removes the internal spring-jcl bridge module that was introduced in Spring 5 to avoid a hard dependency on Apache Commons Logging. Starting from Spring 7, the framework depends directly on Apache Commons Logging 1.3.0, which ships its own zero-dependency bridge implementation. The change is transparent for most applications — the logging API calls remain the same — but any explicit dependency on spring-jcl in a pom.xml must be removed.

Dependency

<!-- REMOVE this from your pom.xml if present -->
<!-- <dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-jcl</artifactId>
</dependency> -->

<!-- Spring 7 core now brings commons-logging 1.3+ transitively -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>

Example

// Logging code is unchanged — use the same Commons Logging API as before
import org.apache.commons.logging.Log;
import org.apache.commons.logging.LogFactory;

public class OrderService {

    private static final Log log = LogFactory.getLog(OrderService.class);

    public void processOrder(Order order) {
        log.debug("Processing order id=" + order.getId());
        // ... business logic ...
        log.info("Order " + order.getId() + " processed successfully");
    }
}
Migration note Remove any explicit spring-jcl dependency from your POM. Also, annotations from javax.annotation and javax.inject (e.g. @javax.annotation.Resource, @javax.inject.Inject) are no longer supported — switch to their jakarta.* equivalents.

AntPathMatcher Deprecation for HTTP Routing [Advanced]

Spring 7 deprecates the legacy AntPathMatcher variant used for matching HTTP request mappings in Spring MVC and WebFlux. Applications should migrate to PathPatternParser, which was introduced in Spring 5 and has been the default since Spring 5.3. PathPatternParser is faster (pre-parsed patterns), safer (avoids certain ambiguities), and aligns with the reactive routing model. The AntPathMatcher class itself is not removed — it remains available for non-HTTP pattern matching (e.g. classpath scanning).

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-webmvc</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import org.springframework.web.util.pattern.PathPatternParser;
import org.springframework.web.util.pattern.PathPattern;

// Using PathPatternParser directly (preferred in Spring 7)
PathPatternParser parser = PathPatternParser.defaultInstance;
PathPattern pattern = parser.parse("/api/v{version}/users/{id}");

// Check if a path matches
boolean matches = pattern.matches(
    PathContainer.parsePath("/api/v2/users/42")
);

// In Spring MVC config — PathPatternParser is already the default,
// but this shows explicit configuration
@Configuration
@EnableWebMvc
public class MvcConfig implements WebMvcConfigurer {

    @Override
    public void configurePathMatch(PathMatchConfigurer configurer) {
        // Ensure PathPatternParser is active (it is the default in Spring 5.3+)
        configurer.setPatternParser(PathPatternParser.defaultInstance);
        // Do NOT set AntPathMatcher — it is deprecated for HTTP routing in Spring 7
    }
}
Migration note If your WebMvcConfigurer explicitly calls configurer.setPathMatcher(new AntPathMatcher()), remove that call. The default PathPatternParser handles all standard Ant-style patterns and is a drop-in replacement for most use cases.

REST API Versioning — Server Side [Basic]

Spring MVC and WebFlux 7 introduce first-class server-side REST API versioning. You can now map controller methods to specific API versions using @RequestMapping attributes, and configure how the version is resolved (path segment, query parameter, or request header). Spring parses and validates the version value automatically, and returns a 406 Not Acceptable when a requested version is unsupported.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-webmvc</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import org.springframework.web.bind.annotation.*;
import org.springframework.web.servlet.config.annotation.*;

// Configure the version resolver — here: read version from request header
@Configuration
@EnableWebMvc
public class ApiVersionConfig implements WebMvcConfigurer {

    @Override
    public void configureApiVersioning(ApiVersionConfigurer configurer) {
        configurer
            .useRequestHeader("X-API-Version")   // or .usePathPrefix("/v{version}")
            .defaultVersion("1");                 // fallback when header absent
    }
}

// Controller — map each method to its supported version(s)
@RestController
@RequestMapping("/api/users")
public class UserController {

    // Serves requests where X-API-Version: 1 (or no header — uses default)
    @GetMapping(version = "1")
    public UserV1 getUserV1(@PathVariable long id) {
        return userV1Service.get(id);
    }

    // Serves requests where X-API-Version: 2
    @GetMapping(version = "2")
    public UserV2 getUserV2(@PathVariable long id) {
        return userV2Service.get(id);
    }
}
Version formats supported Spring 7 parses semantic versions (2.1, 2.1.3) and simple integers (2). You can supply a custom ApiVersionParser for proprietary schemes.

REST API Versioning — Client Side (RestClient / WebClient) [Intermediate]

The client-side counterpart allows you to set the API version on outgoing requests via RestClient, WebClient, and declarative HTTP Interface clients. The version is applied according to the same strategy configured on the server (header, path prefix, or query parameter), making client–server versioning symmetric. HTTP Interface proxy clients can declare the API version on the interface or individual method.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-web</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import org.springframework.web.client.RestClient;
import org.springframework.web.service.annotation.*;

// ── RestClient with version ───────────────────────────
RestClient client = RestClient.builder()
    .baseUrl("https://api.example.com")
    .apiVersion("2")                       // sets X-API-Version: 2 on every request
    .build();

UserV2 user = client.get()
    .uri("/api/users/{id}", 42)
    .retrieve()
    .body(UserV2.class);

// ── HTTP Interface client with per-method version ─────
@HttpExchange("/api/users")
public interface UserClient {

    @GetExchange(version = "1")
    UserV1 getUserV1(@PathVariable long id);

    @GetExchange(version = "2")
    UserV2 getUserV2(@PathVariable long id);
}

// Register and use the proxy
UserClient userClient = HttpServiceProxyFactory
    .builderFor(RestClientAdapter.create(client))
    .build()
    .createClient(UserClient.class);

UserV2 result = userClient.getUserV2(42);
Migration note If you currently encode version info manually in request URLs or headers, replace that boilerplate with the new RestClient.builder().apiVersion(...) API for cleaner, centralised version management.

Jackson 3 Support [Intermediate]

Spring Framework 7 adds first-class support for Jackson 3.x, whose biggest breaking change is the package relocation from com.fasterxml.jackson to tools.jackson. Spring 7 auto-detects which Jackson version is on the classpath and configures the correct MappingJackson2HttpMessageConverter or the new MappingJackson3HttpMessageConverter accordingly. Jackson 2.x support is retained but deprecated — Spring Boot 4 ships with Jackson 3 as default, while standalone Spring 7 continues to support both.

Dependency

<!-- Jackson 3.x (new package: tools.jackson) -->
<dependency>
  <groupId>tools.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
  <version>3.0.0</version>
</dependency>

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-web</artifactId>
  <version>7.0.3</version>
</dependency>

Example

// Jackson 3 uses tools.jackson instead of com.fasterxml.jackson
import tools.jackson.databind.JsonMapper;
import tools.jackson.databind.json.JsonMapper;

// JsonMapper replaces ObjectMapper as the preferred entry point in Jackson 3
JsonMapper mapper = JsonMapper.builder()
    .findAndAddModules()                 // auto-register modules (JavaTimeModule, etc.)
    .build();

// Serialize
String json = mapper.writeValueAsString(new User("Alice", "alice@example.com"));

// Deserialize
User user = mapper.readValue(json, User.class);

// In Spring MVC config — explicit registration for Jackson 3 (auto-configured in Boot 4)
@Configuration
public class JacksonConfig {

    @Bean
    public JsonMapper jsonMapper() {
        return JsonMapper.builder()
            .findAndAddModules()
            .build();
    }
}
Migration note Jackson 3 relocates all packages from com.fasterxml.jackson.* to tools.jackson.* and uses JsonMapper (immutable, builder-based) in place of ObjectMapper. Jackson 3 is designed to coexist with Jackson 2 on the classpath to allow a gradual migration.

HTTP Interface Clients with Automatic OTel Trace Propagation [Advanced]

Declarative @HttpExchange interface clients in Spring 7 automatically propagate OpenTelemetry trace context (W3C TraceContext headers: traceparent / tracestate) to downstream services without any manual instrumentation. The integration is driven by Spring's native OTel support — when an OpenTelemetry bean is present in the context, the HttpServiceProxyFactory installs an interceptor that injects the current span context into every outgoing request header.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-web</artifactId>
  <version>7.0.3</version>
</dependency>
<dependency>
  <groupId>io.opentelemetry</groupId>
  <artifactId>opentelemetry-api</artifactId>
  <version>1.36.0</version>
</dependency>

Example

import org.springframework.web.service.annotation.*;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.support.RestClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

// Declare the HTTP interface — OTel propagation is automatic
@HttpExchange("https://inventory.internal")
public interface InventoryClient {

    @GetExchange("/items/{sku}")
    InventoryItem getItem(@PathVariable String sku);

    @PostExchange("/items/{sku}/reserve")
    ReservationResult reserve(@PathVariable String sku, @RequestBody ReserveRequest req);
}

// Configuration — OTel SDK bean triggers automatic trace propagation
@Configuration
public class ClientConfig {

    @Bean
    public InventoryClient inventoryClient(RestClient.Builder builder) {
        RestClient restClient = builder
            .baseUrl("https://inventory.internal")
            .build();
        return HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(restClient))
            .build()
            .createClient(InventoryClient.class);
    }
}

// Usage — trace context is injected automatically into outgoing headers
@Service
public class OrderService {
    private final InventoryClient inventory;

    public Order placeOrder(String sku, int qty) {
        InventoryItem item = inventory.getItem(sku); // traceparent header injected
        ReservationResult res = inventory.reserve(sku, new ReserveRequest(qty));
        return buildOrder(item, res);
    }
}
Zero manual instrumentation As long as an OpenTelemetry or ObservationRegistry bean is present (auto-configured by Spring Boot 4), @HttpExchange clients propagate traces automatically — no custom interceptors or filters needed.

@EnableResilientMethods and @Retryable [Basic]

Spring Framework 7 ships built-in resilience primitives in spring-context — no external library like spring-retry or Resilience4j needed. The @Retryable annotation declares retry behaviour on a method or class, and @EnableResilientMethods on a @Configuration class activates the AOP proxy that intercepts annotated methods. @Retryable automatically adapts to reactive return types, decorating the Reactor pipeline with Reactor's retry capabilities.

Dependency

<!-- No additional dependency — built into spring-context -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableResilientMethods;
import org.springframework.retry.annotation.Retryable;
import org.springframework.stereotype.Service;
import java.io.IOException;

// 1. Activate resilience AOP
@Configuration
@EnableResilientMethods
public class AppConfig {}

// 2. Annotate the method to retry
@Service
public class ExternalApiClient {

    // Retry up to 3 times on IOException, with 500 ms delay between attempts
    @Retryable(
        retryFor = IOException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 500, multiplier = 2.0)
    )
    public WeatherData fetchWeather(String city) throws IOException {
        return httpClient.get("https://weather.api/v1/current?city=" + city,
                              WeatherData.class);
    }

    // Works with reactive types too — decorates the Mono pipeline
    @Retryable(maxAttempts = 4, backoff = @Backoff(delay = 200))
    public Mono<WeatherData> fetchWeatherReactive(String city) {
        return webClient.get()
            .uri("/v1/current?city=" + city)
            .retrieve()
            .bodyToMono(WeatherData.class);
    }
}
Migration note If you use spring-retry, Moderne provides an OpenRewrite recipe (MigrateSpringRetryToSpringFramework7) to automate the migration to the new built-in annotations. Remove the spring-retry and @EnableRetry dependency after migrating.

@ConcurrencyLimit — Declarative Concurrency Control [Intermediate]

@ConcurrencyLimit is a new declarative annotation for constraining the number of concurrent invocations of a Spring-managed method. It is particularly valuable when using virtual threads (Project Loom): since virtual threads are cheap to create, a downstream resource (database, external API) can be overwhelmed without a concurrency guard. @ConcurrencyLimit enforces a semaphore at the proxy level with no need for external libraries.

Dependency

<!-- Built into spring-context; also enable with @EnableResilientMethods -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableResilientMethods;
import org.springframework.resilience.annotation.ConcurrencyLimit;
import org.springframework.stereotype.Service;

@Configuration
@EnableResilientMethods   // activates both @Retryable and @ConcurrencyLimit
public class ResilienceConfig {}

@Service
public class ReportGenerationService {

    // At most 5 concurrent calls — excess callers block (or throw if configured)
    @ConcurrencyLimit(5)
    public Report generateReport(ReportRequest request) {
        // heavy computation or I/O — guarded to 5 concurrent executions
        return reportBuilder.build(request);
    }

    // Combine with @Retryable for resilient + rate-limited calls
    @ConcurrencyLimit(10)
    @Retryable(maxAttempts = 2, backoff = @Backoff(delay = 300))
    public ExternalData callExternalApi(String params) {
        return externalClient.fetch(params);
    }
}
Virtual thread use case When the Spring Boot 4 virtual-thread executor is active, all request-handling runs on virtual threads. Without a concurrency guard, a burst of requests could issue thousands of simultaneous DB queries. @ConcurrencyLimit is the recommended first line of defence.

RetryTemplate — Programmatic Retry [Advanced]

Beyond declarative annotations, Spring 7's built-in resilience module provides a RetryTemplate for programmatic retry control. It supports pluggable RetryPolicy and BackOffPolicy implementations and integrates with Spring's ApplicationEventPublisher to emit retry events that Micrometer can capture as metrics. This is the preferred approach when you need fine-grained control — for example, different policies per exception type, or access to the retry context inside the retry callback.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import org.springframework.retry.RetryTemplate;
import org.springframework.retry.policy.SimpleRetryPolicy;
import org.springframework.retry.backoff.ExponentialBackOffPolicy;

// Build a RetryTemplate with exponential back-off
RetryTemplate retryTemplate = RetryTemplate.builder()
    .maxAttempts(5)
    .exponentialBackoff(100, 2.0, 5000)     // initial=100ms, multiplier=2, max=5s
    .retryOn(IOException.class)
    .retryOn(ServiceUnavailableException.class)
    .build();

// Execute with retry context access
String result = retryTemplate.execute(context -> {
    int attempt = context.getRetryCount() + 1;
    log.debug("Attempt {} of {}", attempt, 5);
    return externalService.call();
}, context -> {
    // Recovery callback — called when all retries exhausted
    log.error("All retries exhausted after {} attempts", context.getRetryCount());
    return "fallback-value";
});

// Register as a bean for injection
@Bean
public RetryTemplate paymentRetryTemplate() {
    return RetryTemplate.builder()
        .maxAttempts(3)
        .fixedBackoff(250)
        .retryOn(PaymentGatewayException.class)
        .build();
}
Observability Combine RetryTemplate with a Micrometer MeterRegistry listener to record retry attempt counts and failure rates as metrics, which surface automatically in Spring Boot 4 Actuator dashboards.

Native OpenTelemetry Integration [Basic]

Spring Framework 7 introduces direct OpenTelemetry support without requiring a Micrometer bridge. When an io.opentelemetry.api.OpenTelemetry bean is registered in the application context, Spring automatically instruments request handling (servlet/reactive), scheduled tasks, and HTTP interface client calls. Traces are exported via OTLP in the W3C TraceContext format. This replaces the need for third-party Java agents for many common instrumentation needs.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>
<dependency>
  <groupId>io.opentelemetry</groupId>
  <artifactId>opentelemetry-sdk</artifactId>
  <version>1.36.0</version>
</dependency>
<dependency>
  <groupId>io.opentelemetry</groupId>
  <artifactId>opentelemetry-exporter-otlp</artifactId>
  <version>1.36.0</version>
</dependency>

Example

import io.opentelemetry.api.OpenTelemetry;
import io.opentelemetry.sdk.OpenTelemetrySdk;
import io.opentelemetry.sdk.trace.SdkTracerProvider;
import io.opentelemetry.exporter.otlp.trace.OtlpGrpcSpanExporter;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class OtelConfig {

    // Register OpenTelemetry bean — Spring 7 detects and uses it automatically
    @Bean
    public OpenTelemetry openTelemetry() {
        OtlpGrpcSpanExporter exporter = OtlpGrpcSpanExporter.builder()
            .setEndpoint("http://otel-collector:4317")
            .build();

        SdkTracerProvider tracerProvider = SdkTracerProvider.builder()
            .addSpanProcessor(BatchSpanProcessor.builder(exporter).build())
            .build();

        return OpenTelemetrySdk.builder()
            .setTracerProvider(tracerProvider)
            .build();
    }
}
// All incoming HTTP requests and @HttpExchange calls are now auto-instrumented.
Spring Boot 4 auto-configuration In Spring Boot 4, the OpenTelemetry bean is auto-configured when the OTel SDK is on the classpath. You just add the exporter dependency and set management.otlp.tracing.endpoint in application.properties.

Micrometer Observability Improvements [Intermediate]

Spring 7 builds on the Micrometer Observation API introduced in Spring 6.0 with additional integration points. @Observed can now be applied at the class level to instrument all public methods, and Spring 7 adds observation support for the new built-in resilience annotations: @Retryable retry attempts and @ConcurrencyLimit rejections are automatically recorded as Micrometer metrics. The ObservationRegistry is injected wherever Spring 7 creates observability-capable components.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-aop</artifactId>
  <version>7.0.3</version>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-observation</artifactId>
  <version>1.13.0</version>
</dependency>

Example

import io.micrometer.observation.annotation.Observed;
import org.springframework.stereotype.Service;

// Class-level @Observed — instruments every public method automatically
@Observed(name = "payment.service", contextualName = "PaymentService")
@Service
public class PaymentService {

    // Each method call creates a span named "payment.service#processPayment"
    public PaymentResult processPayment(PaymentRequest request) {
        // ... payment logic ...
        return PaymentResult.success(request.amount());
    }

    public RefundResult issueRefund(String transactionId) {
        // ... refund logic ... (also auto-instrumented)
        return RefundResult.ok();
    }
}

// Programmatic observation with custom tags
@Service
public class InventoryService {

    private final ObservationRegistry registry;

    public int checkStock(String sku) {
        return Observation.createNotStarted("inventory.stock-check", registry)
            .lowCardinalityKeyValue("sku.category", resolveCategory(sku))
            .observe(() -> stockRepository.findBySku(sku).getQuantity());
    }
}
Tip: Dual signals from one annotation With a Micrometer-OTel bridge on the classpath, a single @Observed annotation emits both metrics (Prometheus counters/timers) and distributed traces (OTel spans) simultaneously.

Structured Concurrency and Observation Scope [Advanced]

Spring 7 integrates Observation scope propagation with Java 21+ Structured Concurrency (preview feature in Java 21, standard in later releases). When a parent observation is active, child tasks forked within a StructuredTaskScope automatically inherit the trace context, ensuring that spans from concurrent sub-tasks are correctly parented under the initiating span. This makes distributed traces accurate even when request handling fans out to multiple virtual-thread sub-tasks.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import java.util.concurrent.StructuredTaskScope;
import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;

@Service
public class DashboardService {

    private final UserClient userClient;
    private final OrderClient orderClient;
    private final ObservationRegistry registry;

    // Fan-out with structured concurrency — child spans parented correctly
    public DashboardData loadDashboard(long userId) throws Exception {
        return Observation.createNotStarted("dashboard.load", registry)
            .observe(() -> {
                try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
                    // Both sub-tasks inherit the active observation/trace context
                    var userFuture  = scope.fork(() -> userClient.getUser(userId));
                    var orderFuture = scope.fork(() -> orderClient.getRecent(userId, 10));
                    scope.join().throwIfFailed();
                    return new DashboardData(userFuture.get(), orderFuture.get());
                }
            });
    }
}
Java version requirement Structured Concurrency requires Java 21+ (preview) or Java 25+ (standard). Ensure your project compiles with --enable-preview on Java 21. Spring Boot 4's virtual thread executor is fully compatible with this pattern.

Enhanced GraalVM Native Image Support [Basic]

Spring 7 deepens its GraalVM native image support, building on the AOT engine introduced in Spring 6. The Spring AOT processor now generates more complete reflect-config.json and resource-config.json files for common Spring patterns (including the new resilience annotations and JSpecify metadata), reducing the number of custom hints that application code must provide. Compilation to native executables is faster and the resulting binary is smaller due to more aggressive dead-code elimination.

Dependency

<!-- In pom.xml — use spring-boot-maven-plugin for native compilation -->
<plugin>
  <groupId>org.graalvm.buildtools</groupId>
  <artifactId>native-maven-plugin</artifactId>
  <version>0.10.3</version>
  <extensions>true</extensions>
</plugin>

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>

Example

// Compile to native with Maven
// mvn -Pnative native:compile

// Resulting binary runs without JVM:
// ./target/my-app --spring.profiles.active=prod

// Spring 7 AOT processes this automatically — no manual hints needed
// for common patterns:
@SpringBootApplication
public class MyApp {
    public static void main(String[] args) {
        SpringApplication.run(MyApp.class, args);
    }
}

// For custom reflection needs, use @ImportRuntimeHints
@Configuration
@ImportRuntimeHints(MyRuntimeHints.class)
public class AppConfig { }

class MyRuntimeHints implements RuntimeHintsRegistrar {
    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.reflection()
            .registerType(DynamicPayload.class,
                MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                MemberCategory.INVOKE_PUBLIC_METHODS);
    }
}
Build time vs. runtime GraalVM native images perform all class loading, reflection resolution, and proxy generation at build time. The AOT processor in Spring 7 handles this for Spring-managed beans automatically; only truly dynamic reflection needs manual RuntimeHintsRegistrar entries.

AOT Processing Improvements [Intermediate]

Spring 7's AOT processor introduces a richer hint inference model, reducing the gap between JVM and native execution modes. The processor can now infer reflection requirements from JSpecify annotations, from the new @Retryable / @ConcurrencyLimit AOP proxies, and from Jackson 3 module registrations. AOT-processed beans are serialised to BeanDefinitionCode classes that the native image loads statically, removing the need for runtime BeanFactory introspection in most scenarios.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>

Example

// Enable AOT-compatible conditional configuration
// @ConditionalOnClass and @ConditionalOnMissingBean are evaluated at build time
// when compiling to native

@Configuration
@ConditionalOnClass(JsonMapper.class)  // resolved at AOT compile time for native
public class Jackson3Config {

    @Bean
    public JsonMapper jsonMapper() {
        return JsonMapper.builder()
            .findAndAddModules()
            .build();
    }
}

// Test native compatibility in the JVM with Spring AOT test mode
// application-test.properties:
// spring.aot.enabled=true

@SpringBootTest
@ActiveProfiles("test")
class MyServiceAotTest {
    @Autowired MyService service;

    @Test

RuntimeHints API — Advanced Registration Patterns [Advanced]

Spring 7 extends the RuntimeHints API with new registration categories for serialization proxies, resource patterns (supporting glob patterns), and JDK dynamic proxies generated for HTTP Interface clients. The @ImportRuntimeHints annotation is now inheritable, so library authors can annotate a @Configuration class once and have all their AOT requirements covered transitively for all consumers.

Dependency

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-core</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import org.springframework.aot.hint.*;
import org.springframework.context.annotation.ImportRuntimeHints;

// Library configuration — hints are inherited by all consumers
@Configuration
@ImportRuntimeHints(CsvLibraryHints.class)
public class CsvLibraryConfig { }

// RuntimeHintsRegistrar — covers reflection, proxies, resources, and serialization
class CsvLibraryHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader loader) {

        // 1. Reflection — dynamic DTO classes
        hints.reflection()
            .registerType(CsvRow.class, MemberCategory.values())
            .registerType(CsvParser.class, MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS);

        // 2. Resource patterns — glob support (new in Spring 7)
        hints.resources()
            .registerPattern("csv-schemas/*.json")
            .registerPattern("META-INF/csv-*.properties");

        // 3. JDK proxy — HTTP Interface client interface
        hints.proxies()
            .registerJdkProxy(CsvDownloadClient.class);

        // 4. Serialization
        hints.serialization()
            .registerType(CsvRow.class);
    }
}
Library authors Place @ImportRuntimeHints on your library's auto-configuration class. Spring Boot 4's AOT processor picks it up transitively, meaning application developers who use your library get native image support for free.

Jakarta Persistence 3.2 [Intermediate]

Spring 7's data access support targets Jakarta Persistence 3.2 (JPA 3.2), which adds Query.getSingleResultOrNull(), expanded @Column options (e.g. check constraint expressions), improved numeric type support (UUID as a first-class mapped type), and a richer Criteria API. Spring Data JPA 3.x is the companion library that wraps JPA 3.2 with repositories and query derivation, and requires Hibernate 6.4+ or EclipseLink 4.0+ as the JPA provider.

Dependency

<dependency>
  <groupId>jakarta.persistence</groupId>
  <artifactId>jakarta.persistence-api</artifactId>
  <version>3.2.0</version>
</dependency>
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-orm</artifactId>
  <version>7.0.3</version>
</dependency>
<!-- JPA 3.2 provider -->
<dependency>
  <groupId>org.hibernate.orm</groupId>
  <artifactId>hibernate-core</artifactId>
  <version>6.6.0.Final</version>
</dependency>

Example

import jakarta.persistence.*;
import java.util.UUID;

@Entity
@Table(name = "products")
public class Product {

    // UUID as first-class JPA 3.2 mapped type — no custom converter needed
    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @Column(nullable = false, length = 200)
    private String name;

    // JPA 3.2 @Column(check) — generates a CHECK constraint in the DDL
    @Column(nullable = false,
            check = @CheckConstraint(constraint = "price > 0"))
    private java.math.BigDecimal price;

    // Getters/setters omitted for brevity
}

// JPA 3.2: Query.getSingleResultOrNull() — cleaner than try/catch NoResultException
@Repository
public class ProductRepository {

    @PersistenceContext
    private EntityManager em;

    public Optional<Product> findByName(String name) {
        Product result = em.createQuery(
                "SELECT p FROM Product p WHERE p.name = :name", Product.class)
            .setParameter("name", name)
            .getSingleResultOrNull();   // returns null instead of throwing
        return Optional.ofNullable(result);
    }
}
Spring Data JPA Use Spring Data JPA 3.x (part of the Spring Data 2025.x release train) for repository-based data access on top of JPA 3.2. It requires no code changes for basic CRUD repositories, but enables new query methods targeting JPA 3.2 features.

Enhanced Virtual Thread Support [Advanced]

Spring 7 deepens its Project Loom virtual thread support beyond the initial integration in Spring 6.1. The scheduler integration for @Scheduled tasks now uses virtual threads by default when running on Java 21+. The new @ConcurrencyLimit annotation is specifically designed to guard virtual-thread-backed methods against resource saturation. Spring 7 also integrates virtual thread metrics into Micrometer, exposing active virtual thread counts and scheduler queue depths through Actuator.

Dependency

<!-- Requires Java 21+; no additional Maven dep — built into the JDK and spring-context -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.3</version>
</dependency>

Example

import org.springframework.context.annotation.*;
import org.springframework.scheduling.concurrent.SimpleAsyncTaskExecutor;
import org.springframework.scheduling.annotation.EnableScheduling;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

// Configure virtual-thread executor for @Async and general task execution
@Configuration
@EnableScheduling
public class VirtualThreadConfig {

    @Bean(name = "applicationTaskExecutor")
    public SimpleAsyncTaskExecutor virtualThreadExecutor() {
        var executor = new SimpleAsyncTaskExecutor("vt-");
        executor.setVirtualThreads(true);   // Java 21+ virtual threads
        return executor;
    }
}

// @Scheduled tasks also run on virtual threads in Spring 7
@Component
public class ReportScheduler {

    @Scheduled(fixedRate = 60_000)  // runs every 60 s on a virtual thread
    public void generateDailyReport() {
        // Blocking I/O here is fine — virtual thread parks, not blocks platform thread
        reportService.generate();
    }
}

// Manual virtual thread creation (Java 21 API) with Spring beans
@Service
public class BatchProcessor {

    public void processBatch(List<Item> items) throws Exception {
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            for (Item item : items) {
                scope.fork(() -> processItem(item));  // each task on a virtual thread
            }
            scope.join().throwIfFailed();
        }
    }
}
Pinning pitfall Virtual threads pin to platform threads when blocking inside a synchronized block or native method. Prefer ReentrantLock in code that may block, and use @ConcurrencyLimit instead of synchronized for Spring-managed concurrency control.
