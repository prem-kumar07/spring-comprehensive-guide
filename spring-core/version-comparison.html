HTTP Client (RestTemplate → WebClient / @HttpExchange)

 RestTemplate RestClient / @HttpExchange No change from Spring 6 Changed
Spring 5 — RestTemplate
// Spring 5 — RestTemplate
@Service
public class UserService {

    private final RestTemplate restTemplate;

    public UserService(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    public User getUser(Long id) {
        return restTemplate.getForObject(
            "https://api.example.com/users/{id}",
            User.class, id);
    }

    public void createUser(User user) {
        restTemplate.postForEntity(
            "https://api.example.com/users",
            user, User.class);
    }
}
Spring 6 — RestClient
// Spring 6 — RestClient (fluent builder API)
@Service
public class UserService {

    private final RestClient restClient;

    public UserService(RestClient.Builder builder) {
        this.restClient = builder
            .baseUrl("https://api.example.com")
            .build();
    }

    public User getUser(Long id) {
        return restClient.get()
            .uri("/users/{id}", id)
            .retrieve()
            .body(User.class);
    }

    public void createUser(User user) {
        restClient.post()
            .uri("/users")
            .body(user)
            .retrieve()
            .toBodilessEntity();
    }
}

Error Response Format (custom → ProblemDetail RFC 7807)

 Custom @ExceptionHandler ProblemDetail (RFC 7807) No change from Spring 6 New
Spring 5 — Custom error body
// Spring 5 — manual error response
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(NotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public Map<String, Object> handleNotFound(
            NotFoundException ex) {
        Map<String, Object> body = new HashMap<>();
        body.put("error", "Not Found");
        body.put("message", ex.getMessage());
        body.put("status", 404);
        return body;
    }
}
Spring 6 — ProblemDetail (RFC 7807)
// Spring 6 — ProblemDetail built-in
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(NotFoundException.class)
    public ProblemDetail handleNotFound(
            NotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Resource Not Found");
        pd.setType(URI.create("/errors/not-found"));
        return pd;
        // Produces: {"type":..., "title":...,
        //   "status":404, "detail":...}
    }
}

Observability (manual Micrometer → @Observed → resilience annotations)

 Micrometer (optional add-on) Micrometer core + @Observed Adds @ConcurrencyLimit annotation; enable via @EnableResilientMethods Changed
Spring 5 — manual Micrometer
// Spring 5 — optional Micrometer dependency
// Must add micrometer-core explicitly
@Service
public class OrderService {

    private final MeterRegistry meterRegistry;

    public Order placeOrder(OrderRequest req) {
        Timer.Sample sample =
            Timer.start(meterRegistry);
        try {
            Order order = processOrder(req);
            sample.stop(meterRegistry.timer(
                "order.placed"));
            return order;
        } catch (Exception e) {
            meterRegistry.counter(
                "order.errors").increment();
            throw e;
        }
    }
}
Spring 6 — @Observed
// Spring 6 — Micrometer core built-in
// @Observed AOP aspect creates spans + metrics
@Service
@Observed(name = "order.service")
public class OrderService {

    // All methods automatically observed —
    // creates both metrics and traces
    @Observed(name = "order.placed",
              contextualName = "placing-order")
    public Order placeOrder(OrderRequest req) {
        return processOrder(req);
    }
    // No boilerplate — framework handles
    // Timer, Counter, and Span lifecycle
}

Spring 6 → 7

Spring 6 — @Observed only
// Spring 6 — observability only
@Service
@Observed(name = "order.service")
public class OrderService {
    // No built-in concurrency throttling
    // For rate limiting, used external libs
    public Order placeOrder(OrderRequest req) {
        return processOrder(req);
    }
}
Spring 7 — @ConcurrencyLimit added
// Spring 7 — resilience annotations built-in
// Enable with @EnableResilientMethods
@Configuration
@EnableResilientMethods
public class AppConfig {}

@Service
public class OrderService {

    // Limit to max 10 concurrent executions
    @ConcurrencyLimit(10)
    @Observed(name = "order.placed")
    public Order placeOrder(OrderRequest req) {
        return processOrder(req);
    }
    // @ConcurrencyLimit is in
    // org.springframework.context.annotation
}

Native Image & Startup (experimental → Spring AOT → CRaC)

 No first-class support Spring AOT + GraalVM CRaC (Coordinated Restore at Checkpoint) support added alongside GraalVM AOT for JVM-fast restore New
Spring 5 — no native support
# Spring 5 — only JVM deployment
# GraalVM with Spring Boot was experimental
# Required heavy manual configuration:
# native-image.properties, reflection-config.json,
# proxy-config.json, resource-config.json

mvn spring-boot:run   # JVM only
Spring 6 — AOT + GraalVM
# Spring 6 — first-class native support
# Spring AOT processes beans at build time,
# generating optimised source for GraalVM

# Build native executable via Spring Boot plugin:
mvn -Pnative native:compile

# Result: fast startup (<100ms), low memory
# AOT hints auto-generated for most use cases
# Custom hints via @ImportRuntimeHints

Spring 6 → 7

Spring 6 — GraalVM native only
// Spring 6 — fast startup via GraalVM native
// Requires compile-time native build
// No JVM warm-up path for instant restore

// application.properties:
// (no CRaC options in Spring 6)
Spring 7 — CRaC checkpoint/restore added
// Spring 7 — CRaC support for JVM fast startup
// Works on Liberica JDK or Azul Zulu with CRaC

// 1. Take a checkpoint (warm JVM snapshot):
//    java -XX:CRaCCheckpointTo=/opt/checkpoint \
//         -jar app.jar
//    After warmup: jcmd <pid> JDK.checkpoint

// 2. Restore instantly from checkpoint:
//    java -XX:CRaCRestoreFrom=/opt/checkpoint

// Spring stops/restarts Lifecycle beans
// automatically around the checkpoint.
// Result: <100ms restore on standard JVM —
// no native compilation needed!

Config Class Proxy (CGLIB → proxyBeanMethods=false)

 proxyBeanMethods=true default proxyBeanMethods=false (lite) available No change from Spring 6 Changed
Spring 5 — CGLIB proxy (default)
// Spring 5 — @Configuration uses CGLIB proxy
// so inter-bean @Bean method calls return
// the same singleton from the container
@Configuration
// proxyBeanMethods=true is the default
public class AppConfig {

    @Bean
    public DataSource dataSource() {
        return new HikariDataSource();
    }

    @Bean
    public JdbcTemplate jdbcTemplate() {
        // Safe: calls through CGLIB proxy —
        // returns the singleton DataSource bean
        return new JdbcTemplate(dataSource());
    }
}
Spring 6 — lite mode (no proxy)
// Spring 6 — proxyBeanMethods=false (lite)
// No CGLIB subclass; direct method calls
// create new instances — avoid inter-bean calls
@Configuration(proxyBeanMethods = false)
public class AppConfig {

    @Bean
    public DataSource dataSource() {
        return new HikariDataSource();
    }

    @Bean
    public JdbcTemplate jdbcTemplate(
            DataSource dataSource) {
        // Use parameter injection instead —
        // Spring injects the singleton safely
        return new JdbcTemplate(dataSource);
    }
    // Benefit: AOT-friendly, no CGLIB overhead
}

// Spring 6 — declare as annotated interface
@HttpExchange("https://api.github.com")
public interface GitHubClient {

    @GetExchange("/repos/{owner}/{repo}")
    Repo getRepo(
        @PathVariable String owner,
        @PathVariable String repo);

        @PathVariable String owner,
        @PathVariable String repo,
        @RequestBody NewIssue issue);
}

Virtual Threads (Spring 6 + Java 21 Project Loom)

 Not supported Project Loom integration Improved virtual thread scheduler; default-enabled in Spring Boot 4 (spring.threads.virtual.enabled defaults to true) New
Spring 5 — platform threads only
// Spring 5 — traditional thread pool
// Each request consumes a platform thread
// High memory overhead for I/O-bound work

@Bean
public TaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor exec =
        new ThreadPoolTaskExecutor();
    exec.setCorePoolSize(10);
    exec.setMaxPoolSize(100);
    // Limited by OS thread count (~thousands)
    return exec;
}
Spring 6 — Virtual Threads (Loom)
// Spring 6 (Java 21+) — virtual threads
// Requires spring.threads.virtual.enabled=true
// in application.properties

// application.properties:
// spring.threads.virtual.enabled=true

// Or configure directly:
@Bean
public TomcatProtocolHandlerCustomizer<?>
        virtualThreadCustomizer() {
    return handler -> handler.setExecutor(
        Executors.newVirtualThreadPerTaskExecutor()
    );
    // Millions of virtual threads possible —
    // ideal for blocking I/O (DB, HTTP calls)
}

Spring 6 → 7

Spring 6 — opt-in virtual threads
# Spring 6 — must explicitly enable
# application.properties:
spring.threads.virtual.enabled=true

# Tomcat uses virtual thread per request
# when this property is set
Spring 7 / Boot 4 — default-enabled
# Spring Boot 4 — virtual threads ON by default
# No configuration required for most apps.
# To disable if needed:
spring.threads.virtual.enabled=false

# Also: improved scheduler pinning detection;
# structured concurrency preview support;
# @Async methods automatically use virtual
# threads when executor is VirtualThreadTaskExecutor

Constructor Injection (implicit in Spring 6 single-constructor)

 All styles equal Recommended as primary style No change from Spring 6 Changed
Spring 5 — field injection common
// Spring 5 — all injection styles used equally
@Service
public class UserService {

    // Field injection — common in Spring 5 code
    @Autowired
    private UserRepository userRepo;

    @Autowired
    private EmailService emailService;

    // Works, but harder to test, hides deps,
    // and fails with final fields
    public void register(User user) {
        userRepo.save(user);
        emailService.sendWelcome(user);
    }
}
Spring 6 — constructor injection recommended
// Spring 6 — constructor injection is idiomatic
// Lombok @RequiredArgsConstructor or explicit
@Service
public class UserService {

    private final UserRepository userRepo;
    private final EmailService emailService;

    // Spring 6 docs + AOT tooling favour this:
    // - Immutable fields (final)
    // - Explicit dependencies
    // - Testable without Spring context
    public UserService(UserRepository userRepo,
                       EmailService emailService) {
        this.userRepo = userRepo;
        this.emailService = emailService;
    }

    public void register(User user) {
        userRepo.save(user);
        emailService.sendWelcome(user);
    }
}

RestTemplate (deprecated → prefer RestClient / WebClient)

 Primary HTTP client Deprecated — use RestClient Still deprecated; maintained for backward compatibility but no new features Deprecated
Spring 5 — RestTemplate (primary)
// Spring 5 — RestTemplate is the standard
@Bean
public RestTemplate restTemplate(
        RestTemplateBuilder builder) {
    return builder
        .rootUri("https://api.example.com")
        .connectTimeout(Duration.ofSeconds(5))
        .readTimeout(Duration.ofSeconds(10))
        .build();
}

// Usage
User user = restTemplate.getForObject(
    "/users/{id}", User.class, 42L);
ResponseEntity<User> resp =
    restTemplate.postForEntity(
        "/users", newUser, User.class);
Spring 6 — RestClient (replacement)
// Spring 6 — RestTemplate is deprecated
// Migrate to RestClient for new code

@Bean
public RestClient restClient(
        RestClient.Builder builder) {
    return builder
        .baseUrl("https://api.example.com")
        .defaultHeader("Accept",
            MediaType.APPLICATION_JSON_VALUE)
        .build();
}

// Usage — fluent, type-safe, exception-friendly
User user = restClient.get()
    .uri("/users/{id}", 42L)
    .retrieve()
    .body(User.class);

ResponseEntity<User> resp = restClient.post()
    .uri("/users")
    .body(newUser)
    .retrieve()
    .toEntity(User.class);

MockMvc Testing API (legacy → MockMvcTester fluent API)

 MockMvc + ResultActions MockMvcTester (Spring 6.2) fluent API No change from Spring 6 Changed
Spring 5 — MockMvc + ResultActions
// Spring 5 — perform/andExpect pattern
@SpringBootTest
@AutoConfigureMockMvc
class UserControllerTest {

    @Autowired MockMvc mockMvc;

    @Test
    void getUser() throws Exception {
        mockMvc.perform(
            get("/users/1")
                .accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isOk())
            .andExpect(
                jsonPath("$.name").value("Alice"))
            .andExpect(
                jsonPath("$.email")
                    .value("alice@example.com"))
            .andDo(print());
        // Throws checked Exception everywhere
    }
}
Spring 6.2 — MockMvcTester (fluent)
// Spring 6.2 — MockMvcTester + AssertJ
@SpringBootTest
@AutoConfigureMockMvc
class UserControllerTest {

    @Autowired MockMvcTester mockMvc;

    @Test
    void getUser() {
        // No checked exceptions — cleaner tests
        assertThat(
            mockMvc.get().uri("/users/1"))
            .hasStatusOk()
            .bodyJson()
            .extractingPath("$.name")
            .asString()
            .isEqualTo("Alice");
        // Full AssertJ fluency —
        // IDE auto-complete works throughout
    }
}

CRaC — Coordinated Restore at Checkpoint

 N/A No CRaC support; GraalVM native only for fast startup First-class CRaC integration via Lifecycle stop/start hooks; JVM-based sub-100ms restore New
Spring 6 — no CRaC, GraalVM native only
# Spring 6 — fast startup via native image only
# GraalVM compilation required (slow build):
mvn -Pnative native:compile

# Result: native binary, ~50ms startup
# But: no JVM profiling, native image maintenance,
#      platform-specific binaries
Spring 7 — CRaC checkpoint + restore
# Spring 7 — CRaC on standard JVM
# Requires CRaC-enabled JDK (Liberica / Azul)

# Step 1: Start app and take checkpoint
java -XX:CRaCCheckpointTo=/checkpoint -jar app.jar
# After warmup / HTTP warm request:
jcmd $(pgrep java) JDK.checkpoint

# Step 2: Restore from snapshot (instant)
java -XX:CRaCRestoreFrom=/checkpoint
# <100ms restore time on standard JVM!

# Spring auto-manages Lifecycle beans:
# stop() before checkpoint, start() after restore
# No code changes needed in most Spring apps

HttpHeaders API (no longer extends MultiValueMap)

 N/A HttpHeaders extends MultiValueMap<String, String> HttpHeaders no longer extends MultiValueMap; use asMultiValueMap() (deprecated bridge) Changed
Spring 6 — HttpHeaders is a MultiValueMap
// Spring 6 — HttpHeaders extends MultiValueMap
HttpHeaders headers = new HttpHeaders();
headers.add("X-Request-ID", "abc123");

// Works: HttpHeaders used as MultiValueMap
MultiValueMap<String, String> map = headers;
map.set("Content-Type",
    MediaType.APPLICATION_JSON_VALUE);

// Passed directly where MultiValueMap expected:
restTemplate.exchange(uri, HttpMethod.GET,
    new HttpEntity<>(headers), String.class);
Spring 7 — use asMultiValueMap() bridge
// Spring 7 — HttpHeaders no longer extends
//            MultiValueMap (breaking change!)
HttpHeaders headers = new HttpHeaders();
headers.add("X-Request-ID", "abc123");

// Compile error if assigned to MultiValueMap:
// MultiValueMap<String, String> map = headers; // ❌

// Use the bridge method (marked @Deprecated):
MultiValueMap<String, String> map =
    headers.asMultiValueMap(); // deprecated bridge

// Preferred: use HttpHeaders API directly:
headers.set("Content-Type",
    MediaType.APPLICATION_JSON_VALUE);
restClient.get().uri("/api")
    .headers(h -> h.addAll(headers))
    .retrieve().body(String.class);
