Spring Framework 6 Features

Spring 6.2.x Current Java 17+ baseline • GA: Nov 2022 • Jakarta EE 9+

Spring Framework 6 is the most significant release since Spring 5 — it raises the baseline to Java 17 and Jakarta EE 9+, completing the javax.* → jakarta.* namespace migration. It adds first-class support for GraalVM native images via Spring AOT, a declarative HTTP client via @HttpExchange, built-in Micrometer observability, RFC 7807 ProblemDetail error responses, and Project Loom virtual-thread support. Spring 6.1 added RestClient (the synchronous counterpart to WebClient), and Spring 6.2 shipped MockMvcTester for fluent assertion-style MVC tests.

javax.* → jakarta.* Namespace Migration — All Major Packages [Basic]

The most impactful change in Spring 6 is the complete migration from javax.* to jakarta.* namespaces, mandated by the transfer of Java EE to the Eclipse Foundation as Jakarta EE. Every import in your codebase that references a Java EE API must be updated. The most frequently touched packages are shown below.

// ── Servlet API ───────────────────────────────────────
// Spring 5 (javax)
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import javax.servlet.http.HttpSession;
import javax.servlet.Filter;
import javax.servlet.FilterChain;

// Spring 6 (jakarta)
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.servlet.http.HttpSession;
import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;

// ── JPA / Persistence ─────────────────────────────────
// Spring 5 (javax)
import javax.persistence.Entity;
import javax.persistence.Id;
import javax.persistence.Column;
import javax.persistence.OneToMany;
import javax.persistence.GeneratedValue;
import javax.persistence.EntityManager;
import javax.persistence.PersistenceContext;

// Spring 6 (jakarta)
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Column;
import jakarta.persistence.OneToMany;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;

// ── Bean Validation ───────────────────────────────────
// Spring 5 (javax)
import javax.validation.Valid;
import javax.validation.constraints.NotNull;
import javax.validation.constraints.Size;
import javax.validation.constraints.Email;

// Spring 6 (jakarta)
import jakarta.validation.Valid;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;
import jakarta.validation.constraints.Email;

// ── Common Annotations (JSR-250) ──────────────────────
// Spring 5 (javax)
import javax.annotation.PostConstruct;
import javax.annotation.PreDestroy;
import javax.annotation.Resource;

// Spring 6 (jakarta)
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import jakarta.annotation.Resource;
Rule of thumb Any import that starts with javax. from a Java EE / Jakarta EE API package needs to change to jakarta.. Pure Java SE packages (e.g. javax.net, javax.crypto) do not change — only EE-origin APIs were transferred.

Jakarta EE 10 Features in Spring 6 — Virtual Threads & Records [Advanced]

Spring 6 targets Jakarta EE 9+ (moving to EE 10 with Spring 6.1). Jakarta EE 10 brought CDI 4.0, Servlet 6.0, and various API cleanups. Combined with Java 17's sealed classes and records, Spring 6 fully embraces these idioms. Entity classes can now be Java records (with some limitations), and @Async methods can be backed by virtual threads from Project Loom.

import jakarta.persistence.*;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Email;

// Java record as a DTO — works natively with Spring 6 data binding
public record UserRequest(
    @NotBlank String name,
    @Email String email,
    @NotNull String role
) {}

// Jakarta annotations on a standard entity class
@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @Column(unique = true, nullable = false)
    private String email;

    // Getters/setters or use Lombok
}

// Sealed class hierarchy for domain modeling (Java 17+)
public sealed interface PaymentResult
        permits PaymentResult.Success, PaymentResult.Failure {

    record Success(String transactionId, java.math.BigDecimal amount)
            implements PaymentResult {}

    record Failure(String code, String message)
            implements PaymentResult {}
}

// Virtual thread configuration (Spring 6.1+ / Java 21)
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.SimpleAsyncTaskExecutor;

@Configuration
public class AsyncConfig {

    @Bean
    public SimpleAsyncTaskExecutor taskExecutor() {
        SimpleAsyncTaskExecutor executor = new SimpleAsyncTaskExecutor();
        executor.setVirtualThreads(true);  // Java 21 virtual threads
        return executor;
    }
}
Records as DTOs vs Entities Java records work well as request/response DTOs. Using them directly as JPA @Entity classes is problematic because JPA requires a no-arg constructor and mutable state. Use records for data transfer and standard classes for entities.

@HttpExchange — Declarative HTTP Client (NEW in Spring 6) [Basic]

@HttpExchange lets you declare an HTTP client as a Java interface — similar to how Spring Data repositories work. You annotate a method with the HTTP method and URI; Spring generates a proxy implementation backed by either WebClient (reactive) or RestClient (synchronous, Spring 6.1+). This replaces the verbose boilerplate of manually calling RestTemplate or building WebClient chains.

<!-- Spring 5 equivalent: manual RestTemplate boilerplate -->
<!-- OLD: dozens of lines per endpoint -->

<!-- Spring 6: spring-web already includes @HttpExchange support -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-web</artifactId>
  <version>6.2.0</version>
</dependency>
import org.springframework.web.service.annotation.HttpExchange;
import org.springframework.web.service.annotation.GetExchange;
import org.springframework.web.service.annotation.PostExchange;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestBody;

// Declare the client as an interface — no implementation needed
@HttpExchange(url = "/api/products", accept = "application/json")
public interface ProductClient {

    @GetExchange
    List<Product> listAll();

    @GetExchange("/{id}")
    Product getById(@PathVariable Long id);

    @PostExchange
    Product create(@RequestBody Product product);

    @PutExchange("/{id}")
    Product update(@PathVariable Long id, @RequestBody Product product);

    @DeleteExchange("/{id}")
    void delete(@PathVariable Long id);
}

// Spring 5 equivalent (manual WebClient calls):
// webClient.get().uri("/api/products/{id}", id)
//          .retrieve().bodyToMono(Product.class).block()
// — repeated per method, no type safety on URL params
Spring 5 equivalent In Spring 5, you would call RestTemplate or WebClient imperatively in a service class. @HttpExchange removes all that boilerplate — the interface declaration IS the implementation.

@GetExchange, @PostExchange, @PutExchange, @DeleteExchange [Basic]

Spring 6 ships four convenience annotations — each is a specialization of @HttpExchange with the HTTP method pre-set. They mirror the server-side @GetMapping / @PostMapping annotations, making the client interface immediately readable.

import org.springframework.web.service.annotation.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.http.ResponseEntity;

@HttpExchange(url = "https://api.example.com")
public interface OrderServiceClient {

    // GET /orders
    @GetExchange("/orders")
    List<Order> getOrders();

    // GET /orders/{id}  — path variable
    @GetExchange("/orders/{id}")
    Order getOrder(@PathVariable Long id);

    // GET /orders?status=PENDING  — query param
    @GetExchange("/orders")
    List<Order> getOrdersByStatus(@RequestParam String status);

    // POST /orders  — request body
    @PostExchange("/orders")
    ResponseEntity<Order> createOrder(@RequestBody Order order);

    // PUT /orders/{id}  — path + body
    @PutExchange("/orders/{id}")
    Order updateOrder(@PathVariable Long id, @RequestBody Order order);

    // PATCH /orders/{id}
    @PatchExchange("/orders/{id}")
    Order patchOrder(@PathVariable Long id, @RequestBody Map<String, Object> patch);

    // DELETE /orders/{id}
    @DeleteExchange("/orders/{id}")
    void deleteOrder(@PathVariable Long id);

    // HEAD — check existence
    @HttpExchange(method = "HEAD", url = "/orders/{id}")
    ResponseEntity<Void> existsById(@PathVariable Long id);
}

HttpServiceProxyFactory — Wiring the Client Proxy [Intermediate]

HttpServiceProxyFactory creates the runtime proxy that implements your @HttpExchange interface. You configure it with an HTTP adapter — either WebClientAdapter (reactive) or RestClientAdapter (synchronous, Spring 6.1+) — and then ask it to create an instance of your interface. The resulting bean can be injected anywhere in the application context.

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.reactive.function.client.WebClient;
import org.springframework.web.reactive.function.client.support.WebClientAdapter;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.support.RestClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

@Configuration
public class HttpClientConfig {

    // ── Option A: backed by WebClient (reactive / non-blocking) ──
    @Bean
    public ProductClient productClientReactive() {
        WebClient webClient = WebClient.builder()
                .baseUrl("https://products.example.com")
                .defaultHeader("X-API-Key", "secret")
                .build();

        HttpServiceProxyFactory factory = HttpServiceProxyFactory
                .builderFor(WebClientAdapter.create(webClient))
                .build();

        return factory.createClient(ProductClient.class);
    }

    // ── Option B: backed by RestClient (synchronous, Spring 6.1+) ──
    @Bean
    public OrderServiceClient orderServiceClient() {
        RestClient restClient = RestClient.builder()
                .baseUrl("https://orders.example.com")
                .defaultHeader("Authorization", "Bearer token")
                .build();

        HttpServiceProxyFactory factory = HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(restClient))
                .build();

        return factory.createClient(OrderServiceClient.class);
    }
}

// ── Using the generated proxy in a service ──
@Service
public class CheckoutService {

    private final ProductClient productClient;
    private final OrderServiceClient orderServiceClient;

    public CheckoutService(ProductClient productClient,
                           OrderServiceClient orderServiceClient) {
        this.productClient       = productClient;
        this.orderServiceClient  = orderServiceClient;
    }

    public Order checkout(Long productId, int qty) {
        Product product = productClient.getById(productId);  // HTTP GET
        Order order = new Order(product, qty);
        return orderServiceClient.createOrder(order).getBody();  // HTTP POST
    }
}

Custom Headers, Error Handling, Timeout & Retry [Advanced]

Advanced @HttpExchange usage involves per-request headers, structured error decoding, connect/read timeouts, and retry policies. These are configured on the underlying WebClient or RestClient rather than the interface itself, giving you full control over the HTTP transport behaviour.

import org.springframework.web.service.annotation.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.http.HttpHeaders;

// Per-method header via @RequestHeader
@HttpExchange(url = "/api/secure")
public interface SecureApiClient {

    @GetExchange("/resource")
    Resource fetchResource(@RequestHeader("X-Correlation-Id") String correlationId,
                           @RequestHeader(HttpHeaders.AUTHORIZATION) String bearerToken);

    @PostExchange("/resource")
    Resource createResource(@RequestBody Resource resource,
                            @RequestHeader Map<String, String> headers);
}

// ── Advanced factory setup: timeout + retry ──
import io.netty.channel.ChannelOption;
import reactor.netty.http.client.HttpClient;
import org.springframework.http.client.reactive.ReactorClientHttpConnector;
import java.time.Duration;
import reactor.util.retry.Retry;

@Configuration
public class AdvancedClientConfig {

    @Bean
    public SecureApiClient secureApiClient() {
        // Netty HTTP client with connect + read timeout
        HttpClient httpClient = HttpClient.create()
                .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 3000)
                .responseTimeout(Duration.ofSeconds(10));

        WebClient webClient = WebClient.builder()
                .baseUrl("https://secure.example.com")
                .clientConnector(new ReactorClientHttpConnector(httpClient))
                // Global error decoder — maps 4xx/5xx to exceptions
                .defaultStatusHandler(
                    status -> status.isError(),
                    response -> response.bodyToMono(ErrorPayload.class)
                                       .map(body -> new ApiException(body.message())))
                .build();

        return HttpServiceProxyFactory
                .builderFor(WebClientAdapter.create(webClient))
                .build()
                .createClient(SecureApiClient.class);
    }
}

// ── Retry policy with resilience4j or Reactor's built-in retry ──
@Service
public class ResilientOrderClient {

    private final WebClient webClient;

    public ResilientOrderClient(WebClient.Builder builder) {
        this.webClient = builder.baseUrl("https://orders.example.com").build();
    }

    public Mono<Order> fetchWithRetry(Long orderId) {
        return webClient.get()
                .uri("/orders/{id}", orderId)
                .retrieve()
                .bodyToMono(Order.class)
                .retryWhen(Retry.backoff(3, Duration.ofMillis(200))
                               .filter(ex -> ex instanceof ApiException));
    }
}

Micrometer — Now Core in Spring 6 (Not Optional) [Basic]

Spring Framework 6 integrates Micrometer as a first-class dependency (not an optional add-on). Micrometer is the vendor-neutral instrumentation facade for JVM applications — it provides a single API to record metrics (counters, gauges, timers) and traces, then ships the data to any backend: Prometheus, Datadog, Zipkin, Grafana, etc. In Spring 6 the ObservationRegistry replaces ad-hoc metric and tracing configuration.

<!-- spring-webmvc 6+ already includes micrometer-observation transitively -->
<!-- For full metrics + tracing add: -->
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
  <version>1.12.0</version>
</dependency>

<!-- Distributed tracing (Micrometer Tracing) -->
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-tracing-bridge-brave</artifactId>
  <version>1.2.0</version>
</dependency>
// In Spring 5 you had to wire Micrometer metrics manually.
// In Spring 6 the ObservationRegistry is auto-configured and ready to use.

import io.micrometer.observation.ObservationRegistry;
import org.springframework.stereotype.Service;

@Service
public class ProductService {

    private final ObservationRegistry registry;

    public ProductService(ObservationRegistry registry) {
        this.registry = registry;
    }

    public Product findById(Long id) {
        // Wrap business logic in an observation — records both metric + span
        return io.micrometer.observation.Observation
                .createNotStarted("product.find-by-id", registry)
                .lowCardinalityKeyValue("db", "postgres")
                .observe(() -> repository.findById(id)
                        .orElseThrow(() -> new ProductNotFoundException(id)));
    }
}
Spring 5 equivalent In Spring 5 you'd manually call meterRegistry.timer("...", ...).record(...). Spring 6's Observation API unifies metrics and distributed tracing in one call — one observation becomes both a Micrometer timer and a trace span automatically.

@Observed — Automatic Method-Level Instrumentation [Intermediate]

The @Observed annotation (from Micrometer, usable in Spring 6 via AOP) wraps an entire method in an observation without any boilerplate code. When placed on a class, it applies to all public methods. Spring generates a timer metric and a trace span named after the class and method automatically.

import io.micrometer.observation.annotation.Observed;
import org.springframework.stereotype.Service;

// @Observed on the class applies to ALL public methods
@Observed(name = "order.service",
          contextualName = "OrderService",
          lowCardinalityKeyValues = {"team", "checkout"})
@Service
public class OrderService {

    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    // This method is automatically observed as "order.service"
    // — timer metric + trace span created and closed around the call
    public Order placeOrder(Order order) {
        return orderRepository.save(order);
    }

    // Override the name for a specific method
    @Observed(name = "order.cancel", contextualName = "CancelOrder")
    public void cancelOrder(Long orderId) {
        orderRepository.deleteById(orderId);
    }
}

// ── Enable AOP-based @Observed processing ──
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import io.micrometer.observation.ObservationRegistry;
import io.micrometer.observation.aop.ObservedAspect;

@Configuration
public class ObservabilityConfig {

    // Required to activate @Observed AOP interception
    @Bean
    ObservedAspect observedAspect(ObservationRegistry registry) {
        return new ObservedAspect(registry);
    }
}

ObservationRegistry — Configuring Metrics & Tracing Backends [Intermediate]

ObservationRegistry is the central hub. You configure it once with metric and tracing handlers; then all observations flow to those backends. Spring Boot auto-configures this for common backends — in plain Spring 6 (without Boot) you configure it manually.

import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.simple.SimpleMeterRegistry;
import io.micrometer.observation.ObservationRegistry;
import io.micrometer.observation.ObservationHandler;
import io.micrometer.observation.ObservationTextPublisher;
import io.micrometer.core.instrument.observation.DefaultMeterObservationHandler;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ObservationRegistryConfig {

    // ── Metrics backend: Prometheus / SimpleMeterRegistry ──
    @Bean
    public MeterRegistry meterRegistry() {
        // In production: use PrometheusMeterRegistry or DatadogMeterRegistry
        return new SimpleMeterRegistry();
    }

    // ── Observation registry wired to metrics ──
    @Bean
    public ObservationRegistry observationRegistry(MeterRegistry meterRegistry) {
        ObservationRegistry registry = ObservationRegistry.create();

        // Each observation creates a Micrometer timer
        registry.observationConfig()
                .observationHandler(new DefaultMeterObservationHandler(meterRegistry));

        // Optional: print observations to stdout (dev only)
        registry.observationConfig()
                .observationHandler(new ObservationTextPublisher());

        return registry;
    }
}

Custom ObservationConvention & ObservationHandler [Advanced]

To customise what tags (key-values) appear on observations, implement ObservationConvention. To intercept observation lifecycle events (start, stop, error), implement ObservationHandler. These are the extension points for custom instrumentation that goes beyond what @Observed provides.

import io.micrometer.observation.*;
import io.micrometer.common.KeyValues;

// ── 1. Custom context — carries extra data through the observation ──
public class OrderObservationContext extends Observation.Context {

    private final String orderId;
    private final String customerId;

    public OrderObservationContext(String orderId, String customerId) {
        this.orderId    = orderId;
        this.customerId = customerId;
    }

    public String getOrderId()    { return orderId; }
    public String getCustomerId() { return customerId; }
}

// ── 2. Custom convention — controls metric name and tags ──
public class OrderObservationConvention
        implements ObservationConvention<OrderObservationContext> {

    @Override
    public String getName() {
        return "order.processing";
    }

    @Override
    public String getContextualName(OrderObservationContext ctx) {
        return "Process Order " + ctx.getOrderId();
    }

    @Override
    public KeyValues getLowCardinalityKeyValues(OrderObservationContext ctx) {
        return KeyValues.of("customer.tier", resolveCustomerTier(ctx.getCustomerId()));
    }

    @Override
    public KeyValues getHighCardinalityKeyValues(OrderObservationContext ctx) {
        return KeyValues.of("order.id", ctx.getOrderId());  // high cardinality — traces only
    }

    @Override
    public boolean supportsContext(Observation.Context context) {
        return context instanceof OrderObservationContext;
    }

    private String resolveCustomerTier(String customerId) {
        return customerId.startsWith("VIP") ? "premium" : "standard";
    }
}

// ── 3. Custom handler — lifecycle hooks ──
public class OrderObservationHandler
        implements ObservationHandler<OrderObservationContext> {

    @Override
    public void onStart(OrderObservationContext ctx) {
        System.out.println("Order processing started: " + ctx.getOrderId());
    }

    @Override
    public void onStop(OrderObservationContext ctx) {
        System.out.println("Order processing stopped, duration tracked");
    }

    @Override
    public void onError(OrderObservationContext ctx) {
        System.err.println("Order processing error for: " + ctx.getOrderId());
    }

    @Override
    public boolean supportsContext(Observation.Context context) {
        return context instanceof OrderObservationContext;
    }
}

// ── 4. Usage ──
@Service
public class OrderProcessor {

    private final ObservationRegistry registry;

    public OrderProcessor(ObservationRegistry registry) {
        this.registry = registry;
    }

    public void process(Order order) {
        OrderObservationContext ctx = new OrderObservationContext(
                order.id().toString(), order.customerId());

        Observation.createNotStarted(new OrderObservationConvention(), ctx, registry)
                   .observe(() -> doProcess(order));
    }

    private void doProcess(Order order) { /* business logic */ }
}

GraalVM Native Image — Why & What [Basic]

A GraalVM native image is a standalone executable compiled ahead-of-time from Java bytecode. Unlike a JVM-based application that JIT-compiles at runtime, a native image is already fully compiled before deployment. The benefits are dramatic: startup in tens of milliseconds instead of seconds, and memory footprint reduced by 60–80%. The trade-off is a longer build time and restrictions on dynamic features (reflection, proxies, serialization) that must be declared ahead of time.

# Traditional JVM app startup
java -jar my-app.jar
# Startup: 2–8 seconds, heap: ~256 MB

# GraalVM native image startup
./my-app-native
# Startup: 20–100 ms, RSS: ~40–80 MB

# Build native image with Maven (Spring Boot 3 / Spring 6)
./mvnw -Pnative native:compile

# Or with Gradle
./gradlew nativeCompile
<!-- pom.xml — native build plugin -->
<build>
  <plugins>
    <plugin>
      <groupId>org.graalvm.buildtools</groupId>
      <artifactId>native-maven-plugin</artifactId>
      <version>0.10.0</version>
      <extensions>true</extensions>
    </plugin>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <configuration>
        <image>
          <builder>paketobuildpacks/builder-jammy-tiny:latest</builder>
        </image>
      </configuration>
    </plugin>
  </plugins>
</build>
When to use native images Ideal for serverless functions (AWS Lambda, Google Cloud Run), CLI tools, and microservices where cold-start latency matters. Long-running applications that have already warmed up JIT compilation may see lower peak throughput with native vs. JVM.

Spring AOT Processing — Build-Time vs. Runtime [Intermediate]

Spring 6 introduced Ahead-of-Time (AOT) processing as a build phase that runs before GraalVM compilation. During the AOT phase Spring analyzes the application context, generates optimized source code (bean factory code without reflection), and produces the hint files (reflect-config.json, proxy-config.json) that GraalVM needs. The generated sources live in target/spring-aot/.

# What happens during mvn -Pnative native:compile:

# Phase 1: Spring AOT (runs at build time)
#   1. Loads your ApplicationContext
#   2. Analyzes all bean definitions
#   3. Generates: BeanFactoryRegistrations.java  (no-reflection bootstrap)
#   4. Generates: reflect-config.json, resource-config.json, proxy-config.json
#   5. Output: target/spring-aot/main/sources/  and  .../resources/

# Phase 2: GraalVM native-image compilation
#   1. Compiles BeanFactoryRegistrations.java along with your source
#   2. Uses hint files to include only referenced types/resources
#   3. Output: target/my-app (native executable)
// Generated AOT bootstrap code (target/spring-aot/main/sources/...)
// You don't write this — Spring generates it automatically.
// Example shape:

// com/example/MyApplication__BeanFactoryRegistrations.java (generated)
public class MyApplication__BeanFactoryRegistrations
        implements BeanFactoryInitializer<DefaultListableBeanFactory> {

    @Override
    public void initialize(DefaultListableBeanFactory beanFactory) {
        // Registers all beans WITHOUT reflection
        RootBeanDefinition def = new RootBeanDefinition(ProductService.class);
        def.setInstanceSupplier(ProductService::new);

@RuntimeHints — Declaring Reflection & Resource Needs [Intermediate]

GraalVM's static analysis cannot discover reflection, proxies, serialization, or classpath resources used at runtime. You must declare these needs explicitly using RuntimeHints. Spring 6 provides @RegisterReflectionForBinding, @ImportRuntimeHints, and the RuntimeHintsRegistrar interface for this purpose. Spring auto-detects many common cases but library authors and advanced use cases need manual hints.

import org.springframework.aot.hint.*;
import org.springframework.aot.hint.annotation.*;

// ── Simple annotation style — register one class for reflection ──
@RegisterReflectionForBinding(ProductDto.class)
@Service
public class ProductService { /* ... */ }

// ── Register a resource file needed at runtime ──
@ImportRuntimeHints(MyRuntimeHints.class)
@Configuration
public class AppConfig { /* ... */ }

// ── RuntimeHintsRegistrar — full control ──
import org.springframework.context.annotation.ImportRuntimeHints;

public class MyRuntimeHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {

        // Reflection — allow all methods and fields to be accessed at runtime
        hints.reflection()
             .registerType(ProductDto.class,
                           MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                           MemberCategory.INVOKE_PUBLIC_METHODS)
             .registerType(OrderEvent.class,
                           MemberCategory.DECLARED_FIELDS,
                           MemberCategory.INVOKE_DECLARED_CONSTRUCTORS);

        // Resources — include config files in the native image
        hints.resources()
             .registerPattern("sql/*.sql")
             .registerPattern("templates/**/*.html");

        // JDK proxies — register interfaces that will be proxied
        hints.proxies()
             .registerJdkProxy(UserRepository.class);

        // Serialization — types used with Java serialization
        hints.serialization()
             .registerType(OrderEvent.class);
    }
}

ProblemDetail — RFC 7807 Standardized Error Responses (NEW in Spring 6) [Basic]

Spring 6 ships ProblemDetail — an implementation of RFC 7807 (Problem Details for HTTP APIs). Instead of ad-hoc error JSON shapes, your API returns a standardised object with well-known fields (type, title, status, detail, instance) that API consumers can programmatically interpret.

import org.springframework.http.ProblemDetail;
import org.springframework.http.HttpStatus;
import java.net.URI;

// Creating a ProblemDetail manually
ProblemDetail problem = ProblemDetail
        .forStatusAndDetail(HttpStatus.NOT_FOUND, "Product with id 42 not found");

problem.setType(URI.create("https://api.example.com/errors/product-not-found"));
problem.setTitle("Product Not Found");
problem.setInstance(URI.create("/api/products/42"));

// Add custom properties beyond the RFC standard
problem.setProperty("productId", 42);
problem.setProperty("catalog", "electronics");

// JSON response shape:
// {
//   "type":     "https://api.example.com/errors/product-not-found",
//   "title":    "Product Not Found",
//   "status":   404,
//   "detail":   "Product with id 42 not found",
//   "instance": "/api/products/42",
//   "productId": 42,
//   "catalog":  "electronics"
// }

// Spring 5 equivalent: custom ErrorResponse record/class per project
// (no standard shape, inconsistent between teams)
Content type The RFC 7807 content type is application/problem+json (or application/problem+xml). Spring 6 sets this automatically when a ProblemDetail is returned.

ErrorResponse Interface & @ExceptionHandler with ProblemDetail [Intermediate]

The ErrorResponse interface (implemented by ResponseEntityExceptionHandler and custom exceptions) unifies exception classes with the ProblemDetail they produce. Exceptions that implement ErrorResponse can carry their own ProblemDetail, making the error definition self-contained in the exception class itself.

import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.ErrorResponse;
import java.net.URI;

// ── Custom exception that implements ErrorResponse ──
public class ProductNotFoundException extends RuntimeException
        implements ErrorResponse {

    private final Long productId;
    private final ProblemDetail problemDetail;

    public ProductNotFoundException(Long productId) {
        super("Product not found: " + productId);
        this.productId = productId;
        this.problemDetail = ProblemDetail
                .forStatusAndDetail(HttpStatus.NOT_FOUND,
                        "No product exists with id " + productId);
        this.problemDetail.setTitle("Product Not Found");
        this.problemDetail.setType(
                URI.create("https://api.example.com/probs/product-not-found"));
        this.problemDetail.setProperty("productId", productId);
    }

    @Override
    public ProblemDetail getBody() {
        return problemDetail;
    }
}

// ── Global handler using Spring's ResponseEntityExceptionHandler ──
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

@ControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    // Spring 6 auto-converts ErrorResponse exceptions to ProblemDetail
    @ExceptionHandler(ProductNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleProductNotFound(
            ProductNotFoundException ex) {
        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(ex.getBody());
    }

    // Override Spring's built-in handler to enrich with custom fields
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            org.springframework.web.bind.MethodArgumentNotValidException ex,
            HttpHeaders headers, HttpStatusCode status, WebRequest request) {

        ProblemDetail problem = ex.getBody();
        problem.setProperty("violations",
                ex.getBindingResult().getFieldErrors().stream()
                  .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
                  .toList());

        return ResponseEntity.status(status).headers(headers).body(problem);
    }
}

RestClient — Synchronous HTTP Client (NEW in Spring 6.1) [Intermediate]

Spring 6.1 introduced RestClient — a modern, fluent, synchronous HTTP client that replaces the deprecated RestTemplate. Unlike WebClient (which is reactive), RestClient blocks until the response arrives, making it a drop-in conceptual replacement for RestTemplate in non-reactive applications. It shares the same HttpMessageConverter stack and supports the same request building patterns as WebClient.

import org.springframework.web.client.RestClient;
import org.springframework.http.ResponseEntity;
import org.springframework.http.MediaType;

// ── Create a RestClient ──
RestClient restClient = RestClient.builder()
        .baseUrl("https://api.example.com")
        .defaultHeader("Accept", MediaType.APPLICATION_JSON_VALUE)
        .build();

// ── GET — retrieve body ──
Product product = restClient.get()
        .uri("/products/{id}", 42)
        .retrieve()
        .body(Product.class);

// ── GET — retrieve with full response ──
ResponseEntity<Product> response = restClient.get()
        .uri("/products/{id}", 42)
        .retrieve()
        .toEntity(Product.class);

// ── GET list ──
List<Product> products = restClient.get()
        .uri("/products")
        .retrieve()
        .body(new ParameterizedTypeReference<List<Product>>() {});

// ── POST — send body ──
Product created = restClient.post()
        .uri("/products")
        .contentType(MediaType.APPLICATION_JSON)
        .body(new Product("Widget", 9.99))
        .retrieve()
        .body(Product.class);

// ── Error handling ──
Product result = restClient.get()
        .uri("/products/{id}", 99)
        .retrieve()
        .onStatus(status -> status.is4xxClientError(), (req, res) -> {
            throw new ProductNotFoundException(99L);
        })
        .body(Product.class);

// Spring 5 equivalent (RestTemplate — deprecated):
// restTemplate.getForObject("/products/{id}", Product.class, 42)
RestTemplate migration RestClient is the intended migration path from RestTemplate. The API is intentionally similar so migration is mechanical. RestTemplate is not removed in Spring 6 but is in maintenance mode — no new features.

Virtual Threads (Project Loom) — Spring 6.1+ on Java 21 [Advanced]

Java 21 (LTS) made Project Loom's virtual threads generally available. Virtual threads are JVM-managed lightweight threads — millions can exist simultaneously without exhausting OS thread pools. Spring 6.1 added first-class support: you can configure Tomcat, Jetty, or Undertow to dispatch requests on virtual threads, and @Async methods can run on a virtual-thread executor.

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.SimpleAsyncTaskExecutor;
import org.springframework.scheduling.annotation.EnableAsync;
import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Service;
import java.util.concurrent.Executor;
import java.util.concurrent.Executors;

// ── 1. Configure @Async to use virtual threads ──
@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean(name = "applicationTaskExecutor")
    public Executor virtualThreadExecutor() {
        SimpleAsyncTaskExecutor executor = new SimpleAsyncTaskExecutor("vt-");
        executor.setVirtualThreads(true);  // Java 21: uses Thread.ofVirtual()
        return executor;
    }
}

// ── 2. Use @Async — now backed by virtual threads ──
@Service
public class ReportService {

    @Async  // executes on a virtual thread from the pool above
    public CompletableFuture<Report> generateReport(Long reportId) {
        // Blocking I/O is fine here — virtual thread unmounts while waiting
        Report report = slowDatabaseQuery(reportId);
        return CompletableFuture.completedFuture(report);
    }
}

// ── 3. Configure Tomcat to use virtual threads for request dispatch ──
import org.springframework.boot.web.embedded.tomcat.TomcatProtocolHandlerCustomizer;

@Configuration
public class TomcatVirtualThreadConfig {

    @Bean
    public TomcatProtocolHandlerCustomizer<?> virtualThreadProtocolHandlerCustomizer() {
        return protocolHandler ->
            protocolHandler.setExecutor(
                Executors.newVirtualThreadPerTaskExecutor());
    }
}

// application.properties alternative (Spring Boot 3.2+):
// spring.threads.virtual.enabled=true
Virtual threads vs. reactive (WebFlux) Virtual threads provide the scalability benefits of reactive programming without the reactive programming model. You write blocking, imperative code and the JVM handles the non-blocking suspension automatically. Choose virtual threads when you want simplicity; choose WebFlux when you need streaming or backpressure.

MockMvcTester — Fluent AssertJ API for MockMvc (NEW in Spring 6.2) [Basic]

Spring 6.2 introduced MockMvcTester — a new fluent, AssertJ-native entry point for MockMvc tests. The classic MockMvc API uses a DSL of static methods and result matchers; MockMvcTester returns an MvcTestResult that AssertJ's assertThat() can reason about directly — making errors much more readable and enabling IDE autocompletion throughout the assertion chain.

import org.springframework.test.web.servlet.assertj.MockMvcTester;
import org.springframework.test.web.servlet.assertj.MvcTestResult;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.beans.factory.annotation.Autowired;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

@WebMvcTest(ProductController.class)
class ProductControllerMvcTesterTest {

    @Autowired
    MockMvcTester mvc;  // autowired directly in Spring 6.2

    @MockBean
    ProductService productService;

    @Test
    void getProduct_returns200() {
        given(productService.findById(1L))
                .willReturn(new Product(1L, "Widget", new BigDecimal("9.99")));

        // MockMvcTester: fluent chain, no checked exceptions
        assertThat(mvc.get().uri("/api/products/1"))
                .hasStatusOk()
                .hasContentTypeCompatibleWith(MediaType.APPLICATION_JSON)
                .bodyJson()
                .extractingPath("$.name").isEqualTo("Widget");
    }

    @Test
    void getProduct_notFound_returns404() {
        given(productService.findById(99L))
                .willThrow(new ProductNotFoundException(99L));

        assertThat(mvc.get().uri("/api/products/99"))
                .hasStatus(HttpStatus.NOT_FOUND)
                .bodyJson()
                .extractingPath("$.status").isEqualTo(404);
    }

    // Spring 5 equivalent (classic MockMvc):
    // mockMvc.perform(get("/api/products/1").accept(APPLICATION_JSON))
    //        .andExpect(status().isOk())
    //        .andExpect(jsonPath("$.name").value("Widget"));
    // (checked exception, static imports, less readable on failure)
}
Spring 5 comparison Classic MockMvc requires throws Exception on every test method and uses static-import chains (MockMvcResultMatchers.*). MockMvcTester removes the checked exception, is fully fluent with AssertJ, and produces cleaner failure messages.

ApplicationContextRunner — Testing Auto-Configurations [Advanced]

ApplicationContextRunner is the recommended way to test custom Spring Boot auto-configurations and @Conditional beans. It creates a lightweight application context programmatically, applies your configuration, and lets you assert which beans are present (or absent) — all without a full @SpringBootTest startup.

import org.springframework.boot.test.context.runner.ApplicationContextRunner;
import org.springframework.boot.autoconfigure.AutoConfigurations;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class CacheAutoConfigurationTest {

    // Reusable runner — apply your auto-configuration
    private final ApplicationContextRunner contextRunner =
            new ApplicationContextRunner()
                .withConfiguration(AutoConfigurations.of(CacheAutoConfiguration.class));

    @Test
    void cacheManagerBeanIsPresent_whenPropertyEnabled() {
        contextRunner
            .withPropertyValues("app.cache.enabled=true")
            .run(ctx -> {
                assertThat(ctx).hasSingleBean(CacheManager.class);
                assertThat(ctx.getBean(CacheManager.class))
                        .isInstanceOf(RedisCacheManager.class);
            });
    }

    @Test
    void cacheManagerBeanIsAbsent_whenPropertyDisabled() {
        contextRunner
            .withPropertyValues("app.cache.enabled=false")
            .run(ctx -> {
                assertThat(ctx).doesNotHaveBean(CacheManager.class);
            });
    }

    @Test
    void userDefinedBeanTakesPrecedence() {
        contextRunner
            .withPropertyValues("app.cache.enabled=true")
            .withUserConfiguration(UserCacheConfig.class)  // user-provided
            .run(ctx -> {
                // Auto-configuration backs off when user defines their own
                assertThat(ctx).hasSingleBean(CacheManager.class);
                CacheManager cm = ctx.getBean(CacheManager.class);
                assertThat(cm).isInstanceOf(ConcurrentMapCacheManager.class);
            });
    }

    @org.springframework.context.annotation.Configuration
    static class UserCacheConfig {
        @org.springframework.context.annotation.Bean
        CacheManager customCacheManager() {
            return new ConcurrentMapCacheManager("user-cache");
        }
    }
}

Constructor Injection — The Official Canonical Style in Spring 6 [Basic]

Spring 6 and the accompanying Spring team guidance make constructor injection the canonical and recommended injection style. Field injection (which requires reflection to set private fields) conflicts with GraalVM native image constraints. When there is a single constructor, @Autowired is optional — Spring uses it implicitly. Lombok's @RequiredArgsConstructor generates the boilerplate constructor automatically.

import org.springframework.stereotype.Service;

// ── RECOMMENDED in Spring 6: Constructor injection ──
// @Autowired is not required — single constructor is implicitly used
@Service
public class ProductService {

    private final ProductRepository productRepository;  // final — immutable
    private final PricingService pricingService;

    // Single constructor — Spring 6 injects without @Autowired
    public ProductService(ProductRepository productRepository,
                          PricingService pricingService) {
        this.productRepository = productRepository;
        this.pricingService    = pricingService;
    }

    public Product findById(Long id) {
        return productRepository.findById(id)
                .map(pricingService::applyPricing)
                .orElseThrow(() -> new ProductNotFoundException(id));
    }
}

// ── AVOID: Field injection — breaks native image, not testable without Spring ──
@Service
public class BadProductService {
    @Autowired private ProductRepository productRepository;  // no final, requires reflection
    @Autowired private PricingService pricingService;
}

// ── Lombok shortcut — generates the constructor ──
import lombok.RequiredArgsConstructor;

@Service
@RequiredArgsConstructor
public class OrderService {
    // Lombok generates: public OrderService(OrderRepository repo) { this.repo = repo; }
    private final OrderRepository repo;
    private final ProductService productService;
}
Native image benefit Field injection requires Spring to call setAccessible(true) on private fields via reflection — an operation that must be pre-declared in native images. Constructor injection requires no reflection, reducing the set of hints needed.

BeanDefinitionRegistry & Programmatic Container Configuration [Advanced]

Spring 6 improves the programmatic container API. BeanDefinitionRegistry allows registering, removing, and querying bean definitions at any point before the context is refreshed. Combined with BeanDefinitionParserDelegate improvements, this is the foundation that framework authors use to support custom XML namespaces and programmatic context bootstrapping.

import org.springframework.beans.factory.support.*;
import org.springframework.beans.factory.config.BeanDefinition;
import org.springframework.context.support.GenericApplicationContext;
import org.springframework.core.ResolvableType;

public class ProgrammaticContainerDemo {

    public static void main(String[] args) {
        GenericApplicationContext ctx = new GenericApplicationContext();

        // Access the registry
        BeanDefinitionRegistry registry = ctx.getBeanFactory();

        // Register a bean definition programmatically
        RootBeanDefinition def = new RootBeanDefinition(ProductService.class);
        def.setScope(BeanDefinition.SCOPE_SINGLETON);
        def.setLazyInit(false);
        def.getConstructorArgumentValues()
           .addGenericArgumentValue(new RuntimeBeanReference("productRepository"));

        registry.registerBeanDefinition("productService", def);

        // Register a bean with a generic type (Spring 6 improvement)
        // Useful for registering generic repository beans by type
        RootBeanDefinition repoDefinition = new RootBeanDefinition();
        repoDefinition.setTargetType(
                ResolvableType.forClassWithGenerics(JpaRepository.class, Product.class, Long.class));
        repoDefinition.setBeanClass(SimpleJpaRepository.class);
        registry.registerBeanDefinition("productJpaRepository", repoDefinition);

        // Introspect registered beans before refresh
        String[] beanNames = registry.getBeanDefinitionNames();
        for (String name : beanNames) {
            BeanDefinition bd = registry.getBeanDefinition(name);
            System.out.printf("Bean: %-30s scope: %s%n", name, bd.getScope());
        }

        ctx.refresh();

        // Remove a bean definition post-refresh (advanced, careful)
        // registry.removeBeanDefinition("productService");

        ctx.close();
    }
}

// ── BeanDefinitionParserDelegate — for custom XML namespace support ──
import org.springframework.beans.factory.xml.BeanDefinitionParserDelegate;

public class CustomBeanDefinitionParser
        implements org.springframework.beans.factory.xml.BeanDefinitionParser {

    @Override
    public BeanDefinition parse(
            org.w3c.dom.Element element,
            org.springframework.beans.factory.xml.ParserContext parserContext) {

        BeanDefinitionParserDelegate delegate = parserContext.getDelegate();

        // Spring 6: improved type resolution in delegate
        RootBeanDefinition definition = new RootBeanDefinition();
        definition.setBeanClass(CustomProcessor.class);
        delegate.parsePropertyElements(element, definition);

        parserContext.getRegistry()
                     .registerBeanDefinition("customProcessor", definition);
        return definition;
    }
}
Framework authors BeanDefinitionRegistry and BeanDefinitionParserDelegate are primarily for framework and library authors. Application code should prefer @Configuration + @Bean for readability and AOT compatibility.
