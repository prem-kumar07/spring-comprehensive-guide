Spring Framework 5 Features

Spring 5.3.x LTS Java 8+ baseline • GA: Sep 2017 • LTS: Oct 2020

Spring Framework 5 represents a major generational leap — it moved to a Java 8+ baseline, introduced the fully reactive WebFlux stack built on Project Reactor, adopted JUnit 5 as a first-class testing citizen, added null-safety annotations, and provided dedicated support for Kotlin. Spring 5.3 (October 2020) became the Long-Term Support branch, receiving backported fixes until the end of 2024 to give teams a stable migration bridge to Spring 6.

Stereotype Annotations & Dependency Injection [Basic]

@Component marks a class so the classpath scanner registers it as a Spring-managed bean. @Autowired instructs the container to resolve and inject a matching bean by type at the annotated field, constructor, or setter. @Value injects scalar values from property sources or Spring Expression Language (SpEL) expressions directly into fields.

<!-- pom.xml -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>5.3.39</version>
</dependency>
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

@Component
public class GreetingService {

    @Value("${app.greeting:Hello}")
    private String greeting;

    public String greet(String name) {
        return greeting + ", " + name + "!";
    }
}

@Component
public class WelcomeController {

    private final GreetingService greetingService;

    @Autowired
    public WelcomeController(GreetingService greetingService) {
        this.greetingService = greetingService;
    }

    public String welcome(String name) {
        return greetingService.greet(name);
    }
}
Tip Prefer constructor injection (shown above) over field injection. It makes dependencies explicit, allows the class to be unit-tested without a Spring context, and the field can be final.

XML vs Annotation Configuration [Basic]

Spring supports three configuration styles that can be freely mixed: legacy XML (<bean> elements), annotation-driven classpath scanning (@Component + @ComponentScan), and Java-based configuration (@Configuration + @Bean). Modern projects almost exclusively use annotation or Java config, but XML is still used to import legacy or third-party bean definitions.

<!-- legacy-beans.xml (XML style) -->
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
           http://www.springframework.org/schema/beans/spring-beans.xsd">

  <bean id="dataSource" class="com.example.SimpleDataSource">
    <property name="url" value="jdbc:h2:mem:testdb"/>
  </bean>

</beans>
// Annotation config style — Java equivalent
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.ImportResource;

@Configuration
@ComponentScan("com.example")          // scan for @Component beans
@ImportResource("classpath:legacy-beans.xml")  // pull in XML if needed
public class AppConfig {
    // @Bean methods go here (see next card)
}

@Configuration, @Bean, @Conditional & @Profile [Intermediate]

A class annotated with @Configuration acts as a bean factory: its @Bean-annotated methods produce beans managed by the container. @Profile restricts a bean or configuration class to a named Spring profile (e.g. dev, prod), and @Conditional evaluates arbitrary logic to decide whether to register a bean — the foundation for Spring Boot's auto-configuration.

import org.springframework.context.annotation.*;
import org.springframework.core.type.AnnotatedTypeMetadata;

@Configuration
public class InfraConfig {

    // Always registered — active datasource
    @Bean
    @Profile("prod")
    public DataSource prodDataSource() {
        HikariDataSource ds = new HikariDataSource();
        ds.setJdbcUrl("jdbc:postgresql://db:5432/mydb");
        return ds;
    }

    @Bean
    @Profile("!prod")  // all non-prod profiles
    public DataSource devDataSource() {
        return new EmbeddedDatabaseBuilder()
                .setType(EmbeddedDatabaseType.H2)
                .build();
    }

    // Only register when the class is on the classpath
    @Bean
    @Conditional(CacheOnClasspathCondition.class)
    public CacheManager cacheManager() {
        return new ConcurrentMapCacheManager("users", "products");
    }
}

class CacheOnClasspathCondition implements Condition {
    @Override
    public boolean matches(ConditionContext context, AnnotatedTypeMetadata metadata) {
        try {
            Class.forName("org.springframework.cache.CacheManager");
            return true;
        } catch (ClassNotFoundException e) {
            return false;
        }
    }
}

Constructor vs Field vs Setter Injection [Intermediate]

Spring supports three injection styles. Constructor injection (recommended by the Spring team since 5.0) makes dependencies mandatory and immutable, enables final fields, and simplifies unit testing. Field injection (@Autowired on a field) is concise but hides dependencies, prevents final, and requires a Spring context in tests. Setter injection is appropriate for optional or reconfigurable dependencies.

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

// RECOMMENDED: Constructor injection
@Service
public class OrderService {

    private final PaymentGateway paymentGateway;
    private final InventoryService inventoryService;

    // @Autowired is implicit when there is a single constructor (Spring 4.3+)
    public OrderService(PaymentGateway paymentGateway,
                        InventoryService inventoryService) {
        this.paymentGateway = paymentGateway;
        this.inventoryService = inventoryService;
    }
}

// AVOID: Field injection — hides dependencies, prevents final
@Service
public class BadOrderService {
    @Autowired private PaymentGateway paymentGateway;   // hard to test
    @Autowired private InventoryService inventoryService;
}

// ACCEPTABLE for optional dependencies: Setter injection
@Service
public class NotificationService {

    private EmailSender emailSender;

    @Autowired(required = false)
    public void setEmailSender(EmailSender emailSender) {
        this.emailSender = emailSender;
    }
}
Circular dependency gotcha Constructor injection correctly surfaces circular dependencies as a startup error. Field injection hides them until a NullPointerException occurs at runtime. Prefer constructor injection so the container fails fast.

Functional Bean Registration (GenericApplicationContext) [Advanced]

Spring 5 introduced a functional, lambda-friendly API for registering beans without annotation scanning or XML. GenericApplicationContext.registerBean() accepts a supplier lambda and optional customizers, making it possible to build a Spring context with zero classpath scanning — ideal for GraalVM native images and lambda-cold-start optimization.

import org.springframework.context.support.GenericApplicationContext;

public class FunctionalContextDemo {

    public static void main(String[] args) {
        GenericApplicationContext ctx = new GenericApplicationContext();

        // Register beans with lambda suppliers — no annotation scanning needed
        ctx.registerBean(DataSourceConfig.class, DataSourceConfig::new);

        ctx.registerBean("primaryRepo", UserRepository.class,
                () -> new UserRepository(ctx.getBean(DataSourceConfig.class)),
                bd -> {
                    bd.setPrimary(true);
                    bd.setLazyInit(true);
                });

        ctx.registerBean(UserService.class,
                () -> new UserService(ctx.getBean(UserRepository.class)));

        ctx.refresh();

        UserService userService = ctx.getBean(UserService.class);
        System.out.println("Context started, UserService: " + userService);

        ctx.close();
    }
}
Native image benefit Functional registration avoids runtime classpath scanning and reflection, which significantly reduces the work required for Spring Native / GraalVM ahead-of-time compilation hints.

@Lazy, @Primary, @Qualifier, @DependsOn [Advanced]

@Primary designates the preferred candidate when multiple beans of the same type exist; @Qualifier targets a specific bean by name when @Primary is not specific enough. @Lazy defers bean initialization until first use (useful for heavy resources or circular-dependency breaking). @DependsOn forces the container to initialize named beans before the annotated one, even when there is no direct injection relationship.

import org.springframework.beans.factory.annotation.*;
import org.springframework.context.annotation.*;

@Configuration
public class CacheConfig {

    @Bean
    @Primary  // injected by default when CacheManager is autowired
    public CacheManager redisCacheManager() {
        return new RedisCacheManager();
    }

    @Bean("local")
    public CacheManager localCacheManager() {
        return new ConcurrentMapCacheManager();
    }
}

@Service
@DependsOn("schemaInitializer")  // ensure DB schema exists before this bean
public class ProductService {

    private final CacheManager primary;    // gets RedisCacheManager
    private final CacheManager local;      // targeted by qualifier

    public ProductService(CacheManager primary,
                          @Qualifier("local") CacheManager local) {
        this.primary = primary;
        this.local   = local;
    }
}

@Component
@Lazy  // not created until first getBean() or injection
public class HeavyAnalyticsEngine {
    public HeavyAnalyticsEngine() {
        System.out.println("Initializing expensive analytics engine...");
    }
}

@RestController, @GetMapping, @PostMapping, @RequestBody, @PathVariable [Basic]

@RestController is a composed annotation combining @Controller and @ResponseBody, so every method return value is serialized directly to the HTTP response body (JSON by default via Jackson). The @GetMapping / @PostMapping shortcuts bind HTTP methods to handler methods; @PathVariable extracts URI template variables and @RequestBody deserializes the request body into a Java object.

<!-- pom.xml -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-webmvc</artifactId>
  <version>5.3.39</version>
</dependency>
import org.springframework.web.bind.annotation.*;
import java.util.List;

@RestController
@RequestMapping("/api/products")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping
    public List<Product> listAll() {
        return productService.findAll();
    }

    @GetMapping("/{id}")
    public Product getById(@PathVariable Long id) {
        return productService.findById(id);
    }

    @PostMapping
    public Product create(@RequestBody Product product) {
        return productService.save(product);
    }

    @PutMapping("/{id}")
    public Product update(@PathVariable Long id,
                          @RequestBody Product product) {
        return productService.update(id, product);
    }

    @DeleteMapping("/{id}")
    public void delete(@PathVariable Long id) {
        productService.delete(id);
    }
}

@ExceptionHandler, @ControllerAdvice & ResponseEntity<T> [Intermediate]

@ExceptionHandler methods catch exceptions thrown by handler methods and produce a structured error response. When placed in a @ControllerAdvice class they apply globally across all controllers in the application. ResponseEntity<T> gives full control over the HTTP status code, headers, and body of the response.

import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;

// Global error response shape
record ErrorResponse(int status, String error, String path) {}

@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(
            ResourceNotFoundException ex,
            jakarta.servlet.http.HttpServletRequest req) {
        ErrorResponse body = new ErrorResponse(
                404, ex.getMessage(), req.getRequestURI());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(body);
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<ErrorResponse> handleBadRequest(
            IllegalArgumentException ex,
            jakarta.servlet.http.HttpServletRequest req) {
        ErrorResponse body = new ErrorResponse(
                400, ex.getMessage(), req.getRequestURI());
        return ResponseEntity.badRequest().body(body);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleAll(
            Exception ex,
            jakarta.servlet.http.HttpServletRequest req) {
        ErrorResponse body = new ErrorResponse(
                500, "Internal Server Error", req.getRequestURI());
        return ResponseEntity.internalServerError().body(body);
    }
}

// Example: ResponseEntity usage inside a controller method
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<Order> place(@RequestBody Order order) {
        Order created = orderService.place(order);
        URI location = URI.create("/api/orders/" + created.id());
        return ResponseEntity
                .created(location)
                .header("X-Order-Id", String.valueOf(created.id()))
                .body(created);
    }
}

HandlerInterceptor for Cross-Cutting Concerns [Intermediate]

HandlerInterceptor hooks into the Spring MVC request lifecycle at three points: preHandle (before the handler method; return false to abort), postHandle (after the handler but before view rendering), and afterCompletion (after the full request, including any exceptions). Interceptors are registered via WebMvcConfigurer.addInterceptors().

import org.springframework.web.servlet.*;
import org.springframework.web.servlet.config.annotation.*;
import jakarta.servlet.http.*;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class RequestLoggingInterceptor implements HandlerInterceptor {

    private static final Logger log =
            LoggerFactory.getLogger(RequestLoggingInterceptor.class);
    private static final String START_ATTR = "requestStartMs";

    @Override
    public boolean preHandle(HttpServletRequest req,
                             HttpServletResponse res,
                             Object handler) {
        req.setAttribute(START_ATTR, System.currentTimeMillis());
        log.info("--> {} {}", req.getMethod(), req.getRequestURI());
        return true;  // continue processing
    }

    @Override
    public void afterCompletion(HttpServletRequest req,
                                HttpServletResponse res,
                                Object handler,
                                Exception ex) {
        long start = (long) req.getAttribute(START_ATTR);
        long elapsed = System.currentTimeMillis() - start;
        log.info("<-- {} {} {}ms", res.getStatus(),
                req.getRequestURI(), elapsed);
    }
}

@org.springframework.context.annotation.Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new RequestLoggingInterceptor())
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/health");
    }
}

ModelAndView — Combining Model Data with View Resolution

Spring 5

ModelAndView is a holder for both the model (data attributes) and view (name or View instance) returned from a controller handler method. Spring MVC's DispatcherServlet uses it to invoke ViewResolver and render the response.

Basic Usage

@Controller
public class GreetingController {

    @GetMapping("/greet")
    public ModelAndView greet(@RequestParam String name) {
        ModelAndView mav = new ModelAndView("greet"); // view name → greet.html / greet.jsp
        mav.addObject("greeting", "Hello, " + name + "!");
        mav.addObject("timestamp", LocalDateTime.now());
        return mav;
    }
}

Intermediate — Pre-populating model with @ModelAttribute

@Controller
@RequestMapping("/users")
public class UserController {

    @ModelAttribute("roles")
    public List<String> loadRoles() {
        return List.of("ADMIN", "USER", "GUEST"); // added to every ModelAndView in this controller
    }

    @GetMapping("/{id}")
    public ModelAndView show(@PathVariable Long id) {
        ModelAndView mav = new ModelAndView("users/detail");
        mav.addObject("user", userService.findById(id)); // "roles" already in model from above
        return mav;
    }
}
Modern alternative: Most Spring MVC controllers now return a String view name (or ResponseEntity) and populate the model via Model parameter injection. ModelAndView remains useful when you need to determine the view name programmatically or return different views from a single method.

Async Request Processing: Callable<?> and DeferredResult<T> [Advanced]

Spring MVC can release the Servlet container thread while the response is still pending, allowing the container to handle more concurrent requests with fewer threads. Returning a Callable<T> offloads the work to Spring's task executor thread pool. DeferredResult<T> is more flexible — the result can be set from any thread (e.g. a message broker callback) and supports configurable timeouts.

import org.springframework.web.bind.annotation.*;
import org.springframework.web.context.request.async.*;
import java.util.concurrent.*;

@RestController
@RequestMapping("/api/reports")
public class ReportController {

    private final ReportService reportService;
    private final TaskExecutor taskExecutor;

    public ReportController(ReportService reportService,
                            TaskExecutor taskExecutor) {
        this.reportService = reportService;
        this.taskExecutor  = taskExecutor;
    }

    // Servlet thread released immediately; Spring runs work in taskExecutor
    @GetMapping("/callable/{id}")
    public Callable<Report> generateCallable(@PathVariable Long id) {
        return () -> reportService.generateHeavyReport(id);
    }

    // DeferredResult — result set externally (e.g. from a message listener)
    @GetMapping("/deferred/{id}")
    public DeferredResult<Report> generateDeferred(@PathVariable Long id) {
        DeferredResult<Report> result = new DeferredResult<>(30_000L);  // 30 s timeout

        result.onTimeout(() ->
            result.setErrorResult(new TimeoutException("Report timed out"))
        );

        taskExecutor.execute(() -> {
            try {
                result.setResult(reportService.generateHeavyReport(id));
            } catch (Exception e) {
                result.setErrorResult(e);
            }
        });

        return result;  // servlet thread returns here immediately
    }
}
Servlet 3.1 requirement Async processing requires a Servlet 3.0+ container and must be enabled on the DispatcherServlet. Spring Boot auto-configures this. For WebFlux consider switching to reactive controllers returning Mono/Flux instead.

Reactive vs Imperative — Mono and Flux [Basic]

Spring WebFlux (introduced in Spring 5.0) is built on Project Reactor and implements the Reactive Streams specification. Instead of blocking threads while waiting for I/O, reactive code describes a pipeline of transformations over asynchronous data. Mono<T> represents a stream of zero or one item; Flux<T> represents a stream of zero to N items — both are lazy and only execute when subscribed.

<!-- pom.xml -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-webflux</artifactId>
  <version>5.3.39</version>
</dependency>
<dependency>
  <groupId>io.projectreactor</groupId>
  <artifactId>reactor-core</artifactId>
  <version>3.4.38</version>
</dependency>
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

public class ReactiveIntro {

    public static void main(String[] args) {
        // Mono — exactly one result (or empty/error)
        Mono<String> greeting = Mono.just("Hello, Spring 5!");

        // Flux — zero to N results
        Flux<Integer> numbers = Flux.range(1, 5);

        // Pipeline: transform and filter — nothing executes until subscribe()
        numbers
            .map(n -> n * n)
            .filter(n -> n > 5)
            .subscribe(
                value  -> System.out.println("Value: " + value),
                error  -> System.err.println("Error: " + error),
                ()     -> System.out.println("Complete")
            );

        // Blocking subscriber (only for demo / tests — never in reactive handlers)
        String result = greeting.block();
        System.out.println(result);
    }
}
Never block inside a reactive pipeline Calling .block(), Thread.sleep(), or any blocking I/O inside a reactive chain starves the non-blocking event loop threads. Use reactive operators (flatMap, then, zip) to compose async operations.

@RestController with Mono<T> Return Types [Basic]

WebFlux reuses Spring MVC annotations like @RestController and @GetMapping. The key difference is that handler methods return Mono<T> (single result) or Flux<T> (collection), signaling to the framework that the response is asynchronous. The container subscribes to the publisher and writes the serialized response when items arrive.

import org.springframework.web.bind.annotation.*;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

@RestController
@RequestMapping("/api/users")
public class UserController {

    private final ReactiveUserRepository userRepository;

    public UserController(ReactiveUserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @GetMapping
    public Flux<User> listAll() {
        return userRepository.findAll();  // streams each user as it arrives
    }

    @GetMapping("/{id}")
    public Mono<User> getById(@PathVariable Long id) {
        return userRepository.findById(id)
                .switchIfEmpty(Mono.error(
                    new ResourceNotFoundException("User not found: " + id)));
    }

    @PostMapping
    public Mono<User> create(@RequestBody Mono<User> userMono) {
        return userMono.flatMap(userRepository::save);
    }
}

WebClient — Reactive HTTP Client [Intermediate]

WebClient is the reactive, non-blocking replacement for the deprecated RestTemplate. It is part of spring-webflux and can be used even in traditional Spring MVC applications. It supports request/response streaming, exchange functions, and integrates with Reactor operators for composing complex HTTP call sequences.

import org.springframework.web.reactive.function.client.WebClient;
import reactor.core.publisher.Mono;

public class ExternalApiService {

    private final WebClient webClient;

    public ExternalApiService(WebClient.Builder builder) {
        this.webClient = builder
                .baseUrl("https://api.example.com")
                .defaultHeader("Accept", "application/json")
                .build();
    }

    public Mono<Product> fetchProduct(Long id) {
        return webClient.get()
                .uri("/products/{id}", id)
                .retrieve()
                .onStatus(status -> status.is4xxClientError(),
                          resp  -> resp.bodyToMono(String.class)
                                       .map(ResourceNotFoundException::new))
                .bodyToMono(Product.class);
    }

    public Mono<Order> placeOrder(Order order) {
        return webClient.post()
                .uri("/orders")
                .bodyValue(order)
                .retrieve()
                .bodyToMono(Order.class);
    }

    // Parallel calls with zip
    public Mono<CombinedResult> fetchBoth(Long productId, Long userId) {
        Mono<Product> productMono = fetchProduct(productId);
        Mono<User>    userMono    = fetchUser(userId);
        return Mono.zip(productMono, userMono,
                (product, user) -> new CombinedResult(product, user));
    }

    private Mono<User> fetchUser(Long userId) {
        return webClient.get()
                .uri("/users/{id}", userId)
                .retrieve()
                .bodyToMono(User.class);
    }
}
RestTemplate deprecation RestTemplate was deprecated in Spring 5.0 for new code. Migrate to WebClient even in servlet-based apps — it requires adding spring-webflux to the classpath but does not require switching the web stack.

Router Functions — Functional Web Endpoints [Advanced]

Spring 5 introduced a functional, lambda-based alternative to annotated controllers for WebFlux. A RouterFunction<ServerResponse> maps request predicates to HandlerFunction<ServerResponse> implementations. This style is entirely type-safe, easily unit-testable without a server, and composes naturally with reactive operators.

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.reactive.function.server.*;
import reactor.core.publisher.Mono;

import static org.springframework.web.reactive.function.server.RequestPredicates.*;
import static org.springframework.web.reactive.function.server.RouterFunctions.route;
import static org.springframework.web.reactive.function.server.ServerResponse.*;

@Configuration
public class RouterConfig {

    @Bean
    public RouterFunction<ServerResponse> productRouter(ProductHandler handler) {
        return route()
                .GET("/functional/products",      handler::listAll)
                .GET("/functional/products/{id}", handler::getById)
                .POST("/functional/products",     handler::create)
                .DELETE("/functional/products/{id}", handler::delete)
                .build();
    }
}

import org.springframework.stereotype.Component;
import org.springframework.web.reactive.function.server.*;

@Component
public class ProductHandler {

    private final ReactiveProductRepository repository;

    public ProductHandler(ReactiveProductRepository repository) {
        this.repository = repository;
    }

    public Mono<ServerResponse> listAll(ServerRequest request) {
        return ok().body(repository.findAll(), Product.class);
    }

    public Mono<ServerResponse> getById(ServerRequest request) {
        Long id = Long.valueOf(request.pathVariable("id"));
        return repository.findById(id)
                .flatMap(p  -> ok().bodyValue(p))
                .switchIfEmpty(notFound().build());
    }

    public Mono<ServerResponse> create(ServerRequest request) {
        return request.bodyToMono(Product.class)
                .flatMap(repository::save)
                .flatMap(p -> created(
                    request.uriBuilder().path("/{id}").build(p.id()))
                    .bodyValue(p));
    }

    public Mono<ServerResponse> delete(ServerRequest request) {
        Long id = Long.valueOf(request.pathVariable("id"));
        return repository.deleteById(id).then(noContent().build());
    }
}

JdbcTemplate Basics [Basic]

JdbcTemplate is Spring's classic JDBC abstraction that eliminates boilerplate resource management (opening/closing connections, catching SQLExceptions) while keeping full control of SQL. The three most common methods are query() for SELECT returning a list, queryForObject() for single-row SELECT, and update() for INSERT/UPDATE/DELETE.

<!-- pom.xml -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-jdbc</artifactId>
  <version>5.3.39</version>
</dependency>
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.RowMapper;
import org.springframework.stereotype.Repository;
import java.util.List;
import java.util.Optional;

@Repository
public class ProductJdbcRepository {

    private final JdbcTemplate jdbc;

    private static final RowMapper<Product> PRODUCT_ROW_MAPPER = (rs, rowNum) ->
            new Product(
                rs.getLong("id"),
                rs.getString("name"),
                rs.getBigDecimal("price")
            );

    public ProductJdbcRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<Product> findAll() {
        return jdbc.query("SELECT id, name, price FROM products", PRODUCT_ROW_MAPPER);
    }

    public Optional<Product> findById(Long id) {
        List<Product> results = jdbc.query(
                "SELECT id, name, price FROM products WHERE id = ?",
                PRODUCT_ROW_MAPPER, id);
        return results.isEmpty() ? Optional.empty() : Optional.of(results.get(0));
    }

    public int save(Product product) {
        return jdbc.update(
                "INSERT INTO products (name, price) VALUES (?, ?)",
                product.name(), product.price());
    }

    public int delete(Long id) {
        return jdbc.update("DELETE FROM products WHERE id = ?", id);
    }

    public int count() {
        Integer result = jdbc.queryForObject(
                "SELECT COUNT(*) FROM products", Integer.class);
        return result != null ? result : 0;
    }
}

@Transactional — Propagation and Isolation [Intermediate]

Spring's @Transactional demarcates transaction boundaries declaratively via AOP proxy. The most important attributes are propagation (what happens when a transactional method calls another transactional method) and isolation (what concurrent transactions can see of each other's in-flight data). The default propagation is REQUIRED (join existing or create new); the default isolation is DEFAULT (delegate to the database, typically READ_COMMITTED).

import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.stereotype.Service;

@Service
@Transactional  // class-level default: REQUIRED propagation
public class OrderService {

    private final OrderRepository orderRepo;
    private final AuditService auditService;
    private final PaymentService paymentService;

    public OrderService(OrderRepository orderRepo,
                        AuditService auditService,
                        PaymentService paymentService) {
        this.orderRepo      = orderRepo;
        this.auditService   = auditService;
        this.paymentService = paymentService;
    }

    // REQUIRED (default): joins caller's transaction, or opens a new one
    public Order place(Order order) {
        Order saved = orderRepo.save(order);
        auditService.log("ORDER_PLACED", saved.id()); // same transaction
        paymentService.charge(saved);                  // REQUIRES_NEW (below)
        return saved;
    }

    // REQUIRES_NEW: always suspends caller tx and starts its own
    // Audit is persisted even if the outer tx rolls back
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAuditEntry(String event, Long entityId) {
        // persisted in its own separate transaction
        auditService.log(event, entityId);
    }

    // NESTED: savepoint within the outer tx — inner rollback doesn't affect outer
    @Transactional(propagation = Propagation.NESTED)
    public void processOptionalStep(Order order) {
        try {
            orderRepo.processOptional(order);
        } catch (OptionalStepException e) {
            // rolls back to savepoint, outer tx continues
        }
    }

    // Serializable isolation: strongest, prevents phantom reads
    @Transactional(isolation = Isolation.SERIALIZABLE,
                   timeout = 10,
                   readOnly = false)
    public void transferStock(Long fromId, Long toId, int qty) {
        orderRepo.decrementStock(fromId, qty);
        orderRepo.incrementStock(toId, qty);
    }
}
Self-invocation bypass Calling a @Transactional method from within the same class bypasses the AOP proxy and the transaction is NOT started. Extract the method to a separate Spring bean to ensure the proxy intercepts the call.

NamedParameterJdbcTemplate & TransactionSynchronizationManager [Advanced]

NamedParameterJdbcTemplate replaces positional ? placeholders with named parameters like :name, making complex queries more readable and maintainable. TransactionSynchronizationManager provides programmatic access to the current transaction context and allows registering callbacks (TransactionSynchronization) to run logic after commit, after rollback, or after completion.

import org.springframework.jdbc.core.namedparam.*;
import org.springframework.transaction.support.TransactionSynchronizationManager;
import org.springframework.transaction.support.TransactionSynchronizationAdapter;
import org.springframework.stereotype.Repository;
import java.util.List;
import java.util.Map;

@Repository
public class AdvancedProductRepository {

    private final NamedParameterJdbcTemplate namedJdbc;

    public AdvancedProductRepository(NamedParameterJdbcTemplate namedJdbc) {
        this.namedJdbc = namedJdbc;
    }

    public List<Product> findByCategoryAndPriceRange(
            String category, double minPrice, double maxPrice) {

        String sql = "SELECT id, name, price FROM products " +
                     "WHERE category = :category " +
                     "  AND price BETWEEN :minPrice AND :maxPrice " +
                     "ORDER BY price";

        MapSqlParameterSource params = new MapSqlParameterSource()
                .addValue("category", category)
                .addValue("minPrice",  minPrice)
                .addValue("maxPrice",  maxPrice);

        return namedJdbc.query(sql, params,
                (rs, rowNum) -> new Product(
                    rs.getLong("id"),
                    rs.getString("name"),
                    rs.getBigDecimal("price")));
    }

    // Register a post-commit hook using TransactionSynchronizationManager
    public void saveWithCacheEviction(Product product) {
        String sql = "INSERT INTO products (name, price) VALUES (:name, :price)";
        namedJdbc.update(sql,
                Map.of("name", product.name(), "price", product.price()));

        if (TransactionSynchronizationManager.isActualTransactionActive()) {
            TransactionSynchronizationManager.registerSynchronization(
                new TransactionSynchronizationAdapter() {
                    @Override
                    public void afterCommit() {
                        // Only evict cache after the transaction successfully commits
                        System.out.println("TX committed — evicting product cache");
                    }
                });
        }
    }
}

@WebMvcTest & MockMvc — Controller Slice Tests [Intermediate]

@WebMvcTest is a slice test that loads only the MVC layer — controllers, @ControllerAdvice, filters, and converters — without starting an actual HTTP server or loading service/repository beans. Dependencies that are not in the MVC layer must be provided as mocks. MockMvc executes requests against the DispatcherServlet in-process, making assertions on status, headers, and JSON body.

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import static org.mockito.BDDMockito.given;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(ProductController.class)  // loads ONLY ProductController + MVC layer
class ProductControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean  // Spring-managed mock injected into ProductController
    private ProductService productService;

    @Test
    void getProduct_returns200WithJson() throws Exception {
        Product product = new Product(1L, "Widget", new java.math.BigDecimal("9.99"));
        given(productService.findById(1L)).willReturn(product);

        mockMvc.perform(get("/api/products/1")
                        .accept(MediaType.APPLICATION_JSON))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.id").value(1))
               .andExpect(jsonPath("$.name").value("Widget"))
               .andExpect(jsonPath("$.price").value(9.99));
    }

    @Test
    void getProduct_notFound_returns404() throws Exception {
        given(productService.findById(99L))
                .willThrow(new ResourceNotFoundException("Product not found: 99"));

        mockMvc.perform(get("/api/products/99"))
               .andExpect(status().isNotFound())
               .andExpect(jsonPath("$.error").value("Product not found: 99"));

@MockBean vs @SpyBean [Intermediate]

@MockBean replaces a Spring bean in the application context with a Mockito mock (all methods return default values unless stubbed). @SpyBean wraps an existing Spring bean in a Mockito spy — real methods execute unless explicitly stubbed — making it useful when you want to test the real implementation but verify interactions or override one method.

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.boot.test.mock.mockito.SpyBean;

import static org.mockito.BDDMockito.*;
import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest
class NotificationIntegrationTest {

    @Autowired
    private OrderService orderService;

    // Full mock — all methods are no-ops unless stubbed
    @MockBean
    private EmailClient emailClient;

    // Real bean, wrapped in spy — only doReturn/when overrides specific calls
    @SpyBean
    private AuditService auditService;

    @Test
    void placeOrder_sendsEmailAndAudits() {
        Order order = new Order("product-42", 1);

        // Stub emailClient to track calls without sending real email
        willDoNothing().given(emailClient).send(any(EmailMessage.class));

        orderService.place(order);

        // Verify email was attempted
        then(emailClient).should(times(1)).send(any(EmailMessage.class));

        // Real auditService.log() ran — verify it was called
        then(auditService).should(atLeastOnce()).log(eq("ORDER_PLACED"), anyLong());
    }
}

WebTestClient, @TestConfiguration & Context Caching [Advanced]

WebTestClient is the reactive equivalent of MockMvc, used to test WebFlux controllers either against a running server or bound to the ApplicationContext directly. @TestConfiguration adds beans to the test context without replacing the production configuration. Spring caches the ApplicationContext between test classes — any modification (new mocks, properties, beans) creates a new context, slowing the suite.

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.reactive.WebFluxTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.context.annotation.Bean;
import org.springframework.test.context.TestPropertySource;
import org.springframework.test.web.reactive.server.WebTestClient;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import static org.mockito.BDDMockito.given;

@WebFluxTest(UserController.class)
@TestPropertySource(properties = "feature.flag.new-ui=true")
class UserControllerWebFluxTest {

    @Autowired
    private WebTestClient webTestClient;

    @MockBean
    private ReactiveUserRepository userRepository;

    @Test
    void listUsers_returnsFluxOfUsers() {
        given(userRepository.findAll())
                .willReturn(Flux.just(
                    new User(1L, "Alice"),
                    new User(2L, "Bob")));

        webTestClient.get()
                .uri("/api/users")
                .exchange()
                .expectStatus().isOk()
                .expectBodyList(User.class)
                .hasSize(2)
                .contains(new User(1L, "Alice"));
    }

    @Test
    void getUser_notFound_returns404() {
        given(userRepository.findById(99L)).willReturn(Mono.empty());

        webTestClient.get()
                .uri("/api/users/99")
                .exchange()
                .expectStatus().isNotFound();
    }

    // @TestConfiguration — adds extra beans without replacing production config
    @org.springframework.boot.test.context.TestConfiguration
    static class TestConfig {
        @Bean
        public TestAuditRecorder testAuditRecorder() {
            return new TestAuditRecorder();  // captured audit entries for assertions
        }
    }
}
Context caching rules Spring caches the context keyed on the set of configuration classes, active profiles, property sources, and context loader. Keep slice tests using the same @MockBean / @SpyBean set to share a cached context. Every unique combination creates a separate context — minimize them for faster CI runs.

@Nullable / @NonNull — Null-Safety Annotations [Basic]

Spring 5 introduced package-level null-safety annotations (@NonNullApi, @NonNullFields in org.springframework.lang), making the entire Spring Framework API null-safe and IDE-verifiable. Individual parameters or return types that can legitimately be null are annotated with @Nullable. IDEs (IntelliJ IDEA, Eclipse) and tools like SpotBugs can now warn at development time rather than throwing NullPointerException at runtime.

<!-- pom.xml — included transitively in spring-core -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-core</artifactId>
  <version>5.3.39</version>
</dependency>
import org.springframework.lang.NonNull;
import org.springframework.lang.Nullable;

public class UserService {

    /**
     * Returns the user, guaranteed non-null — throws if not found.
     */
    @NonNull
    public User findById(@NonNull Long id) {
        return userRepository.findById(id)
                .orElseThrow(() -> new ResourceNotFoundException("User: " + id));
    }

    /**
     * Returns null when no user matches the email — caller must check.
     */
    @Nullable
    public User findByEmail(@NonNull String email) {
        return userRepository.findByEmail(email).orElse(null);
    }

    public void updateProfile(@NonNull Long id,
                               @Nullable String displayName,
                               @Nullable String avatarUrl) {
        User user = findById(id);
        if (displayName != null) user.setDisplayName(displayName);
        if (avatarUrl   != null) user.setAvatarUrl(avatarUrl);
        userRepository.save(user);
    }
}

JUnit 5 (Jupiter) as First-Class Citizen [Intermediate]

Spring 5 dropped support for JUnit 4 in the core spring-test module and made JUnit 5 (Jupiter) the primary testing framework. The @ExtendWith(SpringExtension.class) annotation replaces JUnit 4's @RunWith(SpringJUnit4ClassRunner.class). Spring Boot 2.1+ auto-applies SpringExtension via @SpringBootTest and other slice annotations, so you rarely need to write it explicitly.

import org.junit.jupiter.api.*;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.test.context.junit.jupiter.SpringExtension;
import org.junit.jupiter.api.extension.ExtendWith;
import org.springframework.test.context.ContextConfiguration;

import static org.assertj.core.api.Assertions.assertThat;
import static org.junit.jupiter.api.Assertions.assertThrows;

// @ExtendWith replaces JUnit 4's @RunWith
@ExtendWith(SpringExtension.class)
@ContextConfiguration(classes = AppConfig.class)
class UserServiceTest {

    @Autowired
    private UserService userService;

    @Test
    @DisplayName("findById returns user when present")
    void findById_returnsUser() {
        User user = userService.findById(1L);
        assertThat(user).isNotNull();
        assertThat(user.id()).isEqualTo(1L);
    }

    @Test
    @DisplayName("findById throws when not found")
    void findById_throwsWhenMissing() {
        assertThrows(ResourceNotFoundException.class,
                () -> userService.findById(999L));
    }

    // JUnit 5 parameterized tests integrate cleanly with Spring context
    @ParameterizedTest
    @CsvSource({ "alice@example.com, Alice", "bob@example.com, Bob" })
    void findByEmail_returnsCorrectUser(String email, String expectedName) {
        User user = userService.findByEmail(email);
        assertThat(user).isNotNull();
        assertThat(user.name()).isEqualTo(expectedName);
    }

    @BeforeEach
    void setUp() {
        // JUnit 5 lifecycle hooks — Spring beans already injected here
    }
}

ApplicationContext.registerBean() — Functional Style [Advanced]

Spring 5 added the registerBean() method to GenericApplicationContext as a functional bean registration API. Unlike @Bean methods (which rely on CGLIB proxying and reflection), this API is lambda-based, avoids annotation processing, and allows programmatic customization of every bean definition attribute — a key enabler for Spring Native / GraalVM ahead-of-time compilation.

import org.springframework.context.support.GenericApplicationContext;
import org.springframework.beans.factory.config.BeanDefinition;

public class FunctionalAppBootstrap {

    public static void main(String[] args) {
        GenericApplicationContext ctx = new GenericApplicationContext();

        // Simple registration with supplier
        ctx.registerBean(AppConfig.class, AppConfig::new);

        // Registration with customizer lambda — set scope, lazy, primary flags
        ctx.registerBean("userRepository", UserRepository.class,
            () -> new UserRepository(ctx.getBean(DataSource.class)),
            bd -> {
                bd.setScope(BeanDefinition.SCOPE_SINGLETON);
                bd.setLazyInit(false);
                bd.setPrimary(true);
            });

        ctx.registerBean(UserService.class,
            () -> new UserService(ctx.getBean(UserRepository.class)));

        ctx.registerBean(ProductService.class, ProductService::new);

        ctx.refresh();

        // Use the context
        UserService userService = ctx.getBean(UserService.class);
        System.out.println("UserService ready: " + userService.getClass().getSimpleName());

        ctx.close();
    }
}

Classpath Scanning Improvements — Component Index [Advanced]

Spring 5.0 introduced a compile-time component index (spring-context-indexer) to replace expensive runtime classpath scanning. During the build, an annotation processor generates META-INF/spring.components listing all candidate components. At startup the container reads the index instead of scanning JARs, reducing startup time significantly in large applications.

<!-- pom.xml — annotation processor; compile scope only -->
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context-indexer</artifactId>
  <version>5.3.39</version>
  <optional>true</optional>
</dependency>
// No code changes needed — the annotation processor runs at compile time.
// It generates: META-INF/spring.components
// Contents look like:
//   com.example.service.UserService=org.springframework.stereotype.Component
//   com.example.repo.UserRepository=org.springframework.stereotype.Component

// Spring automatically uses the index when present.
// Verify it's active by setting the log level:
// logging.level.org.springframework.context.index=DEBUG

// To disable the index for debugging (forces full classpath scan):
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;

@Configuration
@ComponentScan(
    basePackages = "com.example",
    useDefaultFilters = true
    // Spring uses the index when META-INF/spring.components exists
    // and all packages are indexed
)
public class AppConfig {
    // No changes required here — index is transparent
}
Startup improvement The component index is most beneficial in large monoliths with hundreds of beans spread across many JARs. Spring Boot applications with a few dozen beans may see minimal benefit, but it becomes significant in modular microservice platforms with shared library JARs.
