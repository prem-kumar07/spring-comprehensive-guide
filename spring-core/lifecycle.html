Spring Bean Lifecycle

The Spring Bean Lifecycle is the complete sequence of steps that the Spring IoC container executes from the moment it creates a bean to the moment it destroys it. Understanding this lifecycle lets you hook into exactly the right phase — whether you need to validate configuration after injection, warm a cache before your first request, or release database connections on shutdown. Spring provides a rich set of interfaces and annotations at each phase, giving you fine-grained control without modifying the container itself.

Stage-by-Stage Deep Dive

Stage 1 — Instantiation (Constructor)

Spring calls the bean's constructor (or a factory method) to create the object instance. If you have multiple constructors, Spring uses the one annotated with @Autowired, or the single no-arg constructor by default. At this point no dependencies have been injected — the object is just allocated.

import org.springframework.stereotype.Component;

@Component
public class OrderService {

    private final PaymentService paymentService;

    // Spring calls this constructor during instantiation
    public OrderService(PaymentService paymentService) {
        System.out.println("OrderService constructor called");
        this.paymentService = paymentService;
    }
}
Practice tip Use constructor injection rather than field injection — it makes the dependency explicit at instantiation time, and the field can be final, which prevents accidental reassignment.

Stage 2 — Populate Properties (Setter / Field Injection)

After construction, Spring resolves all @Autowired fields and setter methods. It also applies values from @Value expressions. This is when the bean's dependency graph is fully satisfied.

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

@Component
public class NotificationService {

    // Field injection — populated after construction
    @Autowired
    private EmailClient emailClient;

    @Value("${notifications.enabled:true}")
    private boolean enabled;

    // Setter injection — also populated at this stage
    private SmsClient smsClient;

    @Autowired
    public void setSmsClient(SmsClient smsClient) {
        this.smsClient = smsClient;
    }
}

Stage 3 — BeanNameAware.setBeanName()

If the bean implements BeanNameAware, Spring calls setBeanName(String name) passing the bean's registered name in the container. This is the first of the Aware interface callbacks and fires immediately after property population.

import org.springframework.beans.factory.BeanNameAware;
import org.springframework.stereotype.Component;

@Component
public class MyService implements BeanNameAware {
    private String beanName;

    @Override
    public void setBeanName(String name) {
        this.beanName = name;
        System.out.println("Bean name set to: " + name);
    }
}
When to use Rarely needed in application code — mostly useful when writing generic infrastructure components (like a custom scope or a factory) that need to know their own registration name for logging or lookup purposes.

Stage 4 — BeanClassLoaderAware.setBeanClassLoader()

BeanClassLoaderAware gives the bean a reference to the ClassLoader used to load it. This is useful for frameworks that need to dynamically load classes by name using the same classloader as the bean.

import org.springframework.beans.factory.BeanClassLoaderAware;
import org.springframework.stereotype.Component;

@Component
public class PluginLoader implements BeanClassLoaderAware {
    private ClassLoader classLoader;

    @Override
    public void setBeanClassLoader(ClassLoader classLoader) {
        this.classLoader = classLoader;
    }

    public Class<?> loadPluginClass(String className) throws ClassNotFoundException {
        return classLoader.loadClass(className);
    }
}

Stage 5 — BeanFactoryAware.setBeanFactory()

BeanFactoryAware injects the owning BeanFactory into the bean. This lets a bean programmatically retrieve other beans from the container — though this is generally an anti-pattern since it couples your code to the Spring API. Prefer constructor injection.

import org.springframework.beans.BeansException;
import org.springframework.beans.factory.BeanFactory;
import org.springframework.beans.factory.BeanFactoryAware;
import org.springframework.stereotype.Component;

@Component
public class BeanLocator implements BeanFactoryAware {
    private BeanFactory beanFactory;

    @Override
    public void setBeanFactory(BeanFactory beanFactory) throws BeansException {
        this.beanFactory = beanFactory;
    }

    public Object getBean(String name) {
        return beanFactory.getBean(name);
    }
}

Stage 6 — EnvironmentAware.setEnvironment()

EnvironmentAware provides the bean with the Environment object, which gives access to property sources, profiles, and system properties. Useful for infrastructure beans that need to read configuration values programmatically.

import org.springframework.context.EnvironmentAware;
import org.springframework.core.env.Environment;
import org.springframework.stereotype.Component;

@Component
public class ConfigInspector implements EnvironmentAware {
    private Environment environment;

    @Override
    public void setEnvironment(Environment environment) {
        this.environment = environment;
    }

    public String getActiveProfiles() {
        return String.join(", ", environment.getActiveProfiles());
    }

    public String getProperty(String key) {
        return environment.getProperty(key, "not set");
    }
}

Stage 7 — ApplicationContextAware.setApplicationContext()

ApplicationContextAware is the most commonly used Aware interface. It injects the full ApplicationContext, giving access to the entire bean registry, event publishing, message sources, and resource loading. A common pattern is a static holder so non-Spring code can access the context.

import org.springframework.beans.BeansException;
import org.springframework.context.ApplicationContext;
import org.springframework.context.ApplicationContextAware;
import org.springframework.stereotype.Component;

@Component
public class AppContextHolder implements ApplicationContextAware {
    private static ApplicationContext context;

    @Override
    public void setApplicationContext(ApplicationContext ctx) throws BeansException {
        AppContextHolder.context = ctx;
    }

    public static ApplicationContext getContext() {
        return context;
    }
}
Thread safety The static field pattern above is safe because setApplicationContext is called once during startup before any request threads run. Do not mutate the field after initialization.

Stage 8 — BeanPostProcessor.postProcessBeforeInitialization()

BeanPostProcessor is a container extension point: implementations are called for every bean in the context, not just beans that implement a specific interface. The postProcessBeforeInitialization hook fires after the Aware callbacks but before the bean's own init methods. You can return the original bean or a wrapper/proxy.

import org.springframework.beans.BeansException;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.stereotype.Component;

@Component
public class LoggingBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName)
            throws BeansException {
        System.out.println("Before init: " + beanName);
        return bean; // must return the bean (or a wrapped proxy)
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName)
            throws BeansException {
        System.out.println("After init: " + beanName);
        return bean;
    }
}
How Spring AOP works Spring's AOP proxy creation happens inside a BeanPostProcessor (AbstractAutoProxyCreator). When you annotate a class with @Transactional, it's a BeanPostProcessor that wraps the bean in a proxy at this stage.

Stage 9 — @PostConstruct / InitializingBean.afterPropertiesSet()

Two hooks fire at this stage in order: the JSR-250 @PostConstruct method first, then InitializingBean.afterPropertiesSet(). Both run after all dependencies have been injected. Use them to perform any initialization that requires access to injected dependencies — warming caches, opening connections, validating configuration.

import jakarta.annotation.PostConstruct;
import org.springframework.stereotype.Component;
import java.util.HashMap;
import java.util.Map;

@Component
public class CacheService {
    private Map<String, String> cache;

    @PostConstruct
    public void init() {
        // Runs after all dependencies injected
        this.cache = new HashMap<>();
        System.out.println("CacheService initialized");
    }
}

InitializingBean.afterPropertiesSet() is the programmatic alternative — it avoids the Jakarta annotation dependency but couples your class to the Spring API:

import org.springframework.beans.factory.InitializingBean;
import org.springframework.stereotype.Component;
import java.util.HashMap;
import java.util.Map;

@Component
public class CacheServiceAlt implements InitializingBean {
    private Map<String, String> cache;

    @Override
    public void afterPropertiesSet() {
        this.cache = new HashMap<>();
        System.out.println("CacheServiceAlt initialized via afterPropertiesSet");
    }
}

Stage 10 — Custom init-method

A custom init method fires after afterPropertiesSet(). Declare it on a @Bean definition with initMethod, or in XML with init-method. This lets you hook lifecycle behavior into third-party classes you can't annotate.

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

// Third-party class — cannot add @PostConstruct
public class ConnectionPool {
    private int size;

    public ConnectionPool(int size) {
        this.size = size;
    }

    // Custom init: called by Spring after afterPropertiesSet
    public void openConnections() {
        System.out.println("Opening " + size + " connections in pool");
    }

    public void closeConnections() {
        System.out.println("Closing all connections in pool");
    }
}

@Configuration
public class InfraConfig {

    @Bean(initMethod = "openConnections", destroyMethod = "closeConnections")
    public ConnectionPool connectionPool() {
        return new ConnectionPool(10);
    }
}

Stage 11 — BeanPostProcessor.postProcessAfterInitialization()

The second BeanPostProcessor hook fires after all init callbacks complete. This is when AOP proxies are typically installed — if the bean needs to be wrapped, the proxy replaces the original instance in the container from this point on. The object returned here is what callers will receive when they request this bean.

import org.springframework.beans.BeansException;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.stereotype.Component;
import java.lang.reflect.Proxy;

@Component
public class MetricsBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName)
            throws BeansException {
        // Only wrap beans annotated with @Timed (illustrative)
        if (bean.getClass().isAnnotationPresent(Timed.class)) {
            return Proxy.newProxyInstance(
                bean.getClass().getClassLoader(),
                bean.getClass().getInterfaces(),
                (proxy, method, args) -> {
                    long start = System.nanoTime();
                    Object result = method.invoke(bean, args);
                    System.out.println(method.getName() + " took "
                        + (System.nanoTime() - start) + "ns");
                    return result;
                }
            );
        }
        return bean;
    }
}

// Marker annotation used above
import java.lang.annotation.*;
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@interface Timed {}

Stage 12 — Bean Ready (In Use)

At this point the bean is fully initialized and stored in the container. Calls to applicationContext.getBean() or any injection point will receive this bean (or its proxy). The bean remains in this state until the container begins shutdown.

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class Main {
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(AppConfig.class)) {
            // All beans are fully initialized here — ready for use
            OrderService orders = ctx.getBean(OrderService.class);
            orders.createOrder("item-42");
        }
        // ctx.close() triggers destroy phase automatically (try-with-resources)
    }
}

Stage 13 — @PreDestroy / DisposableBean.destroy()

When the container is closed (e.g., context.close() or JVM shutdown hook), Spring calls destroy callbacks in reverse order. The @PreDestroy method fires first, then DisposableBean.destroy(). Use these to release resources: close database connections, flush caches, stop background threads.

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Component;
import java.sql.Connection;
import java.util.ArrayList;
import java.util.List;

@Component
public class ConnectionPool {
    private List<Connection> connections;

    @PostConstruct
    public void initialize() {
        connections = new ArrayList<>();
        // open connections...
    }

    @PreDestroy
    public void shutdown() {
        // Called before bean is destroyed — clean up resources
        connections.forEach(c -> { try { c.close(); } catch (Exception ignored) {} });
        System.out.println("ConnectionPool shut down");
    }
}

DisposableBean.destroy() is the programmatic equivalent:

import org.springframework.beans.factory.DisposableBean;
import org.springframework.stereotype.Component;

@Component
public class BackgroundScheduler implements DisposableBean {
    private Thread workerThread;

    public void start() {
        workerThread = new Thread(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                // ... background work
            }
        });
        workerThread.start();
    }

    @Override
    public void destroy() throws Exception {
        if (workerThread != null) {
            workerThread.interrupt();
            workerThread.join(5000);
        }
        System.out.println("BackgroundScheduler stopped");
    }
}

Stage 14 — Custom destroy-method

A custom destroy method fires after DisposableBean.destroy(). Declare it on a @Bean with destroyMethod. Spring also has a convention: if a bean has a close() or shutdown() method and no destroyMethod is specified, Spring infers it automatically for @Bean declarations.

// Already shown in Stage 10 — same @Bean definition handles both:
@Bean(initMethod = "openConnections", destroyMethod = "closeConnections")
public ConnectionPool connectionPool() {
    return new ConnectionPool(10);
}

// Spring also auto-detects close()/shutdown() — no annotation needed:
@Bean  // Spring will call pool.close() automatically
public HikariDataSource dataSource() {
    HikariDataSource ds = new HikariDataSource();
    ds.setJdbcUrl("jdbc:h2:mem:test");
    return ds; // HikariDataSource has close() — Spring infers it
}

Scope Comparison: Singleton vs Prototype

Bean scope fundamentally changes how much of the lifecycle the container manages. Singleton beans enjoy full lifecycle management. Prototype beans are handed off to the caller after creation — the container does not track them after that point.

Aspect Singleton Prototype
Created Once per container New instance per request
Destroy callbacks ✅ Called on context close ❌ NOT called — developer responsible
@PreDestroy ✅ Yes ❌ No
DisposableBean.destroy() ✅ Yes ❌ No
Custom destroy-method ✅ Yes ❌ No
Default scope ✅ Yes (default) No
Prototype beans are NOT destroyed by the container. If your prototype bean holds resources (connections, file handles), you must implement cleanup yourself. Consider using a BeanPostProcessor to track prototype instances, or switch to a custom scope that manages the lifecycle boundary explicitly. 
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;

@Component
@Scope("prototype")
public class ReportGenerator {
    // Each getBean() call returns a new instance
    // @PreDestroy will NOT be called — clean up manually!
    public void generate(String reportId) {
        System.out.println("Generating report: " + reportId);
    }
}

ApplicationContext vs BeanFactory

ApplicationContext is a superset of BeanFactory. In practice you always use ApplicationContext — the only reason to use BeanFactory directly is in highly resource-constrained environments (e.g., embedded devices) where eager initialization overhead matters.

Feature BeanFactory ApplicationContext
Bean initialization Lazy (on first getBean()) Eager at startup (all singletons)
Event publishing ❌ No ✅ Yes (ApplicationEventPublisher)
ApplicationContextAware ❌ Not triggered ✅ Triggered
MessageSource (i18n) ❌ No ✅ Yes
BeanPostProcessors Manual registration ✅ Auto-detected from context
AOP support Limited ✅ Full proxy creation
Common implementation DefaultListableBeanFactory AnnotationConfigApplicationContext
Rule of thumb Always use ApplicationContext in application code. Only reach for BeanFactory when writing a framework-level component that must initialize before the full context is available (e.g., inside a BeanFactoryPostProcessor).
