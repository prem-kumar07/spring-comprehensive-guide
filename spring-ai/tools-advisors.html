Spring AI Tools & Advisors

Spring AI 1.x Spring AI 2.x

Tools (function calling) let an AI model invoke Java methods at runtime — the model decides when to call a tool, Spring AI dispatches it, and the result is fed back automatically so the model can produce a final answer. Advisors are the middleware layer around every ChatClient call: they can pre-process requests, post-process responses, inject RAG context, manage conversation memory, filter harmful content, or add observability — all without changing the call-site code.

@Tool — Declaring a Java Method as a Tool

Annotate any Spring-managed bean method with @Tool to expose it to the model as a callable function. Spring AI reads the method signature at startup and auto-generates a JSON schema that describes the function name, description, and parameters. The description string is what the model reads to decide when to call the function, so write it in plain English explaining the purpose and when the tool should be used.

Register tools on a per-call basis via .tools(weatherService) on the ChatClient fluent call. You can pass individual method references or entire service beans — Spring AI introspects all @Tool methods on the bean.

Tool Definition

import org.springframework.ai.tool.annotation.Tool;
import org.springframework.stereotype.Service;

@Service
public class WeatherService {

    @Tool("Get the current weather conditions for a city. "
        + "Use this when the user asks about weather in a specific location.")
    public String getCurrentWeather(String city) {
        // Real implementation would call a weather API
        return String.format("{\"city\":\"%s\",\"temp\":\"22°C\",\"condition\":\"Sunny\"}", city);
    }
}

Registering the Tool with ChatClient

@RestController
public class WeatherController {

    private final ChatClient chatClient;
    private final WeatherService weatherService;

    public WeatherController(ChatClient.Builder builder,
                              WeatherService weatherService) {
        this.chatClient = builder.build();
        this.weatherService = weatherService;
    }

    @GetMapping("/weather-chat")
    public String ask(@RequestParam String question) {
        return chatClient.prompt()
            .user(question)
            .tools(weatherService)       // register all @Tool methods on the bean
            .call()
            .content();
    }
}

@ToolParam — Documenting Tool Parameters

@ToolParam annotates individual method parameters to provide the model with a human-readable description and optionally mark a parameter as not required. Without @ToolParam, Spring AI uses the Java parameter name and type only. Rich descriptions significantly improve tool selection accuracy, especially when a tool has multiple parameters with similar types.

Set required = false for optional parameters. The generated JSON schema will mark them as not required, allowing the model to omit them when they are not applicable.

Example

import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.tool.annotation.ToolParam;

@Service
public class FlightService {

    @Tool("Search for available flights between two airports on a given date. "
        + "Returns a list of flight options with price and duration.")
    public String searchFlights(
        @ToolParam(description = "IATA airport code for departure, e.g. LHR")
        String origin,

        @ToolParam(description = "IATA airport code for destination, e.g. JFK")
        String destination,

        @ToolParam(description = "Departure date in YYYY-MM-DD format")
        String date,

        @ToolParam(description = "Seat class: ECONOMY, BUSINESS, or FIRST",
                   required = false)
        String seatClass
    ) {
        // Implementation calls flight search API
        return "{\"flights\": [{\"airline\":\"BA\",\"price\":450,\"duration\":\"7h30m\"}]}";
    }
}

Transparent Tool Invocation Loop

When the model decides to invoke a tool, it returns a response containing a tool_calls array rather than a text answer. Spring AI detects this, dispatches the tool call to the registered Java method, serializes the result as a tool message, and automatically re-submits the conversation — including the tool result — back to the model. The model then generates its final text answer. All of this happens inside a single .call().content() invocation from the caller's perspective. No user code is needed to manage the loop.

The loop repeats if the model issues multiple tool calls. Parallel tool calls (multiple functions requested in a single model response) are also supported and dispatched concurrently by default in Spring AI 2.x.

How the Loop Works

// From the caller's perspective — just one blocking call
String answer = chatClient.prompt()
    .user("What is the weather in London and Berlin?")
    .tools(weatherService)
    .call()
    .content();

// Internally Spring AI handles:
// 1. Sends user message to model
// 2. Model responds with tool_calls: [getCurrentWeather("London"), getCurrentWeather("Berlin")]
// 3. Spring AI dispatches both (potentially in parallel)
// 4. Results injected as tool role messages
// 5. Re-submitted to model
// 6. Model generates final answer — returned as 'answer' above

Verifying Tool Calls Were Made

// Use ChatResponse to inspect tool call metadata
ChatResponse response = chatClient.prompt()
    .user("What's the temperature in Tokyo?")
    .tools(weatherService)
    .call()
    .chatResponse();

// The final generation has the text answer
String text = response.getResult().getOutput().getText();

// Tool calls are recorded in the metadata / result list
System.out.println("Answer: " + text);

ToolCallbackProvider — Global Tool Registration

ToolCallbackProvider is a Spring bean interface that registers a set of tools globally so they are available to every ChatClient call without being passed explicitly via .tools(). Implement ToolCallbackProvider and return a list of ToolCallback instances, or use Spring AI's built-in MethodToolCallbackProvider to wrap service beans automatically.

This pattern is particularly useful in large applications where you want to centralize tool registration rather than scattering .tools(weatherService, flightService, ...) across many call sites.

Defining a ToolCallbackProvider Bean

import org.springframework.ai.tool.ToolCallbackProvider;
import org.springframework.ai.tool.method.MethodToolCallbackProvider;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ToolConfig {

    @Bean
    public ToolCallbackProvider applicationTools(WeatherService weatherService,
                                                  FlightService flightService,
                                                  CalendarService calendarService) {
        // Wraps all @Tool methods on the given beans into ToolCallback instances
        return MethodToolCallbackProvider.builder()
            .toolObjects(weatherService, flightService, calendarService)
            .build();
    }
}

ChatClient Uses All Registered Tools Automatically

// No .tools() call needed — ToolCallbackProvider bean is auto-discovered
String answer = chatClient.prompt()
    .user("Book me a flight from Heathrow to JFK next Friday "
        + "and check the weather forecast for New York that day.")
    .call()
    .content();

Tool Return Types and Schema Generation

Spring AI generates the tool's parameter schema from the Java method signature at startup. Supported parameter types include String, primitive wrappers (Integer, Double, Boolean), enums, and POJOs. Nested POJOs are recursively converted to nested JSON schema objects. Return types are not part of the schema — they are returned as a plain String tool result message.

For complex parameter types, annotate fields of the POJO with @JsonProperty(required = true) and @JsonPropertyDescription("...") (from Jackson) to enrich the schema. Spring AI uses Jackson for schema reflection.

POJO Parameter with Jackson Annotations

import com.fasterxml.jackson.annotation.JsonProperty;
import com.fasterxml.jackson.annotation.JsonPropertyDescription;

// Schema-enriched record for use as a tool parameter
public record BookingRequest(
    @JsonProperty(required = true)
    @JsonPropertyDescription("Hotel name or ID to book")
    String hotelId,

    @JsonPropertyDescription("Check-in date in YYYY-MM-DD format")
    String checkIn,

    @JsonPropertyDescription("Check-out date in YYYY-MM-DD format")
    String checkOut,

    @JsonPropertyDescription("Number of guests (adults)")
    int guests
) {}

@Service
public class HotelService {

    @Tool("Create a hotel booking for the specified hotel and dates.")
    public String bookHotel(BookingRequest request) {
        return String.format(
            "{\"confirmationId\":\"HTL-%s\",\"hotel\":\"%s\",\"checkIn\":\"%s\"}",
            java.util.UUID.randomUUID().toString().substring(0, 8),
            request.hotelId(), request.checkIn());
    }
}

returnDirect — Bypassing the Model After Tool Execution

By default, tool results are fed back to the model so it can generate a natural-language final answer. Setting returnDirect = true on @Tool makes Spring AI return the raw tool result string directly to the caller, skipping the second model call. This is useful for deterministic tools where the answer is already machine-readable (e.g. a JSON API response your frontend consumes directly) and a round-trip to the model would only add latency and cost.

returnDirect Example

@Service
public class DataExportService {

    // returnDirect=true: tool result is the final response — no second model call
    @Tool(value = "Export user data as a structured JSON report for download.",
          returnDirect = true)
    public String exportUserData(
        @ToolParam(description = "User ID to export") String userId,
        @ToolParam(description = "Report format: FULL or SUMMARY", required = false)
        String format
    ) {
        String reportFormat = (format != null) ? format : "FULL";
        // This JSON is returned directly to the ChatClient caller
        return String.format(
            "{\"userId\":\"%s\",\"format\":\"%s\",\"records\":142,\"exportedAt\":\"%s\"}",
            userId, reportFormat, java.time.Instant.now());
    }
}

ToolContext — Injecting Runtime State into Tools

ToolContext provides a mechanism for passing runtime state — such as the authenticated user's ID, a tenant identifier, a security token, or a request-scoped value — into a tool method without polluting the model's prompt with that data. The context is set by the caller and is available to all tools invoked during that request.

To receive context, add a ToolContext parameter to the tool method. Spring AI injects it automatically at invocation time. The context map supports any String-keyed values and is separate from the chat messages.

Spring AI 2.x — ToolContext is part of the redesigned composable tool-calling architecture in Spring AI 2.0. It allows secure, request-scoped state to flow into tools without being serialized into the prompt or exposed to the model.

Tool Method Receiving Context

import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.tool.execution.ToolContext;

@Service
public class UserDataService {

    @Tool("Retrieve the current user's profile data including name and preferences.")
    public String getUserProfile(ToolContext context) {
        // Read runtime state injected by the caller
        String userId = (String) context.getContext().get("userId");
        String tenantId = (String) context.getContext().get("tenantId");

        // Use these values securely — they were never in the prompt
        return fetchProfileFromDatabase(userId, tenantId);
    }

    private String fetchProfileFromDatabase(String userId, String tenantId) {
        return String.format("{\"userId\":\"%s\",\"tenant\":\"%s\",\"name\":\"Alice\"}",
            userId, tenantId);
    }
}

Passing Context at the Call Site

// Inject runtime context via toolContext() — never expose this in the user message
String answer = chatClient.prompt()
    .user("What are my profile settings?")
    .tools(userDataService)
    .toolContext(Map.of(
        "userId",   currentUser.getId(),
        "tenantId", currentTenant.getId()
    ))
    .call()
    .content();

Tool Invocation Loop — Internals

Understanding the internal flow helps debug tool-calling issues and design more reliable agentic pipelines. Spring AI's tool loop follows the standard function-calling protocol: the model signals intent via a structured tool_calls block in its response, Spring AI dispatches the calls, and the results are injected as tool-role messages before re-invoking the model. The loop continues until the model returns a response that contains no tool_calls.

Sequence Diagram (ASCII)

User prompt
    │
    ▼
ChatClient.prompt().user(...).tools(...).call()
    │
    ▼
[1] Send messages to ChatModel
    │
    ▼
[2] Model response: tool_calls present?
    │
    ├─ YES ──▶ [3] Extract tool call list
    │               │
    │               ▼
    │           [4] Dispatch each ToolCallback (parallel if multiple)
    │               │
    │               ▼
    │           [5] Wrap results as ToolResponseMessage list
    │               │
    │               ▼
    │           [6] Append to conversation, go to [1]
    │
    └─ NO ───▶ [7] Return AssistantMessage text to caller

Controlling Loop Depth

// Spring AI 2.x — control max iterations via ToolCallingManager
import org.springframework.ai.tool.execution.DefaultToolCallingManager;

ToolCallingManager manager = DefaultToolCallingManager.builder()
    .maxIterations(5)   // stop after 5 tool-call rounds
    .build();

ChatClient chatClient = ChatClient.builder(chatModel)
    .defaultToolCallingManager(manager)
    .build();

Spring AI 2.x Composable Tool Architecture

Spring AI 2.0 introduced a fully redesigned tool-calling architecture based on composable, explicit components. The ToolCallingManager interface encapsulates the dispatch-and-loop logic. You can provide a custom implementation to add retry, circuit-breaking, observability spans per tool call, or custom error recovery — without forking framework internals.

The new architecture also decouples tool execution from the advisor chain, making it easier to reason about ordering and to test tool-calling logic in isolation.

Spring AI 2.x — The composable architecture replaces the implicit, internal function-call loop of 1.x. Key changes: ToolCallingManager is now a first-class bean; ToolContext is the standard way to pass request state; and ToolCallbackProvider beans are auto-discovered. Upgrade paths are documented in the Spring AI 2.0 migration guide.

Custom ToolCallingManager

import org.springframework.ai.tool.execution.ToolCallingManager;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ToolCallingConfig {

    @Bean
    public ToolCallingManager customToolCallingManager() {
        return DefaultToolCallingManager.builder()
            .maxIterations(10)
            // Add custom error handling or observability here
            .build();
    }
}

Explicit Tool Context Pipeline

// Full 2.x style — explicit context, global tools via provider
@Service
public class AgentService {

    private final ChatClient chatClient;

    public AgentService(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    public String runAgent(String task, String userId, String tenantId) {
        return chatClient.prompt()
            .user(task)
            // ToolCallbackProvider bean supplies the tools automatically
            .toolContext(Map.of("userId", userId, "tenantId", tenantId))
            .call()
            .content();
    }
}

Handling Tool Execution Exceptions

When a tool throws an unchecked exception, Spring AI's default behavior in 2.x is to convert it to a tool error result string and feed it back to the model rather than immediately propagating the exception to the caller. This gives the model a chance to recover or inform the user. You can customize this behavior by providing a ToolExecutionExceptionProcessor bean.

Configure the processor to rethrow certain exception types (e.g. SecurityException) while converting others to recoverable messages. This gives fine-grained control over which errors abort the loop and which the model can handle.

Spring AI 2.x — The ToolExecutionExceptionProcessor interface is part of the 2.x composable architecture. In Spring AI 1.x, unchecked exceptions from tools propagated directly to the caller without the model seeing them.

Custom Exception Processor

import org.springframework.ai.tool.execution.ToolExecutionExceptionProcessor;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ToolExceptionConfig {

    @Bean
    public ToolExecutionExceptionProcessor toolExceptionProcessor() {
        return (toolName, exception) -> {
            // Rethrow security violations immediately — do not let the model handle them
            if (exception instanceof SecurityException) {
                throw (SecurityException) exception;
            }
            // For everything else, return a structured error for the model
            return String.format(
                "{\"error\": \"Tool '%s' failed: %s. Please try a different approach.\"}",
                toolName, exception.getMessage());
        };
    }
}

Multi-Tool Orchestration

A single agent can be equipped with multiple tools, enabling it to decompose a complex task into a sequence of tool calls. The model acts as the orchestrator — it selects which tool to call, in what order, and how to combine the results into a final answer. No explicit routing code is needed in the application. This pattern is sometimes called a ReAct (Reason + Act) agent.

Design principle: keep each tool small and focused on a single responsibility. The model is better at orchestration when tools have clear, non-overlapping descriptions.

Tool Definitions

@Service
public class ResearchTools {

    @Tool("Search the web for current information on a given topic. "
        + "Returns a list of relevant snippets with source URLs.")
    public String webSearch(
        @ToolParam(description = "The search query string") String query
    ) {
        // Integration with a search API (e.g. Brave Search, Serper)
        return "[{\"title\":\"Spring AI Overview\",\"snippet\":\"...\",\"url\":\"https://docs.spring.io\"}]";
    }

    @Tool("Perform arithmetic calculation. "
        + "Accepts a mathematical expression as a string and returns the numeric result.")
    public String calculate(
        @ToolParam(description = "Mathematical expression, e.g. '(42 * 3.14) / 2'") String expression
    ) {
        // Use ScriptEngine or expression parser for safe evaluation
        return "65.94";
    }

    @Tool("Summarize a block of text into bullet points. "
        + "Use after retrieving raw web content to condense it.")
    public String summarize(
        @ToolParam(description = "The raw text content to summarize") String text,
        @ToolParam(description = "Maximum number of bullet points", required = false)
        Integer maxPoints
    ) {
        // Could recursively call a smaller/faster model
        return "• Spring AI provides a portable API\n• Supports OpenAI, Anthropic, Gemini";
    }
}

Wiring the Multi-Tool Agent

@Service
public class PlannerAgent {

    private final ChatClient chatClient;
    private final ResearchTools researchTools;

    public PlannerAgent(ChatClient.Builder builder, ResearchTools researchTools) {
        this.chatClient = builder
            .defaultSystem("""
                You are a research assistant. Break down complex questions into steps.
                Use the webSearch tool to find information, the calculate tool for math,
                and the summarize tool to condense long results before answering.
                """)
            .build();
        this.researchTools = researchTools;
    }

    public String research(String question) {
        return chatClient.prompt()
            .user(question)
            .tools(researchTools)
            .call()
            .content();
    }
}

Error Handling in Tool Responses

When a tool method encounters an error, the recommended approach is to return a structured error string (or JSON) rather than throwing an exception. The model receives the error message as the tool result and can decide how to proceed — retry with different arguments, use a fallback tool, or inform the user gracefully. Throwing unchecked exceptions propagates up through Spring AI and may abort the entire loop.

For predictable failures (network errors, not-found conditions), catch the exception inside the tool and return a meaningful error payload. Reserve exception propagation for truly unexpected failures that should halt the agent.

Defensive Tool Implementation

@Service
public class DatabaseQueryTool {

    private final DataSource dataSource;

    public DatabaseQueryTool(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    @Tool("Execute a read-only SQL query against the application database. "
        + "Returns results as JSON. Only SELECT statements are allowed.")
    public String executeQuery(
        @ToolParam(description = "A read-only SQL SELECT statement") String sql
    ) {
        // Validate — only allow SELECT
        if (!sql.trim().toUpperCase().startsWith("SELECT")) {
            return "{\"error\": \"Only SELECT statements are permitted\"}";
        }
        try (Connection conn = dataSource.getConnection();
             Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(sql)) {

            return resultSetToJson(rs);

        } catch (SQLException e) {
            // Return structured error — model can decide what to do
            return String.format("{\"error\": \"Query failed: %s\"}", e.getMessage());
        } catch (Exception e) {
            return "{\"error\": \"Unexpected error during query execution\"}";
        }
    }

    private String resultSetToJson(ResultSet rs) throws SQLException {
        // Simplified — real implementation uses ObjectMapper
        return "[{\"result\": \"data\"}]";
    }
}

Tool Result Formatting — JSON vs Plain String

Spring AI passes whatever your tool method returns (as a String) directly to the model as the tool result message. The model treats it as raw content. Choosing the right format affects how reliably the model can parse and use the result in its final answer.

Prefer JSON for structured data (lists, objects with multiple fields) — the model handles JSON well and can extract specific fields. Prefer plain text for simple scalar answers (a temperature, a count, a yes/no) — it is less error-prone for the model and produces cleaner responses. Avoid returning binary data or very large payloads; truncate or paginate instead.

JSON Result — Structured Data

@Tool("List the top N open issues from a GitHub repository.")
public String getOpenIssues(
    @ToolParam(description = "GitHub repo in owner/repo format") String repo,
    @ToolParam(description = "Max number of issues to return", required = false)
    Integer limit
) {
    int max = (limit != null) ? limit : 5;
    // Return compact JSON — model extracts fields cleanly
    return """
        {"issues": [
          {"number": 42, "title": "NPE in ChatClient when model is null", "labels": ["bug"]},
          {"number": 38, "title": "Add support for Gemini 2.0 Flash", "labels": ["enhancement"]}
        ], "total_open": 17}
        """;
}

Plain String Result — Simple Scalars

@Tool("Get the current UTC time as an ISO-8601 string.")
public String getCurrentUtcTime() {
    // Simple scalar — plain string is clearest
    return java.time.Instant.now().toString();
    // Returns: "2025-09-14T10:30:00Z"
}

@Tool("Check if a domain name is available for registration.")
public String checkDomainAvailability(
    @ToolParam(description = "Domain name with TLD, e.g. myapp.com") String domain
) {
    boolean available = domainRegistrar.checkAvailability(domain);
    // Unambiguous boolean as string is fine for the model
    return available ? "AVAILABLE" : "TAKEN";
}

Parallel Tool Calls

When the model requests multiple tools in a single response (parallel tool calling), Spring AI 2.x dispatches them concurrently by default using a CompletableFuture-based dispatcher. Parallel dispatch significantly reduces end-to-end latency when tools perform independent I/O (e.g. querying weather for London and Berlin simultaneously rather than sequentially). Tools that share mutable state must be thread-safe.

Parallel calling is controlled at the ToolCallingManager level. To force sequential dispatch (useful for tools with side effects that must run in order), configure the manager with a sequential executor.

Verifying Parallelism (Test Example)

// Tools that record invocation timestamps to verify parallel execution
@Service
public class TimestampedWeatherTool {

    private final List<Long> invocationTimestamps =
        Collections.synchronizedList(new ArrayList<>());

    @Tool("Get weather for a city. Records timestamp of execution.")
    public String getWeather(String city) {
        invocationTimestamps.add(System.currentTimeMillis());
        // Simulate I/O delay
        try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return "{\"city\":\"" + city + "\",\"temp\":\"20°C\"}";
    }

    public List<Long> getInvocationTimestamps() {
        return Collections.unmodifiableList(invocationTimestamps);
    }
}

Tools with Structured Output

Combining Spring AI's BeanOutputConverter with tool calling lets you receive the model's final answer as a typed Java object rather than a raw string. The model uses the tools to gather data and then produces a structured JSON answer conforming to a schema generated from your target class. This pattern is effective for agentic workflows that need the final result in a format immediately usable by downstream code.

Typed Response from a Tool-Augmented Call

// Target record for structured output
public record WeatherSummary(
    String city,
    String temperature,
    String condition,
    String recommendation
) {}

@Service
public class WeatherAssistant {

    private final ChatClient chatClient;
    private final WeatherService weatherService;

    public WeatherAssistant(ChatClient.Builder builder, WeatherService weatherService) {
        this.chatClient = builder.build();
        this.weatherService = weatherService;
    }

    public WeatherSummary getWeatherSummary(String city) {
        return chatClient.prompt()
            .system("Always respond with valid JSON matching the requested schema.")
            .user("Get the current weather for " + city
                + " and provide a packing recommendation.")
            .tools(weatherService)
            .call()
            .entity(WeatherSummary.class);  // Spring AI deserializes JSON to the record
    }
}

CallAdvisor and StreamAdvisor Interfaces

Advisors in Spring AI are middleware that wrap the ChatClient call pipeline. CallAdvisor wraps blocking calls; StreamAdvisor wraps streaming calls. Both receive the request before it reaches the model and the response after the model replies, giving them the ability to modify, enrich, log, filter, or augment either side.

The getOrder() method returns an integer determining where in the advisor chain this advisor executes. Lower values run earlier on the way in (pre-processing) and later on the way out (post-processing). Use Ordered.HIGHEST_PRECEDENCE and Ordered.LOWEST_PRECEDENCE as anchors. The AdvisorChain (or RequestResponseAdvisorChain) is passed to nextAroundCall() — call it to continue the chain.

CallAdvisor Interface

import org.springframework.ai.chat.client.advisor.api.AdvisedRequest;
import org.springframework.ai.chat.client.advisor.api.AdvisedResponse;
import org.springframework.ai.chat.client.advisor.api.CallAdvisor;
import org.springframework.ai.chat.client.advisor.api.CallAroundAdvisorChain;

public interface CallAdvisor {

    // Intercept the call — pre-process request, post-process response
    AdvisedResponse aroundCall(AdvisedRequest request, CallAroundAdvisorChain chain);

    // Chain order: lower = runs earlier in pre-processing
    default int getOrder() {
        return 0;
    }
}

StreamAdvisor Interface

import org.springframework.ai.chat.client.advisor.api.StreamAdvisor;
import org.springframework.ai.chat.client.advisor.api.StreamAroundAdvisorChain;
import reactor.core.publisher.Flux;

public interface StreamAdvisor {

    // Intercept streaming calls
    Flux<AdvisedResponse> aroundStream(AdvisedRequest request,
                                        StreamAroundAdvisorChain chain);

    default int getOrder() {
        return 0;
    }
}

QuestionAnswerAdvisor — RAG in One Line

QuestionAnswerAdvisor implements Retrieval-Augmented Generation (RAG) by intercepting the request, retrieving the most semantically similar documents from a VectorStore, and injecting them into the system prompt as context before the model sees the user's question. The default retrieval retrieves the top-K documents (K=4 by default) using similarity search. The advisor appends a context block to the system prompt containing the retrieved documents, enabling the model to ground its answer in your data.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.ai</groupId>
  <artifactId>spring-ai-advisors-vector-store</artifactId>
</dependency>

Wiring QuestionAnswerAdvisor

import org.springframework.ai.chat.client.advisor.QuestionAnswerAdvisor;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.ai.vectorstore.SearchRequest;

@Service
public class RagService {

    private final ChatClient chatClient;

    public RagService(ChatClient.Builder builder, VectorStore vectorStore) {
        this.chatClient = builder
            .defaultAdvisors(
                new QuestionAnswerAdvisor(vectorStore))   // default top-4 retrieval
            .build();
    }

    public String ask(String question) {
        return chatClient.prompt()
            .user(question)
            .call()
            .content();
    }

    // Custom retrieval: top-8, filter by metadata
    public String askFiltered(String question, String category) {
        return chatClient.prompt()
            .user(question)
            .advisors(spec -> spec.param(
                QuestionAnswerAdvisor.FILTER_EXPRESSION,
                "category == '" + category + "'"))
            .call()
            .content();
    }
}

MessageChatMemoryAdvisor vs VectorStoreChatMemoryAdvisor

MessageChatMemoryAdvisor stores and retrieves the raw conversation messages in chronological order using a sliding window. It is simple, fast, and requires no embedding model — ideal for short-to-medium conversations where recency matters more than semantic relevance. The window size bounds token consumption.

VectorStoreChatMemoryAdvisor embeds each message and stores it in a vector database. Retrieval is similarity-based: past messages most semantically similar to the current query are pulled in, regardless of when they occurred. This enables long-term, cross-session memory but requires an embedding model and a vector store. Choose this when conversations span many turns or sessions and exact recency is less important than topical relevance.

Advisor Storage Retrieval Best For
MessageChatMemoryAdvisor In-memory / Redis / JDBC Last-N messages (window) Short conversations, chatbots
VectorStoreChatMemoryAdvisor PGVector / Pinecone / Chroma Similarity search Long-term memory, cross-session recall

Choosing Window Size vs Semantic Memory

// Message-window memory — last 10 turns, keyed by conversation ID
ChatMemory windowMemory = new InMemoryChatMemory();
ChatClient windowClient = ChatClient.builder(chatModel)
    .defaultAdvisors(
        MessageChatMemoryAdvisor.builder(windowMemory)
            .conversationId("default")
            .chatHistoryWindowSize(10)
            .build())
    .build();

// Semantic memory — similarity search, 6 relevant past messages
ChatClient semanticClient = ChatClient.builder(chatModel)
    .defaultAdvisors(
        VectorStoreChatMemoryAdvisor.builder(vectorStore)
            .conversationId("default")
            .order(Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER)
            .build())
    .build();

SafeGuardAdvisor — Content Filtering

SafeGuardAdvisor is a pre-call advisor that inspects the user's message for blocked phrases before the request reaches the model. If any blocked phrase is found (case-insensitive substring match), the advisor short-circuits the chain and returns a configurable rejection message instead of calling the model. This provides a lightweight first-pass content filter for known toxic or disallowed terms, without requiring an external moderation API.

For production use, combine SafeGuardAdvisor with a more sophisticated moderation service (such as OpenAI's moderation endpoint) as a second layer.

Wiring SafeGuardAdvisor

import org.springframework.ai.chat.client.advisor.SafeGuardAdvisor;

@Service
public class SafeChatService {

    private final ChatClient chatClient;

    public SafeChatService(ChatClient.Builder builder) {
        List<String> blockedPhrases = List.of(
            "drop table", "rm -rf", "ignore previous instructions",
            "jailbreak", "disregard your guidelines"
        );

        this.chatClient = builder
            .defaultAdvisors(
                new SafeGuardAdvisor(
                    blockedPhrases,
                    "I'm sorry, but I cannot process that request."))
            .build();
    }

    public String chat(String userMessage) {
        return chatClient.prompt()
            .user(userMessage)
            .call()
            .content();
        // If userMessage contains a blocked phrase, returns the rejection message
        // without calling the model
    }
}

SimpleLoggerAdvisor — Request/Response Logging

SimpleLoggerAdvisor logs the full AdvisedRequest and AdvisedResponse at DEBUG level using SLF4J. It is the recommended first advisor to add during development and debugging because it surfaces the exact prompt, model parameters, advisor parameters, and response that the framework sees — after all other advisors have transformed the request. Enable it via the standard Spring Boot logging configuration.

Set its order to Ordered.LOWEST_PRECEDENCE so it runs last in the pre-processing chain (closest to the model) and first in post-processing — logging what actually reaches the model rather than the raw user input.

Adding SimpleLoggerAdvisor

import org.springframework.ai.chat.client.advisor.SimpleLoggerAdvisor;
import org.springframework.core.Ordered;

@Service

    private final ChatClient chatClient;

    public DebugChatService(ChatClient.Builder builder, VectorStore vectorStore) {
        this.chatClient = builder

                new QuestionAnswerAdvisor(vectorStore),
                new MessageChatMemoryAdvisor(new InMemoryChatMemory()),
                new SimpleLoggerAdvisor()   // logs the final assembled prompt
            )
            .build();
    }
}

RecursiveAdvisor — Self-Refining Agentic Loops

RecursiveAdvisor (introduced in Spring AI 1.1) enables a self-refining agentic loop by re-invoking the chat pipeline from within an advisor. After the model produces a response, the advisor evaluates it (e.g. against a quality criterion, a format check, or a factuality constraint) and can resubmit the conversation with additional instructions if the response does not meet the bar. This loop continues up to a configurable MAX_RECURSION_DEPTH.

Use RecursiveAdvisor sparingly and always set a recursion limit — unbounded loops are costly and may time out. It is best suited for structured-output refinement (e.g. ensuring valid JSON) or factual self-checking tasks.

Spring AI 2.x — RecursiveAdvisor was introduced in Spring AI 1.1 and continues in 2.x. Set MAX_RECURSION_DEPTH as an advisor parameter at the call site to override the default. Monitor token usage carefully when using recursive advisors in production.

Custom Recursive Advisor Example

import org.springframework.ai.chat.client.advisor.api.AdvisedRequest;
import org.springframework.ai.chat.client.advisor.api.AdvisedResponse;
import org.springframework.ai.chat.client.advisor.api.CallAdvisor;
import org.springframework.ai.chat.client.advisor.api.CallAroundAdvisorChain;

/**
 * Re-asks the model if the response is not valid JSON, up to MAX_TRIES times.
 */
public class JsonValidationAdvisor implements CallAdvisor {

    private static final int MAX_TRIES = 3;
    private int attempt = 0;

    @Override
    public AdvisedResponse aroundCall(AdvisedRequest request,
                                       CallAroundAdvisorChain chain) {
        AdvisedResponse response = chain.nextAroundCall(request);
        String content = response.response().getResult().getOutput().getText();

        if (!isValidJson(content) && attempt < MAX_TRIES) {
            attempt++;
            // Augment the request with a correction instruction
            AdvisedRequest retryRequest = AdvisedRequest.from(request)
                .withUserText(request.userText()
                    + "\n\nIMPORTANT: Your previous response was not valid JSON. "
                    + "Respond ONLY with valid JSON, no markdown fences.")
                .build();
            return aroundCall(retryRequest, chain);   // recurse
        }
        attempt = 0;
        return response;
    }

    @Override
    public int getOrder() {
        return Ordered.LOWEST_PRECEDENCE - 10;
    }

    private boolean isValidJson(String text) {
        try {
            new com.fasterxml.jackson.databind.ObjectMapper().readTree(text);
            return true;
        } catch (Exception e) {
            return false;
        }
    }
}

Writing a Custom CallAdvisor

Implement CallAdvisor to insert custom logic into the ChatClient pipeline. Common use cases include: request enrichment (inject tenant metadata), response transformation (strip PII from output), latency measurement, audit logging, token-budget enforcement, and A/B testing different system prompts. The advisor receives the full AdvisedRequest (including all messages, options, and advisor parameters) and can modify it before calling the chain.

Best practice: keep each advisor focused on one concern. Chain multiple single-purpose advisors rather than building one monolithic advisor. Register them via ChatClient.Builder.defaultAdvisors() so they apply to every call, or pass them per-call for conditional behavior.

Custom Latency-Tracking Advisor

import org.springframework.ai.chat.client.advisor.api.*;
import org.springframework.core.Ordered;

import java.time.Instant;
import java.util.Map;

public class LatencyAdvisor implements CallAdvisor {

    private final MeterRegistry meterRegistry;

    public LatencyAdvisor(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
    }

    @Override
    public AdvisedResponse aroundCall(AdvisedRequest request,
                                       CallAroundAdvisorChain chain) {
        Instant start = Instant.now();
        try {
            // Delegate to next advisor (or model if last in chain)
            AdvisedResponse response = chain.nextAroundCall(request);

            long millis = java.time.Duration.between(start, Instant.now()).toMillis();

            // Record latency metric
            meterRegistry.timer("spring.ai.chatclient.latency")
                .record(millis, java.util.concurrent.TimeUnit.MILLISECONDS);

            // Optionally add metadata to the response context
            return AdvisedResponse.from(response)
                .withAdvisedContext(Map.of("latencyMs", millis))
                .build();

        } catch (Exception ex) {
            meterRegistry.counter("spring.ai.chatclient.errors").increment();
            throw ex;
        }
    }

    @Override
    public int getOrder() {
        // Run first (outermost) to capture full round-trip latency
        return Ordered.HIGHEST_PRECEDENCE;
    }
}

Registering Custom Advisors

@Service
public class ObservableChatService {

    private final ChatClient chatClient;

    public ObservableChatService(ChatClient.Builder builder,
                                  MeterRegistry meterRegistry,
                                  VectorStore vectorStore) {
        this.chatClient = builder
            .defaultAdvisors(
                new LatencyAdvisor(meterRegistry),             // order=HIGHEST: outermost
                new QuestionAnswerAdvisor(vectorStore),        // order=0: RAG
                new MessageChatMemoryAdvisor(new InMemoryChatMemory()), // order=0
                new SimpleLoggerAdvisor()                      // innermost: logs final prompt
            )
            .build();
    }

    public String ask(String question) {
        return chatClient.prompt()
            .user(question)
            .call()
            .content();
    }
}

Advisor Chain Ordering — Design Rules

The order in which advisors run matters because each advisor can transform both the request (going in) and the response (coming out). Think of the chain as a stack: the advisor with the lowest order number runs first on the way in (closest to the caller) and last on the way out (post-processing). The advisor with the highest order number (or Ordered.LOWEST_PRECEDENCE) runs last on the way in (closest to the model) and first on the way out.

Follow this recommended ordering: observability/security (highest precedence) → context enrichment (RAG, memory) → logging (lowest precedence). This ensures the logger sees the fully assembled prompt and the metrics advisor captures the full round-trip time.

Order Advisor Role
HIGHEST_PRECEDENCELatencyAdvisorOutermost — measures full round-trip
0 (default)SafeGuardAdvisorBlock disallowed input early
0 (default)QuestionAnswerAdvisorInject RAG context before model
DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDERMessageChatMemoryAdvisorPrepend history after RAG
LOWEST_PRECEDENCESimpleLoggerAdvisorInnermost — logs final assembled prompt

Configuring Order in Code

import org.springframework.core.Ordered;

// Explicit order constant
public class MetricsAdvisor implements CallAdvisor {
    @Override
    public int getOrder() {
        return Ordered.HIGHEST_PRECEDENCE;   // runs first in, last out
    }
}

public class AuditLogAdvisor implements CallAdvisor {
    @Override
    public int getOrder() {
        return Ordered.LOWEST_PRECEDENCE;    // runs last in, first out
    }
}

Modifying Requests and Responses in an Advisor

Advisors modify requests by creating a new AdvisedRequest via AdvisedRequest.from(request).with...().build() and passing the modified request to the chain. Response modification works the same way with AdvisedResponse. Common modifications include: appending instructions to the system message, injecting retrieved documents into the user message, stripping PII from the response text, or normalizing whitespace in the output.

Request Enrichment Advisor

public class TenantContextAdvisor implements CallAdvisor {

    private final TenantResolver tenantResolver;

    public TenantContextAdvisor(TenantResolver tenantResolver) {
        this.tenantResolver = tenantResolver;
    }

    @Override
    public AdvisedResponse aroundCall(AdvisedRequest request,
                                       CallAroundAdvisorChain chain) {
        // Pre-process: inject tenant-specific system instructions
        String tenantInstructions = tenantResolver.getSystemInstructions();
        String enrichedSystem = request.systemText()
            + "\n\n[Tenant context] " + tenantInstructions;

        AdvisedRequest enriched = AdvisedRequest.from(request)
            .withSystemText(enrichedSystem)
            .build();

        // Execute the chain with the enriched request
        AdvisedResponse response = chain.nextAroundCall(enriched);

        // Post-process: strip internal metadata comments from response
        String cleanedText = response.response()
            .getResult().getOutput().getText()
            .replaceAll("\\[INTERNAL:[^\\]]+\\]", "").trim();

        return response;
    }

    @Override
    public int getOrder() {
        return 10;  // after security, before RAG
    }
}
