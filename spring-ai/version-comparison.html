Spring AI 1.x vs 2.x — Feature Comparison

Spring AI reached its first GA milestone with 1.0 (May 2024), introducing a stable API contract and modular starter structure. The 1.x line continued with 1.1 (July 2024), adding Model Context Protocol (MCP) client/server support, RetrievalAugmentationAdvisor, reasoning-model streaming, and the RecursiveAdvisor for agentic loops. Spring AI 2.0 (GA June 2026) is the current major line, introducing composable tool-calling via ToolCallingAdvisor in the advisor chain, annotation-driven MCP server authoring (@McpTool, @McpResource, @McpPrompt), self-correcting structured output, and a Spring Boot 4 / Spring Framework 7 baseline. This page compares each significant area of change. Click any row to expand a side-by-side code diff.

Tool Calling API (@FunctionCallback → @Tool → ToolCallingManager)

 Spring AI 1.0 introduced the @Tool annotation for declaring callable functions. Earlier milestones used @Bean-registered FunctionCallback instances passed via ChatClient.functions(). Spring AI 2.0 introduced the composable ToolCallingManager — a dedicated service that resolves, validates, and executes tools in the agentic loop. Tool definitions are now first-class beans with lifecycle management. Changed
Spring AI 1.x — @Tool annotation
// Spring AI 1.x — @Tool on a service method
@Service
public class WeatherService {

    @Tool(description = "Get current weather for a city")
    public String getWeather(String city) {
        return weatherClient.fetch(city);
    }
}

// Wire into ChatClient:
@Autowired WeatherService weatherService;

String response = chatClient.prompt()
    .user("What's the weather in London?")
    .tools(weatherService)
    .call()
    .content();
Spring AI 2.x — ToolCallingManager
// Spring AI 2.x — composable ToolCallingManager
// Tools still declared with @Tool, but the manager
// controls execution strategy and context propagation.

@Service
public class WeatherService {

    @Tool(description = "Get current weather for a city")
    public String getWeather(
            String city, ToolContext ctx) {
        // ToolContext carries conversation state
        String userId = (String) ctx.getContext()
            .get("userId");
        return weatherClient.fetch(city);
    }
}

// ToolCallingManager wired automatically;
// override to customise execution order or retry

Structured Output (BeanOutputConverter → provider-native schemas)

 Spring AI 1.x used BeanOutputConverter to generate a JSON schema string, embed it in the prompt, and then parse the model's text response back into a Java bean — a pure prompt-engineering approach. Spring AI 2.0 adds useProviderStructuredOutput() to leverage the model provider's native JSON-mode or function-calling constraint, plus validateSchema() for a self-correcting retry loop when the response does not match. Changed
Spring AI 1.x — BeanOutputConverter
// Spring AI 1.x — prompt-based structured output
record Actor(String name, List<String> movies) {}

ActorFilms result = chatClient.prompt()
    .user(u -> u.text(
        "Generate filmography for {name}")
        .param("name", "Tom Hanks"))
    .call()
    .entity(ActorFilms.class);
// Schema injected into prompt as system text;
// parsing via Jackson on the returned string
Spring AI 2.x — provider-native + validateSchema
// Spring AI 2.x — provider-native JSON mode
ActorFilms result = chatClient.prompt()
    .user(u -> u.text(
        "Generate filmography for {name}")
        .param("name", "Tom Hanks"))
    .call()
    .entity(
        EntityResponseSpec.forEntity(
            ActorFilms.class)
        .useProviderStructuredOutput()
        // ↑ uses OpenAI response_format / Anthropic
        //   tool-use constraint instead of prompt text
        .validateSchema()
        // ↑ retries automatically if schema mismatch
    );

Model Context Protocol (MCP) Client and Server

 Spring AI 1.0 had no built-in MCP support. Tool calling relied on custom FunctionCallback or @Tool beans defined within the same application context. Spring AI 1.1+ ships spring-ai-mcp-client-spring-boot-starter and spring-ai-mcp-server-spring-boot-starter. The client auto-discovers MCP servers via SSE or stdin/stdout; the server exposes any @Tool-annotated bean as an MCP endpoint. New
Spring AI 1.0 — no MCP, local tools only
<!-- Spring AI 1.0 — only local tool calling -->
<dependency>
  <groupId>org.springframework.ai</groupId>
  <artifactId>spring-ai-openai-spring-boot-starter</artifactId>
</dependency>
<!-- Tools must live in the same JVM -->
Spring AI 1.1+ — MCP client starter
<!-- MCP client: auto-discover remote tool servers -->
<dependency>
  <groupId>org.springframework.ai</groupId>
  <artifactId>spring-ai-mcp-client-spring-boot-starter</artifactId>
</dependency>
# application.yml — connect to an MCP server
spring:
  ai:
    mcp:
      client:
        sse:
          connections:
            filesystem-server:
              url: http://localhost:3001/sse
// @Tool beans on the remote server auto-exposed
// ChatClient discovers and invokes them via MCP

RecursiveAdvisor for Self-Refining Agentic Loops

 Spring AI 1.0 offered QuestionAnswerAdvisor and basic advisor chaining, but no built-in support for iterative self-refinement loops where a model evaluates and corrects its own output. Spring AI 1.1 introduced RecursiveAdvisor, which wraps the inner advisor chain and re-invokes it when a configured condition (such as a validation failure or a low-confidence score) is met, up to a configurable maximum number of iterations. New
Spring AI 1.0 — manual retry loop
// Spring AI 1.0 — manual validation + retry
for (int attempt = 0; attempt < 3; attempt++) {
    String response = chatClient.prompt()
        .user("Summarise the document")
        .advisors(ragAdvisor)
        .call().content();
    if (isValid(response)) break;
    // otherwise retry — no framework support
}
Spring AI 1.1+ — RecursiveAdvisor
// Spring AI 1.1 — RecursiveAdvisor built-in
RecursiveAdvisor recursive = RecursiveAdvisor
    .builder()
    .delegate(ragAdvisor)
    .maxIterations(3)
    .continueCondition(ctx -> {
        String answer = ctx.response()
            .getResult().getOutput().getContent();
        return !isValid(answer); // retry if invalid
    })
    .build();

String response = chatClient.prompt()
    .user("Summarise the document")
    .advisors(recursive)
    .call().content();

Agentic Architecture (ToolCallingManager, ToolContext)

 Spring AI 1.x wired tool execution inline within the ChatClient request — tools were resolved and invoked in a single embedded loop with limited lifecycle control. ToolContext was introduced late in the 1.x line. Spring AI 2.x extracts the agentic loop into a dedicated ToolCallingManager bean. It handles tool resolution, invocation, result injection, and maximum-call-depth enforcement, and supports custom execution strategies (parallel, sequential). Changed
Spring AI 1.x — inline tool execution
// Spring AI 1.x — tools executed inside ChatClient
String result = chatClient.prompt()
    .user("Book a flight from LHR to JFK")
    .tools(flightSearchService, bookingService)
    .call()
    .content();
// Tool loop runs transparently inside .call()
// — no direct control over execution order
Spring AI 2.x — ToolCallingManager
// Spring AI 2.x — override ToolCallingManager
@Bean
ToolCallingManager toolCallingManager(
        List<ToolCallback> tools) {
    return DefaultToolCallingManager.builder()
        .toolCallbacks(tools)
        .maxToolCalls(10)
        // parallel execution for independent tools:
        .executionStrategy(
            ToolCallingManager.Strategy.PARALLEL)
        .build();
}

// ToolContext passed to every @Tool method
// carries conversation-scoped state

Reasoning Model Support (streaming thinking events)

 Spring AI 1.0 treated all models uniformly via the ChatModel abstraction — no special handling for chain-of-thought or reasoning tokens beyond what the provider returned in the final content field. Spring AI 1.1 introduced first-class streaming support for reasoning models (Anthropic Claude thinking, OpenAI o-series, Ollama reasoning). A new ThinkingEvent (or reasoning_content metadata) surfaces intermediate reasoning steps during streaming before the final answer arrives. New
Spring AI 1.0 — no reasoning token visibility
// Spring AI 1.0 — streaming gives final content only
Flux<String> stream = chatClient.prompt()
    .user("Solve: if 2x + 3 = 11, what is x?")
    .stream()
    .content();

// No way to observe intermediate reasoning steps;
// model's chain-of-thought is opaque
Spring AI 1.1+ — ThinkingEvent streaming
// Spring AI 1.1 — Anthropic extended thinking
AnthropicChatOptions options =
    AnthropicChatOptions.builder()
        .model("claude-opus-4-5")
        .thinkingEnabled(true)
        .thinkingBudgetTokens(8000)
        .build();

chatClient.prompt()
    .user("Solve: if 2x + 3 = 11, what is x?")
    .options(options)
    .stream()
    .chatResponse()
    .doOnNext(resp -> {
        // metadata contains reasoning_content
        // when thinking block arrives before answer
        resp.getResults().forEach(g ->
            System.out.println(
                g.getMetadata()));
    })
    .blockLast();

RetrievalAugmentationAdvisor (modular RAG pipeline)

 Spring AI 0.x / early 1.x provided QuestionAnswerAdvisor — a fixed advisor that performed similarity search against a VectorStore and injected the results into the prompt. The retrieval, augmentation, and filtering steps were not independently customisable. Spring AI 1.x introduced RetrievalAugmentationAdvisor built on a composable pipeline: QueryTransformer → DocumentRetriever → DocumentPostProcessor → ContextualQueryAugmenter. Each stage is a separate interface you can replace. New
Spring AI 0.x / early 1.x — QuestionAnswerAdvisor
// Fixed RAG pipeline — minimal customisation
QuestionAnswerAdvisor advisor =
    new QuestionAnswerAdvisor(vectorStore);

String answer = chatClient.prompt()
    .user(question)
    .advisors(advisor)
    .call()
    .content();
// Cannot customise re-ranking, query rewriting,
// or document post-processing independently
Spring AI 1.x — RetrievalAugmentationAdvisor
// Modular RAG pipeline
RetrievalAugmentationAdvisor advisor =
    RetrievalAugmentationAdvisor.builder()
        .queryTransformers(
            // rewrite query for better retrieval:
            RewriteQueryTransformer.builder()
                .chatClientBuilder(
                    chatClient.mutate())
                .build())
        .documentRetriever(
            VectorStoreDocumentRetriever.builder()
                .vectorStore(vectorStore)
                .similarityThreshold(0.7)
                .topK(6)
                .build())
        .documentPostProcessors(
            // re-rank by relevance score:
            new CohereRerankDocumentPostProcessor(
                cohereClient))
        .build();

Dependency Structure (monolithic 0.x → modular starters in 1.0)

 Spring AI 0.x milestone releases were distributed as a single monolithic artifact (spring-ai-core pulling in all model adapters). Dependency management was done via the BOM but all providers were bundled. Spring AI 1.0 GA introduced provider-specific starters (spring-ai-openai-spring-boot-starter, spring-ai-anthropic-spring-boot-starter, etc.) with auto-configuration isolation. The BOM (spring-ai-bom) still manages all versions. Changed
Spring AI 0.x — milestone monolith

Self-Correcting Structured Output (validateSchema loop)

 Spring AI 1.x relied on prompt engineering to constrain output format. If the model returned malformed JSON, the application had to handle the parsing exception itself and decide whether to retry. Spring AI 2.0 adds a validateSchema() option on EntityResponseSpec that automatically re-prompts the model with the validation error when the returned JSON does not satisfy the declared schema, up to a configurable retry count. New
Spring AI 1.x — manual exception handling
// Spring AI 1.x — catch parse failures manually
for (int i = 0; i < 3; i++) {
    try {
        Recipe recipe = chatClient.prompt()
            .user("Give me a pasta recipe as JSON")
            .call()
            .entity(Recipe.class);
        return recipe; // success
    } catch (JsonParseException e) {
        // log and retry — no framework help
        log.warn("Parse failed, retrying: {}", e);
    }
}
throw new RuntimeException("Gave up after 3 tries");
Spring AI 2.x — validateSchema() auto-retry
// Spring AI 2.x — built-in self-correcting loop
Recipe recipe = chatClient.prompt()
    .user("Give me a pasta recipe as JSON")
    .call()
    .entity(
        EntityResponseSpec.forEntity(Recipe.class)
        .validateSchema()          // auto-retry on mismatch
        .maxRetries(3)             // default: 3
        .useProviderStructuredOutput() // optional
    );
// Framework re-prompts with the validation error;
// no try/catch needed in application code

Observability API (Micrometer auto-instrumentation)

 Spring AI 0.x / early 1.x had no built-in observability. Token usage, latency, and model metadata required custom logging or third-party wrappers around the ChatModel interface. Spring AI 1.x introduced automatic Micrometer instrumentation via ObservationRegistry. When Micrometer is on the classpath, every ChatModel.call() produces an observation that records latency, prompt token count, completion token count, model name, and finish reason. New
Spring AI 0.x — no built-in observability
// Spring AI 0.x — wrap manually to track tokens
public class InstrumentedChatModel
        implements ChatModel {

    private final ChatModel delegate;
    private final MeterRegistry registry;

    @Override
    public ChatResponse call(Prompt prompt) {
        long start = System.nanoTime();
        ChatResponse resp = delegate.call(prompt);
        long elapsed = System.nanoTime() - start;
        registry.timer("ai.call.latency")
            .record(elapsed, TimeUnit.NANOSECONDS);
        // Token counts: parse from resp manually
        return resp;
    }
}
Spring AI 1.x — auto Micrometer observations
# application.yml — enable AI observations
management:
  observations:
    spring-ai:
      chat:
        enabled: true
        # records: gen_ai.operation.name,
        # gen_ai.system, gen_ai.response.model,
        # gen_ai.usage.input_tokens,
        # gen_ai.usage.output_tokens
// No wrapper needed — auto-configured
// ChatModel bean is already instrumented.
// Works with Prometheus, Zipkin, OTLP, etc.
// Access via Actuator /actuator/metrics/
//   gen_ai.client.operation.duration

0.x → 1.0 Breaking Changes (package renames, ChatClient refactor)

 Spring AI 0.x was a milestone series with no stability guarantee. Key classes lived in org.springframework.ai.client; the fluent ChatClient API did not exist — you called ChatModel.call(Prompt) directly. Spring AI 1.0 GA formalised the ChatClient fluent builder API (wrapping ChatModel), renamed packages from org.springframework.ai.client to org.springframework.ai.chat.client, and introduced the semantic versioning stability guarantee. Changed
Spring AI 0.x — direct ChatModel.call()
// Spring AI 0.x milestones — low-level call
import org.springframework.ai.chat.ChatResponse;
import org.springframework.ai.chat.prompt.Prompt;
// package: org.springframework.ai.openai.OpenAiChatModel

@Autowired OpenAiChatModel chatModel;

ChatResponse response = chatModel.call(
    new Prompt("Tell me a joke"));
String text = response
    .getResult()
    .getOutput()
    .getContent();
Spring AI 1.0 GA — ChatClient fluent API
// Spring AI 1.0 GA — ChatClient builder
import org.springframework.ai.chat.client.ChatClient;
// Auto-configured ChatClient.Builder injected

@Autowired ChatClient.Builder builder;

ChatClient chatClient = builder.build();

// Fluent API — replaces direct ChatModel usage
String joke = chatClient.prompt()
    .user("Tell me a joke")
    .call()
    .content();

// ChatModel still accessible for low-level use;
// ChatClient is the recommended entry point
