Spring AI Structured Output

Spring AI 1.x Spring AI 2.x

Structured Output lets you instruct an AI model to return JSON that maps directly to a Java record or class, turning unstructured language model responses into strongly-typed objects your application can work with immediately. Spring AI ships several StructuredOutputConverter implementations — BeanOutputConverter<T>, ListOutputConverter, and MapOutputConverter — that derive a JSON Schema from your types, inject formatting instructions into the prompt, and parse the model's response back into Java objects automatically.

How Structured Output Works

Spring AI's structured output pipeline has three stages. First, a StructuredOutputConverter derives a JSON Schema (JSON Schema DRAFT_2020_12) from your target class and calls getFormat() to produce instructions telling the model to output JSON matching that schema. Second, those instructions are appended to the prompt before the call is made. Third, after the model replies, convert(String) parses the raw text response into the desired Java type using Jackson. With Spring AI 2.x you can also enable self-correcting validation via validateSchema() and provider-native structured output via useProviderStructuredOutput(), which skips prompt injection entirely and delegates schema enforcement to the provider's API.

BeanOutputConverter<T> — Basics and ChatClient Shorthand

BeanOutputConverter<T> is the primary StructuredOutputConverter for mapping model output to a specific Java class. It derives a JSON Schema (DRAFT_2020_12) from the target class using Jackson's schema module and injects schema instructions into the prompt via getFormat(). The ChatClient fluent API exposes a convenient shorthand: .call().entity(MyRecord.class) creates and applies a BeanOutputConverter internally — no need to instantiate it yourself. The model receives the schema instructions with its prompt and returns JSON; Spring AI parses it back to your Java type automatically.

Dependency (pom.xml)

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.ai</groupId>
      <artifactId>spring-ai-bom</artifactId>
      <version>2.0.0</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-openai-spring-boot-starter</artifactId>
  </dependency>
</dependencies>

Example — .call().entity(Class<T>) shorthand

// Define the target record
record ActorsFilms(String actor, List<String> movies) {}

// ChatClient shorthand — creates BeanOutputConverter<ActorsFilms> internally
ActorsFilms result = chatClient.prompt()
    .user(u -> u.text("Generate the filmography of 5 movies for {actor}.")
                .param("actor", "Tom Hanks"))
    .call()
    .entity(ActorsFilms.class);

System.out.println(result.actor());   // "Tom Hanks"
System.out.println(result.movies());  // ["Forrest Gump", ...]

Defining a Java Record as the Target Type

Java records are the ideal target type for BeanOutputConverter: they are concise, immutable, and their component names map directly to JSON property names. For richer schema generation, annotate record components with @JsonPropertyDescription("...") to embed human-readable hints in the schema — the model uses these hints to understand what value is expected in each field. Use @JsonPropertyOrder({"field1", "field2"}) on the record to control the order of properties in the generated JSON Schema, which can improve model compliance. Nested records are fully supported — Spring AI recursively derives schemas for each nested type.

Example — Record with annotations and nesting

import com.fasterxml.jackson.annotation.JsonPropertyDescription;
import com.fasterxml.jackson.annotation.JsonPropertyOrder;

// Simple record
record MovieReview(String title, int rating, String summary) {}

// Annotated record for richer schema hints
@JsonPropertyOrder({"title", "year", "rating", "summary", "pros"})
record DetailedReview(
    @JsonPropertyDescription("Exact movie title as released") String title,
    @JsonPropertyDescription("Release year as 4-digit integer") int year,
    @JsonPropertyDescription("Rating from 1 (worst) to 10 (best)") int rating,
    @JsonPropertyDescription("Two-sentence plot summary") String summary,
    @JsonPropertyDescription("Up to three positive aspects") List<String> pros
) {}

// Nested record
record Actor(String name, String nationality) {}
record FilmCredit(Actor actor, String role, MovieReview review) {}

// Usage
DetailedReview review = chatClient.prompt()
    .user("Review the movie Inception.")
    .call()
    .entity(DetailedReview.class);

System.out.printf("Title: %s, Rating: %d/10%n", review.title(), review.rating());

Extracting a List — ParameterizedTypeReference

Java type erasure means that List.class carries no information about its element type at runtime. To extract a List<T> of records, pass a ParameterizedTypeReference<List<T>> anonymous subclass to .entity(). This preserves the full generic type information so BeanOutputConverter can derive the correct JSON Schema for an array of objects and Jackson can deserialize each element. Without ParameterizedTypeReference, the converter would not know what element type to use during parsing.

Note: ParameterizedTypeReference<List<T>> works with the prompt-based flow. It is not compatible with useProviderStructuredOutput() because the OpenAI Structured Outputs API rejects top-level JSON arrays. Use a wrapper record (e.g. record ReviewList(List<MovieReview> reviews) {}) when combining lists with provider-native structured output.

Example — .call().entity(new ParameterizedTypeReference<List<MovieReview>>() {})

import org.springframework.core.ParameterizedTypeReference;

// Extracting a list of records
List<MovieReview> reviews = chatClient.prompt()
    .user("Write brief reviews for three recent sci-fi films.")
    .call()
    .entity(new ParameterizedTypeReference<List<MovieReview>>() {});

// Each element is a fully typed MovieReview record
reviews.forEach(r ->
    System.out.printf("%s — %d/10: %s%n", r.title(), r.rating(), r.summary()));

// Also works for Map<String, Object>
Map<String, Object> data = chatClient.prompt()
    .user("Return a JSON object with the keys 'count' and 'items' for five fruits.")
    .call()
    .entity(new ParameterizedTypeReference<Map<String, Object>>() {});

ListOutputConverter and MapOutputConverter

ListOutputConverter and MapOutputConverter are simpler alternatives to BeanOutputConverter for common output shapes. ListOutputConverter instructs the model to output a comma-separated list and converts the text to a List<String> using Spring's ConversionService — no JSON schema involved. MapOutputConverter instructs the model to output a YAML-like key-value format and returns a Map<String, Object>. Both converters are passed as converter instances to the .entity() overload that accepts a StructuredOutputConverter directly.

Example — ListOutputConverter and MapOutputConverter

import org.springframework.ai.converter.ListOutputConverter;
import org.springframework.ai.converter.MapOutputConverter;
import org.springframework.core.convert.support.DefaultConversionService;

// ListOutputConverter — returns List<String>
List<String> flavors = chatClient.prompt()
    .user(u -> u.text("List five {subject}")
                .param("subject", "ice cream flavors"))
    .call()
    .entity(new ListOutputConverter(new DefaultConversionService()));

System.out.println(flavors); // ["Vanilla", "Chocolate", "Strawberry", ...]

// MapOutputConverter — returns Map<String, Object>
Map<String, Object> capitals = chatClient.prompt()
    .user("Provide a map of three European countries and their capitals.")
    .call()
    .entity(new MapOutputConverter());

System.out.println(capitals); // {France=Paris, Germany=Berlin, Italy=Rome}

BeanOutputConverter with the Low-Level ChatModel API

When you need explicit control over the conversion process — for example, in batch jobs, test stubs, or when using the lower-level ChatModel API without ChatClient — you can instantiate BeanOutputConverter<T> directly. Call getFormat() to obtain the schema instructions string, embed it in a PromptTemplate variable, and after the model call pass the response text to convert(String) to get the typed result. This is also useful when you want to inspect or log the generated JSON Schema before sending it to the model.

Example — Manual BeanOutputConverter with ChatModel

import org.springframework.ai.converter.BeanOutputConverter;
import org.springframework.ai.chat.prompt.PromptTemplate;

// Instantiate the converter
BeanOutputConverter<MovieReview> converter =
    new BeanOutputConverter<>(MovieReview.class);

// Inspect the generated JSON Schema instructions
String formatInstructions = converter.getFormat();
System.out.println(formatInstructions); // "Respond using this JSON Schema: ..."

// Build the prompt with schema injected as a {format} variable
String template = """
    Review the movie "{title}".
    {format}
    """;

Prompt prompt = PromptTemplate.builder()
    .template(template)
    .variables(Map.of("title", "The Matrix", "format", formatInstructions))
    .build()
    .create();

// Call the model directly
Generation generation = chatModel.call(prompt).getResult();

// Convert raw text to a typed record
MovieReview review = converter.convert(generation.getOutput().getText());
System.out.printf("Rating: %d — %s%n", review.rating(), review.summary());

validateSchema() — Automatic Self-Correction

Spring AI 2.x — validateSchema() is a new Spring AI 2.0 feature. It is available on the .entity() spec consumer and requires no manual wiring beyond enabling it.

validateSchema() activates a retry loop that validates the model's JSON response against the derived schema before returning the result. Internally it registers a StructuredOutputValidationAdvisor around the call. When the model's response fails schema validation — for example, a required field is missing, a numeric field arrives as a string, or the JSON is syntactically invalid — Spring AI automatically sends a follow-up prompt containing the original response, the schema, and the validation errors, asking the model to correct its output. The corrected response is validated again, and the cycle repeats until validation passes or the retry limit is reached. By default up to 3 attempts are made (1 original + 2 retries).

Example — enabling validateSchema()

// Enable schema validation with default 3 attempts
MovieReview review = chatClient.prompt()
    .user("Review the film Oppenheimer.")
    .call()
    .entity(MovieReview.class, spec -> spec.validateSchema());

// Combined: validate AND use provider-native output
DetailedReview detail = chatClient.prompt()
    .user("Review Interstellar in detail.")
    .call()
    .entity(DetailedReview.class, spec -> spec
        .useProviderStructuredOutput()
        .validateSchema());

Configuring Max Retry Attempts

The default retry count of 3 (1 original call + 2 corrective retries) is suitable for most use cases. For schemas that are complex or for models that frequently deviate from structured output, you can increase the retry limit. Conversely, for cost-sensitive pipelines, setting a lower retry count (or none) may be appropriate. When all retry attempts are exhausted without a valid response, Spring AI throws a StructuredOutputValidationException containing the last received response and the validation errors, which you can catch and handle — for example, by falling back to a simpler schema or logging for manual review.

Example — custom retry count and exception handling

import org.springframework.ai.converter.StructuredOutputValidationException;

// Allow up to 5 total attempts (1 original + 4 retries)
try {
    DetailedReview review = chatClient.prompt()
        .user("Give a detailed review of Blade Runner 2049.")
        .call()
        .entity(DetailedReview.class, spec -> spec
            .validateSchema()
            .maxRetries(5));
    return review;
} catch (StructuredOutputValidationException ex) {
    // All retries exhausted — ex.getLastResponse() has the raw output
    // ex.getValidationErrors() has the schema violations
    log.warn("Schema validation failed after all retries: {}",
             ex.getValidationErrors());
    // Fall back or rethrow
    throw new ServiceException("Could not parse movie review", ex);
}

Self-Correction with Complex Nested Records

Deeply nested records with required fields and constrained types are the cases most likely to trip up a language model on the first attempt. A model might omit a nested object's required field, return a number as a string, or emit an enum value with different casing. validateSchema() catches all of these on the first pass and automatically resends a corrective prompt showing the model exactly which fields failed and why. The self-correction approach is especially valuable for schemas with three or more levels of nesting or with array-typed fields that must have specific element types.

Example — nested schema that benefits from self-correction

// Three-level nested record — LLMs sometimes omit the inner "director" object
record Director(String name, String nationality) {}
record ProductionDetails(
    Director director,
    int budget,                // LLMs may emit as "120 million" (String) — fails schema
    List<String> castMembers
) {}
record FullFilmReport(
    String title,
    int year,
    String genre,
    ProductionDetails production,
    List<MovieReview> criticReviews
) {}

// validateSchema() will catch "director" missing / budget as String, etc.
FullFilmReport report = chatClient.prompt()
    .user("""
        Produce a full report on the film 'Dune: Part Two' (2024).
        Include director details, budget in millions (integer only),
        at least two cast members, and two brief critic reviews.
        """)
    .call()
    .entity(FullFilmReport.class, spec -> spec
        .validateSchema()
        .maxRetries(4));

System.out.println(report.production().director().name()); // Denis Villeneuve

Combining validateSchema() with ParameterizedTypeReference

Self-correction works with ParameterizedTypeReference for list extraction as well. Pass the type reference as the first argument to .entity() and chain the spec consumer as the second argument. Spring AI validates that the model returned a JSON array with all element objects conforming to the element type's schema, and re-prompts automatically on failure. This combination is useful when parsing collections from documents where a field might be omitted for some items but not others — the self-correction loop fills in or fixes individual array elements.

Example — validateSchema() with a list

// Self-correcting list extraction
List<MovieReview> reviews = chatClient.prompt()
    .user("""
        Write reviews for these three films: 'Everything Everywhere All at Once',
        'The Banshees of Inisherin', and 'Tar'. Each review must include title,
        an integer rating from 1-10, and a one-sentence summary.
        """)
    .call()
    .entity(
        new ParameterizedTypeReference<List<MovieReview>>() {},
        spec -> spec.validateSchema().maxRetries(3));

// Guaranteed: every element in the list has all required fields
reviews.forEach(r ->
    System.out.printf("[%d/10] %s: %s%n", r.rating(), r.title(), r.summary()));

useProviderStructuredOutput() — Provider-Native JSON Schema

Spring AI 2.x — useProviderStructuredOutput() is a new Spring AI 2.0 feature. It replaces prompt-based schema injection with a provider API-level constraint, producing more reliable structured output without consuming additional prompt tokens for format instructions.

useProviderStructuredOutput() instructs Spring AI to send the JSON Schema derived from your target record directly to the provider's structured output API instead of injecting it into the prompt text. For OpenAI, this sets response_format: {"type": "json_schema", "json_schema": <schema>} in the request; for Anthropic it uses the tool-use mechanism internally. The provider then enforces the schema at the API level, eliminating the risk of the model ignoring format instructions. Because the schema is not in the prompt, you save tokens on every call. Enable globally via AdvisorParams.ENABLE_NATIVE_STRUCTURED_OUTPUT or per-call via the spec consumer.

Example — per-call and global enablement

// Per-call: useProviderStructuredOutput()
ActorsFilms result = chatClient.prompt()
    .user("Generate the filmography of 5 movies for a random actor.")
    .call()
    .entity(ActorsFilms.class, spec -> spec.useProviderStructuredOutput());

// Per-call: with schema validation as a safety net
DetailedReview review = chatClient.prompt()
    .user("Write a detailed review of 'Poor Things'.")
    .call()
    .entity(DetailedReview.class, spec -> spec
        .useProviderStructuredOutput()
        .validateSchema());

// Global: set on ChatClient.Builder so every .entity() call uses it
@Bean
ChatClient chatClient(ChatClient.Builder builder) {
    return builder
        .defaultAdvisors(AdvisorParams.ENABLE_NATIVE_STRUCTURED_OUTPUT)
        .build();
}

OpenAI response_format: json_schema

OpenAI's Structured Outputs feature (available on GPT-4o models from gpt-4o-2024-08-06 and later) guarantees that the model's response conforms to the provided JSON Schema. When useProviderStructuredOutput() is active, Spring AI generates the JSON Schema from your record using BeanOutputConverter's schema generator and sends it as the response_format.json_schema field in the OpenAI API request. The model is constrained at inference time — not just prompted — so the JSON is structurally guaranteed. One important limitation is that the OpenAI API does not accept a top-level JSON array as the schema root; wrapping the list in a record resolves this.

Example — OpenAI provider-native with wrapper record for lists

// Top-level List<T> does NOT work with useProviderStructuredOutput() on OpenAI
// Use a wrapper record instead:
record FilmographyList(List<ActorsFilms> filmographies) {}

FilmographyList result = chatClient.prompt()
    .options(OpenAiChatOptions.builder()
        .model("gpt-4o-2024-08-06")   // minimum version for Structured Outputs
        .build())
    .user("Generate filmographies for Tom Hanks, Meryl Streep, and Denzel Washington.")
    .call()
    .entity(FilmographyList.class, spec -> spec.useProviderStructuredOutput());

// Unwrap the list
List<ActorsFilms> films = result.filmographies();
films.forEach(f -> System.out.printf("%s: %s%n", f.actor(), f.movies()));

Trade-offs: Provider-Native vs BeanOutputConverter

Choosing between useProviderStructuredOutput() (provider-native) and the default prompt-based BeanOutputConverter approach involves three main trade-offs: reliability, portability, and token cost. Provider-native structured output offers stronger guarantees — the model's output is constrained at the API level — but it locks you into a specific provider (OpenAI, Anthropic, etc.) and requires a model version that supports it. The default prompt-based approach works with any model that follows instructions, including local models via Ollama, but is dependent on the model faithfully following schema instructions in the prompt text. Self-correction (validateSchema()) bridges the gap by automatically retrying when the model fails to comply.

Comparison Table

Dimension Prompt-Based (BeanOutputConverter) Provider-Native (useProviderStructuredOutput)
Schema enforcement Best-effort (model must follow instructions) Guaranteed at API level
Token overhead Extra tokens for format instructions No extra prompt tokens
Provider portability Works with any model (OpenAI, Anthropic, Ollama, …) Only supported providers (OpenAI GPT-4o+, Anthropic Claude 3.5+, Gemini, Mistral)
Top-level arrays Supported via ParameterizedTypeReference<List<T>> Not supported — wrap in a record
Retry on failure Manual, or via validateSchema() Provider-enforced; combine with validateSchema() for extra safety
Minimum Spring AI version 1.x 2.x

Anthropic Claude — Tool-Use JSON Mode

For Anthropic Claude models (Claude 3.5 Sonnet and later), useProviderStructuredOutput() works by instructing Spring AI to use Anthropic's tool-use mechanism as a structured output channel. Rather than using a response_format field (which OpenAI-style APIs provide), Anthropic's API exposes structured output by defining a tool with the desired JSON Schema as its input schema and forcing the model to call that tool. Spring AI handles this automatically when targeting an Anthropic ChatModel — the call site looks identical to the OpenAI path. Supported models include claude-3-5-sonnet-20241022 and later. The same wrapper-record restriction applies if you need list output with provider-native mode.

Example — Anthropic provider-native structured output

// spring-ai-anthropic-spring-boot-starter on classpath
// Spring AI auto-selects tool-use mode for Anthropic ChatModel

record BookRecommendation(
    String title,
    String author,
    String genre,
    @JsonPropertyDescription("Short reason this book is recommended") String reason
) {}

// Same API as OpenAI — Spring AI handles tool-use internally for Anthropic
BookRecommendation book = chatClient.prompt()
    .options(AnthropicChatOptions.builder()
        .model("claude-3-5-sonnet-20241022")
        .build())
    .user("Recommend one classic science fiction novel.")
    .call()
    .entity(BookRecommendation.class, spec -> spec.useProviderStructuredOutput());

System.out.printf("Recommended: %s by %s (%s)%n",
    book.title(), book.author(), book.genre());

Image to Java Record — Parsing a Receipt Photo

Spring AI supports combining multimodal input (an image) with structured output (a Java record) in a single call. Attach the image via UserMessage with a Media object, and instead of calling .content() for raw text, call .entity(ReceiptRecord.class). Spring AI injects the JSON Schema instructions alongside the image and your text prompt, and the vision model returns JSON that is parsed into your record. This pattern is useful for document digitization, receipt parsing, form data extraction, and any task requiring both visual understanding and structured output.

Example — Parsing a receipt image into a Java record

import org.springframework.ai.chat.messages.UserMessage;
import org.springframework.ai.model.Media;
import org.springframework.core.io.ClassPathResource;
import org.springframework.util.MimeTypeUtils;

// Records for structured receipt data
record LineItem(String name, int quantity, double price) {}
record Receipt(
    String merchant,
    String date,
    List<LineItem> items,
    double subtotal,
    double tax,
    double total
) {}

// Attach the image and request structured output
Resource receiptImage = new ClassPathResource("receipts/coffee-shop.jpg");
UserMessage message = new UserMessage(
    "Extract all information from this receipt into structured JSON.",
    List.of(new Media(MimeTypeUtils.IMAGE_JPEG, receiptImage)));

Receipt receipt = chatClient.prompt()
    .options(OpenAiChatOptions.builder().model("gpt-4o").build())
    .messages(message)
    .call()
    .entity(Receipt.class);

System.out.printf("Merchant: %s, Total: $%.2f%n", receipt.merchant(), receipt.total());
receipt.items().forEach(i ->
    System.out.printf("  %dx %s @ $%.2f%n", i.quantity(), i.name(), i.price()));

Combining Text and Image for Structured Extraction

You can mix a detailed text instruction with an image reference in a single UserMessage to guide the model's visual reasoning and constrain its output format simultaneously. Adding clear extraction instructions (which fields to include, how to handle ambiguous values, what to do with missing data) alongside the image improves schema compliance and reduces the need for retries. For best results, describe the schema's required fields explicitly in the text instruction rather than relying solely on the injected schema instructions — models respond better when the human-readable prompt reinforces the machine-readable schema.

Example — text + image with structured extraction

record BusinessCard(
    String name,
    String title,
    String company,
    String email,
    String phone,
    String website
) {}

Resource cardImage = new ClassPathResource("images/business-card.png");
UserMessage message = new UserMessage(
    """
    Extract the contact information from this business card.
    For any field not visible on the card, use null.
    Pay special attention to the email address and phone number.
    """,
    List.of(new Media(MimeTypeUtils.IMAGE_PNG, cardImage)));

// Add validateSchema() for robustness — vision models may miss optional fields
BusinessCard contact = chatClient.prompt()
    .options(OpenAiChatOptions.builder().model("gpt-4o").build())
    .messages(message)
    .call()
    .entity(BusinessCard.class, spec -> spec.validateSchema());

System.out.printf("Contact: %s (%s) at %s%n",
    contact.name(), contact.title(), contact.company());

Provider Support for Multimodal Structured Output

Multimodal structured output requires both vision capability (to process the image) and structured output support (to return typed JSON). Not all providers support both simultaneously. OpenAI's GPT-4o family and Anthropic's Claude 3+ family are the primary production choices for combining image input with .entity() structured output calls. Google Gemini models (via Spring AI's Vertex AI starter) also support multimodal structured output. Local models via Ollama may support vision (e.g. llava, moondream) but their structured output compliance varies significantly by model size.

Provider Support Matrix

Provider / Model Vision Input Structured Output (.entity()) Notes
OpenAI GPT-4o Yes (URL + base64) Yes (prompt + native) Best overall support; use gpt-4o for multimodal structured output
Anthropic Claude 3+ Yes (base64 only) Yes (prompt + tool-use native) claude-3-5-sonnet-20241022 and later; no URL-based images
Google Gemini 1.5+ Yes (URL + file API) Yes (prompt-based) Native structured output support varies by model version
Ollama (vision models) Yes (base64 — llava, moondream) Limited (prompt-based only) Schema compliance varies; use validateSchema() with retries
Azure OpenAI Yes (same as OpenAI) Yes (same as OpenAI) Requires GPT-4o deployment; same model restrictions apply

validateSchema() with Multimodal Calls

Vision models are more likely to miss required fields or produce slightly malformed JSON than text-only models — they are simultaneously reasoning about the image and following schema instructions. Adding validateSchema() to multimodal .entity() calls is therefore especially recommended. The retry mechanism sends the original image and instructions along with the corrective prompt on each retry, so the model can revisit both the visual content and the failed schema constraints. Setting a higher maxRetries value (4–5) is worthwhile for complex documents such as tables, forms, or multi-section receipts where the model may need more than one correction pass.

Example — multimodal entity extraction with validation and retries

record ProductLabel(
    String productName,
    String brand,
    String servingSize,
    int calories,
    double totalFatGrams,
    double sodiumMg,
    List<String> ingredients
) {}

Resource labelImage = new ClassPathResource("images/nutrition-label.jpg");
UserMessage message = new UserMessage(
    """
    Extract the nutritional information from this product label.
    Calories and sodium must be integers/numbers, not strings.
    Ingredients should be a list of individual ingredient names.
    """,
    List.of(new Media(MimeTypeUtils.IMAGE_JPEG, labelImage)));

ProductLabel label = chatClient.prompt()
    .options(OpenAiChatOptions.builder().model("gpt-4o").build())
    .messages(message)
    .call()
    .entity(ProductLabel.class, spec -> spec
        .validateSchema()
        .maxRetries(4));   // vision tasks may need extra attempts

System.out.printf("%s by %s — %d cal per %s%n",
    label.productName(), label.brand(),
    label.calories(), label.servingSize());
