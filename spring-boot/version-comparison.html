Spring Boot 3.x vs 4.x — Feature Comparison

Spring Boot 4.0 (November 2025) is a major revision built on Spring Framework 7, targeting Jakarta EE 11, Java 17+, Hibernate 7, Jackson 3, and Spring Security 7. This page compares each significant area of change from Boot 3.x (latest: 3.5.7) to Boot 4.x. Click any row to expand a side-by-side code diff.

 Spring Framework 6.x — requires Java 17+, Jakarta EE 9+, AOT processing, GraalVM native support. Spring Framework 7.x — built on Jakarta EE 11, adds JSpecify null safety, built-in retry/concurrency, CRaC checkpoint support. Changed

 Java 17 minimum; Java 21 recommended for virtual threads (opt-in with spring.threads.virtual.enabled=true). Java 17 minimum retained; Java 21+ strongly recommended for default-on virtual threads; Java 25 (next LTS) supported. Changed

 Jakarta EE 9 baseline — Servlet 5.0, JPA 3.0, Bean Validation 3.0, CDI 3.0. All javax.* replaced with jakarta.*. Jakarta EE 11 — Servlet 6.1, JPA 3.2 (@Find, @Query), Bean Validation 3.1, CDI 4.1. Changed

<dependency>

  <version>6.1.0</version>

Hibernate ORM Version (6.x → 7.x)

 Hibernate ORM 6.x — Jakarta EE 9 namespace, improved HQL, SQM query engine, lazy loading improvements. Hibernate ORM 7.x — Jakarta EE 11 alignment, stateless session improvements, enhanced batch processing, removed legacy APIs. Changed
Boot 3.x — Hibernate 6
// Hibernate 6 in Boot 3 — jakarta namespace

import jakarta.persistence.Id;

    // better query caching, SQM engine
}
Boot 4.x — Hibernate 7
// Hibernate 7 in Boot 4
// JPA 3.2 @Find, @Query natively supported
// StatelessSession improvements for batch ops
import jakarta.persistence.Entity;
import jakarta.persistence.Id;

@Entity
public class Product {
    @Id

    private String name;

    // Enhanced batch insert/update performance

Jackson Version (2.x → 3.x default)

 Jackson 2.x (2.17+) — com.fasterxml.jackson groupId. Standard ObjectMapper, JsonNode API. Jackson 3.x default — groupId changed to tools.jackson. Updated ObjectMapper, ValueType API, improved records support. Changed
Boot 3.x — Jackson 2.x
<!-- Boot 3 — jackson 2.x -->
<dependency>
  <groupId>com.fasterxml.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
  <version>2.17.x</version>
</dependency>
// Jackson 2 usage
ObjectMapper mapper = new ObjectMapper();
JsonNode node = mapper.readTree(json);
String name = node.get("name").asText();
Boot 4.x — Jackson 3.x
<!-- Boot 4 — jackson 3.x (breaking change!) -->
<dependency>
  <groupId>tools.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
  <version>3.0.x</version>
</dependency>
// Jackson 3 — groupId and API changes
// ValueType replaces TypeReference in some APIs
// Records serialized without annotations needed
ObjectMapper mapper = new ObjectMapper();
JsonNode node = mapper.readTree(json);
// Core traversal API updated — check migration guide

Spring Security Version (6.x → 7.x)

 Spring Security 6.x — SecurityFilterChain component model, HttpSecurity lambda DSL. AntPathRequestMatcher still available. Spring Security 7.x — AntPathRequestMatcher removed; use MvcRequestMatcher or PathPatternRequestMatcher. Enhanced OAuth2/OIDC. Changed
Boot 3.x — Security 6 + AntPathRequestMatcher
// Boot 3 — AntPathRequestMatcher still usable
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(
            HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
            .requestMatchers(
                new AntPathRequestMatcher("/api/**"))
            .authenticated()
            .anyRequest().permitAll()
        );
        return http.build();
    }
}
Boot 4.x — Security 7: AntPathRequestMatcher removed
// Boot 4 — AntPathRequestMatcher REMOVED
// Migrate to PathPatternRequestMatcher or
// the simplified string-based matchers
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(
            HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
            // Use string patterns directly:
            .requestMatchers("/api/**")
                .authenticated()
            .anyRequest().permitAll()
        );
        return http.build();
    }
}

Virtual Threads (opt-in in Boot 3 → default in Boot 4)

 Virtual threads available since Boot 3.2 on Java 21+; must opt in via spring.threads.virtual.enabled=true. Virtual threads are enabled by default in Boot 4 on Java 21+. Set spring.threads.virtual.enabled=false to disable. Changed
Boot 3.x — virtual threads opt-in
# Boot 3 application.properties
# Virtual threads must be explicitly enabled:
spring.threads.virtual.enabled=true

# Default: platform threads (OS-backed pool)
# If omitted, Tomcat uses traditional thread pool
Boot 4.x — virtual threads on by default
# Boot 4 application.properties
# Virtual threads are ON by default (Java 21+)
# No configuration needed for most apps.

# To revert to platform threads if needed:
spring.threads.virtual.enabled=false

# Also: @Async methods auto-use virtual threads
# when VirtualThreadTaskExecutor is configured

Structured Logging (introduced in 3.4, enhanced in Boot 4)

 Boot 3.4 introduced opt-in structured logging (JSON format via Logback/Log4j2) with logging.structured.format.console=ecs. Boot 4 matures structured logging — improved field ordering, additional built-in formats, structured MDC propagation with virtual threads. Changed
Boot 3.4 — structured logging opt-in
# Boot 3.4 application.properties
# Enable Elastic Common Schema JSON output:
logging.structured.format.console=ecs

# Or logstash format:
logging.structured.format.console=logstash

# Output (ECS):
# {"@timestamp":"...","log.level":"INFO",
#  "message":"Request received","service.name":"..."}
Boot 4.x — enhanced structured logging
# Boot 4 application.properties
# Structured logging more refined:
logging.structured.format.console=ecs

# New: structured MDC carries through virtual threads
# New: additional built-in formats (gelf, etc.)
# New: consistent field ordering in all formats

# MDC with virtual threads — context propagated:
logging.structured.format.console=logstash

AutoConfiguration Mechanism (.imports file improvements)

 Boot 3 replaced spring.factories with META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Boot 4 refines the imports format — supports conditional ordering annotations, improved failure analysis, and AOT-safe configuration ordering. Changed
Boot 3.x — AutoConfiguration.imports
# META-INF/spring/
# org.springframework.boot.autoconfigure.AutoConfiguration.imports

com.example.MyDatabaseAutoConfiguration
com.example.MySecurityAutoConfiguration
// Boot 3 auto-configuration class
@AutoConfiguration
@ConditionalOnClass(DataSource.class)
@ConditionalOnMissingBean(DataSource.class)
public class MyDataSourceAutoConfiguration {
    @Bean
    public DataSource dataSource(
            DataSourceProperties props) {
        return props.initializeDataSourceBuilder()
            .build();
    }
}
Boot 4.x — improved ordering + failure analysis
# Same file format, refined ordering support
# META-INF/spring/
# org.springframework.boot.autoconfigure.AutoConfiguration.imports

com.example.MyDatabaseAutoConfiguration
com.example.MySecurityAutoConfiguration
// Boot 4: @AutoConfiguration gets enhanced
// @AutoConfigureAfter / @AutoConfigureBefore
// more reliable for AOT processing
@AutoConfiguration
@AutoConfigureAfter(DataSourceAutoConfiguration.class)
@ConditionalOnClass(DataSource.class)
public class MyDataSourceAutoConfiguration {
    // Better failure-analysis messages in Boot 4
    // when conditions are not met
    @Bean
    public DataSource dataSource(
            DataSourceProperties props) {
        return props.initializeDataSourceBuilder()
            .build();
    }
}

@HttpExchange Interface Clients (enhanced in Boot 4)

 Boot 3 introduced @HttpExchange declarative HTTP clients (backed by RestClient or WebClient). Boot 4 enhances @HttpExchange — auto-registration via @ImportHttpServices, improved error handling, reactive + sync unified API. Changed
Boot 3.x — @HttpExchange manual registration
// Boot 3 — must register manually via factory
@HttpExchange("https://api.example.com")
public interface ProductClient {

    @GetExchange("/products/{id}")
    Product getProduct(@PathVariable Long id);

    @PostExchange("/products")
    Product createProduct(@RequestBody Product p);
}

// Manual wiring:
@Bean
ProductClient productClient(
        RestClient.Builder builder) {
    RestClient restClient = builder
        .baseUrl("https://api.example.com")
        .build();
    return HttpServiceProxyFactory
        .builderFor(RestClientAdapter
            .create(restClient))
        .build()
        .createClient(ProductClient.class);
}
Boot 4.x — @ImportHttpServices auto-registration
// Boot 4 — auto-register with @ImportHttpServices
@SpringBootApplication
@ImportHttpServices(types = ProductClient.class)
public class App {
    public static void main(String[] args) {
        SpringApplication.run(App.class, args);
    }
}

@HttpExchange("https://api.example.com")
public interface ProductClient {

    @GetExchange("/products/{id}")
    Product getProduct(@PathVariable Long id);

    @PostExchange("/products")
    Product createProduct(@RequestBody Product p);
}
// Bean is auto-created — no @Bean boilerplate
// application.properties sets base-url, timeouts

Null Safety via JSpecify Integration

 Spring Framework 6 used its own @NonNull / @Nullable annotations in org.springframework.lang. Boot 4 / Framework 7 adopts JSpecify (org.jspecify.annotations) for standardised null safety across the entire Spring API surface. New
Boot 3.x — Spring's own null annotations
// Spring Framework 6 null annotations
import org.springframework.lang.NonNull;
import org.springframework.lang.Nullable;

public interface UserService {

    @NonNull
    User findById(@NonNull Long id);

    @Nullable
    User findByEmail(@NonNull String email);
}
// These are Spring-specific; IDEs vary
// in how well they understand them
Boot 4.x — JSpecify standardised null safety
// Spring Framework 7 adopts JSpecify
// org.jspecify.annotations.*
import org.jspecify.annotations.NonNull;
import org.jspecify.annotations.Nullable;

// Package-level null-marked (common pattern):
// @NullMarked on package-info.java makes all
// types non-null by default in the package
@NullMarked
package com.example.service;

public interface UserService {

    User findById(Long id);  // non-null by default

    @Nullable
    User findByEmail(String email);
}
// Kotlin interop improved; tool support wider

gRPC First-Class Support

 Boot 3 offered no built-in gRPC support; required third-party starters (e.g. grpc-spring-boot-starter from the community). Boot 4 provides spring-boot-starter-grpc with auto-configuration for gRPC server/client, health checks, and Micrometer metrics. New
Boot 3.x — third-party gRPC starter required
<!-- Boot 3 — community starter needed -->
<dependency>
  <groupId>net.devh</groupId>
  <artifactId>grpc-spring-boot-starter</artifactId>
  <version>2.x.x.RELEASE</version>
</dependency>
// Community gRPC — vendor-specific annotations
@GrpcService
public class UserGrpcService
        extends UserServiceGrpc.UserServiceImplBase {

    @Override
    public void getUser(GetUserRequest req,
            StreamObserver<User> resp) {
        // manual error handling, no Boot integration
    }
}
Boot 4.x — first-class spring-boot-starter-grpc
<!-- Boot 4 — official starter -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-grpc</artifactId>
</dependency>
// Boot 4 — Spring-idiomatic gRPC service
@Service
@GrpcService  // from org.springframework.grpc
public class UserGrpcService
        extends UserServiceGrpc.UserServiceImplBase {

    @Override
    public void getUser(GetUserRequest req,
            StreamObserver<UserReply> resp) {
        // Auto health check, Micrometer metrics,
        // Spring Security integration built-in
    }
}
// application.properties:
// spring.grpc.server.port=9090

Built-in API Versioning

 Boot 3 had no built-in API versioning; developers implemented versioning manually (URL prefix, headers, content negotiation). Boot 4 introduces @ApiVersionMapping and configurable versioning strategies (URI, header, media type) supported natively by Spring MVC and WebFlux. New
Boot 3.x — manual URL-based versioning
// Boot 3 — manual version prefix in URL
@RestController
@RequestMapping("/api/v1/users")
public class UserV1Controller {

    @GetMapping("/{id}")
    public UserV1Response getUser(@PathVariable Long id) {
        return userService.getUserV1(id);
    }
}

@RestController
@RequestMapping("/api/v2/users")
public class UserV2Controller {

    @GetMapping("/{id}")
    public UserV2Response getUser(@PathVariable Long id) {
        return userService.getUserV2(id);
    }
}
// Duplicated controllers — hard to maintain
Boot 4.x — @ApiVersionMapping built-in
// Boot 4 — built-in versioning via annotation
// application.properties:
// spring.mvc.versioning.type=uri-path
// spring.mvc.versioning.uri-path.prefix=/api/{version}

@RestController
@RequestMapping("/users")
public class UserController {

    @GetMapping("/{id}")
    @ApiVersionMapping({"v1", "v2"})
    public UserResponse getUser(
            @PathVariable Long id,
            ApiVersion version) {
        // Same controller handles multiple versions
        if (version.isAtLeast("v2")) {
            return userService.getUserV2(id);
        }
        return userService.getUserV1(id);
    }
}

ListenableFuture Removed

 Boot 3 deprecated ListenableFuture and AsyncResult; CompletableFuture recommended as replacement. Boot 4 / Framework 7 removes ListenableFuture, AsyncResult, and SettableListenableFuture entirely. Removed
Boot 3.x — ListenableFuture (deprecated)
// Boot 3 — ListenableFuture deprecated
// @Async returning ListenableFuture still works
// but generates deprecation warnings
@Service
public class EmailService {

    @Async
    public ListenableFuture<Boolean> sendEmail(
            String to, String subject) {
        boolean result = doSend(to, subject);
        return AsyncResult.forValue(result);
        // Deprecated — migrate to CompletableFuture
    }
}
Boot 4.x — CompletableFuture required
// Boot 4 — ListenableFuture REMOVED
// Migrate to CompletableFuture (Java 8+)
@Service
public class EmailService {

    @Async
    public CompletableFuture<Boolean> sendEmail(
            String to, String subject) {
        boolean result = doSend(to, subject);
        return CompletableFuture.completedFuture(
            result);
    }

    // Or use reactive Mono from Project Reactor:
    public Mono<Boolean> sendEmailReactive(
            String to, String subject) {
        return Mono.fromCallable(
            () -> doSend(to, subject));
    }
}

Undertow Embedded Server Removed

 Boot 3 supported Undertow as an embedded servlet container alongside Tomcat and Jetty via spring-boot-starter-undertow. Boot 4 removes Undertow support. Use Tomcat (default) or Jetty. Reactor Netty remains the reactive server. Removed
Boot 3.x — Undertow as an option
<!-- Boot 3 — switch to Undertow -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-tomcat</artifactId>
    </exclusion>
  </exclusions>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-undertow</artifactId>
</dependency>
Boot 4.x — Tomcat or Jetty only
<!-- Boot 4 — Undertow removed, use Tomcat (default) -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <!-- Uses Tomcat by default -->
</dependency>

<!-- Or switch to Jetty: -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>
<!-- Reactive: Reactor Netty via WebFlux starter -->

Deprecated MVC APIs Removed (WebMvcConfigurationSupport legacy methods)

 Boot 3 retained deprecated WebMvcConfigurationSupport override methods and legacy HandlerInterceptorAdapter. Boot 4 removes HandlerInterceptorAdapter and various deprecated WebMvcConfigurer / WebMvcConfigurationSupport methods. Removed
Boot 3.x — HandlerInterceptorAdapter deprecated
// Boot 3 — HandlerInterceptorAdapter deprecated
// but still compiles with warning
public class LoggingInterceptor
        extends HandlerInterceptorAdapter {

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler) {
        log.info("Request: {}", request.getRequestURI());
        return true;
    }
}
Boot 4.x — implement HandlerInterceptor directly
// Boot 4 — HandlerInterceptorAdapter REMOVED
// Implement HandlerInterceptor interface directly
public class LoggingInterceptor
        implements HandlerInterceptor {

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler) {
        log.info("Request: {}", request.getRequestURI());
        return true;
    }
    // postHandle and afterCompletion are
    // default methods — override only what you need
}

CrudRepository count/exists Return Types (deprecated in Boot 4)

 Boot 3: CrudRepository.count() returns long; existsById() returns boolean. Boot 4: boxed Long / Boolean overloads added; primitive versions deprecated to align with null-safe API contracts. Deprecated
Boot 3.x — primitive return types
// Boot 3 — CrudRepository returns primitives
@Repository
public interface ProductRepository
        extends CrudRepository<Product, Long> {
}

// Usage:
long count = productRepository.count();
boolean exists = productRepository
    .existsById(42L);
Boot 4.x — boxed types preferred
// Boot 4 — primitive methods deprecated
// Migrate to boxed type methods
@Repository
public interface ProductRepository
        extends CrudRepository<Product, Long> {
}

// Preferred in Boot 4 (null-safe, JSpecify aligned):
Long count = productRepository.count();
// or use Optional-returning query methods

Boolean exists = productRepository
    .existsById(42L);
// Primitive versions still work but emit warnings
