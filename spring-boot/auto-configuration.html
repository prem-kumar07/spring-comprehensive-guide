Spring Boot Auto-Configuration

Spring Boot auto-configuration automatically configures your application based on the dependencies present on the classpath, eliminating the need for manual bean declarations. It evaluates @Conditional annotations at startup and only registers beans when the relevant conditions — a class being present, a property being set, a bean being absent — are satisfied, so user-defined beans always take precedence over auto-configured ones.

How Auto-Configuration Works

Auto-configuration is driven by a fixed loading sequence: @SpringBootApplication includes @EnableAutoConfiguration, which activates AutoConfigurationImportSelector. The selector reads a list of candidate configuration classes from a metadata file, then evaluates each class's @Conditional annotations before deciding whether to register its beans.

@SpringBootApplication as Entry Point

@SpringBootApplication is a composed annotation that combines @SpringBootConfiguration, @EnableAutoConfiguration, and @ComponentScan. The @EnableAutoConfiguration part is what kicks off the entire auto-configuration process. Placing it on your main class tells Spring Boot to search for auto-configuration candidates and selectively apply them before the application context is fully refreshed.

Example

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

AutoConfigurationImportSelector

AutoConfigurationImportSelector implements DeferredImportSelector and is the class responsible for reading the list of auto-configuration candidates. In Spring Boot 3 it reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (one fully-qualified class name per line). It then filters the list by excluding any classes listed in spring.autoconfigure.exclude, and hands the remaining candidates to the condition evaluation engine.

Relevant dependency

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-autoconfigure</artifactId>
</dependency>

Auto-Configuration Ordering

Auto-configuration classes can declare ordering constraints using @AutoConfigureBefore and @AutoConfigureAfter to control which configurations are processed first. For example, a security auto-configuration may need to run after the data-source auto-configuration. Additionally, @AutoConfigureOrder (analogous to @Order) provides numeric ordering. These hints are resolved by AutoConfigurationSorter before the conditions are evaluated.

Example

@AutoConfiguration
@AutoConfigureAfter(DataSourceAutoConfiguration.class)
@ConditionalOnBean(DataSource.class)
public class MyDataAutoConfiguration {
    // Only applied after DataSourceAutoConfiguration
}

@Conditional Annotations

Spring Boot ships a rich set of @Conditional annotations that allow auto-configuration classes to declare precisely when they should apply. All of these annotations can be placed on @Configuration classes or individual @Bean methods. When multiple conditions are present, all must pass for the configuration to be applied.

@ConditionalOnClass

Matches when the specified class (or all specified classes) are present on the classpath. This is the most common condition in auto-configurations — it ensures that a driver or library class exists before registering beans that depend on it. The check is done at the bytecode level without actually loading the class, so it is safe to reference classes that may not be on the classpath.

Example

@AutoConfiguration
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public DataSource dataSource(DataSourceProperties props) {
        return props.initializeDataSourceBuilder().build();
    }
}

@ConditionalOnMissingBean

Matches when no bean of the specified type (or name) has been registered yet in the application context. This is the primary mechanism that lets users override auto-configured beans — by declaring their own bean of the same type, they suppress the auto-configuration's bean silently. When used without arguments it checks for a bean of the same type as the return type of the @Bean method.

Example

@AutoConfiguration
@ConditionalOnClass(ObjectMapper.class)
public class JacksonAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(ObjectMapper.class)
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}

@ConditionalOnProperty

Matches based on the value of a Spring Environment property. You can require the property to exist (matchIfMissing = false, the default) or to have a specific value. The havingValue attribute enables matching only when the property equals a particular string. This is the standard way to make a feature opt-in or opt-out via application.properties.

Example

@AutoConfiguration
@ConditionalOnProperty(
    prefix = "my.feature",
    name = "enabled",
    havingValue = "true",
    matchIfMissing = false
)
public class MyFeatureAutoConfiguration {

    @Bean
    public MyFeatureService myFeatureService() {
        return new MyFeatureService();
    }
}

application.properties

my.feature.enabled=true

@ConditionalOnWebApplication

Matches when the application is a web application. You can restrict to a specific web application type using type = Type.SERVLET (traditional blocking Spring MVC) or type = Type.REACTIVE (Spring WebFlux). The default matches either. Web auto-configurations like DispatcherServletAutoConfiguration use this to avoid registering servlet-specific beans in non-web contexts.

Example

@AutoConfiguration
@ConditionalOnWebApplication(type = ConditionalOnWebApplication.Type.SERVLET)
@ConditionalOnClass(DispatcherServlet.class)
public class WebMvcAutoConfiguration {
    // Only applied in a Servlet-based web application
}

@ConditionalOnExpression

Matches when a SpEL (Spring Expression Language) expression evaluates to true. This is the most flexible — and most expensive — condition because the expression is evaluated at runtime. It should be used as a last resort when no simpler condition covers the requirement, because SpEL expressions are not optimised for AOT/GraalVM native image compilation.

Example

@AutoConfiguration
@ConditionalOnExpression(
    "${my.feature.enabled:false} and '${my.feature.mode:default}' == 'advanced'"
)
public class AdvancedFeatureAutoConfiguration {
    // Only applied when both conditions are met via SpEL
}

@ConditionalOnBean

Matches when at least one bean of the specified type or name is already registered in the context. This is the inverse of @ConditionalOnMissingBean. A common pattern is to declare additional infrastructure beans (metrics adapters, health indicators) only when the primary service bean already exists, ensuring the extension is activated only when the feature it decorates is present.

Example

@AutoConfiguration
@ConditionalOnBean(DataSource.class)
public class DataSourceHealthIndicatorAutoConfiguration {

    @Bean
    public DataSourceHealthIndicator dbHealthIndicator(DataSource ds) {
        return new DataSourceHealthIndicator(ds, "SELECT 1");
    }
}

@ConditionalOnSingleCandidate

Matches when exactly one bean of the specified type exists in the context, or when multiple candidates exist but one is marked @Primary. This is especially useful in reactive vs. blocking scenarios where a configuration should activate only when there is an unambiguous primary candidate, rather than failing with a NoUniqueBeanDefinitionException.

Example

@AutoConfiguration
@ConditionalOnSingleCandidate(DataSource.class)
public class JdbcTemplateAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public JdbcTemplate jdbcTemplate(DataSource ds) {
        return new JdbcTemplate(ds);
    }
}

@ConditionalOnNotWebApplication

Matches only when the application is not a web application — the complement of @ConditionalOnWebApplication. Useful for configurations that should only apply in batch jobs, command-line runners, or standalone Spring contexts where no embedded server is present. Scheduling and batch auto-configurations use this to register lightweight executors that would otherwise conflict with web-thread management.

Example

@AutoConfiguration
@ConditionalOnNotWebApplication
@ConditionalOnClass(Job.class)
public class BatchAutoConfiguration {
    // Only applies in non-web (e.g. batch) contexts
}

@ConditionalOnJava

Matches based on the JVM version at runtime. You specify a range using JavaVersion enum constants and a range attribute (EQUAL_OR_NEWER or OLDER_THAN). This allows library authors to provide different implementation strategies depending on which language features are available, without branching at the application level.

Example

@AutoConfiguration
@ConditionalOnJava(JavaVersion.TWENTY_ONE)
public class VirtualThreadAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public AsyncTaskExecutor virtualThreadExecutor() {
        return new SimpleAsyncTaskExecutor("vt-");
    }
}

@ConditionalOnResource

Matches when a specific resource (file, classpath entry) is present. The resource location uses the standard Spring resource syntax: classpath:, file:, etc. This is useful for auto-configurations that need a configuration file (such as a logback.xml) to be present before they activate their default logging configuration.

Example

@AutoConfiguration
@ConditionalOnResource(resources = "classpath:myconfig.properties")
public class MyConfigAutoConfiguration {
    // Only applied if myconfig.properties exists on the classpath
}

@ConditionalOnCloudPlatform

Matches when the application is running on a specific cloud platform. Spring Boot detects platforms like CLOUD_FOUNDRY, HEROKU, SAP, and KUBERNETES by inspecting environment variables. This allows starters to register cloud-native infrastructure beans — such as service binding adapters — only when running on the target platform.

Example

@AutoConfiguration
@ConditionalOnCloudPlatform(CloudPlatform.KUBERNETES)
public class KubernetesAutoConfiguration {
    // Registers k8s-specific health indicators and config sources
}

Writing a Custom @Condition

When none of the built-in conditions fit, extend SpringBootCondition and implement getMatchOutcome(). Return a ConditionOutcome that carries both a boolean match result and a human-readable message explaining the decision. The message appears in the conditions evaluation report (accessible via --debug or /actuator/conditions), which is invaluable during development.

Example

public class OnWeekdayCondition extends SpringBootCondition {

    @Override
    public ConditionOutcome getMatchOutcome(ConditionContext ctx, AnnotatedTypeMetadata meta) {
        int day = LocalDate.now().getDayOfWeek().getValue();
        boolean weekday = day >= 1 && day <= 5;
        String message = weekday ? "Is a weekday" : "Is weekend";
        return new ConditionOutcome(weekday, ConditionMessage.of(message));
    }
}

@Retention(RetentionPolicy.RUNTIME)
@Target({ ElementType.TYPE, ElementType.METHOD })
@Conditional(OnWeekdayCondition.class)
public @interface ConditionalOnWeekday {}

@AutoConfiguration
@ConditionalOnWeekday
public class WeekdayJobAutoConfiguration {
    // Only active Monday–Friday
}

AutoConfiguration.imports vs spring.factories

Spring Boot 2 used META-INF/spring.factories to register many extension points, including auto-configurations. Spring Boot 3 introduced a dedicated file for auto-configurations to improve startup performance, AOT compatibility, and tooling support. Understanding this change is critical when upgrading starters or writing new ones.

spring.factories — Legacy Mechanism (Boot 2)

In Spring Boot 2, auto-configuration classes were registered under the org.springframework.boot.autoconfigure.EnableAutoConfiguration key in META-INF/spring.factories. The file used a Java properties format and supported multiple comma-separated class names per key. SpringFactoriesLoader read this file and loaded all extension points — not just auto-configurations — from a single place, which caused class-loading overhead even for unused extension points.

Boot 2 registration (legacy — do not use in Boot 3)

# META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  com.example.MyFeatureAutoConfiguration,\
  com.example.AnotherAutoConfiguration

AutoConfiguration.imports — Boot 3+ Mechanism

Spring Boot 3 introduced a dedicated file at META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Each line contains exactly one fully-qualified auto-configuration class name. The new mechanism is more efficient because it is parsed lazily and is compatible with GraalVM native image compilation. The spring.factories EnableAutoConfiguration key is no longer supported in Spring Boot 3 — migrating to the new file is mandatory.

Boot 3 registration

# META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.example.MyFeatureAutoConfiguration
com.example.AnotherAutoConfiguration

Migrating from spring.factories to AutoConfiguration.imports

To migrate a Boot 2 starter to Boot 3: create the directory src/main/resources/META-INF/spring/, add a file named org.springframework.boot.autoconfigure.AutoConfiguration.imports, and list each auto-configuration class on its own line. Remove the EnableAutoConfiguration entry from spring.factories (you may keep other keys in spring.factories for non-auto-configuration extension points). Replace @Configuration with @AutoConfiguration on each class.

File layout after migration

src/main/resources/
  META-INF/
    spring/
      org.springframework.boot.autoconfigure.AutoConfiguration.imports
    # spring.factories may still exist for other extension points

@AutoConfiguration Annotation

Spring Boot 3 introduced the @AutoConfiguration annotation as a replacement for bare @Configuration on auto-configuration classes. It is a meta-annotation that includes @Configuration(proxyBeanMethods = false) for performance, plus support for before and after ordering attributes directly on the annotation (equivalent to @AutoConfigureBefore / @AutoConfigureAfter). Using @AutoConfiguration is now the idiomatic way to write auto-configuration classes in Boot 3+.

Example

// Boot 3+ — preferred
@AutoConfiguration(after = DataSourceAutoConfiguration.class)
@ConditionalOnClass(DataSource.class)
public class MyAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    public MyService myService(DataSource ds) {
        return new MyService(ds);
    }
}

// Boot 2 equivalent (still works in Boot 3 but not idiomatic)
@Configuration
@AutoConfigureAfter(DataSourceAutoConfiguration.class)
@ConditionalOnClass(DataSource.class)
public class MyAutoConfigurationLegacy { ... }

Debugging Auto-Configuration

Spring Boot provides several mechanisms for understanding which auto-configurations were applied and why others were skipped. The conditions evaluation report is the primary tool, available both at startup via the --debug flag and at runtime via the Actuator /actuator/conditions endpoint.

--debug Flag — Conditions Evaluation Report

Launching a Spring Boot application with --debug (or setting debug=true in application.properties) prints the full conditions evaluation report to the console at startup. The report lists three sections: Positive matches (conditions that passed and beans that were registered), Negative matches (conditions that failed and why), and Unconditional classes (applied without any condition). Reading negative matches tells you exactly which condition blocked an auto-configuration from activating.

Enable via command line

java -jar myapp.jar --debug

Enable via application.properties

debug=true

Sample report output

============================
CONDITIONS EVALUATION REPORT
============================

Positive matches:
-----------------
   DataSourceAutoConfiguration matched:
      - @ConditionalOnClass found required classes
      - @ConditionalOnMissingBean (types: javax.sql.DataSource) did not find any beans (OnBeanCondition)

Negative matches:
-----------------
   ActiveMQAutoConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class 'jakarta.jms.ConnectionFactory'

Actuator /actuator/conditions Endpoint

When spring-boot-starter-actuator is on the classpath, the /actuator/conditions endpoint exposes the same conditions evaluation report as a JSON response, queryable at runtime without restarting the application. This is useful for production troubleshooting — combine it with /actuator/beans to see exactly which beans are registered and where they came from.

Enable actuator dependency

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

Expose the endpoint in application.properties

management.endpoints.web.exposure.include=conditions,beans,health
management.endpoint.conditions.access=read-only

Query

curl http://localhost:8080/actuator/conditions | jq .positiveMatches

Reading the Conditions Report

Each entry in the positive-matches section shows the auto-configuration class name, the conditions that were evaluated, and the outcome message explaining why the condition passed. Negative-match entries show which specific condition failed and the class or property that was missing. The message text comes directly from the ConditionOutcome returned by the condition — so well-written custom conditions should always provide a clear message for this report.

Key fields in the JSON response

Field Description
positiveMatches Auto-configurations that matched — beans were registered
negativeMatches Auto-configurations that did not match — beans were skipped
unconditionalClasses Auto-configurations applied with no conditions at all
exclusions Auto-configurations excluded by spring.autoconfigure.exclude

Excluding Auto-Configurations

If an auto-configuration is activating when you do not want it to, you can exclude it explicitly using the exclude attribute of @SpringBootApplication, or via the spring.autoconfigure.exclude property. The property approach is useful when the class you want to exclude is not on your compile-time classpath. Excluded classes appear in the exclusions section of the conditions report.

Via annotation

@SpringBootApplication(exclude = {
    DataSourceAutoConfiguration.class,
    SecurityAutoConfiguration.class
})
public class DemoApplication { ... }

Via application.properties

spring.autoconfigure.exclude=\
  org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration,\
  org.springframework.boot.autoconfigure.security.servlet.SecurityAutoConfiguration

Building a Custom Starter

A Spring Boot starter is a convention-based packaging of auto-configuration and dependencies that other projects can consume with a single Maven or Gradle dependency. The recommended structure separates the auto-configuration logic into an -autoconfigure module and exposes a thin -starter module that aggregates dependencies. Following the naming convention {name}-spring-boot-starter (for third-party starters) signals that it is a community starter rather than an official Spring Boot starter.

Step 1 — The autoconfigure Module

Create a separate Maven module named my-feature-spring-boot-autoconfigure. This module contains the @AutoConfiguration class, any @ConfigurationProperties classes, and the AutoConfiguration.imports registration file. The only required dependency is spring-boot-autoconfigure. Do not add spring-boot-starter here — that goes in the starter module.

pom.xml (autoconfigure module)

<artifactId>my-feature-spring-boot-autoconfigure</artifactId>
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-autoconfigure</artifactId>
  </dependency>
</dependencies>

@AutoConfiguration class

@AutoConfiguration
@ConditionalOnClass(MyFeatureService.class)
public class MyFeatureAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public MyFeatureService myFeatureService() {
        return new MyFeatureService();
    }
}

Step 2 — The starter Module

Create a second Maven module named my-feature-spring-boot-starter. This module is intentionally lightweight — it contains no Java source, only a pom.xml that declares dependencies on both the autoconfigure module and any other libraries the feature requires. Consumers add just this single starter dependency; Maven pulls in the autoconfigure module and the feature library transitively.

pom.xml (starter module)

<artifactId>my-feature-spring-boot-starter</artifactId>
<dependencies>
  <!-- The autoconfigure module -->
  <dependency>
    <groupId>com.example</groupId>
    <artifactId>my-feature-spring-boot-autoconfigure</artifactId>
  </dependency>
  <!-- The actual feature library -->
  <dependency>
    <groupId>com.example</groupId>
    <artifactId>my-feature-lib</artifactId>
  </dependency>
  <!-- Pull in Spring Boot starter basics (logging, core, etc.) -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter</artifactId>
  </dependency>
</dependencies>

Step 3 — Register via AutoConfiguration.imports

Inside the autoconfigure module, create the file src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Add one line per auto-configuration class. This file is what Spring Boot reads at startup to discover your configuration — without it, the @AutoConfiguration class is never found, even if the JAR is on the classpath.

File path

src/main/resources/
  META-INF/
    spring/
      org.springframework.boot.autoconfigure.AutoConfiguration.imports

File contents

com.example.myfeature.autoconfigure.MyFeatureAutoConfiguration

Optional: add annotation processor for metadata

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-autoconfigure-processor</artifactId>
  <optional>true</optional>
</dependency>

Step 4 — Consuming the Starter

In any Spring Boot project that wants to use your feature, add a single dependency on the starter module. No @Import, no component-scan of the library's package — Spring Boot discovers and applies the auto-configuration automatically via the AutoConfiguration.imports file. If the user wants to override the auto-configured bean, they simply declare their own @Bean of the same type and @ConditionalOnMissingBean suppresses the starter's bean.

Consumer pom.xml

<dependency>
  <groupId>com.example</groupId>
  <artifactId>my-feature-spring-boot-starter</artifactId>
  <version>1.0.0</version>
</dependency>

Optional override in consumer application

@Configuration
public class AppConfig {

    // This bean suppresses MyFeatureAutoConfiguration's default bean
    @Bean
    public MyFeatureService customFeatureService() {
        MyFeatureService svc = new MyFeatureService();
        svc.setMode("custom");
        return svc;
    }
}
