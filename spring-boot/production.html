Spring Boot Production & Tooling

Production-grade topics that go beyond getting an app running locally: Kubernetes health probes, custom Micrometer metrics, structured JSON logging, containerization with layered JARs, integration testing with Testcontainers, and graceful shutdown. All topics target Spring Boot 3.x (Java 17+) and are compatible with Spring Boot 4.x (Java 21+).

Phase 1 tooling page Basic setup (Initializr, DevTools, Actuator overview, IDE configuration) is covered in Spring Core — Tooling & Setup. This page picks up where that page ends.

Actuator Health Groups

Spring Boot Actuator supports health groups — named collections of health indicators that are exposed on their own sub-path under /actuator/health/<group>. When the application is deployed to Kubernetes, Boot automatically maps the built-in liveness and readiness availability states to two dedicated groups, giving the cluster exact endpoints for its probes without any polling of the aggregate /health response.

Health Groups for Kubernetes

Spring Boot detects that it is running inside Kubernetes via the KUBERNETES_SERVICE_HOST environment variable and automatically enables liveness and readiness probes. You can also enable them explicitly. The liveness probe (/actuator/health/liveness) reports whether the JVM is alive and not stuck; if it fails, Kubernetes restarts the pod. The readiness probe (/actuator/health/readiness) reports whether the application has finished starting and is ready to receive traffic; if it fails, Kubernetes removes the pod from load-balancer rotation without restarting it.

application.yml — enabling probes and health groups

# application.yml
management:
  endpoint:
    health:
      probes:
        enabled: true
  health:
    livenessState:
      enabled: true
    readinessState:
      enabled: true
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus

Kubernetes Deployment YAML — liveness and readiness probes

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-spring-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-spring-app
  template:
    metadata:
      labels:
        app: my-spring-app
    spec:
      containers:
        - name: my-spring-app
          image: my-spring-app:latest
          ports:
            - containerPort: 8080
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 5
            failureThreshold: 3

Adding dependency checks to the readiness group

management:
  health:
    group:
      readiness:
        include: readinessState,db,redis

Keep the liveness group limited to livenessState only. Adding slow dependency checks to liveness causes unnecessary pod restarts when a downstream service is temporarily unavailable.

Custom HealthIndicator

Implement the HealthIndicator interface (or ReactiveHealthIndicator for WebFlux) to contribute a custom signal to the aggregate health endpoint. Spring Boot discovers the bean automatically via component scanning and names the indicator after the class by stripping the HealthIndicator suffix and converting to lower-case. For example, ExternalApiHealthIndicator appears as externalApi in the health JSON.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

Example — custom HealthIndicator

import org.springframework.boot.actuate.health.Health;
import org.springframework.boot.actuate.health.HealthIndicator;
import org.springframework.stereotype.Component;

@Component
public class ExternalApiHealthIndicator implements HealthIndicator {

    private final ExternalApiClient client;

    public ExternalApiHealthIndicator(ExternalApiClient client) {
        this.client = client;
    }

    @Override
    public Health health() {
        try {
            boolean ok = client.ping();
            if (ok) {
                return Health.up()
                        .withDetail("latencyMs", client.lastLatencyMs())
                        .build();
            }
            return Health.down()
                    .withDetail("reason", "ping returned false")
                    .build();
        } catch (Exception ex) {
            return Health.down(ex)
                    .withDetail("reason", ex.getMessage())
                    .build();
        }
    }
}

To include a custom indicator in only one health group, configure management.health.group.<name>.include explicitly and omit the indicator from other groups.

Securing Actuator Endpoints

By default, Spring Security (if present) protects all endpoints including Actuator. Best practice is to allow the liveness and readiness probes without authentication (since Kubernetes nodes cannot authenticate), and require ACTUATOR role for sensitive endpoints like /actuator/env, /actuator/beans, and /actuator/heapdump. The configuration below uses a SecurityFilterChain with request matchers.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Example — SecurityFilterChain for Actuator

import org.springframework.boot.actuate.autoconfigure.security.servlet.EndpointRequest;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class ActuatorSecurityConfig {

    @Bean
    public SecurityFilterChain actuatorSecurity(HttpSecurity http) throws Exception {
        http
            .securityMatcher(EndpointRequest.toAnyEndpoint())
            .authorizeHttpRequests(auth -> auth
                // Probe endpoints are accessible without auth (used by Kubernetes)
                .requestMatchers(EndpointRequest.to("health", "info")).permitAll()
                // All other actuator endpoints require the ACTUATOR role
                .anyRequest().hasRole("ACTUATOR")
            )
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }
}

application.properties

# Expose only the endpoints you need
management.endpoints.web.exposure.include=health,info,metrics,prometheus
# Require roles for sensitive endpoints
management.endpoint.health.show-details=when-authorized

Micrometer Metrics

Micrometer is the metrics instrumentation facade that Spring Boot uses out of the box. It provides a vendor-neutral API for counters, timers, gauges, and distribution summaries, and ships with registry implementations for Prometheus, Datadog, CloudWatch, InfluxDB, and many others. Spring Boot auto-configures a MeterRegistry composite and automatically registers dozens of meters without any application code.

Auto-Configured Meters

Spring Boot auto-registers the following meter sets when the relevant classes are on the classpath. JVM metrics include garbage collection pause times, heap/non-heap memory pools, loaded class counts, and thread states — contributed by JvmGcMetrics, JvmMemoryMetrics, and JvmThreadMetrics. HTTP server metrics are instrumented via WebMvcMetricsFilter (Servlet) or MetricsWebFilter (WebFlux) and produce http.server.requests timers tagged with URI, method, status, and outcome. DataSource metrics instrument HikariCP connection pool size and wait times via HikariDataSourcePoolMetrics.

Custom Counter, Timer, and Gauge

Inject MeterRegistry into any Spring bean to register custom meters. Use a Counter for things that only go up (orders placed, errors thrown). Use a Timer for latency-sensitive operations — it records both count and total duration so Prometheus can compute percentiles. Use a Gauge for values that go up and down (queue depth, cache size). Always add meaningful tags to slice metrics by business dimensions.

Example — registering custom meters

import io.micrometer.core.instrument.*;
import org.springframework.stereotype.Service;
import java.util.concurrent.atomic.AtomicInteger;

@Service
public class OrderService {

    private final Counter ordersCreated;
    private final Timer  orderProcessingTimer;
    private final AtomicInteger pendingOrders = new AtomicInteger(0);

    public OrderService(MeterRegistry registry) {
        // Counter: total orders created, tagged by region
        this.ordersCreated = Counter.builder("orders.created")
                .description("Total number of orders created")
                .tag("region", "us-east-1")
                .register(registry);

        // Timer: how long order processing takes
        this.orderProcessingTimer = Timer.builder("orders.processing.duration")
                .description("Time taken to process an order")
                .tag("flow", "standard")
                .publishPercentiles(0.5, 0.95, 0.99)
                .register(registry);

        // Gauge: current size of the pending-orders queue
        Gauge.builder("orders.pending", pendingOrders, AtomicInteger::get)
                .description("Number of orders awaiting processing")
                .register(registry);
    }

    public void createOrder(Order order) {
        pendingOrders.incrementAndGet();
        orderProcessingTimer.record(() -> {
            // ... process the order ...
            ordersCreated.increment();
        });
        pendingOrders.decrementAndGet();
    }
}

Spring Boot 3.x also supports the @Timed and @Counted annotations from micrometer-core combined with AspectJ, letting you instrument methods without injecting MeterRegistry directly.

Structured Logging

Spring Boot 3.4 introduced first-class support for structured logging — emitting each log record as a machine-readable JSON object instead of a free-text line. Structured logs are consumed directly by log aggregation pipelines (Elasticsearch/Logstash, Splunk, Loki) without fragile regex parsing. The feature is built into Spring Boot’s logging infrastructure and requires no extra dependencies.

JSON Structured Logging

Set logging.structured.format.console or logging.structured.format.file in application.properties to one of the built-in formats: ecs (Elastic Common Schema), logstash (Logstash JSON), or gelf (Graylog Extended Log Format). No additional libraries are required — Spring Boot 3.4 includes the formatters in spring-boot core. For production containers, you typically write to stdout and let the container runtime forward logs to a collector.

application.properties — enable JSON logging

# Choose the structured format for console output
logging.structured.format.console=ecs

# Or write JSON to a file
# logging.structured.format.file=logstash
# logging.file.name=/var/log/app/application.log

# Include MDC context (trace IDs, user IDs, etc.)
logging.include-application-name=true

Example JSON log output (ECS format)

Containerization

Spring Boot provides two complementary strategies for packaging applications as container images: layered JARs with a multi-stage Dockerfile and Cloud Native Buildpacks via the spring-boot:build-image Maven/Gradle goal. Layered JARs optimise Docker layer caching by separating slowly-changing dependencies from rapidly-changing application code. Cloud Native Buildpacks do the same automatically without requiring a Dockerfile at all.

Layered JARs

Spring Boot’s fat JAR is split into four layers ordered by change frequency: dependencies (third-party JARs that rarely change), spring-boot-loader (the Boot launcher, almost never changes), snapshot-dependencies (SNAPSHOT JARs that change often), and application (your classes and resources, changes with every build). By copying each layer separately in the Dockerfile, Docker can re-use the cached layers when only the application layer changes — saving minutes of pull time in CI/CD pipelines.

pom.xml — enable layers (enabled by default in Spring Boot 2.3+)

<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <configuration>
        <layers>
          <enabled>true</enabled>
        </layers>
      </configuration>
    </plugin>
  </plugins>
</build>

Listing layers

java -Djarmode=layertools -jar target/myapp.jar list
# Output:
# dependencies
# spring-boot-loader
# snapshot-dependencies
# application

Cloud Native Buildpacks

Cloud Native Buildpacks (CNB) is a CNCF specification that turns application source into an OCI-compliant container image without a Dockerfile. Spring Boot integrates with Buildpacks through the spring-boot:build-image Maven goal (or bootBuildImage Gradle task). The resulting image uses Paketo Buildpacks and includes a hardened OS layer, a JRE, and your application — all following security best practices like running as a non-root user.

Build and push the image

# Build an OCI image using Paketo Buildpacks (no Dockerfile required)
./mvnw spring-boot:build-image -Dspring-boot.build-image.imageName=myorg/myapp:latest

# Publish directly to a registry
./mvnw spring-boot:build-image \
  -Dspring-boot.build-image.imageName=registry.example.com/myorg/myapp:1.0.0 \
  -Dspring-boot.build-image.publish=true

pom.xml — configure image name in the build

<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <image>
      <name>myorg/${project.artifactId}:${project.version}</name>
      <!-- Use a specific Paketo builder -->
      <builder>paketobuildpacks/builder-jammy-base</builder>
    </image>
  </configuration>
</plugin>

The resulting image contains a Bill of Materials (SBOM) layer and is rebased (OS security updates applied without a full rebuild) via the pack rebase command from the Buildpacks CLI.

Dockerfile with Layer Extraction

The canonical multi-stage Dockerfile for Spring Boot uses jarmode=layertools in a builder stage to extract the four layers, then copies them one-by-one into the final image. Because Docker re-uses a layer only if the COPY source has not changed since the previous build, placing dependencies first (they rarely change) and application last (it changes every build) maximises cache hits. Spring Boot 3.2+ uses the fully-qualified org.springframework.boot.loader.launch.JarLauncher class name.

Dockerfile — multi-stage layered JAR extraction

FROM eclipse-temurin:21-jre AS builder
WORKDIR /application
COPY target/*.jar application.jar
RUN java -Djarmode=layertools -jar application.jar extract

FROM eclipse-temurin:21-jre
WORKDIR /application
COPY --from=builder /application/dependencies/ ./
COPY --from=builder /application/spring-boot-loader/ ./
COPY --from=builder /application/snapshot-dependencies/ ./
COPY --from=builder /application/application/ ./
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

Build and run

# Build the JAR first
./mvnw clean package -DskipTests

# Build the Docker image
docker build -t myapp:latest .

# Run
docker run -p 8080:8080 myapp:latest

On subsequent builds where only application code changed, Docker reuses the cached dependencies and spring-boot-loader layers, reducing the layer diff pushed to the registry to a few kilobytes.

Testcontainers

Testcontainers is a Java library that manages Docker containers in JUnit tests. Spring Boot 3.1 added first-class integration via the @ServiceConnection annotation, which automatically wires the container’s host/port into the matching Spring Boot auto-configuration — eliminating the need to manually set spring.datasource.url, spring.redis.host, etc. from a DynamicPropertySource method.

@ServiceConnection

@ServiceConnection is a Spring Boot 3.1+ annotation that, when placed on a @Bean method returning a Testcontainers container, instructs the auto-configuration layer to source its connection properties from the live container rather than from application.properties. This works for PostgreSQL, MySQL, MongoDB, Redis, RabbitMQ, Kafka, and more via the corresponding ConnectionDetails factories shipped in spring-boot-testcontainers.

Dependencies (pom.xml)

<!-- Testcontainers BOM for version alignment -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.testcontainers</groupId>
      <artifactId>testcontainers-bom</artifactId>
      <version>1.20.4</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <!-- Spring Boot Testcontainers integration (version managed by Boot BOM) -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
  </dependency>

  <!-- Testcontainers PostgreSQL module -->
  <dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <scope>test</scope>
  </dependency>

  <!-- JUnit 5 support -->
  <dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
  </dependency>
</dependencies>

Example — @ServiceConnection with PostgreSQL

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@SpringBootTest
@Testcontainers
class OrderRepositoryTest {

    // @ServiceConnection wires host/port/credentials into DataSource auto-config
    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired
    OrderRepository orderRepository;

    @Test
    void savesAndFindsOrder() {
        Order order = new Order("customer-42", BigDecimal.valueOf(99.99));
        orderRepository.save(order);

        Order found = orderRepository.findById(order.getId()).orElseThrow();
        assertThat(found.getCustomerId()).isEqualTo("customer-42");
    }
}

The container is static so it is shared across all test methods in the class. Spring Boot automatically tears down containers after the test context closes. Use @RestartScope (Spring Boot DevTools) in the TestApplication class to keep containers alive across context restarts during local development.

Multiple containers in one test

@Container
@ServiceConnection
static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

@Container
@ServiceConnection
static GenericContainer<?> redis =
        new GenericContainer<>("redis:7-alpine").withExposedPorts(6379);

Graceful Shutdown

When Kubernetes sends SIGTERM to a pod, the JVM receives it and, by default, exits immediately — dropping any in-flight HTTP requests. Setting server.shutdown=graceful tells the embedded server (Tomcat, Jetty, Undertow, or Reactor Netty) to stop accepting new connections and then wait for active requests to complete before the JVM exits. This makes zero-downtime rolling deployments possible.

Graceful Shutdown Configuration

Enable graceful shutdown with two properties. server.shutdown=graceful activates drain mode on the web server. spring.lifecycle.timeout-per-shutdown-phase sets the maximum time the JVM waits for each shutdown phase — including the web server drain phase — before forcing termination. The default is 30s. Set it to match your longest expected request duration plus a small buffer.

application.properties

# Enable graceful shutdown (drain mode)
server.shutdown=graceful

# Maximum time to wait for active requests to complete
spring.lifecycle.timeout-per-shutdown-phase=20s

What happens when SIGTERM arrives

  1. The embedded server switches to drain mode: new connections are rejected (Tomcat/Jetty/Netty) or immediately receive HTTP 503 (Undertow).
  2. Already-accepted requests continue processing normally.
  3. When all active requests finish (or the timeout elapses), the servlet context is destroyed.
  4. Spring’s ApplicationContext closes in reverse bean-registration order — @PreDestroy methods and DisposableBean.destroy() are called.
  5. The JVM exits with code 0.

Kubernetes pre-stop hook — give kube-proxy time to update routing tables

lifecycle:
  preStop:
    exec:
      # Delay SIGTERM by 5 seconds so kube-proxy finishes removing the pod
      # from load-balancer rules before the server stops accepting connections
      command: ["sh", "-c", "sleep 5"]

Without the preStop hook, there is a race between Kubernetes removing the pod from its Endpoints list (and updating kube-proxy rules) and the pod receiving SIGTERM. The sleep gives kube-proxy time to propagate the removal so no new requests are routed to a draining pod.

Verifying graceful shutdown in a test

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class GracefulShutdownTest {

    @Autowired
    private ConfigurableApplicationContext context;

    @Test
    void shutdownDrainsInFlightRequests() throws Exception {
        // Start a slow request in a background thread
        CountDownLatch started = new CountDownLatch(1);
        CompletableFuture<Integer> status = CompletableFuture.supplyAsync(() -> {
            started.countDown();
            // ... send HTTP request that takes 2 seconds ...
            return 200;
        });

        started.await();
        context.close(); // triggers graceful shutdown

        assertThat(status.get(5, TimeUnit.SECONDS)).isEqualTo(200);
    }
}
