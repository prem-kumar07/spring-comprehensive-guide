Spring Boot 4 Features

Spring Boot 4.x — 4.0.0

Spring Boot 4.0 was released on November 20, 2025 — the beginning of a new Spring Boot generation built on Spring Framework 7.x. It requires Java 17 or later (Java 21 or Java 25 strongly recommended) and raises the baseline to Jakarta EE 11 (Servlet 6.1, JPA 3.2, Bean Validation 3.1). The headline themes of the 4.x generation are: a fully modularized auto-configuration codebase (70+ focused modules), portfolio-wide null safety with JSpecify, first-class API versioning in Spring MVC, native gRPC auto-configuration (Boot 4.1), upgraded dependencies including Hibernate 7 and Jackson 3, and improved GraalVM native image support with a smaller footprint.

Jakarta EE 11 baseline Spring Boot 4 moves to Jakarta EE 11, requiring a Servlet 6.1-compatible container. JPA moves to version 3.2 and Bean Validation to 3.1. All jakarta.* imports from Boot 3 remain valid — this is not a namespace change, but API additions and removals within the jakarta.* packages may require minor adjustments.

Modularized Auto-Configuration

Spring Boot 4's most significant architectural change is the complete modularization of its auto-configuration layer. The previously monolithic spring-boot-autoconfigure jar has been split into 70+ focused, self-contained modules — one per technology domain. Each starter now ships its own dedicated auto-configuration module rather than delegating to the shared monolith. This means GraalVM AOT processing only needs to process reachable configurations, reducing native-image build times, binary sizes, and startup overhead significantly. If you rely on the old monolith, classic starters act as a compatibility shim that re-bundles all modular configurations without transitive dependencies.

Dependency (pom.xml)

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.0.0</version>
</parent>

<!-- Each starter now owns its auto-configuration module -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example — registering a custom auto-configuration (unchanged from Boot 3)

# File: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
# This mechanism carries forward from Boot 3 — no change needed

com.example.MyDatabaseAutoConfiguration
com.example.MySecurityAutoConfiguration
Migration from Boot 3 If you published a custom starter that bundled all configurations inside spring-boot-autoconfigure via spring.factories, migrate to modular auto-configuration modules and declare them in AutoConfiguration.imports — the old approach is not supported in Boot 4.

@AutoConfiguration and Conditional Annotations

Conditional annotations remain the cornerstone of Spring Boot auto-configuration in Boot 4. @AutoConfiguration marks a class as a Boot auto-configuration, and the conditional system — @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty, and friends — determines whether each configuration is activated. In Boot 4 the modular split means conditionals are evaluated independently per module, improving performance at startup because Spring does not need to evaluate conditions for auto-configurations whose starter is not on the classpath at all.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-autoconfigure</artifactId>
</dependency>

Example

// Boot 4 auto-configuration class (structure unchanged from Boot 3)
@AutoConfiguration
@ConditionalOnClass(DataSource.class)
@ConditionalOnMissingBean(DataSource.class)
public class MyDataSourceAutoConfiguration {

    @Bean
    public DataSource dataSource(DataSourceProperties props) {
        return props.initializeDataSourceBuilder().build();
    }
}

// Main application — triggers auto-configuration discovery
@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

JSpecify Null Safety

Spring Boot 4 introduces portfolio-wide null safety with JSpecify. JSpecify annotations (@Nullable, @NonNull, @NullMarked) are applied across the Spring Framework 7 and Spring Boot 4 public API surface. This allows IDEs and static analysis tools (SpotBugs, Error Prone, NullAway) to catch NullPointerException risks at compile time rather than at runtime. JSpecify replaces the older Spring-specific @Nullable annotations in org.springframework.lang. Your own code can adopt JSpecify annotations to benefit from the same analysis.

Dependency (pom.xml)

<dependency>
  <groupId>org.jspecify</groupId>
  <artifactId>jspecify</artifactId>
</dependency>

Example

import org.jspecify.annotations.NonNull;
import org.jspecify.annotations.Nullable;
import org.jspecify.annotations.NullMarked;

// Mark the entire package as null-safe by default
@NullMarked
package com.example.service;

// Any parameter or return value that CAN be null must be @Nullable
@Service
public class OrderService {

    // Return is @NonNull by default (package is @NullMarked)
    public Order findById(Long id) {
        return orderRepository.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
    }

    // Explicitly allow null here
    public @Nullable Order findByReference(@Nullable String ref) {
        if (ref == null) return null;
        return orderRepository.findByReference(ref).orElse(null);
    }
}
Migration from Boot 3 Spring's own org.springframework.lang.@Nullable is still present for backward compatibility, but new APIs in Boot 4 and Framework 7 use JSpecify. Update your own code to use org.jspecify.annotations.@Nullable to get accurate static analysis coverage.

Auto-Configuration Conditions Report

Running your Spring Boot 4 application with debug=true or the --debug flag still prints a detailed conditions evaluation report to the console. In Boot 4 the report is more useful because modular auto-configuration makes the "negative matches" section significantly shorter — only modules whose starters are on the classpath are evaluated at all. The /actuator/conditions endpoint continues to expose the report as structured JSON when the Actuator is present.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

Example — application.properties

# Enable conditions report in the console

# Expose the /actuator/conditions endpoint over HTTP
management.endpoints.web.exposure.include=conditions,health,info

API Versioning — First-Class Request Mapping

Spring Framework 7 (the foundation of Spring Boot 4) makes API versioning a first-class feature of request mapping. The version attribute is now available on @GetMapping, @PostMapping, @PutMapping, @DeleteMapping, @PatchMapping, and @RequestMapping. Spring resolves the version from the request using a pluggable ApiVersionResolver strategy — by default via a request header or URL path segment. Multiple versioned handlers can coexist, and Spring routes to the most specific version that satisfies the request, enabling backward-compatible evolution of REST APIs without path duplication.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example

// Configure the API version resolver (header-based in this example)
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void configureApiVersioning(ApiVersioningConfigurer configurer) {
        configurer.useRequestHeader("X-API-Version");
    }
}

// Handlers for different API versions on the same path
@RestController
@RequestMapping("/orders")
public class OrderController {

    // Handles X-API-Version: 1 and X-API-Version: 2
    @GetMapping(value = "/{id}", version = "1")
    public OrderV1 getOrderV1(@PathVariable Long id) {
        return orderService.findV1(id);
    }

    // Handles X-API-Version: 2 only (more specific)
    @GetMapping(value = "/{id}", version = "2")
    public OrderV2 getOrderV2(@PathVariable Long id) {
        return orderService.findV2(id);
    }
}
Migration from Boot 3 Boot 3 had no built-in versioning — teams typically duplicated controller paths (/v1/orders, /v2/orders) or used content negotiation manually. Boot 4's built-in versioning is additive; existing path-based versioning continues to work, but migrating to version attributes enables cleaner routing and less boilerplate.

Enhanced HTTP Service Clients

Spring Boot 4 extends the @HttpExchange declarative HTTP client model introduced in Boot 3. In Boot 4, HttpServiceProxyFactory gains support for request-level API version propagation — the version context set by the server-side versioning mechanism can be forwarded automatically to outbound HTTP service calls. Additionally, the SSRF (Server-Side Request Forgery) mitigation introduced in Boot 4.1 adds a configurable URL allowlist to the auto-configured RestClient.Builder and WebClient.Builder, preventing unintended outbound requests to internal network addresses.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example

// Declare the HTTP interface (unchanged from Boot 3)
@HttpExchange(url = "https://api.example.com/products", accept = "application/json")
public interface ProductClient {

    @GetExchange("/{id}")
    Product getById(@PathVariable long id);

    @PostExchange
    Product create(@RequestBody Product product);
}

// Register the proxy — Boot 4 auto-configuration provides RestClient.Builder
@Configuration
public class HttpClientConfig {

    @Bean
    public ProductClient productClient(RestClient.Builder builder) {
        RestClient restClient = builder
            .baseUrl("https://api.example.com")
            .build();
        HttpServiceProxyFactory factory = HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(restClient))
            .build();
        return factory.createClient(ProductClient.class);
    }
}

# application.properties — SSRF allowlist (Boot 4.1)
# spring.http.client.allowed-host-patterns=api.example.com,*.internal.corp

Virtual Threads — Enhanced for Boot 4

Virtual threads (Project Loom) support that debuted in Spring Boot 3.2 is further polished in Spring Boot 4. With Java 21 or later, setting spring.threads.virtual.enabled=true replaces the embedded-server thread pool with one virtual thread per request. In Boot 4, async context propagation for @Async methods is improved so that observability context (trace IDs, security context) flows correctly across virtual-thread hand-offs without extra configuration. Boot 4 also enables virtual threads on the @Scheduled task executor when virtual threads are active.

Dependency (pom.xml)

<!-- Requires Java 21+ for virtual threads -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example — application.properties

# Enable virtual threads for Tomcat, @Async, and @Scheduled
spring.threads.virtual.enabled=true
// No code changes needed — controllers and async methods run on virtual threads
@RestController
public class OrderController {

    @GetMapping("/orders/{id}")
    public Order getOrder(@PathVariable Long id) {
        // Blocking I/O — safe on a virtual thread
        return orderRepository.findById(id).orElseThrow();
    }
}

@Service
public class ReportService {

    // @Async runs on a virtual thread when spring.threads.virtual.enabled=true
    @Async
    public CompletableFuture<Report> generateAsync(Long reportId) {
        return CompletableFuture.completedFuture(buildReport(reportId));
    }
}

gRPC Auto-Configuration

Spring Boot 4.1 introduces first-class gRPC auto-configuration via the Spring gRPC project. Adding spring-boot-starter-grpc auto-configures a gRPC server supporting both standalone Netty and Servlet HTTP/2 transports. Client-side auto-configuration provides a GrpcChannelFactory bean. The new @GrpcAdvice annotation enables centralized gRPC exception handling, analogous to @ControllerAdvice for REST. An auto-configured ObservationGrpcServerInterceptor adds Micrometer metrics and trace propagation to every gRPC call with no manual wiring.

Dependency (pom.xml)

<!-- Spring Boot 4.1+ -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-grpc</artifactId>
</dependency>

Example

// gRPC service implementation — annotate with @GrpcService
@GrpcService
public class OrderGrpcService extends OrderServiceGrpc.OrderServiceImplBase {

    private final OrderService orderService;

    @Override
    public void getOrder(GetOrderRequest request,
                         StreamObserver<GetOrderResponse> responseObserver) {
        Order order = orderService.findById(request.getId());
        GetOrderResponse response = GetOrderResponse.newBuilder()
            .setOrderId(order.getId())
            .setStatus(order.getStatus())
            .build();
        responseObserver.onNext(response);
        responseObserver.onCompleted();
    }
}

// Centralized exception handling for all gRPC services
@GrpcAdvice
public class GrpcExceptionHandler {

    @GrpcExceptionHandler(OrderNotFoundException.class)
    public StatusException handleOrderNotFound(OrderNotFoundException ex) {
        return Status.NOT_FOUND.withDescription(ex.getMessage()).asException();
    }
}
Migration from Boot 3 Boot 3 had no built-in gRPC support — teams used the grpc-spring-boot-starter community library. Boot 4.1's official starter uses a different artifact ID and annotation set; migrating requires replacing @GrpcService from the community library with Spring Boot's native equivalent and updating configuration properties.

Hibernate 7 and Jakarta Persistence 3.2

Spring Boot 4 ships with Hibernate 7.x and Jakarta Persistence 3.2 (the version bundled with Jakarta EE 11). Hibernate 7 brings improved SQL generation, enhanced support for Java records as embeddable objects and projections, a refined @TenantId API for multi-tenancy, and better integration with virtual threads. Jakarta Persistence 3.2 adds the find() overloads that accept FindOption parameters, a new CriteriaSelect interface, and improved JPQL features. The spring-boot-starter-data-jpa starter pulls in the correct Hibernate 7 version automatically.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

Example — Jakarta Persistence 3.2 entity

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String status;

    // Java record as @Embeddable (Hibernate 7 fully supports records)
    public record Address(String street, String city, String zip) {}

    @Embedded
    private Address shippingAddress;
}

// Jakarta Persistence 3.2 EntityManager.find() with FindOption
Order order = entityManager.find(Order.class, id,
    LockModeType.PESSIMISTIC_READ);  // FindOption overload
Migration from Boot 3 Boot 3 shipped Hibernate 6.x. Hibernate 7 removed several deprecated APIs and changed some SQL generation defaults. Run your full integration test suite against Hibernate 7 before upgrading; check the Hibernate 7 migration guide for removed @Type usages and renamed persistence provider settings.

Spring Data 2025.1 Improvements

Spring Boot 4 bundles Spring Data 2025.1, the generation aligned with Spring Framework 7. Key improvements include: refined scroll (cursor-based) pagination API with better keyset support, improved projection interfaces with null-safety annotations applied, enhanced MongoTemplate aggregation pipeline support, and better Kotlin coroutines integration across reactive repositories. The ListCrudRepository and ListPagingAndSortingRepository interfaces (introduced in Spring Data 3.x) continue as the recommended choice for imperative code returning List<T> instead of Iterable<T>.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-mongodb</artifactId>
</dependency>

Example — scroll (cursor-based) pagination

// Cursor-based pagination — no offset, consistent ordering
public interface ProductRepository extends Repository<Product, String> {

    Window<Product> findTop10ByCategory(String category, ScrollPosition position);
}

// Usage
Window<Product> page = repo.findTop10ByCategory(
    "electronics", ScrollPosition.keyset());
while (!page.isEmpty()) {
    processProducts(page.getContent());
    if (!page.hasNext()) break;
    page = repo.findTop10ByCategory(
        "electronics", page.positionAt(page.size() - 1));
}

Testcontainers @ServiceConnection

Spring Boot 4 continues and extends the @ServiceConnection support introduced in Boot 3.1. Annotating a Testcontainers @Container field with @ServiceConnection automatically derives all connection properties (URL, username, password, port) from the running container and registers a ConnectionDetails bean. Boot 4 adds lazy datasource connections (Boot 4.1): the application context can start without actually connecting to the database, so containers that take longer to become ready do not block the Spring context from initialising. @ServiceConnection now also supports more container types and third-party integrations.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-testcontainers</artifactId>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.testcontainers</groupId>
  <artifactId>postgresql</artifactId>
  <scope>test</scope>
</dependency>

Example

@SpringBootTest
@Testcontainers
class OrderRepositoryTest {

    // @ServiceConnection auto-configures spring.datasource.* from this container
    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:17-alpine");

    @Autowired
    OrderRepository repository;

    @Test
    void saveAndFind() {
        Order order = repository.save(new Order("PENDING", 42.00));
        assertThat(repository.findById(order.getId())).isPresent();
    }
}

Spring Security 7 — SecurityFilterChain

Spring Boot 4 bundles Spring Security 7. The component-based SecurityFilterChain model (mandatory since Spring Security 6 / Boot 3) is unchanged in Boot 4 — you declare security by providing a @Bean of type SecurityFilterChain. Spring Security 7 focuses on null-safety improvements (JSpecify), better integration with virtual threads, and removal of long-deprecated APIs. The Lambda DSL for HttpSecurity configuration remains mandatory and is unchanged from Boot 3.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Example

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain apiFilterChain(HttpSecurity http) throws Exception {
        http
            .securityMatcher("/api/**")
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .anyRequest().authenticated()
            )
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            )
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()));
        return http.build();
    }
}
Migration from Boot 3 Spring Security 7 removes APIs deprecated in Security 5.x and 6.x, including several AuthenticationManagerBuilder shortcuts and legacy LDAP configuration methods. Review the Spring Security 7 migration guide to identify removed APIs before upgrading.

Method Security — @PreAuthorize and SpEL

Spring Security 7's method security infrastructure, introduced in Security 6, is further refined in Boot 4. @EnableMethodSecurity activates @PreAuthorize, @PostAuthorize, @PreFilter, and @PostFilter. In Spring Security 7, the authorization manager chain is more extensible, and the handling of reactive method security via @EnableReactiveMethodSecurity is unified under the same AuthorizationManager-based infrastructure as imperative security. Custom MethodSecurityExpressionHandler beans continue to work unchanged.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Example

@Configuration
@EnableMethodSecurity
public class MethodSecurityConfig {}

@Service
public class OrderService {

    @PreAuthorize("hasRole('MANAGER') or #order.ownerId == authentication.name")
    public void cancelOrder(Order order) { /* ... */ }

    @PostAuthorize("returnObject.ownerId == authentication.name")
    public Order findOrder(Long id) {
        return orderRepository.findById(id).orElseThrow();
    }
}

SSRF Mitigation for HTTP Clients

Spring Boot 4.1 adds Server-Side Request Forgery (SSRF) mitigation to the auto-configured RestClient.Builder and WebClient.Builder. When enabled, the HTTP client validates outbound request URLs against a configurable allowlist of host patterns before making the request. Requests targeting private IP ranges (10.x.x.x, 172.16.x.x, 192.168.x.x, localhost) are blocked by default unless explicitly allowed. This prevents malicious user input from being used to forge requests to internal infrastructure.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example — application.properties (Boot 4.1)

# Allow only specific external hosts for outbound HTTP (SSRF protection)
spring.http.client.allowed-host-patterns=api.example.com,*.partner.com

# To allow a private range for internal services (use with caution)
# spring.http.client.allowed-host-patterns=api.internal.corp
Migration from Boot 3 Boot 3 had no SSRF controls on auto-configured HTTP clients. When upgrading to Boot 4.1, if your application makes outbound requests to internal hostnames or IP addresses, configure spring.http.client.allowed-host-patterns explicitly, otherwise those requests will be blocked by default.

OpenTelemetry Native Support

Spring Boot 4 deepens its commitment to OpenTelemetry as the primary observability standard. The auto-configuration for OpenTelemetrySdk and OTLP (OpenTelemetry Protocol) exporters is now simpler and first-class — adding spring-boot-starter-actuator and an OTel exporter on the classpath wires everything automatically. In Boot 4.1, async context propagation for @Async methods is improved so that OpenTelemetry trace context flows across virtual-thread and executor hand-offs without requiring manual ContextPropagators setup. The management.otlp.tracing.endpoint property configures the OTLP gRPC or HTTP endpoint.

Micrometer Observation API

Spring Boot 4 retains and expands the Micrometer Observation API as the unified abstraction for metrics and distributed tracing. A single Observation.observe() call on an ObservationRegistry automatically emits both a metric (timer/counter) and a trace span, with no separate Tracer and MeterRegistry calls needed. Boot 4 adds JSpecify null safety to the Micrometer Observation API so that IDE tooling can statically verify that ObservationRegistry.NOOP — the safe null-equivalent — is used as a default rather than actual null.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-observation</artifactId>
</dependency>

Example

@Service
public class PaymentService {

    private final ObservationRegistry registry;

    public PaymentService(ObservationRegistry registry) {
        this.registry = registry;
    }

    public PaymentResult charge(Order order) {
        return Observation.createNotStarted("payment.charge", registry)
            .lowCardinalityKeyValue("payment.provider", "stripe")
            .highCardinalityKeyValue("order.id", order.getId().toString())
            .observe(() -> stripeClient.charge(order));
    }
}

GraalVM Native Image — Smaller Footprint

Spring Boot 4's modularized auto-configuration delivers significantly smaller GraalVM native images. Previously, the AOT engine had to process and generate native hints for the entire spring-boot-autoconfigure jar even when most of its configurations would never be activated. With modular auto-configuration, AOT processing only traverses the modules whose starters are on the classpath, reducing the number of generated hint files, compilation time, and the final binary size. The same native-maven-plugin workflow and -Pnative profile from Boot 3 continue to work unchanged.

Dependency (pom.xml)

<build>
  <plugins>
    <plugin>

AOT Processing — Modular Efficiency

Spring Boot 4's Ahead-of-Time (AOT) processing step is faster and produces leaner output because each auto-configuration module ships its own pre-computed AOT metadata. Previously, the AOT engine derived hints dynamically by analysing the single autoconfigure jar at build time. In Boot 4, modules with stable auto-configuration can ship pre-compiled AOT hints, reducing the spring-boot:process-aot build time. Running spring-boot:process-aot remains a mandatory intermediate step before native:compile.

Dependency (pom.xml)

<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <executions>
        <execution>
          <id>process-aot</id>
          <goals><goal>process-aot</goal></goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Example

# Run AOT: generates sources in target/spring-aot/main/sources/
./mvnw spring-boot:process-aot

# Boot 4: AOT output is smaller because modular starters ship pre-computed hints
# target/spring-aot/main/sources/com/example/DemoApplication__BeanDefinitions.java

@ImportRuntimeHints and @RegisterReflection

Spring Boot 4 retains @ImportRuntimeHints and @RegisterReflectionForBinding from Boot 3 for registering custom native hints when the AOT engine cannot derive them automatically. In Boot 4, these annotations are null-safe (JSpecify annotated), and the AOT engine produces better diagnostics when a hint is redundant because the module already ships pre-computed metadata. Use @ImportRuntimeHints to register reflection, resource, serialisation, and proxy hints via a RuntimeHintsRegistrar implementation.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter</artifactId>
</dependency>

Example

// Custom RuntimeHintsRegistrar
public class MyRuntimeHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.reflection()
             .registerType(ReportEngine.class,
                           MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                           MemberCategory.INVOKE_PUBLIC_METHODS);
        hints.resources().registerPattern("templates/*.html");
    }
}

// Apply the registrar
@SpringBootApplication
@ImportRuntimeHints(MyRuntimeHints.class)
public class DemoApplication { /* ... */ }

// Shortcut for Jackson 3 DTOs in native images
@RegisterReflectionForBinding(OrderDto.class)
@Configuration
public class JacksonConfig { /* ... */ }

Test Context Pausing

Spring Framework 7 introduces test context pausing — a new optimization for integration test suites. Previously, Spring contexts stored in the context cache remained fully active between test classes, holding open connections, threads, and other resources. In Boot 4 / Framework 7, the test framework can pause a cached context when it is not in use and resume it when the next test needs it, releasing idle resources. This is especially valuable when tests use real databases, Kafka consumers, or embedded servers — total resource consumption during long test runs drops noticeably.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-test</artifactId>
  <scope>test</scope>
</dependency>

Example

// Standard @SpringBootTest — context pausing is automatic when supported
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class OrderControllerTest {

    @Autowired
    TestRestTemplate restTemplate;

    @Test
    void createOrderReturns201() {
        ResponseEntity<Order> response = restTemplate.postForEntity(
            "/orders", new Order("PENDING", 99.99), Order.class);
        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.CREATED);
    }
}

// Opt into pausable context explicitly (for fine-grained control)
@SpringBootTest
@PausableTestContext  // Framework 7 annotation
class LongRunningIntegrationTest { /* ... */ }
Migration from Boot 3 Test context pausing is a new capability in Framework 7 — no action needed to benefit, but be aware that listeners registered on application events (like ContextRefreshedEvent) may now also fire on context resume. Test tear-down logic that assumes the context is always active between test classes may need adjustment.

Jackson 3 Migration

Spring Boot 4 upgrades to Jackson 3.x. Jackson 3 reorganised several internal packages and changed the default constructor detection strategy for serialization and deserialization. The com.fasterxml.jackson.databind.ObjectMapper class remains the primary entry point, but some rarely-used configuration methods have been removed or renamed. Spring Boot 4's auto-configured ObjectMapper applies sensible defaults compatible with Jackson 3. The most common migration impact is for custom JsonSerializer or JsonDeserializer subclasses that reference removed Jackson internals.

Dependency (pom.xml)

<!-- Jackson 3 is managed by spring-boot-starter-parent 4.0.0 -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<!-- Optional: override Jackson version explicitly -->
<properties>
  <jackson.version>3.0.0</jackson.version>
</properties>

Example — custom ObjectMapper still works via auto-configuration

@Configuration
public class JacksonConfig {

    @Bean
    public Jackson2ObjectMapperBuilderCustomizer customizer() {
        return builder -> builder
            .featuresToDisable(
                SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
            .featuresToEnable(
                DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);
    }
}
Migration from Boot 3 Boot 3 used Jackson 2.x. Jackson 3 changes the package of some internal types (e.g., com.fasterxml.jackson.core.util.* reorganisation). Compile your project against Boot 4 to surface import errors early. Custom serializers that used internal Jackson 2 APIs will need updating; use public Jackson API only for forward compatibility.

ListenableFuture Removal

Spring Boot 4 (via Spring Framework 7) removes ListenableFuture, which was deprecated in Spring Framework 6 in favour of Java's standard CompletableFuture. Any Spring API that previously returned or accepted ListenableFuture<T> — including AsyncRestTemplate, @Async method return types, and TaskExecutor extensions — now uses CompletableFuture<T>. AsyncRestTemplate itself was removed; use WebClient or RestClient for async HTTP.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter</artifactId>
</dependency>

Example — migrate from ListenableFuture to CompletableFuture

// ✗ Boot 3 — ListenableFuture removed in Boot 4
// @Async
// public ListenableFuture<String> computeAsync() { ... }

// ✓ Boot 4 — use CompletableFuture
@Service
public class ComputeService {

    @Async
    public CompletableFuture<String> computeAsync() {
        String result = heavyComputation();
        return CompletableFuture.completedFuture(result);
    }
}
Migration from Boot 3 Search your codebase for ListenableFuture and replace with CompletableFuture. Also search for AsyncRestTemplate (removed) and replace with WebClient (reactive) or the synchronous RestClient. These are compile-time errors — the migration surface is easy to find.

Undertow Removed as Embedded Server

Spring Boot 4 removes Undertow as a supported embedded web server option. Boot 3 supported three embedded server choices — Tomcat, Jetty, and Undertow — but Undertow's adoption was significantly lower than the other two and maintaining Jakarta EE 11 / Servlet 6.1 compatibility in Undertow posed ongoing challenges. Boot 4 ships with Tomcat (default) and Jetty as the two supported embedded server options. Applications currently using Undertow must migrate to Tomcat or Jetty before upgrading to Boot 4.

Dependency (pom.xml)

<!-- Default: Tomcat (no exclusion needed) -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<!-- Switch to Jetty -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-tomcat</artifactId>
    </exclusion>
  </exclusions>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>
Migration from Boot 3 If your Boot 3 application excludes Tomcat and depends on spring-boot-starter-undertow, you must switch to Tomcat or Jetty before upgrading. Tomcat is the recommended default; Jetty is the right choice for applications already tuned for Jetty's threading model.

Deprecated API Removals

Spring Boot 4 removes all APIs that were deprecated in Spring Boot 3.x or Spring Framework 6.x (following the standard Spring two-major-version deprecation policy). Notable removals include: WebSecurityConfigurerAdapter (removed in Security 6, not re-added), spring.factories EnableAutoConfiguration key (replaced by AutoConfiguration.imports in Boot 3), @EnableGlobalMethodSecurity (replaced by @EnableMethodSecurity), and the Spring MVC antMatchers() / mvcMatchers() DSL methods (replaced by requestMatchers()). Running your test suite with Boot 3.5.x and the -Werror deprecation flag before upgrading catches all of these at compile time.

Dependency (pom.xml)

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.0.0</version>
</parent>

Example — compile-time check against Boot 3 deprecations first

# Build with Boot 3.5.x and -Werror to find removed APIs before upgrading
./mvnw compile -Dmaven.compiler.failOnWarning=true

# Common removals — search your codebase:
# grep -r "antMatchers\|mvcMatchers\|WebSecurityConfigurerAdapter" src/
# grep -r "EnableGlobalMethodSecurity\|ListenableFuture\|AsyncRestTemplate" src/
# grep -r "spring.factories" src/main/resources/
Migration from Boot 3 Do not skip directly from Boot 2.x to Boot 4. Always upgrade to Boot 3.x first, resolve all deprecation warnings, then upgrade to Boot 4. The Spring Boot migration guide recommends treating the two upgrades as separate releases with their own test cycles.
