Spring Boot 3 Features

Spring Boot 3.x — 3.5.7

Spring Boot 3.x is the first major revision since Spring Boot 2.0 (2018). It requires Java 17 or later as a baseline, is built on Spring Framework 6.x, and migrates fully to the Jakarta EE 9+ namespace. The headline themes of the 3.x generation are: first-class GraalVM native image support (superseding the experimental Spring Native project), unified Observability via Micrometer and Micrometer Tracing, declarative HTTP clients via @HttpExchange, and RFC-compliant error responses with ProblemDetail.

Jakarta EE 9 namespace migration All javax.* imports became jakarta.* in Spring Boot 3. This is a breaking change from Spring Boot 2.x — update every import in your codebase when upgrading (e.g. javax.servlet.http.HttpServletRequest → jakarta.servlet.http.HttpServletRequest).

AutoConfiguration.imports File

Spring Boot 3 replaces the spring.factories mechanism for registering auto-configurations with a dedicated file at META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Each line of this file contains a fully-qualified class name of an auto-configuration class. The spring.factories EnableAutoConfiguration key is no longer supported in Boot 3, so custom starters must migrate to the new file. This improves startup performance and aligns with GraalVM native image requirements.

Dependency (pom.xml)

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.5.7</version>
</parent>

Example — registering a custom auto-configuration

# File: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

com.example.MyDatabaseAutoConfiguration
com.example.MySecurityAutoConfiguration

@EnableAutoConfiguration and @SpringBootApplication

@SpringBootApplication is a composed annotation that includes @EnableAutoConfiguration, which triggers the auto-configuration machinery. Spring Boot scans the AutoConfiguration.imports file and applies only the configurations whose @Conditional conditions are satisfied — for example, @ConditionalOnClass checks for a class on the classpath, and @ConditionalOnMissingBean only wires a bean if the application has not already defined one of the same type. In Boot 3 the import mechanism is loaded via AutoConfigurationImportSelector, which now reads the new .imports file rather than spring.factories.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-autoconfigure</artifactId>
</dependency>

Example

// Main application entry point — triggers auto-configuration
@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

// Custom auto-configuration class
@AutoConfiguration
@ConditionalOnClass(DataSource.class)
@ConditionalOnMissingBean(DataSource.class)
public class MyDataSourceAutoConfiguration {

    @Bean
    public DataSource dataSource(DataSourceProperties props) {
        return props.initializeDataSourceBuilder().build();
    }
}

Conditional Annotations

Conditional annotations are the foundation of Spring Boot auto-configuration — they prevent a configuration from being applied unless specific conditions are met at runtime. Boot 3 ships the full set of conditions inherited from Boot 2, including @ConditionalOnProperty, @ConditionalOnWebApplication, @ConditionalOnBean, and @ConditionalOnExpression. In Spring Boot 3, @ConditionalOnSingleCandidate is also useful for reactive-vs-blocking scenarios where only one implementation should exist. Writing your own Condition by implementing the SpringBootCondition base class continues to work unchanged.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-autoconfigure</artifactId>
</dependency>

Example

@AutoConfiguration
@ConditionalOnProperty(name = "myapp.cache.enabled", havingValue = "true",
                       matchIfMissing = false)
@ConditionalOnClass(name = "com.github.benmanes.caffeine.cache.Caffeine")
public class CaffeineCacheAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public CacheManager cacheManager() {
        return new CaffeineCacheManager();
    }
}

Auto-Configuration Conditions Report

Running your Spring Boot 3 application with the --debug flag (or setting debug=true in application.properties) prints a detailed conditions evaluation report to the console. The report is split into "Positive matches" (configurations that were applied) and "Negative matches" (configurations that were excluded and why). In Boot 3 this report is also available as a structured JSON payload via the /actuator/conditions endpoint when the Actuator is on the classpath, making it easy to consume programmatically or in CI diagnostics.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

Example — application.properties

# Enable conditions report in the console
debug=true

# Expose the /actuator/conditions endpoint over HTTP
management.endpoints.web.exposure.include=conditions,health,info

@HttpExchange — Declarative HTTP Clients

Spring Framework 6 (and therefore Spring Boot 3) introduced HTTP Interface support: you declare a Java interface annotated with @HttpExchange and method-level annotations like @GetExchange, @PostExchange, and @PutExchange, and Spring generates a proxy implementation at runtime. This replaces hand-written RestTemplate or WebClient call sites with a concise, testable interface, similar in spirit to Spring Data repositories. The proxy is created via HttpServiceProxyFactory backed by either the blocking RestClient or the reactive WebClient.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example

// 1. Declare the HTTP interface
@HttpExchange(url = "https://api.example.com/users", accept = "application/json")
public interface UserClient {

    @GetExchange("/{id}")
    User getById(@PathVariable long id);

    @PostExchange
    User create(@RequestBody User user);

    @DeleteExchange("/{id}")
    void delete(@PathVariable long id);
}

// 2. Register the proxy as a Spring bean
@Configuration
public class HttpClientConfig {

    @Bean
    public UserClient userClient(RestClient.Builder builder) {
        RestClient restClient = builder
            .baseUrl("https://api.example.com")
            .build();
        HttpServiceProxyFactory factory = HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(restClient))
            .build();
        return factory.createClient(UserClient.class);
    }
}

ProblemDetail — RFC 7807 Error Responses

Spring Boot 3 adds native support for RFC 7807 "Problem Details for HTTP APIs" via the ProblemDetail and ErrorResponse types. A ProblemDetail carries a standard set of fields — type (URI identifying the error), title, status, detail, and instance — and can carry extension properties. Spring MVC exception handlers and ResponseEntityExceptionHandler now produce ProblemDetail JSON automatically when you enable the feature via a property. This standardises error payloads across teams without requiring a custom @ControllerAdvice.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example

# Enable RFC 7807 problem details for all Spring MVC exceptions
spring.mvc.problemdetails.enabled=true
// Custom exception handler returning ProblemDetail
@ControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail handleOrderNotFound(OrderNotFoundException ex,
                                      HttpServletRequest request) {
        ProblemDetail detail = ProblemDetail.forStatusAndDetail(
            HttpStatus.NOT_FOUND, ex.getMessage());
        detail.setTitle("Order Not Found");
        detail.setType(URI.create("https://api.example.com/errors/order-not-found"));
        detail.setProperty("orderId", ex.getOrderId());
        return detail;
    }
}

RestClient — Synchronous Fluent HTTP

RestClient was introduced in Spring Boot 3.2 as a modern, synchronous alternative to the now-deprecated RestTemplate. It provides a fluent builder API closely mirroring WebClient — with support for request interceptors, message converters, and URI templates — but executes requests on the calling thread, making it straightforward to use in blocking, servlet-based applications. RestClient.Builder is pre-configured by Spring Boot auto-configuration with codecs and base URL support, so you can inject it directly.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example

@Service
public class ProductService {

    private final RestClient restClient;

    public ProductService(RestClient.Builder builder) {
        this.restClient = builder
            .baseUrl("https://api.example.com")
            .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
            .build();
    }

    public Product findById(Long id) {
        return restClient.get()
            .uri("/products/{id}", id)
            .retrieve()
            .onStatus(HttpStatusCode::is4xxClientError,
                (req, res) -> { throw new ProductNotFoundException(id); })
            .body(Product.class);
    }

    public Product create(Product product) {
        return restClient.post()
            .uri("/products")
            .body(product)
            .retrieve()
            .body(Product.class);
    }
}

Virtual Threads for Web (Project Loom)

Spring Boot 3.2 added first-class support for Project Loom virtual threads (Java 21+). Enabling virtual threads replaces the Tomcat/Jetty thread pool with one virtual thread per HTTP request, dramatically increasing throughput for I/O-bound workloads without changing application code. Each request still appears blocking from the developer's perspective (no reactive programming model needed), but the JVM schedules the lightweight virtual threads efficiently on OS threads. Pair this with spring-boot-starter-web and Java 21 to get near-WebFlux scalability with classic servlet code.

Dependency (pom.xml)

<!-- Requires Java 21+ -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Example — application.properties

# Enable virtual threads (requires Java 21+)
spring.threads.virtual.enabled=true
// No code changes required — every @RestController method runs
// on a virtual thread automatically once the property is enabled.
@RestController
public class OrderController {

    @GetMapping("/orders/{id}")
    public Order getOrder(@PathVariable Long id) {
        // Blocking I/O call — fine on a virtual thread
        return orderRepository.findById(id).orElseThrow();
    }
}

Testcontainers @ServiceConnection

Spring Boot 3.1 introduced @ServiceConnection, a companion annotation for Testcontainers that eliminates boilerplate property configuration in integration tests. Annotate a @Container field with @ServiceConnection and Spring Boot automatically discovers the container type (PostgreSQL, Redis, MongoDB, Kafka, RabbitMQ…) and registers a ConnectionDetails bean, setting up all connection properties without you having to remember property names or override them manually. Boot 3.1 also supports Testcontainers at development time — you can run an application locally with containers started automatically via a TestApplication class, removing the need for a local Docker Compose file.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-testcontainers</artifactId>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.testcontainers</groupId>
  <artifactId>postgresql</artifactId>
  <scope>test</scope>
</dependency>

Example

@SpringBootTest
@Testcontainers
class OrderRepositoryTest {

    // @ServiceConnection auto-configures spring.datasource.* from this container
    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired
    OrderRepository repository;

    @Test
    void saveAndFind() {
        Order order = repository.save(new Order("PENDING", 42.00));
        assertThat(repository.findById(order.getId())).isPresent();
    }
}

Hibernate 6 and Jakarta Persistence

Spring Boot 3 ships with Hibernate 6.x — a major release that dropped the javax.persistence package in favour of jakarta.persistence from the Jakarta EE 9 specification. Hibernate 6 also rewrote its SQL generation layer for improved type-safety, native support for Java records as embeddable objects, and a new @TenantId annotation for multi-tenancy. The spring-boot-starter-data-jpa starter brings in the correct Hibernate 6 version automatically when you declare Spring Boot 3 as the parent.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

Example — Jakarta Persistence entity

// Import jakarta.persistence, not javax.persistence
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String status;

    private Double amount;

    // Java record as @Embeddable also supported in Hibernate 6
    public record Address(String street, String city, String zip) {}

    @Embedded
    private Address shippingAddress;
}

Spring Data 3 Improvements

Spring Data 3.x (bundled with Spring Boot 3) brings several developer-experience improvements: pagination defaults are now configurable globally, scroll queries allow cursor-based pagination without offset, and the CrudRepository and ListCrudRepository split separates reactive from imperative APIs more cleanly. Spring Data MongoDB 4.x (Boot 3) adds aggregation pipeline support in MongoTemplate, while Spring Data Redis 3.x migrates to Lettuce 6 and Jakarta EE 9.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-mongodb</artifactId>
</dependency>

Example — scroll (cursor-based) pagination

// Spring Data 3 scroll API — cursor-based, no offset
public interface ProductRepository extends Repository<Product, String> {

    Window<Product> findTop10ByCategory(String category,
                                         ScrollPosition position);
}

// Usage
Window<Product> page = repo.findTop10ByCategory(
    "electronics", ScrollPosition.offset());
while (!page.isEmpty()) {
    processProducts(page.getContent());
    if (!page.hasNext()) break;
    page = repo.findTop10ByCategory(

}

Docker Compose Integration (Boot 3.1)

Spring Boot 3.1 introduced built-in Docker Compose support. If a compose.yaml (or docker-compose.yml) file is present at the project root and spring-boot-docker-compose is on the classpath, Spring Boot automatically starts the compose file's services before the application context starts, and stops them when the context closes. Each service is detected by its image name and automatically mapped to @ServiceConnection beans — no manual property configuration needed. This replaces ad-hoc shell scripts or TestApplication tricks for dev-time infrastructure.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-docker-compose</artifactId>
  <optional>true</optional>
</dependency>

compose.yaml

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: shopdb
      POSTGRES_USER: shop
      POSTGRES_PASSWORD: secret
    ports:
      - "5432:5432"

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"

application.properties — lifecycle control

# Default: START_AND_STOP (start on app start, stop on app shutdown)
spring.docker.compose.lifecycle-management=start-and-stop

# Skip Docker Compose in CI or production
spring.docker.compose.enabled=false

# Point to a non-default compose file
spring.docker.compose.file=infrastructure/local.yaml

SecurityFilterChain — Configuration-Only Approach

Spring Security 6 (bundled with Spring Boot 3) removes WebSecurityConfigurerAdapter, which was deprecated in Security 5.7. You must now configure security exclusively by declaring a @Bean of type SecurityFilterChain. This component-based model is cleaner and allows multiple filter chains in the same application (e.g. one for an API and one for the management endpoints). Multiple SecurityFilterChain beans are ordered via @Order, and the first chain whose securityMatcher matches the request wins.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Example

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain apiFilterChain(HttpSecurity http) throws Exception {
        http
            .securityMatcher("/api/**")
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .anyRequest().authenticated()
            )
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            )
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()));
        return http.build();
    }
}

Spring Security Lambda DSL

Spring Security 6 mandates the Lambda DSL for all HTTP security configuration. In Security 5, both a chained method style and a lambda style were accepted; in Security 6 the chained style was removed. Each configuration subsystem — authorizeHttpRequests, formLogin, csrf, oauth2Login, etc. — now accepts a lambda Customizer. This makes the configuration self-contained per block, easier to read, and simpler to compose in tests using Customizer.withDefaults().

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Example — Lambda DSL vs old chained style

// ✗ Old chained style — REMOVED in Spring Security 6
// http.authorizeRequests().antMatchers("/admin").hasRole("ADMIN").and()
//     .formLogin().loginPage("/login");

// ✓ New Lambda DSL — required in Spring Security 6 / Spring Boot 3
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .requestMatchers("/public/**").permitAll()
            .anyRequest().authenticated()
        )
        .formLogin(form -> form
            .loginPage("/login")
            .defaultSuccessUrl("/dashboard")
        )
        .logout(logout -> logout
            .logoutSuccessUrl("/login?logout")
        );
    return http.build();
}

Method Security — @PreAuthorize and SpEL

Spring Security 6 rewrote the method security infrastructure with a new AuthorizationManager-based approach. Annotating a @Configuration class with @EnableMethodSecurity (replacing the old @EnableGlobalMethodSecurity) activates @PreAuthorize, @PostAuthorize, @PreFilter, and @PostFilter without requiring an XML-based GlobalMethodSecurityConfiguration. The new implementation runs without proxy composition limitations and supports programmatic customisation via MethodSecurityExpressionHandler beans.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Example

// Activate method-level security (replaces @EnableGlobalMethodSecurity)
@Configuration
@EnableMethodSecurity
public class MethodSecurityConfig {}

// Apply at service layer
@Service
public class OrderService {

    @PreAuthorize("hasRole('MANAGER') or #order.ownerId == authentication.name")
    public void cancelOrder(Order order) { /* ... */ }

    @PostAuthorize("returnObject.ownerId == authentication.name")
    public Order findOrder(Long id) {
        return orderRepository.findById(id).orElseThrow();
    }
}

This is the recommended replacement for the deprecated Spring Security OAuth2 Authorization Server that shipped with Boot 2.

SSL Bundles (Boot 3.1)

Spring Boot 3.1 introduced SSL Bundles — a unified, named way to configure TLS keystores and truststores that can be referenced by any component: embedded servers, RestClient, WebClient, JDBC data sources, and Actuator management endpoints. Instead of duplicating keystore paths and passwords across each component, you define a bundle once under spring.ssl.bundle.* and reference it by name. Bundles support both JKS and PEM formats and can be hot-reloaded without restarting the application.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

application.properties — define a bundle

# PEM bundle (certificate + private key files)
spring.ssl.bundle.pem.myservice.truststore.certificate=classpath:certs/ca.crt
spring.ssl.bundle.pem.myservice.keystore.certificate=classpath:certs/server.crt
spring.ssl.bundle.pem.myservice.keystore.private-key=classpath:certs/server.key

# JKS bundle
spring.ssl.bundle.jks.mystore.keystore.location=classpath:keystore.jks
spring.ssl.bundle.jks.mystore.keystore.password=changeit
spring.ssl.bundle.jks.mystore.key.alias=myapp

# Apply bundle to the embedded server
server.ssl.bundle=mystore

# Apply to Actuator management server
management.server.ssl.bundle=mystore

Use a bundle in RestClient

@Configuration
public class HttpClientConfig {

    @Bean
    public RestClient secureRestClient(RestClient.Builder builder,
                                       SslBundles sslBundles) {
        return builder
            .baseUrl("https://partner-api.example.com")
            .apply(ssl -> ssl.sslBundle(sslBundles.getBundle("myservice")))
            .build();
    }
}

Hot-reload (rotate certs without restart)

# Watch bundle files for changes and reload automatically
spring.ssl.bundle.pem.myservice.reload-on-update=true

Micrometer Observation API

Spring Boot 3 introduces the Micrometer Observation API as the single, unified abstraction for all instrumentation — replacing separate Timer, Counter, and distributed tracing calls with a single Observation that automatically produces both metrics and traces. You create an Observation via ObservationRegistry, wrap your code in observe(), and Micrometer handles propagating context to both the metrics back-end (Prometheus, CloudWatch, etc.) and the tracing back-end (Zipkin, Jaeger, OpenTelemetry). This eliminates the need to wire Tracer and MeterRegistry separately.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-observation</artifactId>
</dependency>

Example

@Service
public class PaymentService {

    private final ObservationRegistry registry;

    public PaymentService(ObservationRegistry registry) {
        this.registry = registry;
    }

    public PaymentResult charge(Order order) {
        return Observation.createNotStarted("payment.charge", registry)
            .lowCardinalityKeyValue("payment.provider", "stripe")
            .highCardinalityKeyValue("order.id", order.getId().toString())
            .observe(() -> stripeClient.charge(order));
    }
}

Micrometer Tracing — Distributed Tracing

Spring Boot 3 ships auto-configuration for Micrometer Tracing, which provides a vendor-neutral tracing facade over Brave (Zipkin) and OpenTelemetry. Adding a bridge dependency and an exporter automatically injects Tracer and propagates TraceId/SpanId across HTTP calls, Kafka messages, and scheduled tasks. The management.tracing.sampling.probability property controls the sampling rate (1.0 = 100%). Log correlation is built in: trace IDs are appended to every log line when using a structured log pattern.

Dependency (pom.xml)

<!-- Micrometer Tracing + OpenTelemetry bridge + Zipkin exporter -->
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
  <groupId>io.opentelemetry</groupId>
  <artifactId>opentelemetry-exporter-zipkin</artifactId>
</dependency>

Example — application.properties

# Sample every request during development (default is 0.1 = 10%)
management.tracing.sampling.probability=1.0

# Zipkin endpoint
management.zipkin.tracing.endpoint=http://localhost:9411/api/v2/spans

# Include trace/span IDs in log lines
logging.pattern.level=%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]

Prometheus Metrics and Actuator

Spring Boot 3 Actuator auto-configures a Prometheus-compatible /actuator/prometheus scrape endpoint when micrometer-registry-prometheus is on the classpath. All Spring Boot built-in meters — JVM memory, GC pauses, HTTP server request duration, data source pool statistics, Tomcat threads, Spring Data repository counts — are exposed automatically. Custom metrics added via MeterRegistry or the Observation API appear in the same scrape. The actuator endpoint security and exposure are controlled independently via management.endpoints.* properties.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
  <scope>runtime</scope>
</dependency>

Example — application.properties

# Expose the Prometheus scrape endpoint
management.endpoints.web.exposure.include=prometheus,health,info
management.endpoint.prometheus.enabled=true

# Add application name as a common tag on all meters
management.metrics.tags.application=${spring.application.name}

Structured Logging

Spring Boot 3.4 added first-class support for structured logging — outputting each log event as a JSON document rather than a plain-text line. Setting logging.structured.format.console=ecs (Elastic Common Schema) or logstash produces machine-parseable JSON directly from the default Logback or Log4j2 configuration without requiring a custom appender. Combined with Micrometer Tracing, each log line automatically includes traceId and spanId fields, enabling seamless correlation in Elasticsearch, Grafana Loki, or Splunk.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter</artifactId>
</dependency>

Example — application.properties

# Output structured JSON to the console (ECS format)
logging.structured.format.console=ecs

# Or to a file
logging.structured.format.file=logstash
logging.file.name=logs/application.log

SBOM Actuator Endpoint (Boot 3.3)

Spring Boot 3.3 added a Software Bill of Materials (SBOM) actuator endpoint at /actuator/sbom. When a CycloneDX or SPDX SBOM file is present in the application's classpath (generated by the Maven/Gradle build), the endpoint exposes it over HTTP, enabling vulnerability scanners and supply-chain tools to retrieve the dependency inventory programmatically. The Spring Boot Maven and Gradle plugins generate the SBOM automatically when native compilation is used; for JVM applications, add the CycloneDX plugin separately.

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

<!-- CycloneDX plugin generates META-INF/sbom/application.cdx.json -->
<plugin>
  <groupId>org.cyclonedx</groupId>
  <artifactId>cyclonedx-maven-plugin</artifactId>
  <executions>
    <execution>
      <phase>package</phase>
      <goals><goal>makeAggregateBom</goal></goals>
    </execution>
  </executions>
</plugin>

application.properties

management.endpoints.web.exposure.include=health,info,sbom

GET /actuator/sbom response (CycloneDX)

{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "components": [
    { "type": "library", "name": "spring-boot", "version": "3.3.0" },
    { "type": "library", "name": "jackson-databind", "version": "2.16.1" }
  ]
}

Kubernetes Liveness & Readiness Probes (Actuator)

Spring Boot 3 exposes Kubernetes-native health probes via Actuator: /actuator/health/liveness (is the application alive and not in a broken state?) and /actuator/health/readiness (is the application ready to accept traffic?). These are automatically enabled when the application detects it is running inside Kubernetes, or can be forced on with a property. Application components can signal liveness/readiness transitions by injecting ApplicationAvailability.

application.properties

# Force probes on (auto-enabled in Kubernetes)
management.endpoint.health.probes.enabled=true
management.endpoints.web.exposure.include=health
management.health.livenessstate.enabled=true
management.health.readinessstate.enabled=true

Programmatically change readiness state

@Service
public class WarmupService implements ApplicationListener<ApplicationReadyEvent> {

    private final ApplicationEventPublisher publisher;

    @Override
    public void onApplicationEvent(ApplicationReadyEvent event) {
        // Signal "not ready" while doing initial cache warming
        publisher.publishEvent(
            new AvailabilityChangeEvent<>(this, ReadinessState.REFUSING_TRAFFIC));
        warmUpCaches();
        // Signal "ready" when done
        publisher.publishEvent(
            new AvailabilityChangeEvent<>(this, ReadinessState.ACCEPTING_TRAFFIC));
    }
}

Kubernetes deployment.yaml

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

GraalVM Native Image

Spring Boot 3 provides first-class support for compiling Spring Boot applications into GraalVM native executables. A native executable contains only the classes and code reachable at build time, launches in milliseconds, and uses far less memory than a JVM application — ideal for serverless functions and container environments where startup time and cold-boot cost matter. Spring Boot's AOT engine analyses the application at build time, generating native hints for reflection, serialization, and proxies so that most Spring applications can be natively compiled without manual configuration.

Dependency (pom.xml)

<build>
  <plugins>
    <plugin>
      <groupId>org.graalvm.buildtools</groupId>
      <artifactId>native-maven-plugin</artifactId>
    </plugin>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
    </plugin>
  </plugins>
</build>

Example — build command

# Compile to native executable (requires GraalVM with native-image)
./mvnw -Pnative native:compile

# Or build a native OCI image with Paketo Buildpacks (no local GraalVM needed)
./mvnw spring-boot:build-image -Pnative

AOT Processing — spring-boot:process-aot

Spring Boot 3's Ahead-of-Time (AOT) processing runs before compilation and transforms the Spring application context into a static, optimised form. The spring-boot:process-aot Maven goal (or bootBuildImage with native profile) generates Java source files and resource descriptors that replace the runtime reflection and dynamic proxy creation normally performed at startup. AOT processing is a mandatory intermediate step for GraalVM native compilation, but it also yields faster startup even on the JVM when running with the spring.aot.enabled=true system property.

Dependency (pom.xml)

<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <executions>
        <execution>
          <id>process-aot</id>
          <goals><goal>process-aot</goal></goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Example — run AOT processing

# Run AOT: generates sources in target/spring-aot/main/sources/
./mvnw spring-boot:process-aot

# Generated class example (by the AOT engine)
# target/spring-aot/main/sources/com/example/DemoApplication__BeanDefinitions.java

@ImportRuntimeHints — Native Reflection Hints

When the AOT engine cannot automatically derive a native hint — for example, because your code uses reflection to instantiate a class by name at runtime — you can provide it explicitly with @ImportRuntimeHints. This annotation references a RuntimeHintsRegistrar implementation where you register reflection, resource, serialisation, and proxy hints programmatically. Spring Boot also ships @RegisterReflectionForBinding as a convenience shortcut to register all members of a type (useful for DTO classes that Jackson deserialises via reflection).

Dependency (pom.xml)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter</artifactId>
</dependency>

Example

// Register a custom RuntimeHintsRegistrar
public class MyRuntimeHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        // Reflection hint: need all constructors + methods of ReportEngine
        hints.reflection()
             .registerType(ReportEngine.class,
                           MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                           MemberCategory.INVOKE_PUBLIC_METHODS);

        // Resource hint: include config file in the native image
        hints.resources().registerPattern("templates/*.html");
    }
}

// Apply the hints registrar on your @Configuration or @SpringBootApplication
@SpringBootApplication
@ImportRuntimeHints(MyRuntimeHints.class)
public class DemoApplication { /* ... */ }

// Shortcut for Jackson DTOs
@RegisterReflectionForBinding(OrderDto.class)
@Configuration
public class JacksonConfig { /* ... */ }

Native Testing with @NativeTest

Spring Boot 3 supports running your test suite against the native executable via @SpringBootTest combined with the native-maven-plugin's test goal. The process-test-aot Maven goal (analogous to process-aot) runs AOT processing over your test classes, generating the corresponding native hints, so integration tests validate real native-image behaviour. This catches native-image-specific failures (missing hints, unsupported proxies) early in CI, before building the production image.

Dependency (pom.xml)

<build>
  <plugins>
    <plugin>
      <groupId>org.graalvm.buildtools</groupId>
      <artifactId>native-maven-plugin</artifactId>
      <extensions>true</extensions>
      <configuration>
        <classesDirectory>${project.build.outputDirectory}</classesDirectory>
      </configuration>
    </plugin>
  </plugins>
</build>

Example — run tests in native image

# Compile test classes and run integration tests as a native executable
./mvnw -PnativeTest test

# Or with the native-maven-plugin directly
./mvnw native:test
// Regular @SpringBootTest — also runs in native image when using native:test
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class OrderControllerNativeTest {

    @Autowired
    TestRestTemplate restTemplate;

    @Test
    void createOrderReturns201() {
        ResponseEntity<Order> response = restTemplate.postForEntity(
            "/orders", new Order("PENDING", 99.99), Order.class);
        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.CREATED);
    }
}

Class Data Sharing — CDS (Boot 3.3)

Spring Boot 3.3 introduced built-in support for Class Data Sharing (CDS) — a JVM feature that pre-processes class metadata into a shared archive, enabling subsequent JVM instances to memory-map the archive rather than loading classes from scratch. This is significantly faster to set up than full GraalVM native compilation but provides meaningful startup-time (15–30%) and heap-reduction improvements for JVM applications. Spring Boot auto-generates a CDS archive via a training run during the Docker image build.

Create CDS archive (Maven)

# Step 1: build the fat jar
./mvnw package -DskipTests

# Step 2: training run — JVM processes classes and writes the archive
java -Dspring.context.exit=onRefresh -XX:ArchiveClassesAtExit=application.jsa \
     -jar target/my-app.jar

# Step 3: production run — load from the archive
java -XX:SharedArchiveFile=application.jsa -jar target/my-app.jar

With Paketo Buildpacks (Docker)

# Boot 3.3 buildpack automatically creates a CDS archive layer
./mvnw spring-boot:build-image

application.properties

# CDS is transparent — no Spring property needed.
# The JVM flag -XX:SharedArchiveFile points to the archive.
# Verify CDS is active at startup:
# java -verbose:class -XX:SharedArchiveFile=application.jsa -jar app.jar | grep "source: shared"
CDS vs GraalVM native CDS runs on a standard JVM and requires no code changes — easy to adopt. GraalVM native provides ~10× faster startup and ~3× lower memory but requires AOT compilation and extra native-image configuration. Use CDS for quick wins on existing apps; native for serverless or tightly resource-constrained environments.
